# Chaos Engineering Review — 2026-08-29

## CHAOS-57 — The request-history store under a damaged data volume

**Scope.** `internal/logstore` (the BadgerDB request-history store), its key
derivation, and the composition-root lifecycle that opens it
(`logstore.go`, `admin_settings.go`, `ui_config.go`).

**Origin.** Register row **R-E**, opened by the CHAOS-50 sweep (§19.6) and
marked *"next sweep candidate"*. That row asserted the exposure from the
category store's measurements and deferred the fix on the grounds that
*"quarantining it silently is an evidence decision, not a cache decision."*
Both halves of that framing turned out to understate the problem.

---

## 1. Executive Summary

**A store that holds no authoritative state could kill an in-line gateway, and
the killing was self-latching.**

`badger.Open` does not always return an error. On a corrupt `.sst` it PANICS
from a goroutine badger itself spawns, so no `recover()` at any call site can
contain it. CHAOS-50 established this for the community category store; this
sweep re-measured it against the history store's own option set — encryption
on, 128 MiB value log — and it reproduces exactly:

```
panic: ... [recovered, repanicked]
  table.(*Table).initBiggestAndSmallest
  table.OpenTable
  badger.newLevelsController.func1
created by github.com/dgraph-io/badger/v4.newLevelsController in goroutine 21
```

The deferral understated the exposure in two ways, and both are worse than the
category store's.

**It is not boot-only.** `enableLogStore` is reachable from the **live admin
API** (`ui_config.go:525`, the history toggle). Opening a damaged store kills a
gateway that is carrying production traffic at the instant an admin flips a
switch in the GUI. No restart, no warning, no error the handler could return —
the process is simply gone.

**And it LATCHES.** The toggle is durable in `admin_settings.json`, and
`LoadAdminSettings` re-applies it on every boot (`admin_settings.go:412`). Under
the shipped `docker-compose.yml`'s `restart: unless-stopped`, one unclean
container kill that damages a table therefore becomes an **unattended crash
loop**: no proxy, no admin UI, no health endpoint — and no way to turn the
setting back off, because turning it off requires the admin UI that the setting
prevents from starting. The category store needed a CLI flag to reach that
state. This one gets there from an admin's saved preference, which means the
blast radius is *every customer who used the feature*.

**The deferral's own reasoning also inverted.** "Quarantining is an evidence
decision" is true, and it argues FOR the fix rather than against it: the
CHAOS-05/07 contract this codebase already follows **moves aside, never
deletes**. The evidence survives on the volume either way. What the deferral
actually chose was to keep the alternative — a crash-looping appliance whose
history is equally unreadable and whose *entire service* is down as well.

**Two further defects sat around it, one of them a silent data-destruction bug
with no relation to corruption at all.**

- **LS-3 — the shared corruption table is WRONG for this store.** badger reports
  KEYREGISTRY damage as `Encryption key mismatch`, and the CHAOS-50 classifier
  lists that message as corruption on the explicit rationale *"this store is
  never opened with a key."* True there; false here. Measured on badger v4.9.6,
  **three conditions produce an indistinguishable error** on a keyed store:

  | Injected condition | Error surfaced |
  |---|---|
  | operator changed the history passphrase | `saved logs use a different encryption key` |
  | salt sidecar truncated / lost | `saved logs use a different encryption key` |
  | KEYREGISTRY scrambled (real corruption) | `saved logs use a different encryption key` |

  Reusing the table unmodified would have moved a **healthy** history store
  aside and re-created it empty in response to an ordinary configuration
  change — data loss caused by the recovery mechanism. This is the finding that
  makes the classifier a per-store *policy* rather than a constant.

- **LS-4 — `EncKey` destroyed key material on the READ path.** It minted and
  **wrote** a fresh 32-byte salt whenever the sidecar was unreadable or the
  wrong length — including when an encrypted store was sitting right next to
  it. The derived key is a pure function of `(passphrase, salt)`, so that
  overwrite replaced the only value that could ever decrypt the store. The
  resulting failure is indistinguishable from a passphrase change, so the
  operator's documented remedy became *"purge"* — destroying history that was
  intact right up until the read path ran. It is reachable by exactly the fault
  this store has to survive: a torn sidecar after an unclean kill. Verified
  live: `salt regenerated by EncKey: true`.

  **This is a rule the codebase had already adopted and then violated
  elsewhere.** `internal/alerts` (SEC-WHSIGN-1) states it exactly: *a failed
  decrypt never mints a key; creation happens on first encrypt.*

## 2. Failure Scenarios

| # | Scenario | Before | After |
|---|---|---|---|
| LS-1a | Corrupt `.sst`; admin toggles history ON | **process dies mid-traffic**, uncatchable | quarantine + re-create; toggle succeeds |
| LS-1b | Same, with the toggle durably ON | **unattended crash loop**, shell-only recovery | recovers on the next open; alert + row + metric |
| LS-2 | Torn `MANIFEST` / missing table | returned error → history silently off forever, one WARN line | quarantined, store re-created, reported once |
| LS-3a | Admin changes the history passphrase | (would quarantine under the naive reuse) | never quarantined; `ErrEncMismatch` 409 |
| LS-3b | KEYREGISTRY scrambled | (indistinguishable from LS-3a) | degrades loudly; operator purges — recorded trade |
| LS-4 | Salt sidecar torn by an unclean kill | fresh salt minted; **history permanently unreadable** | refuses, sidecar untouched; restoring it recovers |
| LS-5 | Live opener holds the directory lock | n/a | never quarantined (a rename would move a live store) |
| LS-6 | Volume full / read-only / EACCES | error | classified environmental; disk untouched |

## 4. Recovery Assessment

**Automatic, no operator action:** LS-1a/LS-1b/LS-2. The damaged directory is
moved aside to `<dir>.corrupt.<unixnano>` and an empty store is created in its
place; history resumes immediately. Bounded to one retry — no loop.

**Automatic detection, manual remedy:** LS-3b (real KEYREGISTRY damage) and LS-4
(lost salt). Both degrade loudly with a named remedy. Neither self-heals, and
that is deliberate: they are indistinguishable from conditions where the data is
intact, so acting automatically would destroy history to fix a configuration
mistake.

**Recovery that the fix newly PRESERVES:** LS-4's refusal keeps the original
sidecar on disk, so an operator who has a backup of one 32-byte file recovers
the entire history. Before, that path did not exist — the read had already
overwritten it.

**Evidence is never destroyed.** Quarantine renames within the same parent
(atomic metadata operation, needs no free space) and the salt sidecar is a
SIBLING of the store directory, so it survives the rename. That is required in
both directions: the replacement store derives the same key and keeps working,
**and the quarantined copy stays decryptable with the same sidecar** — the
evidence an operator is handed is evidence they can actually read.

## 5. Operational, Security and Data-Integrity Impact

**Operational.** The dominant win is that the appliance stops dying. Secondary,
and nearly as important: the degradation is now visible. Before, a history store
that failed to open produced exactly one `WARN` line in a process log; the GUI
showed the toggle off, indistinguishable from an admin having turned it off.
Now: a `request_history` operator-contract row on `/api/diagnostics`, three
`culvert_logstore_*` series, and a `state_file_corrupt` alert.

**Security.** No posture change to any enforcement control. Request history is a
queryable convenience over traffic that is ALSO written to the request log
(`internal/reqlog`) and the audit log (`internal/audit`), both independent of
this store — which is why losing it never justifies refusing to serve. Two
security-adjacent improvements: an encrypted store is no longer silently
bricked by its own read path, and the classifier can no longer be talked into
moving a healthy encrypted store aside.

**Data integrity.** Strictly improved in every direction. LS-4 removes a
one-way destruction of key material. The quarantine preserves bytes that
previously either sat unreadable behind a crash loop or were purged by an
operator following the only advice the error gave them.

## 6. Suggested Improvements — shipped in this PR

1. **`internal/storeguard`** — the CHAOS-50 recovery engine, extracted verbatim
   from `internal/catdb/resilient.go` and made store-agnostic. Per-attempt
   flock-owned poison markers, the store lock held ACROSS the rename, the
   environmental-before-corruption classifier, degrade-on-unknown, bounded
   evidence. A second COPY was rejected: the badger message table is derived
   empirically and pinned by a test precisely so a badger upgrade that rewords a
   message fails the build instead of silently switching recovery off. Two
   copies is how that protection rots.
2. **`storeguard.Policy`** — the per-store part of the decision, and it can only
   ever SUBTRACT. There is deliberately no field for adding corruption signals:
   widening destruction from a call site is how a shared safety mechanism
   becomes an unsafe one.
3. **`catdb.OpenResilient`** — now a thin adapter with an EMPTY policy. Its 21
   recovery gates run unchanged — 21 test functions, 97 assertions, identical
   before and after; the only edits are identifier renames — which is the
   evidence the extraction is behaviour-preserving.
4. **`logstore.OpenResilientTTL`** — the guard, with this store's policy
   exempting encryption errors both structurally (`ErrEncMismatch`) and
   textually (the raw badger message), so a future change to `OpenTTL`'s error
   rewrite cannot silently re-arm a quarantine over a passphrase change.
5. **`logstore.EncKey`** — mints a salt only when there is no store it could
   lock us out of; otherwise `ErrSaltUnusable`, sidecar untouched.
6. **Health plane** (`logstore_health.go`) — the `request_history` contract row,
   `culvert_logstore_{available,recovered,quarantined_copies}`, and the existing
   `state_file_corrupt` alert. Reported ONCE, after the outcome is known: a
   quarantine followed by a failed replacement open is a FAILURE, not a
   recovery.
7. **`ui_config.go`** — `ErrSaltUnusable` gets its own 409 naming its own
   remedy (restore one file), rather than inheriting the passphrase mismatch's
   "purge", which would have destroyed the recoverable case.

**Deliberately NOT wired into `/readyz`.** A node with history degraded is
fully able to serve traffic — exactly the posture of a node that never had the
toggle on — so failing readiness would pull a healthy gateway out of a
load-balancer rotation over a query convenience. Same reasoning as CHAOS-50.

## 7. Residual Risk / deliberately left

- **Real KEYREGISTRY damage does not self-heal.** It is indistinguishable from a
  passphrase change and a lost salt, and of the four possible postures the only
  unacceptable one is destroying intact history over a config change. So this
  store degrades loudly and the operator purges — one manual step, no silent
  loss. Recorded as an owner-visible trade, not an oversight.
- **Recovery still costs one process death for the panic case.** The marker
  cannot act until the run after the crash. Zero-crash recovery means probing
  the store in a child process first — better, and a reasonable follow-up,
  larger than the fault warrants. (Inherited from CHAOS-50; unchanged.)
- **A spurious quarantine is possible** if a kill lands inside `badger.Open` for
  an unrelated reason. Cost: one empty history store and a reported incident.
  Accepted, and preferable to a default that never recovers.
- **No circuit breaker on repeated quarantines.** A dying disk re-quarantines on
  every open; `culvert_logstore_quarantined_copies` and the contract row are the
  operator's signal, but nothing in the process gives up.
- **LS-4's sibling condition is not swept.** `EncKey` is now safe, but nothing
  BACKS UP the salt sidecar, and it is (correctly) excluded from archives as key
  material. An operator who loses it with no backup still loses the history.
  Whether the appliance should hold a second copy under the KEK is a key-custody
  decision, not a patch — recorded for an owner.
- **`internal/logstore` was the last known badger store on a
  process-critical path.** `catdb` (CHAOS-50) and this one are now both guarded;
  no third BadgerDB open remains unguarded in the tree.

**Permanent DEFECT PROOF.**
`TestChaos57_BareOpenTTLPanicIsUncatchableAtTheCallSite` re-exec's the test
binary and asserts that plain `OpenTTL` — the call the composition root used to
make — dies on a corrupt table *even with a `recover()` in the frame directly
above it*, and that the panic came from `newLevelsController`. If badger ever
starts returning that error instead, this test fails, so the recovery gate can
never quietly prove less than it claims. (Same discipline as CHAOS-56's
`BareGracefulStopIsUnboundedOnAWedgedStream`.)

**CONTROLS** — a passing gate must not be able to mean the mechanism simply
stopped firing:

- `TestChaos57_HealthyStoreIsUntouched` / `TestChaos57_HealthyEnableReportsNothing`
  — a healthy store is byte-identical to the pre-change behaviour.
- `TestChaos57_SaltIsMintedWhenThereIsNothingToLose` — the refusal did not break
  first-ever enable, the post-purge migration, or encryption-off.
- `TestPolicy_OnlySubtracts` + the unkeyed-store control inside
  `TestChaos57_BothPolicyLayersExemptEncryptionErrors` — the exemption narrowed
  the table for THIS store, not for every store.
- `TestChaos57_LiveOwnerIsNeverQuarantined` — the fix cannot move a live store.

## 9. The process lesson

**A deferral's stated reason is worth re-deriving before inheriting it.**

R-E was left open for a month behind one sentence: *"its content is request
history with retention semantics; quarantining it silently is an evidence
decision, not a cache decision."* Every clause is true. The conclusion does not
follow, because the mechanism being deferred **does not delete** — it moves
aside, by an explicit CHAOS-05/07 rule that predates the row. The evidence
survives either way; what the deferral actually preserved was a crash loop that
took the *whole appliance* down alongside the same unreadable history.

The second half of the lesson is sharper. The row also recorded the exposure as
*"bounded by being opt-in and already non-fatal on ERROR."* Reading the wiring
inverts that: opt-in means **durable in `admin_settings.json`**, which is what
makes the crash loop self-latching, and it means **reachable from the live admin
API**, which is what makes it a runtime kill rather than a boot failure. The one
sentence that was supposed to bound the severity was, on inspection, the
mechanism that raised it.

Neither correction needed new tooling — both are in the register's own words and
two files of wiring. **A row inherited by summary carries its author's
conclusion; a row inherited by re-derivation carries the code's.**

And the finding the sweep did NOT inherit — LS-4 — was found by asking the
obvious next question of the store's key path rather than the corruption path.
The codebase had already written that rule down (SEC-WHSIGN-1, *"a failed
decrypt never mints a key"*) for a different subsystem. **A rule adopted in one
place is a checklist item for every other place that does the same thing**, and
nothing in the tree was checking.
