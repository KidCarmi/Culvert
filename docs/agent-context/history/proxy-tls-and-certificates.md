## Adaptive decryption exclusion (fail-open + auto-learn)

[Original lines 176–176](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L176-L176) · `claude-main-L176-L176`

- **Adaptive decryption exclusion (fail-open + auto-learn)**: `internal/autoexclude` — a volatile, bounded, TTL-bounded in-memory cache of hosts SSL inspection could not decrypt, so subsequent CONNECTs bypass (PAN-OS-style local decryption-exclusion cache). Opt-in per decryption profile via `OnInspectError=="fail-open"`. **SCOPED KEY (policy isolation, not just host):** every entry is keyed by `(scopeID, host)` where `scopeID` is the matched decryption-profile's identity — a host learned under one fail-open profile is consulted ONLY for sessions matched to that same profile, so one fail-open rule/profile/tenant can never create a bypass consumed by another. `resolveSSLAction` consults the cache ONLY when the matched rule opts into fail-open AND within that profile's scope (gated read — a fail-close rule never populates OR consults, so hosts on fail-close rules are un-poisonable and behavior is byte-identical when unused). **SECURITY-GENERATION FENCING (PR2, `roadmap/PR2-autoexclude-security-generation-fencing.md`):** the profile ID is stable across edits, so each entry ALSO records a `securityGen` — a deterministic fingerprint (`decryptprofile.computeSecurityGen`, `SecurityGen()`) over ONLY the security-effective fields (`OnInspectError`, `CertVerification`, `OnUnsupported`, `MinTLSVersion`, `MaxTLSVersion`, `InspectHTTP2`; identity/timestamps/`StallTimeoutSecs` are EXCLUDED so a rename never invalidates). `Observe`/`Contains` are `(scopeID, gen, host)`: a gen MISMATCH is a miss (re-inspect), so a security-relevant same-ID profile edit invalidates learned entries immediately while a rename preserves them. The gen is PRECOMPUTED at store-write time and returned by the hot-path accessors (`FailOpenScope`/`FailOpenScopeByID` now return `(id/scope, gen, ok)`), so the CONNECT path never hashes (benchgate-pinned zero-alloc). It NARROWS the `(scopeID,host)` boundary to `(scopeID,gen,host)`, never broadens it; `scopeID` stays PURE for metrics/audit. The gen is a pure function of the synced fields — never persisted/synced, recomputed identically on every node (CP→DP) and across restarts. **Tightened classifier (`classify{Origin,Client}InspectFailure`, autoexclude_resolve.go):** an origin controls its own TLS alerts, so only NARROW signals learn — origin leg: `client_cert_required` (specific `certificate_required` TLS-1.3 alert; the ONLY reason permitted to LIVE-RESCUE the triggering session) and `unsupported_params` (only the client-side `server selected unsupported protocol version` string — a genuine per-origin version mismatch; the host-independent `no supported versions satisfy` config error and the server-side `no cipher suite` string are deliberately NOT matched; LEARN-ONLY, never rescues); client leg: a specific cert-rejection alert (`client_pinned`, learn-only). Generic/origin-emitted alerts (`handshake failure`, `no application protocol`), cert-verify failures (untrusted/expired/mismatch — a Block signal + the poisoning vector), and EOF/RST/timeout/wrapped errors NEVER learn (fail-closed default). A host is excluded only after a CONFIRM-COUNT of DISTINCT client-evidence tokens (default 2) within a window — the token is the AUTHENTICATED IDENTITY when available, else the client IP (IPv6 collapsed to /64 for single-host churn; IPv4 RAW — a /24 would over-collapse a NAT fleet; NAT/DHCP limitation documented). `client_pinned` gets a shorter TTL (1h vs 12h). Only `client_cert_required` on the strip path live-RESCUES the current session (confirm-count-exempt) via `handleTunnelBypass` (its own inline `isPrivateHost`+`ssrfControl` re-dial); everything else — `unsupported_params`, the native-H2 path, client-pinning — is learn-only (self-heal on the next session after the confirm-count). Promotion fires a SCOPED audit event (actor = triggering client IP) + `fireAlert` + metrics (`culvert_decrypt_autoexclude_{total{reason,scope},hit_total{scope},active{scope},pending}` — F6 labels `hit_total`/`active` by profile scope, same capped label set folding overflow to `_other_`; the process total is `sum()`-able and also on `/api/decryption/health`); pending map is independently bounded (`maxPending`). The learned ENTRIES are VOLATILE — off every config surface (cleared on restart, never CP→DP synced). The five ENGINE PARAMETERS (`confirmN`/`ttl`/`pinnedTTL`/`window`/`maxEntries`) are runtime-tunable (F10, PRs #747/#749/#752/#753): DURABLE in `admin_settings.json` (sentinel `AutoExcludeTunablesSaved`) but node-local — OFF export/import, version-rollback, and CP→DP (AdminDurable-only `configSurfaces` rows, pinned by `config_surfaces_test.go`). `Cache.Reconfigure` applies changes in-place under the mutex (forward-only: active entries keep their expiry; lowering `maxEntries` deterministically evicts oldest-first to exactly the cap). `OnInspectError` is an additive persisted profile field (omitempty) that degrades to fail-close on downgrade (old binary ignores the unknown key). Admin surface: `/api/decryption-exclusions` (GET viewer list+Stats+fail-open footprint+per-scope rule blast-radius / DELETE operator evict-one `?scope=&host=`·clear-all) + `GET/PUT /api/decryption-exclusions/tunables` (GET viewer = defaults+bounds ONLY, current values stay on the Stats surface as the single source of truth; PUT admin = full-set `zero⇒default`, `confirmN`≥2, `maxEntries`≤262144, persist-before-apply: validate→persist target→apply infallible Reconfigure, no rollback branch) + the Decryption Exclusions SPA panel (incl. the admin-only Cache Tuning section). Engine tests use an injected clock; `swapAutoExclude` isolates the global singleton per test (the PR3d fence-pollution class). See `docs/operator/decryption-auto-exclusions.md` and `roadmap/auto-exclusion-cache-plan.md`.

## An OCSP response is a verdict only when it is BOUND, FRESH and AFFIRMATIVE — and the check does not reach inspected HTTPS (CHAOS-65, `internal/ocsp/ocsp.go` + `ocsp_coverage.go`)

[Original lines 188–188](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L188-L188) · `claude-main-L188-L188`

<!-- BEGIN preserved-block: claude-main-L188-L188 -->
- **An OCSP response is a verdict only when it is BOUND, FRESH and AFFIRMATIVE — and the check does not reach inspected HTTPS (CHAOS-65, `internal/ocsp/ocsp.go` + `ocsp_coverage.go`)**: every input this engine acts on is written by **the party being checked** — the responder URLs come out of the peer's own AIA extension, so the peer picks which responder is asked, how many, and therefore what comes back — and nothing in the pipeline treated that as hostile. **(1) The response was not BOUND to the certificate under test.** `cryptoocsp.ParseResponse(b, issuer)` is `ParseResponseForCert(b, nil, issuer)`, which takes `Responses[0]` and NEVER compares the serial (`x/crypto@v0.56.0/ocsp/ocsp.go:509-528`); the signature is verified, which is a far lower bar than it sounds, because a genuine CA-signed `good` about any OTHER certificate of the same issuer is obtained by asking that CA about any live cert and keeping the bytes. The peer names the responder, so the peer serves that reply, and a **revoked certificate is accepted — a complete revocation bypass by its own subject, needing no network position.** Now `ParseResponseForCert(respBytes, leaf, issuer)`; **never call `ParseResponse` here.** **(1b) BINDING THE RESPONSE IS ONLY HALF — THE SIGNER MUST BE BOUND TO AN AUTHORITY TOO, and getting that wrong defeated (1) entirely** (Codex review, PR #1369): `ParseResponseForCert` verifies an embedded responder certificate by asking ONLY whether the ISSUER signed it, never whether it carries RFC 6960 §4.2.2.2's `id-kp-OCSPSigning`. **The peer's own leaf is by definition a certificate the issuer signed, and the peer holds its private key** — so the peer signs a fresh `good` about its OWN serial, embeds its own leaf as the responder, serves it from the responder URL in its own AIA, and a REVOKED certificate is accepted needing no response from anybody else, which is strictly EASIER than the borrowed-response vector (1) closed. `responderAuthorized` now admits exactly two signers: the issuer itself, and a delegate the issuer signed that carries the OCSP-signing EKU and is inside its own validity window. **`ExtKeyUsageAny` is deliberately REFUSED** — honouring it re-admits every ordinary leaf the issuer ever signed, i.e. the whole attack; and **refusing every embedded certificate is NOT the fix** (delegated responders are ordinary and widely deployed — pinned as a CONTROL). The delegate's own revocation status is deliberately unchecked: that is the infinite regress RFC 6960 §4.2.2.2.1 answers with `id-pkix-ocsp-nocheck`. The lesson, which this note had already written and only half applied: *"the peer picks the responder, so the peer picks the answer"* was answered for WHICH CERTIFICATE the response is about and not for WHO WAS ALLOWED TO SAY SO — binding an assertion to its subject is worth nothing until the signer is bound to an authority. **(2) There was NO freshness check.** `ThisUpdate`/`NextUpdate` were parsed and never read, `CreateRequest(leaf, issuer, nil)` sends no nonce, and OCSP rides plaintext HTTP — so a `good` captured before revocation replayed forever, and fixing (1) does not close it (a pre-revocation response for the CORRECT certificate binds perfectly). `responseFresh` requires `ThisUpdate` not in the future and `now` inside `NextUpdate`, with a `maxResponseAge` 24h ceiling when `NextUpdate` is absent (RFC 6960 §2.4 permits omitting it, which without a ceiling is an unbounded replay window). Skew is tolerated **5 min in BOTH directions**, reusing `caClockSkewTolerance`'s value rather than inventing a second one: a clock rollback is a fault, not an attack, and must not take revocation checking down. **(2b) THE CACHE MUST NOT OUTLIVE THE AUTHORIZATION IT IS BUILT ON** (Codex review): freshness was checked at receipt and then thrown away — every confirmed verdict was cached for the fixed 1h `cacheTTL`, so a `good` whose `NextUpdate` was a minute out kept admitting the certificate for another 59 minutes after the responder stopped vouching for it, i.e. (2)'s replay window closed on the wire and reopened in the cache. `cacheResult` now takes the response's own deadline (`responseValidUntil` = `NextUpdate`+skew, else `ThisUpdate`+`maxResponseAge`) and uses the EARLIER of that and `cacheTTL`; a verdict already at its deadline is not cached at all. Same shape as (1b): a rule enforced at one layer and not carried to the next. **(2c) AND THE CACHE MUST NOT OUTLIVE ITS SIGNER EITHER** (Codex review round 3): two checks bound a verdict at PARSE time — `responseFresh` bounds the ASSERTION, `responderAuthorized` bounds the SIGNER — and (2b) carried only the first into the cache. A delegated responder valid for another THIRTY SECONDS could sign a `good` whose `NextUpdate` was a day out, so the handshake that parsed it cached the verdict and later handshakes kept admitting the certificate for the rest of the cache TTL, while a re-parse of those identical bytes would have refused them as an unauthorized responder. `responseValidUntil` now takes the issuer and caps at the EARLIER of the response deadline and the delegate's `NotAfter`+skew, MIRRORING `responderAuthorized`'s branch structure exactly (the issuer-signed branch takes no signer cap, because that branch applies no window check — capping there would expire verdicts the parser still accepts and buy nothing). **This was the THIRD instance of one pattern in this sweep** — (1) bound the response to its subject, (1b) the signer to an authority, (2b) the assertion's deadline into the cache, (2c) the signer's — so the rule to carry forward is: *a check that runs at parse time governs a value that outlives the parse*; for every validity rule, settle what caches the result and for how long IN THE SAME CHANGE. **(3) A verdict is `Good` or `Revoked` or it is NOT A VERDICT.** `unknown` used to be a pass while a responder that could not be REACHED failed closed — two postures for one question; under the CA/Browser Forum baseline requirements a CA must not answer `good` for a certificate it never issued, so `unknown` is exactly the answer a mis-issued or forged certificate draws. An unbindable response, a stale one, an unauthorized signer and an `unknown` are each discarded under their own counter and fall through to the EXISTING fail-closed path with its existing 2-min `indeterminateTTL` — no new posture, no second dialect (CHAOS-53's rule for the scan sidecar). **(4) The verdict cache is keyed by RFC 6960's CertID** (`certKey` = SHA-256 over issuer subject + issuer SPKI + serial), not the serial alone: a serial is unique only WITHIN an issuer, and the dangerous direction of that collision admits a genuinely REVOKED certificate from a different CA off another CA's cached `good`, with no responder query at all — ordinary, not exotic, wherever two enterprise CAs with sequential serials are trusted. **(5) The responder URL is an SSRF sink** and was reached with `http.DefaultClient` and no guard at all, which also follows up to ten redirects: scheme allow-list + `ssrf.PrivateHostContext` INLINE (the context form, so the guard runs under the query budget instead of an unbounded `context.Background()` resolve) at the call site (so CodeQL sees it, repo convention), `ssrf.SafeDialContext` under it to close the rebinding window, and `CheckRedirect` refusing outright — a guard on the first URL alone is bypassed by a `302`. Deliberately **not** `http.DefaultClient`: it shares the process-wide default transport, follows redirects, and honours `HTTP(S)_PROXY`, none of which is wanted for a request whose URL the peer chose; the consequence (responder queries are DIRECT and do not traverse a parent proxy) is a behaviour change recorded in the runbook. **(6) The work is an ENVELOPE, not a per-step allowance** — `maxResponders` 4 inside ONE `queryBudget` 5s, where the budget is deliberately the OLD per-responder timeout so the ordinary one-responder certificate is unchanged and only the worst case shrinks. `leaf.OCSPServer` used to be walked in full under a per-responder 5s timeout on the REQUEST goroutine inside a TLS handshake, holding the client conn, an FD and a per-IP `connlimit` slot: 200 blackholed responders parked it ~17 minutes AND aimed 200 outbound POSTs at hosts the attacker named (CHAOS-58's rule, one subsystem over). **(6b) AN ACCUSATION IS CHARGED ONLY WHEN IT IS DEMONSTRABLE** (Codex review): every `ParseResponseForCert` error used to charge `notForCertTotal`, whose metric help and RED panel banner both read *"something is answering with borrowed responses"* — so an HTML 502 from a broken responder raised a standing claim of attack on a surface whose whole job is to be believed. `noteUnusableResponse` charges `not_for_certificate` only when the response parses, its signature verifies against the issuer, and the serial is someone ELSE's; everything else is `malformed`. **The second parse is required and a string match would not do**: the library checks the serial BEFORE verifying any signature, so its serial-mismatch error alone proves nothing about who signed. A multi-status response that cannot be re-parsed counts as `malformed` — an UNDERCOUNT of the accusation, the only direction it may err in. **(6c) REVOKED WINS OVER GOOD — a Good does NOT short-circuit the responder loop** (Codex review round 2): the pre-CHAOS-65 loop walked every responder and returned revoked if ANY said so; the rewrite added `case Good: return` to save queries, so the FIRST responder decided — and **the peer writes the AIA list AND its order**, which hands the verdict back to the party being checked, this note's own finding reintroduced by the change that bounded the loop (it also accepts a certificate during ordinary responder replication lag). A Good is now remembered with the EARLIEST deadline among the Good answers (that is what the cache may rely on) and the loop continues; only Revoked short-circuits. **A cost change must not quietly move a security posture** — diff the CONTROL FLOW against what it replaced, not just the happy-path outputs. **(6e) AND AN SSRF REFUSAL IS COUNTED ONLY WHEN IT IS ONE** (Codex review round 4): `ssrf.PrivateHostContext` has THREE outcomes — allowed, refused-as-private, and COULD-NOT-DETERMINE (DNS failure, or this query's own budget expiring mid-lookup) — and the call site read any error as the middle one, so an ordinary resolver outage inflated `responder_blocked`, whose runbook tells the operator the responder RESOLVED INTO A PRIVATE RANGE and sends them down a different remediation. Neither guard branch wrapped a sentinel, so the fix is at BOTH layers: `ssrf.ErrBlocked` (previously documented as the connect-time `Control` sentinel only) now wraps the PRE-FLIGHT refusal too — one identity meaning *we refused this destination as private*, at whichever layer decided it — while the resolution-failure branch deliberately does NOT wrap it; the call site charges `blockedTotal` only on `errors.Is(err, ssrf.ErrBlocked)`, and a resolution failure takes NO `response_rejected_total` reason (no response existed to reject; it is already accounted by the fail-closed path). **This is the SECOND accusation-counter defect in this one sweep** — (6b) was the same mistake on `not_for_certificate` — and both came from treating a multi-cause error path as one thing because it arrives as one value. The standing rule: *a counter an operator is told to act on is charged only from evidence supporting the specific claim its runbook makes*, and a guard that can fail for more than one reason must SAY which rather than leave the call site to guess. **(6d) A DIAL-TIME SSRF REFUSAL IS COUNTED** (Codex review round 2): `ssrf.SafeDialContext` catches a responder host that answers public to the pre-flight `ssrf.PrivateHostContext` check and private to the dial — the DNS-rebinding case the dialer exists for — but its `ErrBlocked` landed in the generic transport branch, so the guard's own success moved neither `responderBlockedTotal` nor the `responder_blocked` metric reason. `errors.Is(err, ssrf.ErrBlocked)` now charges it. **(7) Misses are SINGLE-FLIGHTED per CertID** (leader/follower, the `hostIPCache`/`jwksCache` shape): 24 concurrent handshakes used to produce 24 queries, amplifying client rate 1:1 onto a responder that is by hypothesis already the slow dependency. **No follower timer** (it would release the follower to start exactly the query being collapsed), the leader publishes on EVERY exit path INCLUDING a panic, and the flight's defaults are the **fail-closed** verdict so a dead leader leaves followers denied rather than admitted. `resolve` ALSO re-checks the cache before opening a flight (lock order `flightMu` → `mu`, the only order this file takes): the caller's lookup happened earlier, so a handshake descheduled while the leader finished would otherwise open a NEW flight and query again for a verdict already cached — defeating the collapsing during exactly the cold-cache burst it exists for (Codex review). **(8) THE CONTROL IS NOT ON THE PATH THAT HANDSHAKES, and this is REPORTED, not fixed (register row CA-6b / OCSP-8).** `ConfigureTLSConfigOCSP` has exactly two call sites (`mtls_ocsp_startup.go`, the `/api/ocsp` toggle) and both target `upstreamOpTLSCfg` behind the shared upstream `*http.Transport` — which for a forward proxy means an `https://` PARENT PROXY handshake and nothing else, since the plain-HTTP path never negotiates TLS to an origin. Every inspected HTTPS request goes through `upstreamInspectTLSConfig` (`proxy_tunnel.go`), which builds its own `tls.Config` with no callbacks. So revocation is not checked on the one path where this appliance validates an origin certificate on a client's behalf, while the banner, the panel and the API all say "enabled" and every counter reads zero — *"found nothing wrong"* and *"never consulted"* are the same scrape. **Do not close this by simply attaching the callbacks**: that makes EVERY inspected HTTPS request depend on reaching an external responder, FAIL-CLOSED, on networks where outbound port 80 to arbitrary hosts is exactly what egress policy forbids — a fleet-wide HTTPS outage arriving the moment someone ticks a checkbox, and reachable from the LIVE admin API. It needs a soft posture designed alongside it (observe-only counters, or fail-open-and-alert). What shipped instead is visibility: `ocspCoverage()` with a STRUCTURAL gate comparing each claim against the `tls.Config` the named path actually builds (it pins the AGREEMENT, not the gap — whoever wires the inspect path finds the test failing and updates the claim in the same change), a WARNING from both enable paths, a panel banner, `coverage`/`uncheckedEnforcingPaths` on `GET /api/ocsp`, and `culvert_ocsp_path_checked{path}`. Surfaces: `culvert_ocsp_{enabled,revoked_total,fail_closed_total,cache_entries,response_rejected_total{reason},responders_truncated_total,singleflight_joined_total,path_checked{path}}` — **emitted ONLY when the checker is enabled** (the socks5/cluster_ca/dns rule: a flat zero from every appliance that never turned it on is indistinguishable from a broken one). Governance note carried in the register: row **CA-6** named the peer-controlled responder URL as a caveat in July 2026 and scored the row **✓ (+2 caveats), L/M** — the evidence column named the property that makes all seven defects reachable and the verdict looked past it, because the only question asked was *"does it fail closed?"*. Gates: `internal/ocsp/ocsp_chaos_test.go` (8 CHAOS-65 defect gates + 7 Codex-round defect gates, each verified failing against the tree it targets, + 6 CONTROLS — a checker that refused everything would pass all eight while being a fleet-wide HTTPS outage) and `ocsp_coverage_test.go` (4). Deliberately left and recorded: **no OCSP stapling** (`tls.ConnectionState.OCSPResponse` is never requested or consumed — the shape that makes revocation checking cheap, private and egress-free, and the natural companion to closing (8); OCSP-9) and **no CRL fallback**, with a certificate carrying no AIA responder still accepted unchecked (OCSP-10). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §35 and `docs/operator/ocsp-revocation-checking.md`.

[Original lines 189–189](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L189-L189) · `claude-main-L189-L189`

- **Root-CA usability is fail-CLOSED and observable (CHAOS-28, `internal/ca/validity.go` + `ca_health.go`)**: `x509.CreateCertificate` does NOT check the parent's `NotBefore`/`NotAfter`, so an expired inspection CA kept minting well-formed leaves that every client rejects — a fleet-wide inspected-HTTPS outage with the proxy's `/health` reporting `ssl_inspection: ready` throughout. `Ready()` (= `caCert != nil`) is now deliberately DISTINCT from `Usable()` (= inside its own validity window, ±`caClockSkewTolerance` 5 min for clock rollback): `handleTunnel` keeps using `Ready()` to choose inspect-vs-bypass, and an inspect-matched CONNECT on an UNUSABLE CA is **refused 502 before the 200** (`failClosedUnusableCA`), never bypassed. **Do not "simplify" this by folding validity into `Ready()`** — that routes the fault into the `inspect_unavailable` BYPASS branch and silently turns off DLP/AV/YARA/CDR/DPI fleet-wide at the instant the CA expires (the §1 silent-fail-open theme); it also must NOT honour a decryption profile's `OnInspectError=fail-open`, whose confirm-count contract is scoped to PER-ORIGIN incompatibility — an appliance-wide fault would poison the whole auto-exclusion cache. The refusal records ADR-0011 `failed`/`no_fail_open_502`/`client_hello`/`certificate` with NO learner fields (pinned by `TestHandleTunnel_ExpiredCAFailsClosedNotBypass`). `signLeaf` carries the same guard (`ErrCAUnusable`) as defense-in-depth and **clamps the leaf's validity to the issuer's on both ends** (`clampLeafValidity`) so a leaf can never outlive its CA. Health plane mirrors `storage_health.go`: counters, independent 5-min log/alert gates, `HasSubscriber`-gated `cert_expiry` alert, and recovery on OBSERVED evidence only (`caInspectionUsable`) — never elapsed time. Surfaces: `culvert_ca_{usable,expires_in_seconds,sign_refused_total,inspect_blocked_total,rotation_persist_failures_total}`, the proxy's `/health ssl_inspection: expired`, `/ready ca` (report-only; fixed detail — unauthenticated surface; distinct from the admin/UI port's HA-only `/healthz`, which carries no CA/SSL-inspection field), `/api/diagnostics root_ca`, `/api/ca/status` + CA-panel banners. Rotation is the only recovery, so a `SaveCA` failure is no longer swallowed on EITHER path (`RotationPersistFailureObserver`, wired from both `RotateIfNeeded` and the manual `apiCARotate`/`persistRotatedCA`; an in-RAM-only CA re-rotates to a DIFFERENT root every boot). Two paired rules there: the SUCCESS signal (`RotationObserver` → the "rotated" alert + `culvert_ca_rotations_total`) is GATED on persistence so one event never emits two contradictory pages, and the persistence WARNING is keyed on `caRotationPersistDegraded()` (cleared by `RotationPersistSuccessObserver`), NOT on the cumulative counter — a counter-keyed row would latch until process restart even after the operator fixed the volume and re-rotated. Neither persist observer fires when no bundle path is configured. `StartCAAutoRotation` runs one guarded round IMMEDIATELY before its 24h ticker (the old first-check-at-+24h skipped exactly the restart an operator makes to recover). Runbook: `docs/operator/root-ca-expiry.md`.

## The client-supplied destination authority is BOUNDED AT THE ENTRY POINT, and there is no structural half in the leaf (CHAOS-69, `proxy_host_bounds.go`)

[Original lines 198–198](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L198-L198) · `claude-main-L198-L198`

<!-- BEGIN preserved-block: claude-main-L198-L198 -->
- **The client-supplied destination authority is BOUNDED AT THE ENTRY POINT, and there is no structural half in the leaf (CHAOS-69, `proxy_host_bounds.go`)**: the destination authority is written by the client, arrives as `r.Host`, and `net/http` admits its 1 MiB default of request line plus headers. Register row PX-21 recorded the consequence as log amplification — `handleRequest` copies the value into the process log and the request-log entry, `sanitizeLog` neutralises control characters and bounds NOTHING (measured: a 256 KiB authority wrote 262,228 bytes to the process log and a 262,143-byte `Host` field to the request log, from ONE request on the default-deny path). **The copy was the smaller half.** The authority is also WALKED, label by label, by every destination matcher — and two of those walks are QUADRATIC in its length: `internal/urlcat` `lookupIn` (reached by every `DestCategoryGroup` rule via `hostCatScratch.fusion()`) probes the host and then EVERY suffix starting just past a `.` against a non-empty reverse index, hashing each (Σ suffix lengths ≈ L²/4), and `internal/catdb` `CommunityDB.Lookup` walks parent domains opening ONE BadgerDB read transaction per label — with `-cat-feed-db /data/catfeeddb` enabled BY DEFAULT in the shipped compose file. **Measured through the real `handleRequest` with one ordinary category-group rule and the Layer-2 feed present: 251 B → 0.45 ms, 4,095 B → 19.6 ms, 16,383 B → 260 ms, 65,535 B → 3.94 s** — clean quadratic, so ~16 minutes of a core at the 1 MiB header default, inside the request goroutine, holding the conn + FD + per-IP `connlimit` slot, and reached BEFORE authentication (gate order: connlimit → IP filter → rate limit → auth → policy, and all three front-door limiters ship DISABLED — `-rate-limit` defaults to 0, CHAOS-57's finding). ~256 KB/s from one unauthenticated client saturates a four-core gateway. Engine primitives alone: `urlcat.LookupHost` 5.38 s at 1 MiB, `catdb.Lookup` 4.09 s at 64 KiB (32,767 badger transactions). **THE BOUND IS TWO TIERS, BECAUSE A BOUND GOVERNS A REPRESENTATION AND ONE TIER CANNOT DO BOTH JOBS.** (1) A **RAW pre-cap**, `maxRawDestAuthorityBytes` = **1024**, on the authority exactly as the client sent it, at the entry point — it bounds every log sink and every matcher walk before they run. (2) A **CANONICAL bound**, `maxDestHostLen` = **253** (RFC 1035 §2.3.4's 255-octet wire limit in RFC 1123 §2.1 presentation form), applied to the NORMALIZED A-label host at the existing RISK-013 canonicalization gate. **The first version applied the DNS limit to the RAW bytes and that was a customer-visible regression** (Codex P2, PR #1446): an internationalized domain arrives as UTF-8 and SHRINKS under `idna.ToASCII`, so `é`×40 in four labels is 323 raw bytes / 187 canonical and the widest legitimate case is **883 raw / 251 canonical** — all ordinary resolvable destinations, all refused with a 400, i.e. a forward proxy that stops reaching international sites. The raw cap's generosity is DERIVED, not slack: an A-label is ≤63 bytes = `xn--` + ≤59 Punycode bytes, Punycode emits ≥1 byte per encoded code point (RFC 3492 §3) ⇒ ≤59 code points ⇒ ≤236 raw bytes per label ⇒ ~940 per authority; the empirical maximum is 883 and `ControlRawCapExceedsMaximumIDNExpansion` RE-MEASURES it against the shipped normalizer (so an x/net ratio change fails the build rather than silently refusing a resolvable name) and requires ≥64 bytes of margin. **The canonical tier is what keeps the raw tier from being a hole**: 1 KiB alone still admits a 1000-byte dot-dense ASCII authority costing ~1.3 ms of walk, and ASCII does NOT shrink under IDNA, so measuring the canonical form refuses exactly the attacker's shape while the 883-byte IDN passes — realistic worst case back to ~111 µs. Measured costs that chose 1024: 251 B → 111 µs, 511 B → 396 µs, 1023 B → 1.28 ms, 2047 B → 4.72 ms. **The tiers are ordered by what each can MEASURE, not by preference**, and BOTH now sit at the entry point, ahead of every sink AND every matcher. The first version placed the canonical tier ~60 lines down at the IDNA gate, reasoning that the raw pre-cap had already bounded what `IP_BLOCKED`/`RATE_LIMITED` could RETAIN to 1 KiB — true, and about retention ONLY. The canonical tier's other and more important job is bounding the QUADRATIC MATCHER WALK, and **Stage-1 authentication runs a matcher**: `authRuleMatchesScratch` calls `matchDestNorm` with `authMatchScratch.hostCat()`, the same fusion, so a category-scoped auth rule paid the walk for a 1000-byte dot-dense authority before the gate was reached — and a TERMINAL auth outcome (407/403) returned without reaching it at all, so the refusal never happened and the counter never moved (Codex P2, PR #1446). The gate is now hoisted immediately after the raw tier; the host is normalized ONCE per request (`canonicalDestHost`) and the value reused at the IDNA gate, so the hoist costs nothing, and the RISK-013 INVALID_HOST refusal deliberately stays in its original position — the hoisted gate decides LENGTH only, never validity. **THE ORDERING IS A CONTRACT, NOT AN OPTIMISATION**: the gate is the FIRST consumer of `r.Host` in `handleRequest` and sits ahead of the connection limiter, IP filter, rate limiter, authentication and policy, because `IP_BLOCKED` and `RATE_LIMITED` both write `r.Host` into the request log and both run BEFORE the host-canonicalization step where RISK-013's IDNA gate sits — so the intuitive home for a host check is BEHIND two sinks that have already retained the megabyte (pinned by `TestChaos69_DefectIPBlockedPathDoesNotRetainTheAuthority`, which fails against that plausible-wrong fix as well as against the pre-fix tree). **DO NOT add a length guard inside `urlcat`/`catdb`/`blocklist` as a "structural half"** — unlike CHAOS-63's injective `lockout.boundUsername` clamp, it cannot be made safe: the suffix walk exists precisely so `a.b.example.com` matches a stored `example.com`, so an over-long host still has SHORT suffixes that may legitimately match (a megabyte of `a.` prefixed onto `facebook.com` is still Social Media), and skipping the walk on length would change that verdict to no-match, i.e. **fail-OPEN for a block rule** — buying a cost bound with the security failure the matcher exists to prevent. A clamped lockout key is still a usable key; a clamped host is a different host. **That makes the completeness of the entry-point inventory a SECURITY property**: four exist today — `handleRequest`, `handleSOCKS5`, `apiURLCatLookup` and the policy-test handler — and all four go through the SAME shared predicates (`rawAuthorityOversize` for the raw tier, `canonicalHostOversize` for the canonical one — never a hand-rolled length compare at a call site), because two entry points disagreeing about what is too long is the divergence class CHAOS-63 pinned for lockout's `Check`/`RecordFailure` pair, where two call sites computing different keys silently WEAKENED the control while passing every byte-size assertion. **Any new path that hands a client-supplied host to the policy/blocklist/category engines must apply BOTH predicates at its own entry point, ahead of every matcher on that path.** Both admin entry points originally applied the RAW tier only — so a VIEWER could still drive the 1000-byte dot-dense shape into `lookupHostCategory` (and, via `apiPolicyTest`, into the fusion more than once per call) — because the canonical tier had no shared derivation and was written inline at the one place a normalized host was already in scope. `canonicalDestHost` now exists precisely so the four entry points cannot derive that value differently; **enforcing one tier of a two-tier contract is not enforcing the contract.** SOCKS5 is structurally bounded already and that is recorded rather than assumed (RFC 1928 §4 length-prefixes DOMAINNAME with one byte, capping it at 255, which is why SOCKS5 is not the reachable half here — a pleasing contrast with SEC-SOCKS5-LOG-1, where it was the ONLY protocol whose destination reached a sink unvalidated); the gate is applied anyway because 255 still exceeds the 253 a resolvable name can occupy. SOCKS5 therefore carries **only the canonical tier** (`rawAuthorityOversize` is unreachable there — 255 < 1024 — and adding it anyway is precisely the dead-code mistake below), and that gate IS live, because 255 exceeds the canonical 253. A defect found in SELF-REVIEW before review is why this is spelled out: the first version applied a 261-byte raw predicate at SOCKS5, above the 255 the protocol can carry, so the gate was **DEAD CODE on the one protocol whose safety claim is that it is bounded already** — and its test PASSED, because it asserted only that no oversize host reached the request log, which is vacuously true at 255 whether the gate fires or not and would have stayed true if the gate were deleted. The gate now asserts the REFUSAL (SOCKS5 reply `0x02`) and the counter, and `ControlBoundIsInclusiveAndDerived` asserts `maxDestHostLen < 255` — that the bound is REACHABLE within what the protocol delivers — so a gate that cannot fire fails the suite. Standing rule, the not-vacuous-check rule arriving from a new direction: **a bound is only enforced if it sits inside the range the input can occupy, and a gate's test must assert the REFUSAL, never merely the absence of what the refusal would have prevented — absence is what an unreachable gate and a working gate have in common.** The refusal is 400 and **never echoes the value** (the pre-fix proxy reflected it: a 68,392-byte response body for a 64 KiB authority — the amplification arriving by a third road, the same one CHAOS-63's gates had to suppress their own output for), creates NO state (no limiter entry, no request-log row, no top-hosts key, no alert, no label walk), and is COUNTED by `culvert_proxy_oversize_host_rejected_total` — **always emitted**, since there is no configuration to gate it on, so a flat zero means "nothing has been probed" and never "the feature is off" (the inverse of the socks5/cluster_ca emission rule, for the same one-reading-per-gauge reason). The log line is rate-limited to one per minute with the cumulative count on every line (a mitigation for a write-amplification defect must not be one itself) and carries the protocol, client IP and **LENGTH** — deliberately NOT a prefix of the authority, the one divergence from CHAOS-63's truncated audit actor: a username may name an account an operator recognises, an authority past 253 bytes names nothing that can exist. Deliberately left: `MaxHeaderBytes` on the proxy server is UNCHANGED (it bounds the whole header block, not one field, so lowering it cuts the worst case by a constant while breaking clients with large cookie/token headers — the wrong instrument), the inner inspected request's `req.URL.Path` is still unbounded (PX-22 — narrower reach, needs an allowed destination plus a decryption profile, and a real URL can legitimately be long so capping it is a product decision about log fidelity rather than an arithmetic one), and the ARRIVAL rate is still unbounded by default (PX-6). Gates: `proxy_host_bounds_test.go` (27) — 15 defect gates each verified failing against the reintroduced pre-fix shape (including `DefectConnectFormIsBounded`, because every HTTPS request through this proxy is a CONNECT and the other gates drive the plain-HTTP form), the cost gate as a same-run RATIO (1,442x pre-fix against a 20x bound; an absolute timing bound gets re-baselined per machine and then muted — the `sanitizeLog`/`connlimit`/histogram rule), plus 7 CONTROLS verified failing against the refuse-everything shape, because the cheapest way to pass every defect gate is a total egress outage; the IDN controls were additionally verified failing against the SINGLE-TIER shape (raw cap at the DNS limit), which is the regression they exist to catch, and `DefectDotDenseASCIIIsStillRefusedByTheCanonicalTier` against the canonical tier's removal — so each tier is pinned by a gate that fails without it. **THE STANDING RULE FROM THAT ROUND: a bound derived from a specification governs whichever REPRESENTATION that specification is about — name it, check which one the code is holding, and make the control test carry an example of EVERY representation the input can arrive in, because a control that samples one will pass while the other is broken** (the ASCII-only control is what let the IDN regression through). **AND ITS TWIN, from the round after: a bound is a property of its POSITION as much as its value — "behind these two sinks is safe" was answered for the SINKS and never asked of the MATCHERS, and the gate that was supposed to catch it drove only the plain-HTTP proxy path while the auth path and both admin paths were open. Sampling one path is the same error as sampling one representation: enumerate every path that reaches the cost, not every place you happen to be standing.** A second self-review finding is pinned by `ControlRefusalIsAccountedAsABlock`: the first version incremented `statBlocked` on the SOCKS5 gate and not the HTTP one — two refusals of the same class disagreeing about whether they happened — so both now count it, matching the `INVALID_HOST` twins; an atomic counter is not a RETAINING sink, so this does not weaken the no-state property, which is about log rows, map keys and limiter entries an attacker can grow. **A THIRD round found the accounting ORDER wrong on exactly one path**: the SOCKS5 canonical refusal wrote the `0x02` reply BEFORE charging `noteOversizeHostRejection`, so a reader — or a gate — acting on the refusal could observe the counter unmoved (`TestChaos69_DefectSOCKS5RefusesOversizeDestination` failed 1 run in 4). Every other call site was already correct, because `rejectOversizeDestHost`/`rejectOversizeCanonicalHost` charge before `http.Error` and the two admin handlers copy that order; SOCKS5 was the ONE place the accounting-and-reply SEQUENCE was hand-written inline instead of going through the shared helper — it speaks a wire protocol, so there was no `http.ResponseWriter` to hand the helper. So the entry-point rule above needs its twin: **sharing the PREDICATE is not sharing the ACTION** — the four entry points agreed perfectly about what is too long and diverged about what to do about it, and the divergence appeared precisely where the action was not shared. Charge before you reply, on every path (CHAOS-57's `TUNNEL_CLOSED` rule — the accounting lands ahead of what the peer observes). **AND the runbook example DRIFTED through the two-tier rework**: it kept a pre-rework line with no `tier=` and `limit=261` — the derivation-only `maxDestAuthorityLen`, which the emitter NEVER prints — so the doc contradicted its own field list two paragraphs below and an operator building log parsing from it could not tell WHICH bound fired, the one question the two tiers exist to answer (Codex P2, PR #1446). Prose cannot be unit-tested but an EXAMPLE can: `TestChaos69_RunbookLogExampleMatchesTheEmitter` extracts every `OVERSIZE_HOST` line from the runbook and compares it against what `noteOversizeHostRejection` really emits for that tier, normalising only the live `total=`. **It pins the CONTRACT, not the layout** — every printed line must be one the emitter produces and must name its `tier`, while how many examples the doc shows stays the author's call; an earlier draft demanded both tiers and would have failed the build over formatting. **A documented log line is a parsing contract; pin it against the emitter rather than against a regex rewritten in the test, and pin only the property that was broken.** **A FOURTH round found the band the hoist itself opened, and it is the completeness rule biting a third time**: the canonical gate was spelled `destNormOK && rejectOversizeCanonicalHost(...)`, so an authority with NO canonical form — more than `maxDestHostLen` bare bytes, at most `maxRawDestAuthorityBytes` raw, carrying a malformed ACE label such as a 1000-byte dot-dense host ending `xn--0` — skipped the canonical tier ENTIRELY and reached Stage-1's matcher at full length; a terminal 407 then returned before the `INVALID_HOST` refusal below could run, so the walk was paid and the counter never moved (Codex P2, PR #1446; reproduced: 995 raw bytes, `rawAuthorityOversize` false, `canonicalDestHost` ok=false, request answered 407). Both admin handlers carried the same `ok && oversize` shape, so a VIEWER could drive it too. **`unnormalizableHostOversize` bounds the RAW BARE host when normalization fails, and that does NOT reintroduce the round-1 IDN regression** — that regression refused LEGITIMATE internationalized names whose canonical form fitted, whereas here there IS no canonical form, so no resolver can serve the host and refusing it on length cannot reject a destination that could have been served; 400 is the status `INVALID_HOST` already answered. Only the OVERSIZE band changes: a SHORT malformed host keeps its identity-bearing `INVALID_HOST` refusal (pinned by `ControlShortUnnormalizableHostKeepsItsInvalidHostRefusal`, since the cheapest way to pass the defect gate is to refuse every unnormalizable host at the entry point and delete that audit row). **SOCKS5 was never exposed, and the contrast is the lesson**: it refuses `INVALID_HOST` at the normalization point, ahead of its canonical tier and every matcher, while the HTTP path's `INVALID_HOST` deliberately sits AFTER auth so it can carry the authenticated identity — the very decision that left the gap. So the rule is not just *enumerate every path that reaches the cost* but **enumerate every BRANCH on each path: a guard written `ok && bound(...)` silently exempts the `!ok` case, and `!ok` is exactly where a hostile input wants to be.** A third `tier=unnormalizable` class is emitted rather than folded into `canonical`, because the operator's question is which bound fired and on what basis. **A FIFTH round found that the two tiers were measuring a value the matchers never received — the MEASURE-VS-USE gap, and it is the sharpest form of this finding yet because every gate was green and every bound was correct.** `net.SplitHostPort` does NOT require a numeric port, so `a:` followed by a 1000-byte dot-dense string is a 1003-byte authority whose bare host is ONE byte: the raw tier passes (1003 < 1024), `canonicalDestHost` strips the port and normalizes `a`, the canonical tier passes on a length of 1, and the matchers then received the full 1003 bytes and paid the quadratic walk both tiers exist to prevent (Codex P2, PR #1446; reproduced through the real handlers). The two admin entry points derived a bounded value and then handed `host` / `body.Host` — the ORIGINAL — to `lookupHostCategory`, `bl.IsBlocked`, `walkPolicyTestRules` and `simulateAuthOutcome`. **Bounding the ORIGINAL at 253 is not the fix**: that is round 1's IDN regression, since a legitimate internationalized host measures 883 raw and 251 canonical. The fix is `bareDestHost` — the same `net.SplitHostPort` strip — derived ONCE per handler and passed to every matcher, so the tiers and the matchers speak about the same string. It is also a FIDELITY fix, and that half is the more serious one: BOTH runtime stages perform this exact strip before matching (`authRequestContext` for Stage-1, `handleRequest`'s own strip for Stage-2), so the policy tester — whose entire job is to predict the live decision — reported `outcome=Default` ("this exemption does not apply") for `host:port` traffic the live Stage-1 gate EXEMPTS. An admin auditing the blast radius of an auth exemption was shown a NARROWER scope than production enforces. The HTTP proxy path was already correct for the ordinary reason that it strips the port itself before `preDispatchBlocked` and `Evaluate`, and SOCKS5 never carries a port in its DOMAINNAME field — **so the exposure was exactly the two paths whose host value is not derived from a wire protocol that separates them**. Stage-1 was the THIRD call site in `apiPolicyTest` and was missed by the first draft of this very fix, which enumerated the Stage-2 matchers only — round 2's lesson (*Stage-1 runs a matcher*) landing again inside the function that had just been repaired. So the rule completes: **a bound is a claim about a STRING, not about a request — measure the value you will actually hand onward, and if you derive a bounded form, make every consumer on that path take the derived value, never the original beside it.** The gates are BEHAVIOURAL and that is deliberate: the observable is whether a one-entry taxonomy MATCHES (urlcat's suffix walk probes the host then each remainder after a `.`, so a payload of `bb.` labels can never reach the pattern `a` — bounded resolves the category, raw resolves nothing), which needs no populated feed and no timing. **The first two attempts at this gate were VACUOUS and the reason is worth keeping**: a cost-RATIO gate could not see the defect because the quadratic walk needs a large taxonomy the test cannot build, and a structural wall that compared the argument's identifier NAME against a blessed set passed against the pre-fix shape re-spelled `lookupHost := host`. `DefectEveryAdminMatcherTakesTheBoundedHost` therefore checks the ASSIGNMENT — the argument must be an identifier assigned from a `bareDestHost` call in that handler — and covers all five matcher call sites for completeness, with its own not-vacuous count; the partial-revert mutation (Stage-1 alone) fails only the Stage-1 gate and the wall, which is what proves neither is redundant. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §39 (rows PX-21…PX-25) and `docs/operator/destination-host-bounds.md`.

## Relay pattern

[Original lines 202–202](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L202-L202) · `claude-main-L202-L202`

<!-- BEGIN preserved-block: claude-main-L202-L202 -->
- **Relay pattern**: All tunnel relays (CONNECT, WebSocket, SOCKS5) wait for BOTH goroutines; CloseWrite unblocks peers. Shared `relayCounted`/`bidiRelayCounted` (proxy_tunnel.go) do the byte-counted bridge for the WS + CONNECT-bypass paths. Every raw relay is idle-bounded via `idleCopyCounted` (CHAOS-03): read deadlines armed at half of `tunnelIdleTimeout` (default 1h) around `io.CopyBuffer` — preserving the TCP↔TCP kernel-splice fast path — with a shared per-tunnel activity stamp so bytes in EITHER direction keep both goroutines alive, and a hard close of both conns on idle (the peer relay may be blocked in a deadline-less Write that only a close unblocks). Only READ deadlines are used: read timeouts are resumable on `tls.Conn`; a write timeout would corrupt TLS state.

## The plain-HTTP forward path uses the transport, never an `http.Client` (`proxy_http.go`)

[Original lines 205–205](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L205-L205) · `claude-main-L205-L205`

<!-- BEGIN preserved-block: claude-main-L205-L205 -->
- **The plain-HTTP forward path uses the transport, never an `http.Client` (`proxy_http.go`)**: a forward proxy must never follow a redirect — a 3xx belongs to the client — so `handleHTTP` built a per-request `http.Client` whose only jobs were `CheckRedirect: ErrUseLastResponse` and a timeout, and then paid for the redirect machinery anyway: `Client.do` installs it unconditionally BEFORE the first round trip, long before `CheckRedirect` is consulted. Every proxied request therefore bought a full `Header.Clone` of the client's header map (`makeHeadersCopier`), the body-rewind wrapper (`setupRewindBody`), a `cancelTimerBody` wrapper around the response body, and the `Client` itself — none of it reachable. `handleHTTP` now calls `getUpstreamTransport().RoundTrip` directly: **90 -> 81 allocs/op, 11.5 KB -> 10.7 KB per request, -12% ns/op on the 4-core parallel mix** (`proxy_http_forward_bench_test.go`, which keeps the pre-change shape frozen as `BenchmarkHTTPForward_LegacyClientPerRequest` so the comparison stays reproducible in-tree). **Two things `http.Client` was silently providing must stay explicit here.** (1) `Client.Timeout` is NOT dropped — for a `*http.Transport` net/http implements it as a context deadline on the request (`setRequestCancel`'s knownTransport branch), so `upstreamRequestTimeout` is spelled as `context.WithTimeout`, and its `cancel()` is deferred BEFORE `resp.Body.Close()` so it runs AFTER it — the deadline covers the body read, and cancelling early would truncate the response. (2) `http.Client.send` promotes URL userinfo to a Basic `Authorization` header; the transport does not, and it drops userinfo from the request line, so a client's `GET http://user:pass@host/` would reach the origin with no credentials at all. Both, plus redirect pass-through, body forwarding and the 502-on-round-trip-error contract, are pinned in `proxy_http_forward_test.go`; the allocation contract is gated by `TestBenchGate_HTTPForwardAllocs` (bound 85, and it also asserts the direct path stays cheaper than the frozen legacy shape measured in the same run). Dropping `Client.Do` also drops the `*url.Error` wrapper — `isDNSError`/`Attribution.Record` use `errors.As`/`errors.Is` so they are unaffected, but the error log line names the host explicitly to keep the context the wrapper used to carry.

## A bounded-enum projection helper takes a TYPE PARAMETER, never an interface (`decEnumOr`, decryption_observability.go)

[Original lines 207–207](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L207-L207) · `claude-main-L207-L207`

<!-- BEGIN preserved-block: claude-main-L207-L207 -->
- **A bounded-enum projection helper takes a TYPE PARAMETER, never an interface (`decEnumOr`, decryption_observability.go)**: the ADR-0011 decryption record is projected once per CONNECT tunnel by `toBlock` (seven `decEnumOr` calls) and once per tunnel close by `recordDecryptSession` (three more, run UNCONDITIONALLY — `recordTunnelCloseGatedDec` counts a session even for a quiet rule), so on a gateway where effectively all traffic is HTTPS this is the tunnel hot path. Every `decryptobs` enum is a named STRING type and the helper took two INTERFACE parameters, so each call had to BOX both arguments to satisfy the interface — and boxing a non-empty string is a heap allocation (`runtime.convTstring`). **Only the empty string boxes for free, which is exactly why the waste was invisible in review and in the under-populated fixtures**: a bypass outcome sets two enums and paid 2 boxes, while an INSPECTED outcome — which `inspectedOutcome` populates in all seven slots — paid the full price. Measured on `BenchmarkPerfQual_ProxyCONNECT` at `memprofilerate=1`: 6003 objects from `toBlock` and 4002 from `recordDecryptSession` across 2000 tunnels. Constraining a single type parameter by the SAME interface lets the compiler instantiate per concrete type and call `Valid`/`String` directly on the value: `toBlock` **348 → 172 ns/op, 432 → 320 B/op, 8 → 1 allocs/op** on an inspected session (the one remaining allocation is the returned `*logstore.DecryptionBlock` itself, which the caller keeps), 246 → 181 ns at 3 → 1 allocs on a bypassed one, 194 → 125 ns at 4x parallel; the metric-label projection goes **89.6 → 17.3 ns/op at 3 → 0 allocs**, i.e. allocation-free. End to end a bypass CONNECT goes 141 → 137 allocs/op. **Unlike most allocation work this is a win on EVERY axis — fewer objects AND fewer bytes AND fewer ns — and the code got simpler, not cleverer**, which is why it was taken and why a hand-rolled `append`-into-a-pool rewrite of the per-request `POLICY_ALLOW` line, measured in the same sweep, was NOT: that one bought 8 → 1 allocs but cost 128 → 192 B/op and only ~12% of the ns at 4x parallel, in exchange for hand-rolling formatting on the CWE-117 path — the same trade the `sanitizeLog` SWAR experiment was rejected for. **The single type parameter is also a CORRECTNESS improvement**: `v` and `fallback` must now share a type, so a mismatched pair (an `Outcome` value coerced to a `FailStage` sentinel) is a COMPILE error instead of a silently out-of-vocabulary token on a SIEM record. Do not widen it back to two interfaces and do not give `v` and `fallback` separate type parameters — that restores the mismatch hole and buys nothing. Equivalence is exact, not approximate, and is pinned against a VERBATIM copy of the interface body (`decEnumOrLegacy`/`legacyOutcomeToBlock`, which double as the benchmark baseline so the oracle cannot drift from what the comparison measures): `TestDecEnumOr_MatchesInterfaceProjection` walks every member of all seven closed sets plus the zero value and a cast non-member, `TestToBlock_MatchesInterfaceProjection` diffs the whole record, and `TestToBlock_StillCoercesOutOfVocabularyValues` is the CONTROL — two implementations compared against each other would both pass if the coercion were deleted from BOTH, so the bounded-vocabulary property is also asserted directly. Gates: `decryption_observability_benchgate_test.go` (bounds 1/1/1/0, each verified FAILING against the reintroduced interface signature, plus a same-run beats-legacy control). **The general rule: a helper whose parameter is an interface boxes every named scalar passed to it, and on a per-session path that is a heap allocation per argument — take a type parameter instead.**
