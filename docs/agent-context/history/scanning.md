## Both body-scan back ends share ONE budget and ONE posture (CHAOS-53, `internal/secscan/remote.go`)

[Original lines 209–209](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L209-L209) · `claude-main-L209-L209`

<!-- BEGIN preserved-block: claude-main-L209-L209 -->
- **Both body-scan back ends share ONE budget and ONE posture (CHAOS-53, `internal/secscan/remote.go`)**: Culvert has two body-scanning back ends — the in-process `Scanner` and the remote sidecar (`-scan-svc-url`) — and they disagreed about what to do when a scan did not finish in time. The local path bounds a scan by `ScanBodyTimeout` (10 s) and fails CLOSED; the remote path bounded one by a PRIVATE 30 s context inside a client with a 60 s timeout (3x and 6x the same process's budget for the same decision) and surfaced its expiry as an ordinary transport error, which the classifier read as a sidecar fault and handled fail-OPEN. `nil` from a scanner means CLEAN, so *"the sidecar did not answer in time"* and *"the sidecar answered clean"* were the same value at the call site — a security control switched off by SLOWNESS, on healthy infrastructure, reachable by ordinary queueing (the sidecar fronts the same ClamAV that saturates at four concurrent scans), and RECOMMENDED by the CHAOS-52 runbook as the remedy for the local path's capacity behaviour. `ScanBody` now runs under `scanBodyTimeout()` — same value, same test seam — and a budget overrun (or an HTTP 429 capacity refusal) returns the local path's own refusal object (`Source:"timeout"`), increments the same `statScanTimeout`, and therefore lights up `culvert_scan_timeout_total`, the `scan_timeout` alert and the 403 unchanged. **Do not re-introduce a deadline inside this client**: an inner deadline that preempts the outer one inverts its posture, which is the WK-15/RS-1 defect in both paths. A genuine FAULT (unreachable, 5xx, unintelligible) stays fail-OPEN — recorded owner decision WK-2b, the sibling of WK-1b — but is now reached only by an actual fault, because **a verdict must be AFFIRMATIVE**: `Blocked` or `Clean`, since `ScanResponse` unmarshals from `{}` and `null` without error and any 200 with a JSON body used to be read as clean, with no counter, log or alert. Four more rules the fix carries: the Result's `Hash` is computed LOCALLY (it feeds the admin allowlist/cache-evict surfaces, so a sidecar-supplied value let the far end name objects in the operator's UI); the admin hash allowlist is consulted BEFORE the round trip (`SetExclusions`, wired in `scanning_startup.go`); the fail-open alert is `HasSubscriber`-gated with a BOUNDED reason class and a rate-limited log carrying the cause; and `Status()`/`Health()` reads are byte-bounded. `loadScanExclusions` runs in BOTH modes — it used to sit on the local branch only, and because `scanexcl.Store` learns its persistence path FROM `Load`, `Save()` was a silent no-op on a sidecar node: every admin edit returned 200 and was audited as success while persisting nothing. Metrics: `culvert_remote_scan_{fail,saturated}_total` + `culvert_remote_scan_inflight` (a sidecar node used to export NO scanning signal — every `culvert_scan_*` series is structurally zero there). Gates: `internal/secscan/remote_chaos_test.go` (15) + root `TestChaos53_*` (2). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §21 and `docs/operator/scan-capacity-and-timeouts.md` §6.1.

## DPI scan ReDoS budget is enforced ONCE PER SCAN, not per pattern (`internal/scanner`)

[Original lines 210–210](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L210-L210) · `claude-main-L210-L210`

<!-- BEGIN preserved-block: claude-main-L210-L210 -->
- **DPI scan ReDoS budget is enforced ONCE PER SCAN, not per pattern (`internal/scanner`)**: `ContentScanner.Scan` runs on every SSL-inspected response body (`safeDPIScan`, proxy_tunnel.go). `re.Match` is not interruptible, so the per-match ReDoS deadline needs a goroutine to abandon — and that harness (goroutine + channel + timer) used to be paid PER PATTERN: measured 6 allocs/448 B each, so a 20-pattern policy charged 120 allocs/9.0 KB and a 50-pattern policy 300 allocs/22.4 KB to every inspected body. Most operator patterns carry a literal prefix and match in a few hundred ns (`ghp_…` 158 ns/8 KiB), so the guard cost more than the work it guarded. `patternSet.scan` now walks the whole list in ONE worker: **7 allocs/480 B flat at 1/10/20/50 patterns** (−92% ns/op at 50 patterns, −29% on the 4-core parallel mix, throughput 14.0→19.5 MB/s). **The per-pattern budget is preserved exactly** — the worker stamps the start of each match and the parent charges the fired timer against the pattern actually running, extending it when that match still has budget (`budgetRemaining`); a whole-scan budget would have been equally fast but would fail closed on a large body with many individually-fine patterns, i.e. block legitimate traffic. Timeout stays fail-closed (S17), and the budget is enforced from BOTH sides so an overrun can never be forgotten: the parent catches a match still RUNNING past budget, while the worker times each match it COMPLETES (a descheduled parent would otherwise re-arm against the next pattern's stamp and silently admit the overrun — `TestMatch_WorkerCatchesItsOwnOverrun`). Two invariants make it safe: the pattern set is **immutable + copy-on-write** (`Add`/`Remove` publish a replacement — an abandoned worker outlives its scan and must never race a config edit; the old in-place `append`-shift did), and the worker checks an `abandoned` flag between patterns so it stops burning CPU once the parent has given up. Pinned by `TestBenchGate_DPIScanAllocsConstantInPatternCount` (root, benchgate tag) + `internal/scanner/scanner_timeout_test.go`. The `internal/yara` half (the same per-pattern harness, one goroutine per string def) was recorded here as a deliberate follow-up and has since SHIPPED as the per-scan `regexRunner` (`internal/yara/regexrunner.go`) — same hoist, same per-string budget, plus the charge/releaseCharge accounting that keeps `yaraInflight` tracking the MATCH rather than the worker.
