## Destination-host DNS resolution is BOUNDED, SINGLE-FLIGHTED and STALE-SERVING (CHAOS-64 — the resolver half of the CHAOS-60 bullet below, sharing one `hostIPCache`; `geoip.go` + `dns_health.go`)

[Original lines 196–196](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L196-L196) · `claude-main-L196-L196`

<!-- BEGIN preserved-block: claude-main-L196-L196 -->
- **Destination-host DNS resolution is BOUNDED, SINGLE-FLIGHTED and STALE-SERVING (CHAOS-64 — the resolver half of the CHAOS-60 bullet below, sharing one `hostIPCache`; `geoip.go` + `dns_health.go`)**: a `DestCountry` policy rule puts the customer's resolver on the critical path of every request that misses one process-wide cache — `matchDestNorm` calls `geo.LookupCached` on the REQUEST goroutine, once per such rule, and that needs an IP before it can ask for a country. `policy.go`'s own comment names the hazard and drops the evaluation lock because of it, which is the right fix for the LOCK and no fix at all for the REQUEST. Behind it sat `net.LookupHost` with no deadline, no single-flight, no concurrency bound and no counter. Three defects, each reproduced against the pre-fix tree. **(1) No deadline** — the only bound was the OS's (`resolv.conf` ships `timeout:5 attempts:2` per nameserver), spent while holding a client connection and a per-IP `internal/connlimit` slot. **(2) No single-flight** — measured **200 resolver invocations for 200 concurrent requests to ONE host**; during a brownout that is one blocked goroutine per request AND one query per request aimed at the resolver that is already failing (the WK-13 herd, pointed at the customer's own DNS). It also made the negative cache useless as a shock absorber: a negative entry is written only when a resolution COMPLETES, so during an outage every request kept missing for the whole outage. **(3) No stale serving, and this one is the SECURITY half** — an expired entry was discarded, and because the TTL is uniform and entries are created by traffic, the first expiry during an outage took the whole working set cold at once. `LookupCached` then returns `("", false)`, a `DestCountry` rule that cannot determine a country does NOT match, and a rule that does not match is **SKIPPED** — `evalAccessRules` continues to lower-priority rules, so a "block sanctioned countries" rule silently stops enforcing while a broad allow rule beneath it takes over. The in-code "fail-closed" comment is true for an ALLOW rule and exactly inverted for a BLOCK one. Shipped: a 2 s deadline on a context-aware seam (`lookupHostFn` is now `func(context.Context, string)`); single-flight where **followers inherit the leader's answer AND its deadline** (a timer on the follower would release it to start a SECOND lookup — the herd being collapsed); a 64-slot pool that **SHEDS a distinct-host flood instead of queueing it** (the hostname is attacker-controlled, so single-flight alone bounds nothing) and does **not cache the shed result** (saturation is a fact about this node's load, not about the host); and stale-while-revalidate with a `hostIPCacheStaleMax` 1 h ceiling, so **a host resolved in the last hour never blocks a request and never goes dark**. **Stale serving is for POSITIVE entries ONLY** (Codex review): a negative entry's stale value IS nil, so serving it stale buys nothing and would keep a once-failed host returning nil on the synchronous path for an HOUR instead of the 30 s negative TTL — dark for a country-scoped DENY rule, repairable only by a refresh that SHEDS under a saturated pool, and a regression against the pre-fix behaviour that re-resolved the moment the negative TTL lapsed. An expired negative is a MISS. Two invariants keep that safe: a **failed refresh never overwrites a still-servable positive** (a negative is served as FRESH for its TTL, so without the guard the refresh introduced by the fix would itself take geo dark for exactly the window the stale answer existed to cover), and `finishFlight` is **DEFERRED on every leader path** (otherwise a panic inside the resolution leaves followers blocked forever on a flight nobody completes — a bounded resolver fault turned into a permanent request-plane hang no upstream `recover()` can undo). Health plane mirrors `socks5_health.go`: count everything, independent rate gates, recovery on OBSERVED evidence only. **Degradation is a DURATION (60 s) and NXDOMAIN is COUNTED but NEVER escalates** — an authoritative "this name does not exist" is a healthy resolver, a gateway sees a steady stream of them from typos and sinkholed-C2 beaconing, and because the hostname is CLIENT-CHOSEN a count-based threshold would let any client fabricate the page on demand. A private-only answer is likewise a SUCCESS (split-horizon estates are the common case) and clears an episode. Surfaces: `culvert_dns_resolve_{total,failures_total,timeouts_total,shed_total,stale_served_total,degraded}` (emitted only once this node has resolved something — the socks5/cluster_ca rule), the `dns_resolution` contract row (warn, never fail: the gateway is still proxying and a resolver outage is fleet-wide, so failing would eject a serving fleet), and a fire-once page on the **existing** `dns_failure` event (a new name would be silently unsubscribed on every configured webhook). The same change **bounded `fireDNSFailureAlert`'s Detail**, which was a raw `err.Error()`: `Dispatch` dedups on `event + ":" + Detail` and a `*net.DNSError` embeds the queried hostname, so every failure minted a distinct key the 30 s window could not suppress and the fan-out evicted real threat alerts from the 500-entry retry queue (WK-12/RS-5 — remotely triggerable here, since the hostname is the client's). Deliberately unchanged and recorded: the fall-through POSTURE (making an unknown country match a block rule would deny every destination this node cannot resolve — a bounded security gap traded for an unbounded availability one; an admin-selectable `geo_on_unresolvable` toggle is the recorded next step) and the cgo resolver's uncancellable `getaddrinfo` (the deadline releases the request goroutine; the OS thread is bounded by Go's own 500-thread cap). Gates: `dns_resolve_chaos_test.go` (23, incl. two CONTROLS — a resolver that simply stopped resolving would pass every defect gate while being far worse than the defect); `TestResolveHost_TTLExpiry` was INVERTED, since it pinned the synchronous-re-resolve-on-expiry behaviour that IS the defect. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §34 and `docs/operator/dns-resolution-health.md`.

## Destination-category resolution is per-SCAN, not per-rule (`policy_hostcat.go`)

[Original lines 215–215](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L215-L215) · `claude-main-L215-L215`

<!-- BEGIN preserved-block: claude-main-L215-L215 -->
- **Destination-category resolution is per-SCAN, not per-rule (`policy_hostcat.go`)**: `Evaluate` already hoists the request-invariant work out of its rule loop (normalized host, parsed client IP, one `scanNow` clock read). The host→category fusion is the same class of value — it depends on the HOST, not the rule — and is by far the most expensive: `catStore.LookupHost` (which every `DestCategoryGroup` rule reaches via `lookupHostCategory`) deliberately walks every host pattern in the taxonomy instead of the lowercase index, so it can report the admin's configured pattern verbatim for the URL-lookup API — O(patterns), lowercasing + concatenating per pattern — and `communityDB.Lookup` opens a **BadgerDB read transaction per domain label** on a feed-backed deployment. Run per rule, that fixed cost was multiplied by the rule count: measured on a 12-category / 480-pattern taxonomy against an uncategorized host, a category-group scan cost **205 µs at 10 rules, 1.01 ms at 50, and 4.03 ms at 200 — per request**, with 91% of the profile in `LookupHost`. `hostCatScratch` resolves each host-only tier at most once per scan (**−89.7% / −97.8% / −99.3%**; −96.8% at 4x parallel; allocation counts unchanged — the scratch stays on the stack, and non-category scans are statistically unchanged). Every field is lazy, so a scan with no category-scoped rule computes nothing. The per-CATEGORY halves (`MatchesHost`/`MatchesHostAdmin`) are deliberately NOT memoized — they depend on the rule's category and are O(labels) index probes. Freezing `saasEffectiveView.Current()` for the scan is deliberate and mirrors the `scanNow` hoist: one evaluation decides against ONE taxonomy generation instead of racing a mid-scan signed-feed activation. `matchCategory`/`lookupHostCategory` remain the single-shot entry points for callers outside a scan (admin URL-lookup API, `matchDest`) and are byte-identical. Pinned by `TestBenchGate_PolicyCategoryGroupScanFlatInRuleCount` (benchgate tag — a RATIO gate, machine-independent: 1.34x post-fix, 20.15x if the per-rule fusion returns, bound 4x) plus `policy_hostcat_test.go`. The Stage-1 auth scan shares the same scratch via `authMatchScratch.hostCat()`. **The follow-up landed:** `urlcat.Store.LookupHost` is now itself index-backed (see the next bullet), so the once-per-scan call is O(labels) — the two changes compose.

## Host→category resolution is INDEXED in both directions (`internal/urlcat`)

[Original lines 216–216](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L216-L216) · `claude-main-L216-L216`

<!-- BEGIN preserved-block: claude-main-L216-L216 -->
- **Host→category resolution is INDEXED in both directions (`internal/urlcat`)**: the store has always carried a forward index (`index`/`adminIndex`: category → lowercase host set) giving `MatchesHost` an O(labels) probe, but the REVERSE direction — `LookupHost`/`LookupHostAdmin`, host → category — was a nested scan over every host pattern of every category. That is not an admin-API-only call: `lookupHostCategory` (policy.go) reaches it and `categoryGroupMatchesHostRule` (categorygroup.go) reaches THAT once per proxied request for every enabled access rule carrying a `DestCategoryGroup`, so the per-request cost was (category-group rules) × (patterns in the taxonomy), paid inside the request goroutine. Clean traffic is the WORST case — an uncategorized destination cannot short-circuit, so it walks all of them. Measured on the SHIPPED default taxonomy alone (657 patterns / 27 categories): ~24 µs per lookup, and a 20-rule category posture cost **~497 µs of pure CPU per request** in `Evaluate` (1 rule 24.5 µs, 5 rules 126 µs). `hostIndex`/`adminHostIndex` now map a lowercase pattern → the `patternRef` (entry position, host position) of the FIRST entry declaring it, and `lookupIn` probes only the keys that can match (the host, then the remainder after each `.`): 325 ns / 1.3 µs / 4.6 µs for the same 1/5/20 rules (**−98.7% to −99.1%**), flat in taxonomy size (~80 ns at 5657 patterns vs 252 µs before), still 0 allocs/op. **The winner is unchanged, and that is the load-bearing part**: the old loop returned the first `(entry, host)` position whose lowercased pattern matched, so taking the MINIMUM position over the matching keys is the same result — including the case where a LESS specific pattern in an EARLIER category outranks a more specific one in a later category, which a plain most-specific-suffix walk silently inverts. `matchedBy` stays the admin's verbatim configured pattern (hence the index resolves back through `s.entries`). The reverse index deliberately keys on `strings.ToLower(p)` WITHOUT the forward index's `TrimSuffix(".")`, reproducing a pre-existing disagreement between the two matchers on a `"example.com."`-shaped pattern rather than quietly changing matching semantics in a cost change. `rebuildIndex` is the maintenance path for every mutation except a single-host APPEND — `Set`/`Delete`/`RemoveHost` rebuild wholesale instead of patching keys, because a positional index cannot be patched incrementally for those shapes (deleting a category shifts every later position) and each also calls `Save()` (full JSON marshal + atomic rewrite), which dwarfs the rebuild; `AddHost` alone folds in O(one category) (`addHostToIndexes` — the SaaS feed merge calls it once per host, so a wholesale rebuild there would stall the request path per added host; pinned by `urlcat_addhost_incremental_test.go`). **Nothing O(taxonomy) may be added to `AddHost` under the write lock** — that is the whole point of the fold, and the `ContentFingerprint` memo is the cautionary case: implemented eagerly, it re-hashed the entire taxonomy on every `AddHost` (17x on the shipped default, 133x at 50k patterns), inside the lock every category lookup on the request path contends on, and unconditionally — its ONLY consumer is the policy-learning category epoch, which is disabled by default. The memo is now REVISION-KEYED and LAZY: writers only bump the monotonic `rev` (`invalidateFingerprintLocked`, O(1)), and `ContentFingerprint()` serves the cached `{rev, fp}` while `rev` matches, else computes under the READ lock, single-flighted through `fpMu` (lock order `fpMu` → `s.mu`). Freshness stays exact because `rev` advances inside the writer's critical section — a reader that can see new content necessarily sees the advanced revision — and `rev` is monotonic, so a revision names exactly one content state. Pinned by `urlcat_fingerprint_cost_test.go` (ratio cost gate, warm-memo freshness gate, concurrent two-state gate) alongside the value contract in `urlcat_fingerprint_test.go`. Pinned by `internal/urlcat/urlcat_lookup_index_test.go` (differential test against the verbatim pre-index scan: hand-picked divergence shapes, 200 randomized taxonomies, mutation tracking, the whole shipped taxonomy, and a race-detector reader/mutator run) and `urlcat_lookup_bench_test.go` + `BenchmarkPolicyEvaluate_CategoryGroupRules` (policy_bench_test.go). The per-rule repetition within one `Evaluate` is gone too: the scan-scoped `hostCatScratch` (previous bullet) resolves the fusion once per scan.

## The category index key is folded WITHOUT allocating (`internal/urlcat` `categoryKey`)

[Original lines 217–217](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L217-L217) · `claude-main-L217-L217`

<!-- BEGIN preserved-block: claude-main-L217-L217 -->
- **The category index key is folded WITHOUT allocating (`internal/urlcat` `categoryKey`)**: the bullet above made the REVERSE direction (host → category) index-backed. The FORWARD direction — `MatchesHost`/`MatchesHostAdmin`, "is this host in category C?" — was already an O(labels) probe against `index`/`adminIndex`, but it derived the map key with `catKey := strings.ToLower(string(cat))` on every call, and `strings.ToLower` allocates whenever the input carries an uppercase letter. **All 21 shipped SaaS category names do** ("Social Media", "Automation & Integration", …), so the allocation fired on 100% of the shipped taxonomy rather than on some operator's unlucky naming. These are the per-RULE half of destination-category resolution: `hostCatScratch.matchesCategory` (policy_hostcat.go) calls one of them once per category-scoped access rule per proxied request, so a rulebase with N `DestCategory` rules charged **N heap allocations to every proxied request**. What was being re-derived is pure CONFIGURATION — the rule's category name is fixed when the admin writes the rule and is byte-identical on every request that consults it — which makes this the same class as the `hostCatScratch` hoist above, one level down: a value that does not depend on the request, recomputed inside the per-request loop. **`policy_hostcat.go`'s own comment is what dates the finding**: it records that the per-category halves are deliberately NOT memoized because "they depend on the rule's category and are O(labels) index probes, not scans — memoizing them would trade a cheap map probe for a map allocation". That reasoning is correct and the premise was false: the probe allocated. This change makes the premise true instead of revisiting the decision, which is why the fix is here and not a folded key precomputed onto `PolicyRule` — that would put a urlcat implementation detail into the policy struct AND leave every other caller of these two methods still paying. `categoryKey` folds into a CALLER-OWNED stack array and the probe is spelled `idx[string(b)]` on it, which the compiler resolves against the bytes directly (no copy, no allocation, hence no escape — pinned by `-gcflags=-m`: `string(inlineKey) does not escape`, and `keyBuf` never reaches the moved-to-heap list). **It returns TWO forms and that asymmetry is load-bearing** (Codex review, PR #1410): a single `[]byte` return forces the fallback to spell itself `[]byte(strings.ToLower(cat))`, and since strings are IMMUTABLE that conversion COPIES — measured against the pre-optimization code it is a REGRESSION rather than a smaller win (an already-lowercase name past the buffer 0 allocs → 1, an uppercase or non-ASCII one 1 → 2). The admin API accepts names up to 256 bytes (`ui_policy.go`), so a name past `maxInlineCategoryKey` is ORDINARY CONFIGURATION, not a corner case, and a rule carrying one pays that on every proxied request. The fallback therefore keeps the STRING `strings.ToLower` already produced and is probed as a string; only the inline path uses bytes. **The buffer is the caller's so the fold happens BEFORE `s.mu` is taken**, and that too is measured rather than assumed: folding inside the read lock reads more simply and its added hold LOOKS negligible (bounded loop, readers do not block readers, writers are admin-rate CRUD), but interleaved same-run comparisons (n=11, identical except for where the fold runs) put the hoisted form ahead on the 4-way parallel path in both rounds with NON-OVERLAPPING distributions — 83.8 vs 91.4 ns/op on a quiet box, 125.8 vs 155.0 ns/op on a busier one, serial unchanged either way. **Quote that RATIO, never those absolutes**: the box drifted by half again between rounds, which is exactly why both arms must be timed in ONE run — an earlier CROSS-RUN reading of this same question said "53%" and was wrong by an order of magnitude. Measured on a 4-core Xeon @2.80GHz, **both arms benchmarked in ONE session so the comparison is machine-independent** (medians of n=5): `MatchesHost` miss **204.4 → 137.4 ns (−32.8%)**, hit **170.1 → 105.7 ns (−37.9%)**, `MatchesHostAdmin` miss **202.3 → 141.8 ns (−29.9%)**, and **1 alloc / 16 B → 0** in every posture. Through the real policy scan (`BenchmarkPolicyEvaluate_CategoryRules`, 12 categories / 480 patterns, uncategorized destination — the clean-traffic case that cannot short-circuit): 10 rules **2420 → 1635 ns (−32.4%)**, 50 rules **8572 → 5524 ns (−35.6%)**, 200 rules **31670 → 19106 ns (−39.7%)**, with **10/50/200 allocs → 0** and 160/800/3200 B → 0. **The 4-way PARALLEL micro case moves only 94.3 → 88.2 ns (−6.4%), and that number is the most informative one here**: under concurrency the per-call `RLock` dominates, so removing the allocation is largely MASKED — which is the evidence for the follow-up named at the end of this note, not a reason to doubt the win (the serial and policy-scan figures are what a per-request allocation rate is actually paid at). **Semantics are unchanged EXACTLY, and the equivalence is the deliverable, not the speed** — this is a policy MEMBERSHIP matcher, so a divergence is a silently mis-enforced (or silently unenforced) Allow/Deny rule. For a pure-ASCII name `strings.ToLower` is byte-wise `'A'`-`'Z'` + 32, which is what `lowerASCIIInto` writes; anything non-ASCII bails at the FIRST such byte and falls back to `strings.ToLower` itself, so Unicode folding is still done by the standard library and is never reimplemented here (the cases that make that mandatory are in the shape set: KELVIN SIGN U+212A folds to ASCII `k`, U+0130 and U+1E9E fold across byte lengths — a byte-wise fold gets all three wrong). A name longer than `maxInlineCategoryKey` (64; the longest shipped name is 24) takes the same allocating fallback. **The gate that was MISSING is the lesson**: the first version here gated only the SHORT, mixed-case names the shipped taxonomy carries — the shape the change was written for — so it could not see the fallback getting dearer, and the regression above shipped inside an optimization. `TestBenchGate_NeverAllocatesMoreThanTheCodeItReplaced` asserts no number: for EVERY shape (inline or fallback, ASCII or not, short or past the buffer) the real entry points must allocate no more than the verbatim pre-optimization probe does on the same input, a budget it measures at run time — so it holds whatever the implementation becomes and fails for any future variant that makes one path dearer to make another cheaper, with `TestBenchGate_FallbackBudgetIsNotVacuous` pinning that the budgets it compares against really are zero where it matters. **An optimization must be no worse than what it replaces on EVERY path, not just the one it was written for.** Gates (`urlcat_matcheshost_key_test.go`): a DIFFERENTIAL against the verbatim pre-fix key expression over hand-picked divergence shapes (the ASCII/non-ASCII branch boundary, the ASCII neighbours just outside `A`-`Z` and `a`-`z`, which must NOT shift, the 63/64/65-byte buffer boundary, invalid UTF-8) plus a 20 000-case randomized sweep weighted to those boundaries, its own NOT-VACUOUS check requiring both branches to be exercised, `FuzzCategoryKey` (2.28M executions, no divergence), an end-to-end verdict differential driving the real entry points, `TestBenchGate_MatchesHostIsAllocationFree` (**structural via `testing.AllocsPerRun`, not a timing ratio**, so it cannot flake on a loaded runner, under `-race`, or on other hardware — the repo's standing rule for hot-path gates), `TestBenchGate_OversizeCategoryNameStillAnswers` as its CONTROL (the cheapest way to pass an allocation gate is to stop doing the work, the second cheapest is to silently drop names the buffer cannot hold), and `TestCategoryKeyBound_CoversShippedTaxonomy`, which fails if a future taxonomy adds a name past the bound rather than silently moving that category onto the allocating path. Four defects were each verified FAILING against these gates: the reintroduced pre-fix shape (alloc gate, 3 of 4 cases — the lowercase-name case passes, which is exactly why a gate resting on it alone would be vacuous), a removed non-ASCII bail (`"CAFÉ"` → `"cafÉ"`), an off-by-one on the case range, and a bound wider than the buffer. **Still open on this path and deliberately untouched (one concern per change):** both entry points take `s.mu.RLock` once per rule per request, so a category-scoped rulebase multiplies read-lock traffic by the rule count on every core serving traffic — the `internal/blocklist` `hotRW` shard or a `threatfeed`-style `atomic.Pointer` read view is the shape that closes it, and `BenchmarkPolicyEvaluate_CategoryGroupRulesParallel` is the instrument.

## Threat-feed lookups are LOCK-FREE (`internal/threatfeed`)

[Original lines 218–218](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L218-L218) · `claude-main-L218-L218`

<!-- BEGIN preserved-block: claude-main-L218-L218 -->
- **Threat-feed lookups are LOCK-FREE (`internal/threatfeed`)**: `CheckDomain` runs on EVERY proxied request and `CheckURL` additionally on every plain-HTTP one (`preDispatchBlocked`, proxy.go), and both used to take `tf.mu.RLock` **twice** — once inside `Enabled()`, once for the map probe. `sync.RWMutex.RLock` is an atomic read-modify-write on one shared word, so every request wrote the same cache line purely to read tables that in steady state never change. That is not a constant cost but a **throughput ceiling**: measured (4-core Xeon, 100k entries) `CheckDomain` cost **100.6 ns/op serial but 211.7 ns/op at 4x parallel** — it got 2.2x SLOWER as cores were added, on a per-request path, exactly when a gateway is busiest (same shape as the `internal/logsink` finding). The three lookups now read an immutable `readView` published via `atomic.Pointer` (**88.8 ns serial / 22.6 ns at 4x parallel — 3.9x near-linear scaling, 9.4x the old parallel figure**; `CheckURL` parallel 284→187 ns). **The contract is one line and it is load-bearing: a map reachable from a PUBLISHED readView is never mutated in place.** Every writer of `enabled`/`urls`/`domains`/`domainAllowlist` installs a REPLACEMENT map and calls `publishLocked()` before releasing `tf.mu` — `AddDomainAllowlist`/`RemoveDomainAllowlist`/`SeedForTest` were converted from in-place edits to copy-then-swap for exactly this reason (admin-rate paths; the allowlist is tens of entries). **Adding a mutator without a `publishLocked()` call is a silent SECURITY failure, not a perf one** — a synced threat entry that never blocks, or a revoked allowlist exemption that keeps suppressing hits — so it is pinned per mutator by `TestReadView_EveryMutatorRepublishes`; the no-in-place-mutation half is enforced by the race detector via `TestReadView_ConcurrentReadersAndWriters`. The view ALIASES the maps (publishing a 500k-entry sync is one pointer store, not a copy), and taking it ONCE also fixed a latent consistency hole: the old shape dropped the lock between the `Enabled()` probe and the table probe, so a concurrent `Sync` could be observed half-applied. The regression gate (`TestBenchGate_LookupsTakeNoFeedLock`) is deliberately **structural, not timing-based** — it holds the write lock and requires the lookups to complete anyway; the scaling-ratio gate was built first and rejected because its margin narrows to 1.35x under `-race`, too thin for a per-PR runner. Still-locked (cold, correct): `DomainAllowlisted`, `DomainAllowlist`, `saveToDisk`, `Stats`, the export/cluster surfaces.

## The full-URL threat check never serialises a URL it was handed parsed (`internal/threatfeed` `CheckRequestURL`)

## The blocklist read lock is SHARDED, not a read view (`internal/blocklist/hotread.go`)

[Original lines 220–220](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L220-L220) · `claude-main-L220-L220`

<!-- BEGIN preserved-block: claude-main-L220-L220 -->
- **The blocklist read lock is SHARDED, not a read view (`internal/blocklist/hotread.go`)**: `Store.IsBlocked` runs on EVERY proxied destination — plain HTTP, CONNECT, WebSocket and SOCKS5 all reach it through `preDispatchBlocked`, before any policy work begins — and it took ONE process-wide `sync.RWMutex` read lock to reach its verdict. Same finding as `internal/threatfeed` above: `RLock` is an atomic read-modify-write on one shared word, so every request in the process wrote the same cache line purely to read maps that in steady state never change. Measured (4-core Xeon, 100k-entry feed-backed store, one wildcard, an ordinary 33-byte CDN host that MISSES — what every ALLOWED request pays; medians of n=7, aggregate Mlookups/s, `BenchmarkIsBlockedScaling` vs `BenchmarkIsBlockedScaling_Baseline` at `-cpu 1,2,4`): default no-exceptions posture **9.01 / 6.25 / 6.58 before → 8.60 / 10.21 / 16.43 after (2.50x at four cores)**; with exceptions configured **3.47 / 3.34 / 3.52 → 3.55 / 6.01 / 11.08 (3.15x)**. The finding is the BEFORE row: not that the store was slow but that it was **CAPPED** — four cores delivered *less* throughput than one, because each added core only contributed more traffic to the single contended line. **The instrument is deliberately NOT this repo's `atomic.Pointer` read view, and that choice is measured.** threatfeed and IPFilter replace their large maps wholesale and mutate only small ones incrementally; this store is the opposite — `exact`/`wildcards` are LARGE (a feed-backed deployment runs to 10^6 hosts) and are mutated INCREMENTALLY by `ApplyDelta` on every cluster delta sync, plus `Add`/`AddManual`/`Remove` and the pruning paths. A copy-on-write publish costs 0.65 ms/437 KB at 10k, 12 ms/3.5 MB at 100k and **190 ms/56 MB at 1M**, so a view would have traded a read-side ceiling for a per-delta-sync stall and a GC-pressure regression, and the admin bulk-delete handler (`ui_policy.go` loops `bl.Remove`) would have become O(hosts x blocklist-size) — the exact O(N^2) trap IPFilter had to add `AddAll` to escape. Sharding the READ side instead removes the contention with **zero write amplification: every one of the 15 mutator bodies is byte-identical** and writers keep true exclusive access, which also means this change structurally cannot carry the view's failure class — there is no view, so there is no mutator that can forget to publish one. `hotRW` gives readers one of 64 cache-line-padded `sync.RWMutex` shards (index from `rand.Uint64`, per-P and lock-free since Go 1.22; there is no key to shard on, so the goal is only to spread readers across lines) while `Lock` takes EVERY shard in ascending order — readers hold at most one shard, so the ordering is total and deadlock is impossible. Cold admin/persist readers share shard 0 and are unchanged. **The trade, both directions:** a writer now pays 1.52 us instead of 24 ns (62x — just the shard count), against callers that already do far more work and run at admin/feed rate; and at ONE core the read path is ~5% slower (8.60 vs 9.01 Mops/s) from the added `rand.Uint64` — recorded rather than papered over, exactly as `internal/connlimit` recorded its own, because a single-core gateway is the one shape a forward proxy is never in. Gates: `TestHotRW_WriteLockExcludesHotReaders` (the mutual-exclusion contract, deterministic because a writer holds every shard so the reader's draw cannot matter) and `TestHotRW_ConcurrentReadersAndMutators` (every real mutator against the real hot path under `-race` — the two that catch a writer which stops taking all shards; both verified failing against that injected defect), plus `TestBenchGate_HotReadsSpreadAcrossShards`, which is **structural, not timing-based** (it counts distinct shards reached, so a collapse back to one lock fails on any hardware, under any load, with or without `-race` — the scaling-ratio gate was rejected for the same reason connlimit's and the histogram's were). **A parallel benchmark on this path must give each worker its OWN sink**: the serial form (`benchBlocked = st.IsBlocked(...)`) is correct serially and ruinous under `RunParallel`, where every worker then writes one shared cache line per iteration — that false sharing became the bottleneck being measured and flattened the sharded store to the baseline's throughput, hiding the entire finding until a pure-CPU control proved the box scales 4.0x.

## The GeoIP policy accessor is CACHE-ONLY, and the enforcement path owns its own warmer (CHAOS-60, `geoip.go` + `geoip_resolve_health.go`)

[Original lines 222–222](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L222-L222) · `claude-main-L222-L222`

<!-- BEGIN preserved-block: claude-main-L222-L222 -->
- **The GeoIP policy accessor is CACHE-ONLY, and the enforcement path owns its own warmer (CHAOS-60, `geoip.go` + `geoip_resolve_health.go`)**: deciding a country-scoped rule needs TWO cached facts — host→IP (`resolvedHostCache`) and IP→country (`internal/geoip`) — and `matchDestNorm` reads both through `geo.LookupCached` inside the request goroutine, which holds the client connection and a per-IP `connlimit` slot while it runs. **`LookupCached` blocked.** It called `resolveHost`, which on a miss called `net.LookupHost` — **no context, no deadline, no way to abandon**, running to the system resolver's full budget (`resolv.conf` timeout × attempts × nameservers, 10–40 s on a blackholed resolver) — before policy evaluation could continue, and before the plain-HTTP path's `upstreamRequestTimeout` is even armed (the CONNECT path has no overall budget at all). The register recorded this path as SAFE (row WK-3, ✓, *"never blocks on DB/DNS"*); the claim was true when written and was invalidated by the host→IP cache being added in FRONT of the blocking call without removing it — the cache made the common path fast, which is why nothing noticed the miss path. There was no single-flight either, and the negative entry that suppresses the next lookup is written only when a lookup RETURNS, so in exactly the window where lookups do not return nothing suppresses the next one: measured pre-fix, **50 concurrent misses for one host → 50 resolver invocations**, i.e. the proxy amplifies client request rate 1:1 (×2 for the A/AAAA pair) into queries at an already-failing resolver. **The second half is worse and is a security finding**: after resolving, the country is read from a cache whose ONLY populator on the request path was `trackDestinationCountry` — a best-effort DASHBOARD sampler that runs on the ALLOW branch only, after the decision, behind a 256-slot drop-on-full semaphore whose own comment says samples are dropped rather than queued. Country-scoped **enforcement** therefore depended on a telemetry goroutine having won a slot on an earlier request; saturate it (or block the first request, so the sampler never runs) and every country rule silently stops matching, with the rule's hit counter reading exactly like "no traffic matched this rule". Four rules now hold. **(1) The accessor never resolves**: `resolveHostCached` answers from an IP literal or a live entry, a miss returns `("", false)` — the fail-closed answer the call site already documented — and arms a warm; "unknown, nothing cached" and "resolved to nothing usable" are DISTINCT returns because only the first is worth warming (a negative-cached host is governed by its 30 s TTL, never by the request rate). **(2) The warm is bounded by a SEMAPHORE (`geoWarmSem`, 64, drop-on-full), deliberately NOT by a context deadline** — under the cgo resolver a cancelled lookup returns to the caller while the OS thread stays blocked in `getaddrinfo`, so a deadline would release the slot without releasing the thread, converting a bounded goroutine pool into an unbounded THREAD pool; holding the slot for the TRUE duration of the call is what makes the bound real. A queue was rejected for the usual reason: it converts a resolver outage into unbounded memory and unbounded staleness. **(3) Misses are SINGLE-FLIGHTED and the host is CLAIMED BEFORE A POOL SLOT IS TAKEN** (`hostIPCache.begin`/`finish`, the `jwksCache` leader-publishes-to-followers shape). The ORDER is load-bearing and was wrong in the first version of this fix (Codex P1): a pre-CHECK (`resolving`) with the actual claim left to the goroutine (`begin` runs inside `resolveHost`) means concurrent evaluations for ONE uncached host all pass the check, all take a slot, and all but one park as followers HOLDING those slots for the resolver's full delay — so one popular destination drains the 64-slot pool and every unrelated host's warm is dropped and its country rule left unresolved, i.e. the GEO-2 degradation re-entered through the fix for GEO-2. `begin` is now called SYNCHRONOUSLY in the caller before any slot is taken; a non-leader returns having touched nothing, and a leader that cannot get a slot HANDS THE CLAIM BACK (`finish` with nil, deliberately WITHOUT a cache write — nothing was learned and a negative entry would suppress the retry for a full TTL over a transient shortage). `finish` is idempotent (`sync.Once`) so every hand-back path can call it unconditionally. The slot is released to the channel it was TAKEN from (`sem` is captured, not re-read), so a goroutine outliving a swap cannot release into a channel it never acquired. **(4) The warm fills BOTH caches** (`geoip.LookupByIP`, not just the resolver) — that is what removes the dependency on the dashboard sampler, and why it also fires on the country-half miss (host cached, IP never geolocated), the shape that was otherwise permanently undecidable on a saturated node. Surfaces (emitted ONLY when a GeoIP DB is loaded — the socks5/cluster_ca rule: a flat `0` on a node with no GeoIP is indistinguishable from one whose geo rules stopped enforcing): `culvert_geo_{warm_total,warm_dropped_total,warm_failed_total,warm_saturated,warm_inflight}` plus **`culvert_geo_policy_unresolved_total`**, the first signal an operator has ever had that a geo rule is evaluating against an unknown country (a low rate is expected — one per host per cache lifetime; a rate tracking request rate means enforcement is not converging). Saturation logs onset immediately, then ≤1 line/min, then one recovery line naming the suppressed count; recovery clears on OBSERVED evidence (a warm that got a slot), never on elapsed time. **`LookupFull` still blocks by design** — its callers (the 256-slot tracker, admin-rate enrollment) are bounded some other way, and the contract is now written on `resolveHost`. Deliberately left as an OWNER DECISION (WK-3c): a country rule still does not match on the FIRST request to an uncached host — fail-closed for an allow-rule, fall-through for a deny-rule — unchanged by this fix, which only makes the window converge in one request and makes it countable; `geoip.LookupByIP` is an mmap read and could be done inline to close it, but that changes when a rule first matches, which is a policy-semantics decision, not a resilience fix. A leader PUBLISHES ON EVERY EXIT PATH (`resolveAsLeader`'s deferred put+finish — a defect introduced by this fix and caught inside it: publishing after the call meant a panicking leader stranded every follower AND left the slot occupied, so every LATER caller for that host blocked forever, a strictly worse failure than the unbounded block being fixed). Gates: `geoip_resolve_chaos_test.go` (15 — five defect gates verified failing against the reintroduced pre-fix shape, a permanent DEFECT PROOF that rebuilds the pre-fix body inline, and two CONTROLS, because a warmer that did nothing would satisfy every "does not block" and "is bounded" assertion while leaving country rules permanently unenforceable; plus a MANY-TRIAL gate for the claim-ordering P1 — a single trial passes a broken build most of the time because the leader usually wins the registration race, the `TestChaos54_StopIsPromptDuringAcceptBackoff` precedent). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §28 and `docs/operator/geoip-resolution-health.md`.

## Periodic feeds back off, jitter, and report their freshness (CHAOS-59, `internal/feedsched` + `threatfeed_health.go`)

[Original lines 230–230](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L230-L230) · `claude-main-L230-L230`

<!-- BEGIN preserved-block: claude-main-L230-L230 -->
- **Periodic feeds back off, jitter, and report their freshness (CHAOS-59, `internal/feedsched` + `threatfeed_health.go`)**: Culvert ships THREE periodic feed loops and only the newest — the signed SaaS feed's `saasFeedScheduler` — scheduled itself correctly. The two older ones (`internal/threatfeed`, `internal/feedsync`) were bare `time.NewTicker`s that DISCARDED the round's outcome, which fails in three directions at once. **Cadence:** a ticker has no notion of failure, so a failed round waited a FULL interval — 6 h for threat intel, **24 h** for the UT1 category feed — and the triggering fault is a DNS blip, a 503, or a restarted upstream proxy, not an exotic one. **Cold start:** `Start` syncs immediately when the on-disk DB is empty (fresh install, re-image, replaced volume, a §19 quarantine), so a node whose FIRST round failed enforced with an EMPTY threat database — not stale intelligence, NONE — for up to six hours while `/health`, `/ready`, `/metrics` and the dashboard all reported a healthy gateway. **Fleet:** a ticker fires at a fixed offset from process start, so nodes that boot together sync together FOREVER against public third-party origins shared by every deployment (abuse.ch, openphish.com, and a 50+ MB tarball on `raw.githubusercontent.com`); the ordinary answer to that is rate-limiting of the customer's egress IP, which PRODUCES the failure the absent backoff then holds the whole fleet at — a closed loop where the scheduler manufactures the outage it cannot recover from. **And none of it was visible, because the WK-5 carry-forward fix consumed its own detector**: `culvert_threat_feed_entries` is held at its last-good value BY DESIGN, so after that fix a feed dead for three weeks exported metrics byte-identical to one that synced ten minutes ago, and the sole surviving difference (`threat_feed_sync_ok`) reached ONE role-gated admin JSON blob nothing scrapes. `internal/feedsched` is the shared cadence engine, deliberately shaped like the `saasFeedScheduler` rather than invented: interval±**stable per-node jitter** (drawn ONCE — re-rolling per tick lets nodes drift back into phase and makes the cadence untestable) after a clean round, bounded exponential backoff after a failed one (threat feed 5 min→1 h, category feed 15 min→2 h), reset by the first success, waits INTERRUPTIBLE so shutdown never sits out a retry, and a **panicking round charged as a FAILED round** (contained at the iteration per `internal/obs`'s rule, so a hostile feed body backs off instead of hot-looping). **BOTH the retry floor and the ceiling are CLAMPED to the live interval** and that is load-bearing: a ceiling above the interval means a failing feed attempts LESS often than a healthy one, turning the recovery mechanism into an extra delay — a caller cannot express that shape. Clamping the ceiling ALONE is insufficient and the first shipped version got it wrong (Codex review, PR #1305): with an interval shorter than `BackoffMin` (an admin running `-feed-sync-interval 1m` against the 5 min floor) the ceiling clamped to 1 m and was then raised back to the floor, so a failed round waited FIVE TIMES LONGER than a healthy one — the bare-ticker regression this engine exists to remove, reintroduced inside its own fix. The invariant holds at EVERY interval: a retry is never later than the configured cadence. Retries are unbounded in COUNT and bounded in RATE, which does not violate "avoid infinite retries" for CHAOS-55's reason (never silent — counted, classified, alerted past the threshold) and because a feed that STOPPED retrying would freeze intelligence permanently on one transient error. Failures carry a **BOUNDED reason class** (`urlhaus`/`openphish`/`urlhaus+openphish`, sorted so it is stable; `download`/`write` for UT1) — never the verbose summary, which embeds the feed URL and the ephemeral local port and would defeat `Dispatch`'s `event+Detail` dedup by construction and evict real threat alerts from the 500-entry retry queue (the WK-12/RS-5 defect). Surfaces: five `culvert_threat_feed_*` series (`last_success_timestamp_seconds`, `stale_seconds`, `sync_ok`, `sync_failures_total`, `consecutive_sync_failures`) emitted **only when the feed is configured** (the CHAOS-54 rule — `sync_ok 0` on a node that never ran the feed is indistinguishable from a broken one and the paging rule is `== 0`), the `threat_feed` operator-contract row, and a fire-once-per-episode `threat_feed_stale` alert cleared ONLY by an observed clean round (elapsed time never clears it) and ALSO evaluated once at startup for the warm-but-already-stale database — routed through `deferStartupAlert`, because the webhook store loads in a LATER startup slice and a direct fire would fan out to an empty subscriber list and vanish (the never-synced branch is excluded from that startup pass: at boot its age is ~0). **`culvert_threat_feed_sync_ok` derives from the PERSISTED `lastSyncErr`, never from the in-memory consecutive-failure count** — that count is deliberately not persisted, so a gauge keyed on it reported a green `1` for hours after a restart from a failed-sync DB (Codex review); deriving it from the persisted error also makes `/metrics` and the admin API agree by construction. Staleness is 2× the interval, but the **never-synced** case is measured from process start against a 30-min grace instead — it is the severe shape and its usual cause is a deploy-time misconfiguration. Deliberately NOT added and recorded as such: **no `/readyz` row and no `/healthz` failure** (a node with stale threat intel is a fully serving gateway; ejecting it from the load balancer over a degraded deny-list is the trade §19 already refused for the category store), and **no fail-closed toggle** (blocking traffic because a third-party feed is unreachable converts a provider's outage into the customer's — the deliberate asymmetry with WK-1b/WK-2b, which govern a scanner's verdict on content in flight rather than how fresh a deny-list is). The main-side `saasFeedScheduler` is a third instance of this engine and is recorded as a follow-up migration, not silently duplicated. Gates: `internal/feedsched/feedsched_test.go` (10, fake clock, no sleeps), `internal/threatfeed/sync_cadence_test.go` (10), `internal/feedsync/sync_cadence_test.go` (5), `threatfeed_health_test.go` (10) — the cadence gates fail against the bare-ticker shape BY CONSTRUCTION, with four CONTROLS (an immediate retry, a ceiling above the interval, an always-firing alert, and a warm feed re-fetching at boot each pass a defect gate while being worse than the defect). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §27 and `docs/operator/threat-feed-freshness.md`.
