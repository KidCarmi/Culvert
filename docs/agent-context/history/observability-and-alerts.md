## Log sanitisation is ONE pass, and the leading `strings.ReplaceAll` is load-bearing (`sanitizeLog` in proxy.go, `obs.Sanitize` in internal/obs)

[Original lines 192–192](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L192-L192) · `claude-main-L192-L192`

<!-- BEGIN preserved-block: claude-main-L192-L192 -->
- **Log sanitisation is ONE pass, and the leading `strings.ReplaceAll` is load-bearing (`sanitizeLog` in proxy.go, `obs.Sanitize` in internal/obs)**: `sanitizeLog` is the most-called sanitiser in the tree (~377 call sites) and it is on the REQUEST path — `handleRequest` emits one `POLICY_*` line per proxied request that passes FIVE values through it (rule name twice, host, matched conditions, identity), and the tunnel/relay/block paths add more. It used to scan every string FOUR times: `strings.ReplaceAll` for `\n`, then `\r`, then `\t`, then a separate scalar `containsControl` pass, plus a FIFTH full copy pass on a hit. The first three were redundant with the fourth **by construction** — `\n` (0x0A), `\r` (0x0D) and `\t` (0x09) are all `< 0x20`, and every branch mapped its match to the SAME byte, `'_'` — so the whole function was only ever computing *"every byte `< 0x20` or `== 0x7F` becomes `'_'`, length preserved"*, a single predicate one pass decides. Measured (Go 1.26, 4-core Xeon, n=3x1M): rule name 15 B **56.8 -> 28.0 ns**, hostname **59.1 -> 28.5**, identity **60.6 -> 28.3**, conditions 57 B **103.5 -> 55.0**, long URL 270 B **266.8 -> 201.9**, empty **39.7 -> 15.7**, control-carrying 28 B **340 -> 147 ns and 4 -> 2 allocs**; the five calls behind one `POLICY_ALLOW` line go **463 -> 284 ns**, i.e. ~180 ns of CPU off every allowed request. The clean path stays allocation-free, as before. **The surviving newline `ReplaceAll` is NOT vestigial and must stay the FIRST statement** (and therefore on every return path): it is the barrier CodeQL's `go/log-injection` query recognises, and CodeQL runs on PRs touching `proxy.go` and `internal/**`, so removing it risks turning every `logger.Printf(..., sanitizeLog(x))` in the tree into a CWE-117 alert. It is also the cheapest of the four scans (`strings.Count` uses a SIMD `IndexByte`), so keeping it costs ~3 ns and buys the whole convention. A SWAR (8-bytes-per-word) control scan was built and measured — ~60 ns better on 270-byte inputs, nothing on the short strings that dominate — and deliberately thrown away rather than carried: a word-at-a-time bit trick is the wrong kind of clever for the function whose bug class is log injection. `internal/obs.Sanitize` is a deliberate independent COPY (its own comment records why: delegating across a package boundary risks losing CodeQL's recognition) and got the identical treatment plus its own proof. Equivalence is exact, not approximate, and is pinned by a differential test against a VERBATIM copy of the four-scan implementation (hand-picked divergence shapes incl. the C0/DEL boundary bytes, 20k randomized boundary-weighted inputs) plus a fuzz target — ~5.2M executions found no divergence. **The SIZE of the win is hardware-dependent and the spread is wide** — it is governed by how expensive `strings.ReplaceAll`'s per-call overhead is RELATIVE to the scalar control-byte scan, which differs by an order of magnitude between CPUs (the two removed calls: ~24 ns each on the dev box, ~3 ns each on the CI runner), so the same commit improves the 57-byte shape by 47% on one and 10% on the other. The DIRECTION never changes — this form strictly does less work — and the allocation halving is hardware-independent. Gates: `proxy_sanitizelog_test.go` + `internal/obs/sanitize_test.go` (correctness), `proxy_sanitizelog_bench_test.go` (before/after, both forms timed in ONE run so the comparison stays reproducible), `proxy_sanitizelog_benchgate_test.go` (0 allocs on the clean path; <=2 on the scrub path; plus the scan-count gate). **The scan-count gate is STRUCTURAL — an AST assertion that `sanitizeLog` makes exactly ONE `strings.ReplaceAll` call and that it is the FIRST statement — and it was a same-run timing RATIO first.** That ratio was argued to be machine-independent because both forms were timed together; CI falsified it on the first run (0.57 on the dev box vs 0.90 on the runner for identical code, against a 0.80 bound), for the reason above: a same-run ratio cancels the clock, not the instruction mix. Any bound loose enough for both machines is too loose to catch a reintroduction (the CI control measured 1.00). This is the same wall `internal/connlimit`, `internal/threatfeed` and the latency histogram hit, with the same recorded conclusion — *a gate that can flake gets muted* — and the structural form is strictly better here anyway: deterministic under any load or `-race`, AND it pins the CodeQL barrier's POSITION, which no timing gate can observe. It carries its own CONTROL, running the same predicate against the verbatim pre-change `legacySanitizeLog` and requiring it to be REJECTED, so a selector typo that matches nothing cannot pass forever.

## A benchmark that silences the logger with `io.Discard` measures a DISABLED logger, and the per-request decision line is built by appending, not by `Printf` (`emitPolicyDecision`/`appendQuotedForLog` in proxy.go)

[Original lines 193–193](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L193-L193) · `claude-main-L193-L193`

<!-- BEGIN preserved-block: claude-main-L193-L193 -->
- **A benchmark that silences the logger with `io.Discard` measures a DISABLED logger, and the per-request decision line is built by appending, not by `Printf` (`emitPolicyDecision`/`appendQuotedForLog` in proxy.go)**: `applyPolicyDecision` emits exactly ONE `POLICY_*` line per proxied request — HTTP, CONNECT, WebSocket and SOCKS5 all reach it — and the end-to-end allocation profile (`BenchmarkPerfQual_ProxyHTTPForward`, `-memprofilerate=1`, so the counts are EXACT rather than sampled) ranked it the **largest Culvert-owned allocation site in the whole run**: 28,007 objects across 4,000 requests, 7 per request, behind only net/http's own request/response machinery, two thirds of which belongs to the in-process client and backend rather than the proxy. **The finding that made the rest of it visible is a measurement defect, not a code defect.** `log.Logger.output` opens with `if l.isDiscard.Load() { return nil }`, and `SetOutput` sets that flag on `w == io.Discard` EXACTLY — so a benchmark that silences the logger that way does not merely write nowhere, it never FORMATS. Every benchmark of this line, and the shared `benchSilenceLogger` the e2e proxy qualification uses, was timing argument construction and nothing else and under-reporting by **3.6x** (283 ns/op against `io.Discard`, **1042 ns/op** against a sink `log.Logger` cannot recognise). The allocation figure survived the bug — the nine arguments are boxed at the CALL SITE, before `Printf` can short-circuit — which is why the gate's 8-allocs bound was right while its timing was not, and why PR #1256's recorded "419 -> 272 ns" was really 1143 -> 1042: a 9% gain reported as 35%. A gate can be right by accident; this one was. Measured correctly, two costs were removable and one was not. The nine format arguments were boxed into an `[]any` — seven `runtime.convTstring` calls plus the slice, two thirds of the line's CPU profile before fmt parsed a verb — and fmt's own formatting cost ~520 ns, of which **~200 ns is the two `%q` verbs alone** (`strconv.AppendQuote` decodes rune-by-rune through `strconv.IsPrint` and costs **99 ns for a 17-byte ASCII hostname**, 40x a plain append). The emitters now append into a STACK buffer (`policyLineBufSize`, escape-analysis-verified not to escape; 192/320/448/1024 all measure within noise, so it is sized for headroom rather than tuned) and hand the finished line to `logger.Output`, and `appendQuotedForLog` settles printable ASCII with one byte scan (**99.2 -> 16.0 ns**) while falling back to `strconv.AppendQuote` for `"`, `\`, control bytes and everything >= 0x80, so all multi-byte and invalid UTF-8 keeps its exact escaping. Medians of n=8, 4-core Xeon @2.10GHz, Go 1.26.6, against a real sink: **1042 -> 428 ns/op serial (-59%), 8 -> 1 allocs/op**; re-measured on the go1.26.8 toolchain pin after merging main it reproduces within noise (1053 -> 413, ratio 0.39); block 408, drop 418, redirect 497. **Bytes per op go UP (128 -> 192) and that trade is deliberate**: one right-sized string replaces eight small boxes, and GC mark cost is per OBJECT, so 8 -> 1 is the term that matters. Two honest limits, both recorded rather than rounded away. **Parallel gain is much smaller (461 -> 374 ns, -19%)** because four cores queue on `log.Logger`'s own mutex, which this change does not touch. And **the e2e benchmark cannot resolve the saving at all** — ~614 ns against a 148 us in-process op whose run-to-run spread is +/-10 us — because that harness runs the client, the proxy and the backend in one process, so the denominator is dominated by work no deployment does; what it DOES show, exactly, is the allocation drop (185 -> 179 allocs/op, the site itself 7.0 -> 1.0 per request, from 3.81% of all objects to 0.57%). Quote the microbenchmark for the cost and the e2e profile for the allocations; do not quote the e2e timing for either. **WHAT MAKES 20 LINES OF `append` SAFE TO READ IS THAT NOTHING TAKES THEM ON TRUST**: the four `logger.Printf` format strings survive as an executable specification (`plPrintf*Fmt`), and `TestPolicyDecisionLine_RenderIsByteIdentical` renders every branch both ways over a corpus of control characters, quotes, backslashes, multi-byte and invalid UTF-8, driving each awkward value through every field position in turn — these lines are consumed by SIEM forwarders and log parsers, so byte-identity is the acceptance condition for the change, not a nicety. The ` => %q` redirect clause is governed by an explicit `hasTarget` flag and NEVER by `target != ""`, so an empty admin-configured URL cannot silently emit a different line shape. Nine mutations (DEL accepted by the fast path, backslash unescaped, a dropped space, a hex priority, each `sanitizeLog` removed in turn, the redirect clause inferred from emptiness) were each verified to FAIL the suite, and `FuzzAppendQuotedForLog` found no divergence from `strconv.AppendQuote` in 124k executions on top of an exhaustive all-256-byte differential. `TestLogBenchHarness_DiscardShortCircuitsTheLogger` pins the harness trap itself so it cannot come back by habit, and fails loudly if a future Go release drops the short-circuit and makes the note above `plNullSink` stale. **Do not silence a log benchmark with `io.Discard`** — use `plSwapBenchLogger`/`plNullSink`, which drop the I/O (as `internal/logsink` does in production, taking the line on a channel rather than a syscall) while keeping the formatting the request goroutine really pays for.

## Per-request alert producers must gate on `HasSubscriber`

[Original lines 206–206](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L206-L206) · `claude-main-L206-L206`

<!-- BEGIN preserved-block: claude-main-L206-L206 -->
- **Per-request alert producers must gate on `HasSubscriber`**: an alert producer reached from the request path MUST check `globalAlertStore.HasSubscriber(event)` BEFORE `go fireAlert(...)`. `Dispatch` filters non-matching webhooks anyway, so the gate changes no behavior — but it is reached only AFTER the goroutine spawn, the payload build, an RFC3339 format, a dedup-key concat and a round trip through the single process-wide dedup mutex. The default posture is **no webhooks configured**, so ungated that is pure waste on every request. It also lands backwards for a gateway: block and DNS-failure volume peaks under a scanning/beaconing flood or a resolver brownout, so the ungated producer degraded the proxy hardest exactly when it was under attack (measured: a blocked request cost 5–20× an allowed one, 752–3106 ns/op at 2–3 allocs/op vs an allow-path baseline of ~113 ns/op at 0 allocs/op; gated, both paths are ~100 ns/op at 0 allocs/op). Gated producers today: the `recordStats` block path (`threat_detected`, `policy_block`), `fireDNSFailureAlert` (the single `dns_failure` producer shared by all four dial sites — plain HTTP, CONNECT bypass, CONNECT inspect, WebSocket), `fireStorageWriteAlert` (storage_health.go, where the contract originated), and the four SCAN-PLANE producers — `secscan.remoteScanFail` (`scan_svc_down`, the first INTERNAL-package producer to gate, via the `alerts.HasSubscriber` seam; CHAOS-53), `secscan.clamScanError` (`scan_clam_error`), `yara.fireYARADegraded` (`yara_degraded`, both the saturated and the approaching-saturation states), `noteCDRCallError` (`cdr_unavailable`) and `logScanLimitExceeded` (`scan_skipped` — its Detail was already bounded, but its rate is set by TRAFFIC, since an origin chooses its own response size, so it is gated for the work done BEFORE the dedup window is ever consulted; contrast `scan_timeout`, whose rate is bounded by construction because every fire costs a multi-second scan budget). **The last three were the sweep that closed this contract's remaining holes (SEC-ALERTKEY-1)** and each carried BOTH halves of the defect: no gate, and an unbounded Detail. `clamScanError` passed `err.Error()`, and every error `internal/clamav` produces wraps a `net.OpError` whose text embeds the EPHEMERAL LOCAL PORT or a daemon-supplied response string; `cdrHandleCallError` passed `fmt.Sprintf("sluice call failed: %v", err)`, whose gRPC status description is written by the REMOTE END, so Sluice chose this node's dedup keys; and the YARA pair interpolated the LIVE in-flight count (`inflight=%d max=%d`) — the worst of the three, because the number the message reports is the number that changes, so the key was distinct BY CONSTRUCTION rather than merely often, and `matchRegex` evaluates saturation once per STRING DEFINITION per scanned body, so one saturated scan fanned one dispatch out per regex. They now carry bounded classes (`clamFailureClass` over this package's own error prefixes, the gRPC `codes.Code`, and `saturated`/`approaching_saturation`), the cause goes to a rate-limited log line and the magnitude to a counter (`culvert_clamav_scan_errors_total`, `culvert_cdr_errors_total`, and the new `yara_saturation_skips` on the scan-status surface beside `yara_match_panics`). The same sweep hardened the seam itself: `alerts.SetSink(nil)`/`SetSubscriberProbe(nil)` stored a pointer to a NIL FUNC, so `Fire`/`HasSubscriber` passed their `!= nil` pointer check and then called it — a nil-func PANIC on the request goroutine inside the scan path, in the one seam whose documented contract is that producers "never need a nil check"; a nil install now UNINSTALLS. Pinned at 0 allocs/op by `TestBenchGate_BlockPathAlertAllocs` + `TestBenchGate_DNSFailureAlertAllocs`; the gate-must-not-silence-a-real-alert half is pinned by `store_alertgate_test.go`. The scan-plane sweep's gates are `internal/yara/yara_degraded_alert_test.go` (9), `internal/secscan/clam_alert_bound_test.go` (5), `cdr_alert_bound_test.go` (12), `internal/alerts/seam_nil_test.go` (4) and `TestScanSkipped_ProducerIsSubscriberGated` — every defect gate verified FAILING against its reintroduced pre-fix shape, each with a CONTROL, because the cheapest way to pass "the Detail is bounded" and "no dispatch without a subscriber" is to stop alerting or to stop evaluating saturation at all, which would delete the in-flight cap rather than bound its alert. **A gate that waits for the FIRST dispatch to land passes the unbounded shape by luck** — the dispatch is asynchronous, so the key count must be read after ALL of them (`recordFireAlert`, the seam `fireAlert`'s own doc comment exists for). Producers whose rate is bounded by construction (a multi-second scan timeout, a disk-full transition, a lockout) do not need the gate. **The seam for `internal/*` producers is `alerts.HasSubscriber`** (`internal/alerts/alerts.go`), backed by a probe package main installs beside the sink; it returns TRUE when no probe is installed, so a missing wire-up can never silence a real alert. **The DETAIL a request-path producer passes is part of this contract**: `Store.Dispatch` dedups on `event + ":" + Detail`, so a raw `err.Error()` — transport errors embed the ephemeral LOCAL port — yields a distinct key per request that the 30 s window cannot suppress by construction, and the fan-out lands in the 500-entry retry queue where it can evict REAL threat alerts. Pass a BOUNDED reason class in the alert and put the full cause in a rate-limited log line.

## An unusable webhook signing secret is PRESERVED and REPORTED, never blanked away (SEC-WHSIGN-1, `internal/alerts`)

[Original lines 208–208](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L208-L208) · `claude-main-L208-L208`

<!-- BEGIN preserved-block: claude-main-L208-L208 -->
- **An unusable webhook signing secret is PRESERVED and REPORTED, never blanked away (SEC-WHSIGN-1, `internal/alerts`)**: webhook HMAC secrets are AES-GCM encrypted at rest (RISK-003) under a NODE-LOCAL key file (`<dataDir>/.alert_webhook_key`) that is deliberately never archived — the same rule that excludes `.kek` files, since a key must not share a tarball with the material it unwraps. `alert_webhooks.json` IS archived, so restoring a backup onto a fresh volume is the reachable way to hold a secret that cannot be unwrapped (an unreadable key file at boot — permissions, or an EMFILE window — gets there too). Three rules hold. **(1) The in-memory cleartext is still dropped** (never sign with a value that failed authentication), so `deliverAttempt` emits no `X-Culvert-Signature`. **(2) The on-disk ciphertext is KEPT** in the unexported `Webhook.sealedSecret` and written back VERBATIM by `save()`; re-encrypting the blanked cleartext persisted `""` and destroyed recoverable key material, and because `save()` rewrites the WHOLE list that was triggered by an unrelated add/edit/delete/toggle — the code's own "no data loss on a transient key-read failure" comment was not upheld. Restoring the original key file now recovers signing without re-entry. **(3) The state is VISIBLE.** `List()` blanks `Secret`, so "no secret was ever configured" and "the secret is unusable and deliveries are UNSIGNED" used to serialise identically — a monitoring blind spot where a receiver that verifies the HMAC silently stops accepting this node's security alerts, and quiet looks like healthy. `List()` now reports a DERIVED read-only `SigningDegraded` (`signing_degraded`), the `alert_webhook_signing` operator-contract row warns (counts only — no name, URL or ciphertext on that viewer-role surface), and the Alert Webhooks panel badges it. The status is derived and NEVER accepted from a caller or from the file (`Add`/`Update`/`Init` all clear it) and is never persisted. Delivery stays fail-OPEN-but-loud (unsigned, badged) rather than refusing to deliver: silence is worse than a visible authenticity failure on the alerting channel — recorded owner decision. **(4) A failed DECRYPT never mints a key** (`webhookSecretKey(dir, create)`; `create` is true only on the encrypt path). Minting on read meant the restore case wrote a fresh key as a side effect of failing to decrypt, so the preserved ciphertext and every later write sat under DIFFERENT keys and the documented "restore the original key file" recovery would break exactly the secrets the operator had already re-entered (Codex review, PR #1222). Creation now happens on the first encrypt — an explicit operator action — which also stops a failed read from attempting a write on a read-only or full volume. The operator remedy is therefore ORDERED and both surfaces say so: restore the original key file FIRST if you still have it (no re-entry needed), otherwise re-enter each secret, and never restore the old key AFTER re-entering. Gates: `internal/alerts/webhook_signing_degraded_test.go` + root `alert_webhook_signing_test.go`.

## The per-minute time series is SHARDED on its current minute (`store.go`)

[Original lines 211–211](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L211-L211) · `claude-main-L211-L211`

<!-- BEGIN preserved-block: claude-main-L211-L211 -->
- **The per-minute time series is SHARDED on its current minute (`store.go`)**: `tsRecordResult` runs on EVERY proxied request via `recordStats` — HTTP, CONNECT, WebSocket, SOCKS5 alike. It took ONE process-wide `sync.Mutex` and, while HOLDING it, read the clock (`tsAdvance`'s `time.Now`) before bumping three counters, so every request in the process serialised on one lock across a vDSO clock read. Same class as the `internal/threatfeed`, `internal/connlimit`, IP-filter and latency-histogram findings. **The header this replaces recorded the opposite conclusion and the way it was reached is the lesson**: an RLock+atomic fast path had been benchmarked, measured FLAT, and read as "every request bumps the SAME current-minute bucket, so the shared cache line, not the mutex, is the bound". Both halves were wrong — `RWMutex` cannot help a path that MUTATES, so a flat result said nothing about the bound; and the shared cache line is inherent only while the counter stays shared. The measurement that settles it is not ns/op at one core but how ns/op MOVES with core count (4-core box, Go 1.26, ns/op, GOMAXPROCS 1 / 4): mutex with the clock inside it **85.5 / 178.6**; clock hoisted out 83.1 / 144.9; lock-free but counters still shared 78.9 / 62.2; lock-free and SHARDED **85.9 / 38.1**; `time.Now().Unix()/60` alone — the irreducible floor — 64.8 / **16.6**. Read the floor first: at four cores the old path spent 162 of its 179 ns NOT doing the work. In the real code `tsRecordResult` went **172.6 → 36.1 ns/op at four cores** (four cores had been delivering 5.8M records/s against 11.4M on ONE core — adding cores SUBTRACTED throughput — and now deliver 27.7M, **4.8x the old ceiling**), and the whole `recordStats` fan-out **275.8 → 131.2 ns/op**. There is NO low-concurrency price — one core came out AHEAD too (142.9 → 130.0), because dropping the lock/unlock pair and collapsing the verdict pair into a single atomic add together cost less than picking a shard. **Those fan-out figures are TIGHT-LOOP numbers and are not the ones to quote** — `store_stats_bench_test.go`'s methodology note (added by the topHosts work, #1357) records that a tight `recordStats` loop is not the production duty cycle, because speeding one component only raises the arrival rate at the next contended one. The MARGINAL cost, `BenchmarkRequestCycle` in isolated processes (n=5, medians, ns of fan-out per request), is the number a gateway pays and is also where the two sharding changes COMPOSE: sharded topHosts alone **129 / 490** at GOMAXPROCS 1 / 4 — cores made it WORSE, the ceiling had simply moved to the other component — versus **111 / 87** with the time series sharded too, i.e. it FALLS with core count and is 5.6x cheaper at four cores. The bimodality that note warns about shows up in exactly the arm that still has a contended component (main's 4-core WithStats spread 755–784 ns across five runs; this branch's 364–371). Only the CURRENT minute is hot, so only it is sharded — the 60-bucket ring is untouched and still mutex-guarded; requests accumulate into `live` (`tsShardCount` 64, cache-line padded), a `rollover` folds them into the bucket they belong to, and readers (`tsGet` — the SSE dashboard tick, `/api/stats`, the history-store disk estimate) sum the shards in, moving work read-ward exactly as the sharded histogram does. **`record` has no key to shard on** — a request contributes to a global count, not a per-IP or per-host slot — so the index comes from `math/rand/v2`'s per-P generator (aliased `mrand`; this file's `rand` is `crypto/rand`), NOT a shared atomic round-robin counter, which would reintroduce the very cache line being removed. **THE INVARIANT IS CONSERVATION, NOT INSTANT ATTRIBUTION**: a request descheduled between reading `liveMin` and incrementing lands in the NEXT minute's accumulator, an at-most-one-bucket shift on a 60-minute sparkline; nothing is ever lost, because `foldLiveLocked` **SWAPS** each shard to zero rather than reading-then-zeroing, so a late increment is carried into the following fold. That distinction is not theoretical — a read-then-zero fold loses counts on every run of `TestTimeSeries_ConservedAcrossRollover`, which counts writers rather than fixing a total in advance and so is exact regardless of scheduling. **But whole-window conservation is NOT sufficient, and that is the sharp edge**: `/api/timeseries` hands the dashboard three PARALLEL arrays, so the invariant is also PER BUCKET (`allowed[i]+blocked[i] == buckets[i]`). The first shipped shape carried a separate `total`/`allowed`/`blocked` triple, so a writer took TWO independent adds and the fold THREE independent swaps — a fold landing between a writer's two adds banked its total in the OLD bucket and its verdict in the NEW one, a permanent per-bucket mismatch that conserved the window total perfectly and so passed every window-sum test (Codex review, PR #1286). A request's counters therefore live in ONE word: the allow/block pair is PACKED (`verdicts`, allowed high 32 bits / blocked low 32) and a verdict is a SINGLE atomic add, with unverdicted records (`tsRecord`) on their own `plain` word — each writer touches exactly one, so the fold's two swaps are independent BY CONSTRUCTION. The packing is also FASTER (one add, not two), which is why one core came out ahead. Gates: `TestBenchGate_TopHostsRecordTakesNoLock` is **structural** (holds `mu`, requires a tracked-host `Record` to complete anyway — deterministic on any hardware, under `-race`, at any load; the scaling-ratio form was rejected for the reason `connlimit`'s was) with `TestBenchGate_TopHostsNewHostStillSerialises` as its **control** so a passing gate cannot mean the lock simply stopped being taken, plus `TestTopHosts_ConcurrentRecordDecayAndTop` and `TestTopHosts_TrackedCountsAreNotLost`. **Methodology, because it reversed the conclusion twice**: a tight `recordStats` loop is NOT the production duty cycle — speeding up one component there only raises the arrival rate at the next contended one, and the measured TOTAL got ~8% worse while the component got 6x faster. `BenchmarkRequestCycle_{WithoutStats,WithStats}` separate the fan-out with ~1 µs of unrelated work and report the MARGINAL cost, which is what a gateway actually pays; always run these in an isolated process, since the contended arm is bimodal (4-core marginal cost landed at 160 ns in one round and 445 ns in the next).

- **The 60-bucket RING keeps its plain mutex, and that rejection still stands (`timeSeries`, store.go)**: this note previously read *"`tsRecordResult` keeps its plain mutex — tested twice, must not be 'fixed' a third time without new evidence"*. The rejection it records is CORRECT for the design it tested and is kept here, because the alternative it rules out is NOT the one that shipped. **What it rejected: sharding the RING** — 60 buckets x 3 counters per shard, prototyped at 16 shards in mutex and atomic variants — which did not pay on 4-core hardware, since the only shard key available is a `rand.Uint64` and its cost ate the gain. **What shipped instead: sharding only the CURRENT MINUTE** (see the bullet above), 2 words x 64 cache-line-padded shards, ONE atomic add per request, with the ring itself untouched and still mutex-guarded. Three differences decide the outcome: the sharded object is 2 words rather than 180, the shards are PADDED (16 unpadded shards still false-share), and the allow/block pair is PACKED into one add rather than two or three. **Both of the earlier findings reproduce and are worth keeping.** RLock+atomic (2026-07) was FLAT — `RWMutex` cannot help a path that MUTATES. A fully lock-free atomic increment over SHARED counters was NOT the answer either: removing the mutex removes the BATCHING (a holder mutates the line while owning it exclusively, whereas N cores doing atomic RMWs on one address ping-pong it every operation) — measured here as 78.9 / 62.2 ns/op at GOMAXPROCS 1 / 4 against the SHARDED shape's 85.9 / 38.1. The `rand.Uint64` cost is real and reproduces at **~7 ns**, squarely inside the 8-17 ns the earlier note cites; it simply stops mattering above one core. **The new evidence that clause asked for, taken with `BenchmarkRequestCycle` — the marginal-cost benchmark this repo prefers — in isolated processes, paired on one box, n=5 medians, ns of stats fan-out per request:** current main **127 / 339** at GOMAXPROCS 1 / 4 versus this shape's **134 / 72**, i.e. **4.7x cheaper at four cores and ~7 ns dearer at one**. The `WithoutStats` control is identical across both arms (283.5 vs 285.8 at four cores), so the delta is the fan-out and not a base difference. The bimodality the methodology note warns about appears in exactly the contended arm: main's 4-core `WithStats` spread 588-640 ns across five runs, this branch's 356-369. **So the standing rule is narrowed, not deleted: do not shard the ring, and do not re-derive the current minute as shared atomics or as an unpadded/unpacked shard array.** Revisit the ring only on much wider hardware and only with a cheaper shard key than a PRNG call.
