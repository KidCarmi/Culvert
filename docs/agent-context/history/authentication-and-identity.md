## The public admin-login endpoint bounds its username BEFORE any durable write (CHAOS-63, `login_input_bounds.go`)

[Original lines 185–185](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L185-L185) · `claude-main-L185-L185`

- **The public admin-login endpoint bounds its username BEFORE any durable write (CHAOS-63, `login_input_bounds.go`)**: `apiAuthLogin` (`/api/auth/login`) is on `uiAuthMiddleware`'s PUBLIC allowlist and bounded nothing, so the caller's chosen `body.User` reached four retaining sinks — the tier-1 and tier-2 `internal/lockout` map keys (which `Cleanup` deliberately cannot sweep before `lockout.Window` = 10 min elapses), the 500-entry audit ring, the DURABLE audit JSONL, and the `auth_lockout` alert payload. The only limits in front of the handler are `securityMiddleware`'s 1 MiB body cap and the 60-mutating-POST/min per-IP API limiter, so ONE unauthenticated client commits **~60 MiB/min of chosen bytes** into a compliance record that is a `fileutil.RotatingFile(path, 50)` keeping exactly ONE archive (100 MB total, `rotating.go` removes the previous `.1` before renaming) — the entire retained audit trail rotated away in **under two minutes**, and ~1 GB of heap parked for ten. Measured by the gate: **4,195,672 bytes into the audit file from 8 requests.** `internal/audit`'s own header names this outcome (CWE-778/A09:2021) and its `writeErrors` counter CANNOT see it: **every one of these writes SUCCEEDS**, so `storage_write_failed`, the `audit_log_persistence` contract row and `culvert_audit_write_errors_total` all stay green while the record is destroyed. Four rules now hold. **(1) The bound is at the ENTRY POINT** — `rejectOversizeLoginUser` refuses `len(body.User) > maxUsernameLen` (256, the same constant `proxy_portal.go` already applies to Proxy-Authorization) and returns BEFORE the limiter, the credential check and the alert, so a rejected attempt creates no state at all. **A CONFIGURED account is NEVER refused, however long its name** (`cfg.LoginNameConfigured`, a non-retaining probe that MUST mirror `VerifyUIUser`'s own roster-or-legacy resolution — pinned by `TestChaos63_LoginNameConfiguredMatchesVerifyUIUser`, because a divergence is an admin lockout). The first draft claimed no real account could carry such a name, since `apiSetupComplete` and the user-creation API cap at 64; that is FALSE — `-user`/`auth.user` reach `cfg.SetAuth` and `--reset-password` reaches `cfg.SetUIUser`, and neither store bounds the name (`validateAuthStartupCredentials` validates only the password), so an over-long username can already be a valid persisted admin and refusing it would have locked that operator out of the admin UI on upgrade (Codex review, PR #1320). `warnOversizeConfiguredUsernames` (auth_startup.go) warns at boot and is deliberately NOT fatal — the stores never bounded the name, so failing the boot would brick an appliance whose config was legal when written. 400 not 401 is deliberate for a name that exists nowhere: a username's LENGTH is not a secret. The narrow cost is that, past the bound only, 400-vs-401 says "no such account" to a caller who already guessed the exact over-long name — a far better trade than refusing a real admin. **(2) `internal/lockout` carries the structural half** — `MaxUsernameKeyLen`/`boundUsername` clamp at EVERY public entry point (`Check`, `CheckPair`, `RecordFailure`, `RecordPairFailure`, `RecordSuccess`, `AttemptsLeft`, `ResetUser`). **The clamp is INJECTIVE** (rune-safe prefix + a SHA-256 digest of the WHOLE name), and that is a SECURITY property: because a configured over-long name is exempt from the rejection above, it reaches this limiter, so a plain truncation would let an attacker who knew that admin's first 256 bytes submit an ordinary ≤256-byte name clamping to the SAME key and drive the tier-2 account lock against them — lockout-as-DoS, the exact defect the two-tier design (RISK-012) exists to prevent (pinned by `TestBoundUsername_IsInjective`). Applying the clamp at only SOME entry points is worse than not applying it: `Check` and `RecordFailure` disagreeing about the key splits one attacker's failures across two counters and silently WEAKENS the lock while passing any byte-size assertion (pinned by `TestOversizeUsername_CheckAndRecordAgree`, with `TestBoundedNames_BehaviourUnchanged` as the control that an ordinary lockout is untouched). The package's `Cleanup` doc claimed the maps were bounded "against an unbounded-memory DoS" — true on the ENTRY-COUNT axis, never true on the KEY-SIZE axis. **(3) The attempt is still AUDITED** (`auth.login.rejected`, actor truncated via `truncateForAudit` with a self-describing `…[truncated, N bytes]` marker, real length in the detail): bounding the bytes must not delete the evidence that the admin plane is being probed, and the entry is O(1) at the same rate the ordinary `auth.login.fail` entry would have cost, so it adds no ring-eviction capacity the endpoint did not already have. **(4) The rejection is VISIBLE** — `culvert_login_oversize_rejected_total` is the operator's only signal (the caller just gets a 400), and the log line is rate-limited to one per minute with the magnitude in the counter, because a mitigation for a write-amplification defect must not be one itself. **Deliberately NOT done:** no byte cap inside `internal/audit` (the sink cannot tell attacker bytes from a legitimate `auditEventDiff` before/after payload — whole policy objects are marshalled there on purpose — so a cap would destroy real compliance evidence to fix an input-validation defect); no hard entry-count cap on the lockout maps (evicting at a cap evicts a REAL lock — an owner trade-off, recorded as open register row AU-17, now ~4000x smaller per key). Gates: `login_input_bounds_test.go` (10) + `internal/lockout/lockout_keybound_test.go` (9); seven defect gates verified failing against their reintroduced pre-fix shapes. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §32 and `docs/operator/admin-login-input-bounds.md`.

## An admin-roster mutation is DURABLE-OR-REFUSED, and the login path is fail-open-but-counted (CHAOS-70, `store.go` `mutateRosterDurably` + `roster_persist_durability.go`)

[Original lines 186–186](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L186-L186) · `claude-main-L186-L186`

<!-- BEGIN preserved-block: claude-main-L186-L186 -->
- **An admin-roster mutation is DURABLE-OR-REFUSED, and the login path is fail-open-but-counted (CHAOS-70, `store.go` `mutateRosterDurably` + `roster_persist_durability.go`)**: `ui_users.json` is the ONLY durable home of the admin roster — every account, password hash, role, TOTP secret, consumed-backup-code list and TOTP replay counter. Every mutation changes MEMORY first and persists second, so the two can disagree, and the disagreement is resolved at the next restart, when the FILE wins. Three handlers mutated that state, logged the persist error and answered 2xx — precisely the three an operator reaches for during an incident: **delete a compromised administrator** (`204 No Content`, audited as done; the account returns at the next restart with its original hash, role and TOTP enrolment), **downgrade a role** (`{"ok":true}`; the privilege is restored on restart), and **rotate a leaked password** (`{"ok":true}`; the old password still authenticates after a restart). The response, the UI and the AUDIT LOG all said success. **The rule already existed twenty lines away and was applied to the one-time path only**: `apiSetupComplete` treats exactly this hazard as a wrong answer rather than a degraded success, in both branches, with the reasoning written out in `setDefaultAuthOutcomeChecked` and pinned by two tests — that asymmetry, not the individual handlers, is the finding. **This is NOT a silent-failure finding and calling it one overstates it**: `fileutil.AtomicWrite` already notifies the CHAOS-45 observer on every failure branch, so `storage_write_failed` and the degraded contract row fire underneath (the reproduction emitted `Storage: DURABLE WRITE FAILED for "ui_users.json"`). It is MIS-REPORTING: the operator gets an alert saying *some* durable write failed and a `204` saying *this specific revocation succeeded*, and no amount of storage observability makes a wrong HTTP status right. ST-5/ST-6 stay CLOSED and are not the cause — the file is never torn; the gap was what the caller does when the write fails. Six rules now hold. **(1) ONE primitive, because a per-caller inverse operation is where the bugs live** — `mutateRosterDurably` snapshots the roster WHOLESALE, mutates, persists, and on failure restores and returns `ErrRosterNotPersisted`; undoing a delete means restoring the password hash, role, TOTP secret, backup codes AND replay counter, none of which the handler still holds by then, and a PARTIAL restore is worse than no rollback (an account its owner cannot use and an operator cannot see is broken). **(2) The rollback invalidates cached auth decisions** (`authRevision`++ + `cache.clear()`, matching `RollbackFailedSetupAuth`) — otherwise a rolled-back password change leaves a cached positive for the NEW password, a credential the roster no longer contains, still authenticating for the cache TTL. **(3) `fileutil.ErrReplacedNotSynced` is deliberately NOT rolled back** — the rename already landed the content, so every future reader including a restart sees the new roster; rolling back would leave memory contradicting the file and refusing would be a false negative. A naive "non-nil error ⇒ roll back" reintroduces the hazard from the opposite direction. **(4) The mutation's OWN refusals keep their own status codes** — `DeleteUIUser`'s "cannot delete the last admin" guard stays `409`, and must not move the persistence counter (pinned as a control): turning every refusal into the persistence `500` sends an operator to check their disk over a policy decision. **(5) The refusal is AUDITED** (`<action>.refused`) — the success entry is written only on success, so without it the compliance record carries no trace of an attempted revocation that did not take effect. **(6) The LOGIN path stays fail-OPEN and that is a POSTURE, recorded, not an oversight** — advancing the TOTP replay counter and removing a consumed single-use backup code previously discarded their error outright (`//nolint:errcheck`), so a failed write silently weakened a security property: after a restart a consumed single-use code is valid again and the replay window for a used OTP reopens — **the same shape the register recorded as CA-14 for the session revocation list**, closed there by moving to `AtomicWrite` and never checked for the credential store beside it. They are NOT made fail-closed: refusing would mean an operator whose TOTP device is lost, on an appliance whose volume has just gone read-only, cannot reach the admin UI at all during the incident they need it to diagnose — the terminal state CHAOS-55/57 both refuse. Counted and rate-limited-logged instead (one line/min, magnitude in the counter — a mitigation for a write-amplification defect must not be one itself). A VESTIGIAL write was removed alongside: the TOTP FAILURE branch called `SaveUIUsersFile()` after `loginLimiter.RecordFailure`, which changes nothing `ui_users.json` carries (`internal/lockout` is in-memory and deliberately non-persisted, row AU-4) — re-serialising every account and bcrypt hash and fsync'ing a rename on EVERY failed OTP, persisting nothing, on the brute-force path that branch exists to rate-limit. Surfaces: `culvert_admin_roster_persist_{failures,degraded}_total`, emitted UNCONDITIONALLY (unlike the gauges elsewhere, a flat zero here is the healthy steady state for every appliance, so the emit-only-when-armed rule does not apply), deliberately distinct from `storage_write_failed` because they say WHICH administrative decision was affected and therefore what to redo; **no new alert event** (the storage plane already pages for the failing volume — what was missing was not a page but the ability to answer "what did I lose?"). **Nothing is queued and nothing retries** — a privilege change replayed later, out of order, against a roster that has since changed is worse than one the operator reapplies knowingly. Gates: `roster_persist_durability_chaos_test.go` — 4 defect gates each verified failing against the reverted handler shape, 3 CONTROLS (a healthy volume must still apply AND persist; a policy refusal keeps its 409 and moves no counter; `ErrReplacedNotSynced` counts as committed while an ordinary failure does not), and a STRUCTURAL WALL that AST-walks `ui_auth.go` and fails on any `cfg.SaveUIUsersFile()` appearing as a bare expression statement — behavioural coverage cannot reach a future call site that discards the error, since every test keeps passing on a healthy disk (verified by injection, with its own not-vacuous check; SEC-SOCKS5-LOG-1 round 2's lesson applied to the discarded-error shape). **CODEX ROUND 1 — the rollback needed a TRANSACTION and the rate gate needed a CLAIM.** (P1) A whole-roster rollback is only sound if nothing else can write the roster: `ConsumeBackupCode`/`SetTOTPLastCounter` took only `c.mu`, so a login consuming a single-use backup code between a failing admin mutation's SNAPSHOT and its ROLLBACK had that consumption DISCARDED — and since the login's own save blocks on `saveUIUsersMu` and lands AFTER the rollback, it then PERSISTED the reverted state, making the resurrection durable. `setDefaultAuthOutcomeChecked` had the mirror-image problem and is reachable from a live admin API (`ui_config.go`), not just setup. That is the exact property this note exists to protect, broken by the rollback this note introduced — *a mechanism that restores state is only as sound as the boundary that stops anyone else writing it*. `saveUIUsersMu` is now the transaction lock for EVERY persisted roster mutation, held across mutate+persist by all three shapes (`mutateRosterDurably` with rollback, `mutateRosterBestEffort` for the fail-open login path, `setDefaultAuthOutcomeChecked` with its targeted rollback); a mutation reporting NO change issues no write, so a rejected backup code cannot re-serialise the roster (the removed vestigial write does not return through the fix). (P2) The log-rate gate read/compared/stored, so concurrent callers all saw the same expired stamp and all emitted — now a `CompareAndSwap` claim. **That gate is STRUCTURAL and the measurement is why**: a TOCTOU on an atomic is invisible to `-race` (atomics are race-free by definition) and was unreachable behaviourally — 256 goroutines × 200 trials against the pre-fix shape produced >1 winner in 0/200 runs, so a behavioural gate PASSES against the defect (measured), which is worse than no gate. It asserts the mechanism with a control rejecting a verbatim pre-fix copy (the `sanitizeLog` scan-count precedent); the behavioural test is RELABELLED a control pinning that the line is suppressed while the COUNT never is. The pre-existing wall's not-vacuous check EARNED ITS KEEP: moving the login path onto the new primitives dropped its match count and it failed rather than passing against nothing. **Recorded, NOT fixed: TOTP 2FA has no enrolment surface at all** — `SetTOTPSecret`/`ClearTOTP`/`SetBackupCodes` have NO production callers and `uiRoutes` carries no TOTP route, so the feature is half-live (enforced on login, enablable only by hand-editing `ui_users.json`), a GUI-parity gap that also bounds the backup-code item's reachability (row AU-18); and user-level revocation (`RevokeUser`) is neither persisted nor gossiped while token-level revocation is both, bounded today by `uiAuthMiddleware`'s `Provider == "local"` roster backstop (row AU-19). **CODEX ROUND 2 — the transaction had ONE WRITER LEFT OUTSIDE IT, and the runbook named a route that does not exist.** (P1) `SetAuth` mirrors the new admin into `c.uiUsers` under `c.mu` only, so credentialed first-time setup IS a roster mutation, and `apiSetupComplete` ran it as an unserialised `SetAuth` + `SaveUIUsersFile` pair. Round 1 dismissed that on the recorded reasoning that setup and admin user-management are mutually exclusive because the latter requires a configured appliance — FALSE, and **the gate said to be separating them is what makes them overlap**: `uiAuthMiddleware` injects `RoleAdmin` into EVERY request while `!cfg.IsConfigured()`, so `POST /api/auth/users` is reachable with admin authority precisely DURING setup. An admin mutation snapshots the still-empty roster, `SetAuth` inserts the initial admin, the admin mutation's failed write RESTORES that empty snapshot — deleting the account — and setup's own write, queued behind `saveUIUsersMu` the whole time, then persists the empty roster and answers 200; `IsConfigured()` survives only via the legacy `c.user`/`c.passHash` pair, which `ui_users.json` does not carry, so the next restart reopens **unauthenticated first-time setup**. `SetAuthDurably` now holds the transaction lock across mutate+persist, and its compensation stays `RollbackFailedSetupAuth` rather than `restoreRoster` because `rosterSnapshot` does not capture the legacy pair (a wholesale restore would undo the account while leaving `IsConfigured()` true with nothing persisted — exactly the state that rollback exists to clear). **Its gate is STRUCTURAL and the measurement is again why**: the first draft held the transaction open, called `SetAuthDurably` concurrently, slept 50 ms and asserted the roster was untouched — and PASSED against the verbatim pre-fix shape, because `SetAuth` runs bcrypt at `DefaultCost` (~80–100 ms) BEFORE it touches `c.mu`, so the window closed while the defect was still hashing. Round 1's P2 lesson from the other end (there the window was too NARROW to observe, here the observation was taken too EARLY), same standing rule: a behavioural gate that passes against the defect is worse than no gate. The wall asserts the mechanism (`saveUIUsersMu.Lock()` as the FIRST statement, never the self-locking `SaveUIUsersFile`) with a control rejecting a verbatim pre-fix body, and the behavioural half is kept but made SELF-CALIBRATING — its wait is derived from a measured `DefaultCost` hash on the machine running it, so it fails against the defect on fast and slow hardware alike. (P2) The runbook and CHANGELOG named `POST /api/auth/password`; the registered route is `POST /api/auth/change-password`, so an operator following the recovery steps got a 404 mid-incident — corrected, and `Wall_RunbookNamesRegisteredEndpoints` now requires every `/api/` path in the runbook to exist in `uiRoutes`. The pre-existing wall's not-vacuous check fired a SECOND time for the same reason and was widened, not weakened, to all four persisting shapes. **ROUND 3 (SELF-FOUND) — A FOURTH ROSTER MUTATOR, ON A LIVE ADMIN ENDPOINT, AND IT WAS WORSE THAN THE THREE THIS SWEEP FIXED.** Auditing the remaining `cfg.SetAuth` call sites found `apiSettings`' POST branch (`ui_config.go`) — the GUI **Settings panel's Save button** — calling `cfg.SetAuth` and NOTHING else; the admin credential is not in `admin_settings.json` and the only writers of `ui_users.json` are the roster primitives, so **nothing persisted it**. Measured against the real handler: a rotated admin password answered `200`, was audited as `settings.update`, authenticated live, and **reverted at the next restart where the previous (leaked) password authenticated again** — the same hazard as above but UNCONDITIONAL, needing a restart rather than a disk fault; complexity was validated only `if body.Pass != ""`, so a blank password box installed `bcrypt("")` as an ADMIN credential and, for a changed username, an admin ACCOUNT authenticating with NO password (the GUI form posts whatever the box holds, so an operator editing only the username reached it by accident); and an EMPTY user is `SetAuth`'s documented way to DISABLE local authentication, so clearing both fields switched off the admin credential behind a "Settings saved" toast. **Fixing the persistence ALONE would have been a REGRESSION** — persisting is what makes the two input faults survive a restart — so the three are one change; empty user/password are now `400` (credential-free operation stays the `defaultAuthOutcome=Exempt` endpoint's job, which says so) and the change is durable-or-refused through the same transaction. **A CONTROL caught the first version of this fix LOCKING THE ADMINISTRATOR OUT**, and it is this note's own rule (1) turned back on it: routing through `SetAuthDurably` inherited setup's dedicated inverse `RollbackFailedSetupAuth`, which DELETES the account — right for a first-time setup, wrong for a rotation, where a refused write left the admin with no roster entry at all. The cause was an INCOMPLETE snapshot (`rosterSnapshot` captured the roster but not the legacy `c.user`/`c.passHash` pair `SetAuth` also writes, which is why setup needed its own inverse); **completing the snapshot removed the need for a second inverse entirely** — `SetAuthDurably` is now a one-line delegation to `mutateRosterDurably`, so both callers share one rollback, one transaction lock and one `ErrReplacedNotSynced` rule, and `RollbackFailedSetupAuth` has no production callers left. That also RESOLVES the `ErrReplacedNotSynced` inconsistency round 2 recorded as pre-existing: compensating on any persist error was tolerable while this served setup alone and stopped being so once a live endpoint was the second caller, because a rollback after a landed rename leaves memory contradicting the file. The wall's not-vacuous check fired a THIRD consecutive time as the lock moved into the shared primitive, and was widened — it now accepts either taking `saveUIUsersMu` first or delegating wholly to `mutateRosterDurably`, with the control still rejecting the pre-fix body. **The published API contract was RIGHT and the handler did not enforce it**: `SetInitialAdmin` in `api/openapi/openapi.yaml` already declares `required: [user, pass]` with `pass` at `minLength: 8`, so every body the two input faults accepted was one its own contract forbids — and the conformance test covering it asserts only that the SPEC rejects a missing `pass`, never that the HANDLER does, so it passed throughout (a request-conformance suite validating the schema in isolation proves the document is strict and says nothing about the code; live request validation against the contract is a recorded follow-up). Recorded, NOT fixed: the contract documents no `500` for any of the four endpoints that now return one — pre-existing, family-wide, and additive to close, but it needs four spec edits plus a `make api-bundle` regeneration through the API-governance gates. **The governance lesson: this sweep's own note claimed the transaction lock covered EVERY persisted roster mutation while its structural wall AST-walks `ui_auth.go` only — the claim was broader than the wall and the mutator that escaped both lived in another file. Enumerate such a class from the PRIMITIVE (`cfg.SetAuth`, `SaveUIUsersFile`), not from the file being edited.** See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §40 and `docs/operator/admin-roster-durability.md`.

## An unenrolled role never becomes admin (SEC-RBAC-ROLE-1, `store.go` + `ui_session.go` + `ui_middleware.go`)

[Original lines 224–224](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L224-L224) · `claude-main-L224-L224`

<!-- BEGIN preserved-block: claude-main-L224-L224 -->
- **An unenrolled role never becomes admin (SEC-RBAC-ROLE-1, `store.go` + `ui_session.go` + `ui_middleware.go`)**: three layers together turned a role string this build does not know into FULL ADMIN, and each was individually defensible. `POST /api/auth/users` validates the role it is handed (`!role.HasRole(RoleViewer)` ⇒ 400), but `LoadUIUsersFile` — the door the same roster arrives through from DISK — validated nothing and wrote `rec.Role` verbatim, three lines below the `default_auth_outcome` field whose own comment spells out the opposite rule ("key present but empty/invalid ⇒ fail closed"). `VerifyUIUser` then returned that role on a successful login, `apiAuthLogin` minted a genuinely HMAC-signed session with it, and `uiAuthMiddleware` promoted it: its compat branch was written for the pre-RBAC EMPTY role but keyed on `!role.HasRole(RoleViewer)`, which is true of EVERY unenrolled string, so `""`, `"read-only"` and `"Admin"` all came out `RoleAdmin` — on every subsequent request, for the full session TTL, with `apiAuthStatus` reporting `role: admin` so the console rendered the whole admin surface to match. Nothing is forged: the appliance signs the cookie itself, and the reachable sources are the ordinary raw-persistence ones — a restore of a backup taken by a newer build that enrolls a role this one does not (the DOWNGRADE case, which `--prepare-downgrade` exists for elsewhere), a hand-edited or partially-corrupted `ui_users.json`, or any future writer that bypasses the API. **The fix is at all three layers because each is a door the others do not cover**: `HasRole` refuses an unenrolled REQUIREMENT (invariant #8 above); `loadedRosterRole` clamps an unenrolled non-empty roster role to `RoleViewer` — the LEAST privilege the roster can express — rather than dropping the record, because dropping deletes an account off a file the operator can still repair while clamping leaves them able to sign in and read with no authority they did not already hold; and `sessionRoleOrReject` SPLITS the one compat branch in two, so `""` still resolves to `RoleAdmin` (pre-RBAC single-admin deployments must not be locked out mid-session) while every other unenrolled value is refused with a cleared cookie and a 401. **Splitting that branch is what makes the compat case narrow enough to keep** — it was only ever dangerous because one predicate answered two different questions. The clamp is VISIBLE (`culvert_ui_roster_role_clamped_total`, `uiRosterRoleClamped` on `/healthz` and `/api/stats` when non-zero, plus a log line naming the user and the rejected role): an account whose effective authority is deliberately lower than its file says must not be a silent state. Gates: `ui_role_failclosed_test.go` — every defect gate verified failing against the reintroduced pre-fix shape, plus CONTROLS for the two cheapest wrong fixes (refusing the empty session role locks out legacy deployments; refusing or dropping a clamped roster record deletes the account) and a structural WALL over the route table.

- **A credential write NEVER removes a second factor (SEC-TOTP-1, `store.go` `newUIAdminUserPreservingTOTP`)**: `apiAuthLogin` refuses to issue a session for a TOTP-enrolled account until `verifyLoginTOTP` accepts a code, and TOTP failures feed the two-tier lockout — so the enrolment is a real second factor whose whole purpose is to SURVIVE a password compromise. `Config.SetUIUser` and `Config.SetAuth` both assigned a bare `&uiAdminUser{passHash, role}` over the stored record, so EVERY credential write silently dropped `totpSecret`, `backupCodes` and `totpLastCounter` — durably (the next `SaveUIUsersFile` persisted it), with no audit entry naming the de-enrolment, no notification, and no proof of possession of the authenticator. That inverts the control: whoever held the current password could permanently remove the factor that outranks it, turning a temporary session/credential compromise into durable password-only access. Three reachable paths: `POST /api/auth/change-password` (ANY principal from viewer up, for its own account), `POST /api/auth/users` (admin, any account) and `POST /api/settings/auth` (runtime, not boot-only). **The counter is a finding on its own** — resetting `totpLastCounter` to 0 reopens the OTP replay window `SetTOTPLastCounter` closes (RFC 6238 §5.2), the same regression the RESTORE path refuses to perform without `--allow-counter-rollback`. **Why it stayed invisible: `ClearTOTP` — the intended de-enrolment primitive — has no production call site at all**, so reading the tree for "where is a second factor removed?" returned nothing; the only removal was a consequence of struct replacement. Adding a field to `uiAdminUser` and forgetting it there silently drops that field on every password change, which is exactly how the factor was lost, so the constructor is pinned by an AST wall (`TestWall_CredentialWritesGoThroughTOTPPreservingConstructor`). **(2) It CONSTRUCTS a new record rather than mutating the stored one in place**, and that is not style: `VerifyUIUser` takes the entry pointer under `RLock` and dereferences `passHash` AFTER releasing it, so an in-place credential write would be a data race on the authentication hot path — the copy-construct shape preserves the existing publication contract exactly (pinned under `-race`). **(3) De-enrolment stays `ClearTOTP`'s job**, an explicit call, never a side effect. **(4) `--reset-password` is the ONE path that may still remove a factor** — it is the documented sole admin-recovery break-glass (GAP-IAM-01, host/container shell only) and an operator who lost the authenticator as well as the password depends on it, so the OUTCOME is unchanged: it now calls `ClearTOTP` deliberately and PRINTS that the account became single-factor. **(5) The replay counter belongs to the SECRET, so de-enrolment and re-enrolment reset it** — the first version of this fix got that wrong and it took a review to find (Codex, PR #1429). `ClearTOTP` cleared the secret and the backup codes but not `totpLastCounter`, which was harmless ONLY because the next credential write used to replace the whole record and zero it as a side effect; The first shape of (5) compared the stored strings raw, but `verifyTOTPAt` canonicalises (`strings.ToUpper(strings.TrimSpace(secret))`) and then base32-DECODES, so several spellings name ONE authenticator and generate identical codes — a backup-code re-issue spelling the secret in lowercase read as a key change and zeroed the counter for a LIVE key, i.e. the replay window reopened by the change that closed it, invisible to the CONTROL because that test re-passes the same literal. Case folding alone is NOT sufficient either: Go's base32 decoder ignores non-canonical trailing bits, so `MZXW6` and `MZXW7` differ in every case-folded spelling and decode to the SAME key. The canonicalisation is therefore ONE function (`internal/totp.decodeSecret`) that `verifyTOTPAt` itself uses and that backs the exported `totp.SameKey`/`totp.Usable`, so the two layers cannot drift; the decision is three-way and ordered by which way each case must FAIL — an UNUSABLE incoming secret keeps the counter (it authenticates nothing, so it is no evidence the key changed), the SAME key keeps it, and only a positively different usable key (or a first usable key over an unusable one) resets it. Keeping a counter that should have been reset costs at most a step or two of delay on re-enrolment, because counters are time-derived and a past enrolment's counter is already in the past; zeroing one that should have been kept reopens a replay window on a live key — so the reset requires positive evidence. The lesson generalises twice: *a field that was only ever cleared as a side effect has no owner, and the change that removes the side effect inherits it* — when a fix makes state survive where it used to be destroyed, enumerate every field that survives and ask which of them was relying on the destruction; and *when a value's MEANING is decided by one layer, every other layer that compares it must ask that layer, never re-derive the rule* — a comparison that canonicalises differently from the consumer is a silent security failure, which is why the wall (`TestTOTPSameKey_AgreesWithTheVerifier`) asserts the AGREEMENT rather than either spelling of the rule, and fails against drift introduced from either side. **Do not "simplify" a credential write back to a struct literal, and do not make the break-glass clear silent again.** Adjacent and deliberately left: `uiAuthMiddleware`'s public allowlist carries an INERT `"/api/auth/totp"` prefix with no route under it — a route landing there would be served UNAUTHENTICATED, and since a self-service enrolment endpoint is naturally viewer-level neither the C2 gate (`uiRole` defaults to `RoleViewer` with no session) nor `requireRole(RoleViewer)` would stop an anonymous caller from adding or REMOVING a factor; `TestWall_TOTPPublicPrefixIsInert` fails the moment one appears, and `TestWall_PublicAllowlistRoutesAreDeclaredPublic` pins the general form (anything the middleware serves unauthenticated must say `Public: true` in `uiRoutes`). There is also NO in-band TOTP enrolment surface today (`SetTOTPSecret` has no production caller) — enrolment arrives only via a restored or provisioned `ui_users.json`, which is why this scores MEDIUM rather than HIGH and why the blast radius is exactly the deployment set the restore path's counter guard was built for. ## Identity-backend availability (CHAOS-47, `auth_backend_health.go`)

[Original lines 233–233](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L233-L233) · `claude-main-L233-L233`

<!-- BEGIN preserved-block: claude-main-L233-L233 -->
- **Identity-backend availability (CHAOS-47, `auth_backend_health.go`)**: the legacy LDAP and OIDC proxy-auth backends cache authentication OUTCOMES (5 min / 2 min) so a per-request-auth gateway does not re-bind or re-introspect per request. **Only an AUTHORITATIVE answer from a reachable backend is cacheable** — wrong password, inactive token, user not found, not in the required group. A failure to REACH the backend (dial refused, STARTTLS error, service-account bind failure, search error, introspection transport error, non-200 from the introspection endpoint, malformed body) is NOT: the request still fails closed, but caching it kept denying valid credentials for a full TTL *after* the backend recovered, per credential. `verify`/`introspect` therefore return an error reserved for infrastructure failure; `(false, nil)` means the backend answered "no". RFC 7662 is what makes the OIDC split clean — an inactive token is HTTP 200 + `active:false`, so any non-200 is an endpoint fault, never a verdict. On the LDAP user-bind branch only result code 49 (`invalidCredentials`) counts as a password rejection. Not caching the negative would stampede a down backend (every request paying a 10s dial timeout), so each backend carries an `authProbeGate`: unreachable arms a `authBackendProbeCooldown` (3s) window in which requests are denied WITHOUT a round trip, exactly one probe is granted per cooldown, and the gate re-arms on GRANT (not on the result) so a probe that never reports back cannot leave it open. One observed reach clears the gate for every caller. Observability mirrors `storage_health.go`: `culvert_auth_backend_unavailable{,_total}` + `culvert_auth_backend_gated_denials_total`, the `identity_backend` operator-contract row (recovery is reported on EVIDENCE — an observed reach — never on elapsed time), and a `HasSubscriber`-gated, 5-min rate-limited `identity_backend_unreachable` alert (deliberately not `idp_unreachable` — "IdP" is reserved for the federated Identity Provider registry, `auth_idp.go`, a distinct subsystem, brought under this same contract by CHAOS-49 — see below; the retired name is carried forward by `internal/alerts.normalizeEventNames`, applied at EVERY store ingress — `Init` (disk), `Add` and `Update` (admin API **and** `POST /api/config/import`) — because `HasSubscriber` compares names exactly, so a rename migrated at only one ingress silently unsubscribes a restored pre-rename config export). ## A directory that ACCEPTS and then STALLS is bounded, not hung (CHAOS-58, `auth_ldap.go`)

[Original lines 234–234](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L234-L234) · `claude-main-L234-L234`

<!-- BEGIN preserved-block: claude-main-L234-L234 -->
- **A directory that ACCEPTS and then STALLS is bounded, not hung (CHAOS-58, `auth_ldap.go`)**: CHAOS-47's provider-wide cooldown is armed from `noteVerifyError`, i.e. by the error `verify()` RETURNS — so it can only see a fault that returns. `LDAPAuth.verify` dialed with a 10s dialer timeout and then ran up to four blocking operations (StartTLS, service bind, search, user bind) with NO deadline: go-ldap's `Conn` defaults to `requestTimeout: 0` and its message loop arms a timer only `if requestTimeout > 0`, so `Bind`/`Search` waited on a bare `<-msgCtx.responses`. A directory that completes the TCP handshake and then goes silent — overloaded server, firewall dropping established flows without a reset, half-open socket after a peer reboot, hung VM — therefore blocked the REQUEST goroutine forever, with no error, counter, log line or health movement, pinning a goroutine + socket + FD + per-IP conn-limiter slot per cache-missing authentication (`verify` is reached per request from the `proxy.go` credential loop via `LDAPIdPProvider.ResolveIdentity` and `Config.VerifyAuth`). FD exhaustion is the recorded terminal state of PX-6/WK-11 and the entry point to CHAOS-54's SOCKS5 findings. **The safe pattern was already in-tree and applied to the wrong path**: the ADMIN directory-test endpoint (`ui_auth_ldap.go`) called `conn.SetTimeout`; the per-request production path did not. One directory round trip is now bounded END TO END by `ldapRoundTripBudget` (10s) — an ENVELOPE, not a per-step allowance (four per-op budgets would have summed to a ~42s worst case on a per-request path), and deliberately the SAME budget this process already gives one OIDC introspection (`http.Client{Timeout: 10s}`): two identity backends answering the same question on the same request path must not disagree about how long that decision may take, the CHAOS-53 rule applied to the credential back ends. **Two layers, NOT redundant.** (1) `conn.SetTimeout(remaining)` arms go-ldap's per-message timer, so every round trip fails with an `ErrorNetwork` that `ldapUserBindIsUnreachable` ALREADY classifies as unreachable — a stall arms the cooldown exactly like a refused dial, needing no classifier change. (2) `armLDAPConnWatchdog` CLOSES the connection at the envelope, because `Conn.StartTLS` runs its post-response `tls.Client(l.conn, cfg).Handshake()` on the RAW socket, outside the message loop and outside the timer — so a directory that ACKs StartTLS and then never negotiates TLS hangs with `SetTimeout` armed. Verified directly against the library and kept as a permanent DEFECT PROOF (`TestChaos58_SetTimeoutDoesNotBoundStartTLSHandshake`), so a go-ldap release that fixes it fails the build rather than leaving a backstop guarding nothing (the `BareGracefulStopIsUnboundedOnAWedgedStream` role). Closing is what unblocks a deadline-less read (the CHAOS-03 `idleCopyCounted` reason); it is safe because go-ldap's `Close` is idempotent via `setClosing` and `messageMutex` is released before every network wait. The admin test path gets the same watchdog under its own deliberately generous `ldapTestTotalBudget` (a diagnostic should report a slow directory, not clip it). **No new metric, alert or operator vocabulary** — a stall IS an unreachable backend and lands on `identity_backend` / `culvert_auth_backend_*` / `identity_backend_unreachable` unchanged; the one added log line carries a BOUNDED reason class (backend name + budget), never the directory address or a server-supplied diagnostic (WK-12/RS-5). The general rule, recorded as register row **AU-14**: *a cooldown, breaker or health gate armed by a returned error is blind to every fault that hangs — bounding the call is what makes the mitigation reachable.* Gates: `auth_ldap_stall_chaos_test.go` (9 — six defect gates each verified failing against the pre-fix tree, one library defect proof, two controls pinning that a healthy directory is neither clipped nor gated). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §26 and `docs/operator/ldap-directory-stalls.md`.

## Credential verification is a BOUNDED, observable resource (CHAOS-57, `internal/authcost` + `auth_cost_health.go`)

[Original lines 235–235](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L235-L235) · `claude-main-L235-L235`

<!-- BEGIN preserved-block: claude-main-L235-L235 -->
- **Credential verification is a BOUNDED, observable resource (CHAOS-57, `internal/authcost` + `auth_cost_health.go`)**: Culvert authenticates on EVERY proxied request, and when the credential is a local account that means one `bcrypt.CompareHashAndPassword` at `bcrypt.DefaultCost` — **~80 ms of exclusive CPU**, measured. That constant is a property of the DATA PATH, not of a login form, and nothing bounded it. **The cheap branch is the WRONG-username branch**: `verifyAuthWithSnapshot` ran an unconditional comparison against `dummyBcryptHash` whenever the username did not match (RISK-008's timing equaliser — it exists for a good reason), and that branch sat BEFORE the result cache and never populated it, so a flood of DISTINCT usernames was a guaranteed miss every time — no credential, no valid username, no knowledge of the deployment. The three front-door limiters that could have capped the arrival rate all ship DISABLED (`-rate-limit` defaults to 0, connlimit disabled, no IP filter), and nothing capped CONCURRENCY, so N simultaneous requests put N goroutines into bcrypt at once. Measured on the 4-core reference box: **79.6 ms/attempt vs 1.5 µs for a cached auth (51,631x amplification); 66 req/s — ~13 KB/s on the wire — consumed 100% of all four cores; other CPU work degraded 15.6x under 64 attacker connections.** The arithmetic generalises without a benchmark: **12.5 × GOMAXPROCS requests/second saturates the machine.** `internal/authcost` now governs it with two fail-closed bounds and one fairness rule: a **GLOBAL CEILING** of `GOMAXPROCS/2` (floored at 1 — half, not all, because the gateway's real work must keep running while somebody authenticates; a ceiling equal to GOMAXPROCS bounds the fault without preventing the outage, and this is the bound that holds against a DISTRIBUTED flood); a **PER-CLIENT CEILING of 1** on how many slots one source holds AT ONCE (without it the global ceiling contains the CPU but not the OUTAGE — one source occupies every slot and denies everyone else). **A client at its cap WAITS for its own earlier verification; it is NOT refused on the spot** — getting that wrong was the engine's first shape and a self-inflicted outage: a single workstation opening its ordinary parallel connection pool, all of whose cached results expired together, had **five of six VALID credentials DENIED** with no attacker present (measured on the real auth path; it surfaced as a CI determinism failure and not locally, because whether one client's parallel requests overlap depends on machine load). Waiting costs fairness nothing — the cap still bounds what a source HOLDS at any instant — and only changes what happens to the excess: serialised behind its predecessor (~80 ms each) instead of rejected. Parked waiters count against the SAME bounded waiter budget as the global queue, and the wait is bounded, so a burst deeper than roughly `maxWait / verification cost` (about a dozen from one client) still ends in a refusal. **The lesson: "one source, one slot" is a correct FAIRNESS rule and an incorrect ADMISSION rule** — fairness is about what a client may HOLD, admission about what happens to the rest; conflating them turns a bound into a denial; and a **BOUNDED WAIT (1 s) with a BOUNDED QUEUE (8× the ceiling)** so a legitimate synchronised burst is absorbed rather than refused — **the queue is capped because an unbounded one converts a CPU-exhaustion vector into a goroutine-and-memory one, and trading one exhaustion for another is not a fix.** **THE ORDER OF THE CALL SITE IS A SECURITY CONTRACT, not style** (`verifyAuthFrom`, store.go): (1) the cache is consulted FIRST and UNCONDITIONALLY, ahead of the username comparison — this changes no verdict (entries are only ever stored for the configured username, so a wrong username was always a miss) and costs the same one HMAC + map probe either way, but it means a client riding a warm cache never consumes a slot, without which a legitimate high-rate deployment would be throttled by a bound on work it is not doing; (2) **admission is decided BEFORE the username is compared and must not depend on it** — gating only the branch that reaches the real hash (the obvious fix, and the one written first) makes "over budget" FAST for a wrong username and SLOW for a wrong password, handing back exactly the username-enumeration oracle RISK-008 removed, so the bound would have been bought with the vulnerability it protects; (3) refusal is a DENY (fail closed — the cost of a spurious refusal is a 407 the client retries); (4) the slot is held across BOTH branches and released by `defer` so a panic inside bcrypt cannot leak it. Pinned by `TestChaos57_AdmissionDecisionIsUsernameIndependent`, verified failing against the asymmetric shape. **The result cache's EVICTION POLICY is a security control too**: it is populated by UNAUTHENTICATED requests (negative results are cached, deliberately) and used to drop **one arbitrary LIVE entry** at capacity, so a flood of distinct passwords under a known username displaced OTHER clients' cached positives — measured gone by a 2×-capacity flood, after which the victim paid a full bcrypt on EVERY request, landing the attacker's amplification on legitimate traffic. `internal/authstate`'s policy is ported: entries are attributed to a client key and eviction takes the **oldest entry of the client holding the MOST** (ties by oldest entry then client key — deterministic, never map order), so a flooding source evicts ITSELF and a single-entry client is untouchable until every other client is down to one. The bucket index also removes the pre-fix O(cache) expired-entry scan (64 µs per insertion under the process-wide auth mutex); **compaction keys on `len(keys)`, NOT the un-consumed window** — the trap `internal/authstate` documents, where a window-based test never fires under a sustained flood and the backing array grows with request count. The bounds are **CONSTANTS derived from GOMAXPROCS** with NO config surface (and therefore no GUI-parity obligation — recorded deferral, same class as `jwksStaleMaxAge`): a knob here could only widen a DoS window, and headroom is large and checkable (successful results cache for 5 min, so the sustained uncached rate is `active users / 300 s` ≈ 1.7/s for 500 users against ~25/s on four cores). External providers (LDAP/OIDC) BYPASS the governor — they run no bcrypt, and charging them a slot would bound the wrong resource and let a slow directory starve local authentication (their plane is CHAOS-47's `authProbeGate`). Surfaces: `culvert_auth_verify_{total,refused_total{reason},waited_total,inflight,max_concurrent,queued,saturated}` + `culvert_auth_cache_evictions_total`, the `credential_verification` operator-contract row (counts and bounds only — the client key is admin-scoped), a rate-limited `AUTH_VERIFY_REFUSED`/`AUTH_VERIFY_RECOVERED` log pair, and a fire-once-per-episode `auth_verify_saturated` alert. **Recovery requires BOTH halves of the evidence** — a FAST-PATH admission AND no refusal for `authCostRecoveryQuiet` (5s). Neither alone suffices: a queued admission proves the ceiling was still full, and a fast admission proves only that a slot was free AT THAT INSTANT. Clearing on a fast admission alone (the first shape, a Codex P1) meant that under a sustained flood — where every in-flight bcrypt releases its slot, so some arrival wins the fast path roughly once per comparison while its siblings keep being refused — the episode **restarted every ~80 ms and could NEVER reach `authCostDegradedAfter`**: the contract row flapped, an `AUTH_VERIFY_RECOVERED` line was emitted per comparison, and **`auth_verify_saturated` would never have fired for the primary attack the governor exists to expose**. This is NOT a retreat to recovery-on-elapsed-time (the `ca_health.go`/`storage_health.go` rule): elapsed time alone still clears nothing, an admission is still required, so a gateway nobody authenticates against stays reported as refusing rather than declared healthy by silence. **The lesson, twin to the per-client one: the evidence must match the claim** — "a slot was free" and "refusals have stopped" are different propositions, and the signal was keyed on the one easier to observe. **A SECOND finding inside the fix, caught in self-review:** moving the cache lookup ahead of the username comparison made a LATENT non-injective cache key reachable — `cacheKey` hashed `user + ":" + pass`, so `("admin","a:b")` and `("admin:a","b")` collide. That was unreachable while the cache was consulted only AFTER the username matched (every reachable key shared the same prefix); consulted earlier with a CALLER-CHOSEN username it is an **AUTHENTICATION BYPASS** — with a colon anywhere in the configured password, a re-split of it hits the cached positive and authenticates as a caller-controlled subject. `cacheKey` now LENGTH-FRAMES each field. The lesson generalises: **a reordering is not a refactor when a downstream invariant is holding the old order up** — the hash was safe only because of the ordering, and nothing recorded that, because at the time it was a coincidence rather than a dependency. Gates: 15 in `internal/authcost` + 19 in `auth_cost_chaos_test.go`; eleven defect gates verified failing against the shape each replaces. Deliberately left: **AU-3e**, a PRE-EXISTING username-enumeration oracle reached by REPETITION (a negative for the correct username is cached, one for a wrong username is not, so repeating the same wrong pair is ~1.5 µs vs ~80 ms) — reported, not fixed, because closing it changes a security control's behaviour and deserves its own review; the admin-UI login path (bounded by `loginLimiter` instead); and PX-6 (the front-door limiters still ship disabled — the governor bounds the flood's COST, not its arrival). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §25 and `docs/operator/credential-verification-cost.md`.

[Original lines 236–236](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L236-L236) · `claude-main-L236-L236`

- **Interactive-login callback state is bounded FAIRLY, not randomly (`internal/authstate`)**: the OIDC PKCE store (`globalPKCEStore`) and the SAML AuthnRequest store (`globalSAMLStateStore`) hold verifier/nonce/relay state for logins that have not happened yet, and they are populated by **UNAUTHENTICATED** requests — `resolveCaptivePortalURL` mints an entry on the proxy's no-credentials path (`proxy.go`, Default arm, gated only by the quarantined `browserRedirectEligibleLegacy` User-Agent heuristic), `resolveSSOPortalURL` does it on the SSORequired arm, and the public `/auth/select` page does it per render. Both stores are hard-capped at 1000. **The eviction policy is therefore a security control, not housekeeping.** Both previously evicted "one arbitrary entry" — a single-key map range, i.e. a uniformly random LIVE entry — so an anonymous client looping requests through the proxy destroyed other users' in-flight state at one entry per request and every real callback came back `invalid or expired state`: a remotely triggerable, unauthenticated **denial of SSO authentication** for the whole gateway (it failed CLOSED — no bypass — which is exactly why it was silent). Entries are now attributed to a CLIENT KEY (`authStateClientKey` → `realClientIP`, so X-Forwarded-For counts only from a configured trusted proxy; IPv6 collapsed to /64 because one host owns a whole /64; IPv4 RAW), and eviction always takes the OLDEST entry of the client holding the MOST — ties broken by oldest entry, then by client key, so the victim never depends on Go map order. **A flooding source therefore evicts ITSELF**: displacing one honest single-entry login now needs as many distinct client keys as the cap, not one host with a for-loop. TTL, cap, single-use `Pop`, and the fail-closed callback are byte-identical — fairness decides only WHO is evicted, never what is admitted. Two implementation invariants the tests pin: the per-client key list compacts on **total slice length**, not on the un-consumed window (a window-based test never fires while a client sits at the cap, so the backing array would grow with total request count — a memory leak reachable by the same flood), and eviction is **deterministic** (`TestEvictionIsDeterministic`). Surfaced on `/metrics` as `culvert_login_state_{entries,clients}` + `culvert_login_state_evictions_total{store="oidc_pkce"|"saml"}` — a climbing eviction counter is the operator's only signal that logins are being displaced before they can be redeemed. Gates: `internal/authstate/authstate_test.go` + `auth_login_state_flood_test.go`.

- **IdP-registry availability + JWKS integrity (CHAOS-49, `auth_oidc_flow.go`)**: the multi-IdP registry path now carries the SAME contract as the legacy backends above, reusing the same primitives (`authProbeGate`, `noteAuthBackend*`, `cacheKey`, `cloneIdentity`, `maxAuthCacheSize`, `errIntrospectClient`) rather than a second dialect — so registry IdPs land on the existing `identity_backend` row, `culvert_auth_backend_*` metrics, and `identity_backend_unreachable` alert with NO new config and NO new operator vocabulary (backend name = `oidc:<profile-id>`). `resolveByIntrospection` caches only AUTHORITATIVE verdicts (TTL `oidcFlowCacheTTL` 2 min, clamped to the token's declared `exp` via the shared `clampCacheTTLToTokenExpiry`), gates an unreachable IdP behind the 3s cooldown, and treats a 4xx as a client/token error that must NOT arm the provider-wide gate but MUST clear a prior cooldown. This matters more here than on the legacy path because `proxy.go` tries providers **SEQUENTIALLY** — ungated, one down IdP cost N × 10s of serialized dial timeouts per request while holding a goroutine, a connection, and a per-IP slot. **The `jwksCache` is the other half and is the more serious finding**: (1) `refresh()` must never install a key set from a non-200 or one carrying ZERO usable keys — it used to, so a rate-limiter body / edge stub / full EC rotation WIPED the cache on the SUCCESS path, which also destroys `getKey`'s "return the stale key rather than failing" fallback (a silent fleet-wide SSO outage with no log, metric, or health signal); (2) the refetch decision must key on `lastAttempt` (rate, floor `jwksMinRefreshInterval` 1 min), NOT on cache membership — the `kid` comes from an UNVERIFIED token header, so a membership-keyed refetch turned one unauthenticated request into one outbound JWKS GET per provider forever, an amplifier aimed at the customer's own IdP that ALSO fires with no attacker in any 2-IdP estate (the dispatch loop asks every provider about every other provider's token); (3) concurrent misses are single-flighted (leader publishes its error to followers). Keep `jwksMinRefreshInterval` ≪ `jwksCacheTTL` so a genuine rotation is still picked up — pinned by `TestJWKS_StaleCacheStillRefreshesAfterNegativeWindow`. All six defects were reproduced against `main` before the fix; gates live in `auth_oidc_flow_chaos_test.go`. See `docs/engineering/CHAOS-ENGINEERING-REVIEW-2026-08-11.md`. **(4) SEC-JWKS-1 — stale-key trust is CEILINGED (`jwksStaleMaxAge`, 24h):** serving a stale key past the TTL is the right degradation for an outage, but "stale" and "unbounded" are not the same posture — withdrawing a signing key from the JWKS document is the IdP's ONLY revocation lever over an already-minted token, so a cache that can never be refreshed used to keep a REVOKED key authenticating FOREVER (and the two guards in (1), correct as they are, make a persistently-failed refresh MORE likely). `getKey` now serves stale only while `staleServable(fetchedAt)` holds and otherwise fails CLOSED with `errJWKSStaleCeiling` + a rate-limited `logStaleRefusal` line (the transition from "degraded but working" to "authentication is failing" must not be silent — `refreshOnce`'s own line says cached keys are still being served, which stops being true there). Recovery is on OBSERVED evidence only: one refresh that actually returns usable keys re-arms the window by advancing `fetchedAt`; elapsed time never does (same discipline as `storage_health.go`/`ca_health.go`). The ceiling is a CONSTANT by design — an operator override would be a knob whose only use is widening a trust window. Ordering invariant `jwksMinRefreshInterval < jwksCacheTTL < jwksStaleMaxAge` and the fail-closed/availability halves are pinned by `auth_oidc_jwks_stale_ceiling_test.go`; see `docs/engineering/security-reviews/2026-08-18-mcp-pr12-and-idp-registry-window.md` and, for the operator runbook (`oidc_jwks_trust` diagnostics row, recovery steps), `docs/operator/identity-backend-availability.md`.
