## A damaged Layer-2 category store must never stop the boot (CHAOS-50, `internal/catdb/resilient.go`)

[Original lines 181–181](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L181-L181) · `claude-main-L181-L181`

<!-- BEGIN preserved-block: claude-main-L181-L181 -->
- **A damaged Layer-2 category store must never stop the boot (CHAOS-50, `internal/catdb/resilient.go`)**: the community category store is a BadgerDB directory opened on the BOOT path and enabled by DEFAULT in the shipped `docker-compose.yml` (`-cat-feed-db /data/catfeeddb`, on a service with `restart: unless-stopped`). It used to `logFatalf` on any open failure, so one torn `MANIFEST` after an unclean container kill was an unattended CRASH-LOOP — no proxy, no admin UI, no health endpoint, recoverable only by shell access — over the ONE store on that path holding no authoritative state (it is a cache of a downloadable feed; `feedsync.Start` re-syncs an empty store immediately). Worse, the fault a caller cannot handle: a corrupt `.sst` makes `badger.Open` **PANIC from a goroutine badger spawns** (`created by … newLevelsController`), so `recover()` at the call site never fires and returning the error instead of exiting would have fixed nothing. `catdb.OpenResilient` is the boot-path entry point (**direct `catdb.Open` is for callers that already know the directory is sound**): a **per-attempt, flock-OWNED poison marker** — a SIBLING of the store, armed around every attempt and cleared however it returns — turns "a previous process died inside `badger.Open`" into a signal the next boot acts on, and the directory is quarantined **before** badger touches it. A marker counts as poison only when its **flock can be taken**, which the kernel permits only once its owner is gone; it is per-attempt rather than a single shared path because a shared one cannot survive concurrency (a second booting process would clear a still-live opener's breadcrumb, and if that opener then panicked the next boot would walk into the corrupt store again — the crash loop persisting through its own remedy). Four rules keep the rename safe and must not be relaxed: (1) it **moves aside, never deletes** (`.corrupt.<unixnano>`, the CHAOS-05/07 convention, pruned to ONE copy); (2) the DIRECTORY flock — badger's own lock — is **held ACROSS the rename, not probed and released before it** (`rename(2)` does not consult flocks, so probing leaves a window in which a concurrent boot's live store is renamed away); the invariant is carried by the TYPE — `quarantineDir` takes the `*heldLock` as a required argument and refuses a released one (`errStoreLockNotHeld`); (3) a live opener's marker is NEVER touched and a skipped quarantine leaves the breadcrumbs for the next boot; (4) returned errors are matched against the ENVIRONMENTAL deny-list (lock held, ENOTDIR, EACCES, EROFS, ENOSPC, EMFILE, EIO) **before** the corruption allow-list, and anything unrecognised DEGRADES — the fail-safe default is to leave the disk alone. The outcome is reported ONCE, after it is known (a quarantine followed by a failed replacement open is a FAILURE, not a recovery — reporting the quarantine first emitted two contradictory alerts). Note for anyone extending this: **none of these faults are reachable via `errors.Is`** (badger wraps with `y.Wrapf`, no `Unwrap`), so the fault → message table is itself a test (`TestClassifyOpenError_EmpiricalBadgerMessages`) and a badger upgrade that rewords them fails the build rather than silently stopping recovery. `loadCommunityFeedDB` degrades to `communityDB = nil`, which every consumer already nil-guards — byte-identical to running without `-cat-feed-db`. Visibility reuses existing vocabulary: the `state_file_corrupt` alert (same operator action, no second dialect), a `category_feed_db` operator-contract row, and `culvert_catfeeddb_{available,recovered,quarantined_copies}`. **Deliberately NOT on `/readyz`** — Layer-1-only categorisation is a fully serving node, and failing readiness would pull a healthy gateway out of rotation over a degraded cache. `internal/logstore` shares the same uncatchable-panic exposure and is recorded, not fixed (its content is request history with retention semantics). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §19 and `docs/operator/category-store-recovery.md`.

## A damaged request-history store must never kill the process, and an encryption error must never quarantine it (CHAOS-62, `internal/logstore/resilient.go` + `internal/storeguard`)

[Original lines 184–184](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L184-L184) · `claude-main-L184-L184`

<!-- BEGIN preserved-block: claude-main-L184-L184 -->
- **A damaged request-history store must never kill the process, and an encryption error must never quarantine it (CHAOS-62, `internal/logstore/resilient.go` + `internal/storeguard`)**: `logstore.OpenTTL` carries the identical uncatchable-panic exposure as the category store above — re-measured against THIS store's options (encryption on, 128 MiB value log) a corrupt `.sst` still panics from a goroutine badger spawns. It was WORSE in two ways the CHAOS-50 register row (R-E) recorded backwards as "bounded by being opt-in". Opt-in means the toggle is DURABLE in `admin_settings.json` and re-applied by `LoadAdminSettings` on every boot, so one unclean kill is a self-latching **unattended crash loop** with no admin UI left to turn the setting off; and it means `enableLogStore` is reachable from the **LIVE admin API** (`ui_config.go`), so a damaged store kills a gateway carrying production traffic the moment an admin flips a switch — no error the handler could return, because the process is gone. `openLogStore` now goes through `logstore.OpenResilientTTL`; the caller DEGRADES (history off — the posture of a node that never had the toggle on), never exits. **The classifier is a per-store `storeguard.Policy` because of this store, and a Policy can only ever SUBTRACT** (there is deliberately no field for ADDING corruption signals — widening destruction from a call site is how a shared safety mechanism becomes an unsafe one): badger reports a CHANGED PASSPHRASE, a LOST SALT and real KEYREGISTRY damage with the SAME error on a keyed store, and CHAOS-50's table lists that message as corruption on the explicit rationale *"this store is never opened with a key"* — true there, false here — so reusing it unmodified would move a HEALTHY store aside over an ordinary config change. The exemption is expressed at BOTH layers on purpose (structurally on `ErrEncMismatch`, textually on the raw badger message) so a future change to `OpenTTL`'s error rewrite cannot silently re-arm that quarantine. Real KEYREGISTRY damage therefore does not self-heal — a recorded owner trade: of the four postures the only unacceptable one is destroying intact history to fix a configuration mistake. **`EncKey` mints a salt ONLY when there is no store it could lock us out of** (`storeHasContent`; an unreadable directory answers TRUE — refuse rather than overwrite key material on a guess): it used to mint and WRITE a fresh salt whenever the `<dir>.salt` sidecar was unreadable or short, which on the READ path destroyed the only value that could ever decrypt an existing store, surfaced as an error indistinguishable from a passphrase change, and so made the operator's remedy "purge" — the same rule `internal/alerts` already adopted as SEC-WHSIGN-1 (*a failed decrypt never mints a key*). It now returns `ErrSaltUnusable`, sidecar untouched, and the API gives that its OWN 409 naming its own REVERSIBLE remedy (restore one file) rather than inheriting the mismatch's irreversible "purge". The salt is a SIBLING of the store dir, so a quarantine leaves it in place — required in both directions: the replacement store keeps working AND the quarantined copy stays decryptable, so the evidence is readable evidence. Visibility mirrors CHAOS-50 exactly (no second dialect): `request_history` operator-contract row, `culvert_logstore_{available,recovered,quarantined_copies}`, the existing `state_file_corrupt` alert, outcome reported ONCE after it is known. **Deliberately NOT on `/readyz`** — history is a queryable convenience over traffic that is ALSO in `internal/reqlog` and `internal/audit`, both independent of this store. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §31 and `docs/operator/request-history-recovery.md`.

## Audit-log write loss is COUNTED, never silent (`internal/audit`)

[Original lines 187–187](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L187-L187) · `claude-main-L187-L187`

<!-- BEGIN preserved-block: claude-main-L187-L187 -->
- **Audit-log write loss is COUNTED, never silent (`internal/audit`)**: the JSONL file is the DURABLE compliance record — the in-memory ring holds only the newest `MaxRing` (500) entries and is wiped on restart — so `Add` must never discard a persist failure. Every entry that does not reach the file is charged to `WriteErrors()` (write error, **short write with a nil error** — the truncated-JSON-line case an `io.Writer` seam can produce — and the defensive marshal branch); only the FIRST failure is logged (a failing disk fails every write; the counter carries the magnitude), matching `internal/reqlog`'s contract. The audit log is an append-only `fileutil.RotatingFile`, NOT a `fileutil.AtomicWrite`, so the CHAOS-45 durable-write chokepoint observer never sees it — `storage_health.go`'s `init` therefore wires `audit.SetWriteFailureObserver(noteStorageWriteFailure)` explicitly to reach the same plane (degraded operator-contract row, rate-limited log, `storage_write_failed` alert, path redaction). **The observer MUST NOT call `Add`**, directly or transitively: re-entering `Add` from it recurses without bound on a persistently failing disk (the production observer is audit-free by construction; a panicking observer is contained so audit loss can never take down the admin plane it records). Persistence stays best-effort — a failing disk must not make an admin change fail — but it is surfaced on `/api/stats` (`auditLogWriteErrors`), `/metrics` (`culvert_audit_write_errors_total`), `/healthz` (added only when non-zero; never fails the probe) and the dashboard, where audit loss outranks request-log loss. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §13 (register item ST-8).

## Request-log persistence is ASYNC (`internal/reqlog`)

[Original lines 200–200](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L200-L200) · `claude-main-L200-L200`

<!-- BEGIN preserved-block: claude-main-L200-L200 -->
- **Request-log persistence is ASYNC (`internal/reqlog`)**: `Add` rings the entry in memory and enqueues it on a bounded channel; ONE drain goroutine owns the JSONL file, encodes with a reused `json.Encoder` into a `bufio.Writer`, and flushes as soon as the queue drains (so an idle proxy still gets one `write(2)` per entry — no added durability delay — while a backlogged one amortizes the syscall across the batch). Request goroutines must never marshal or `write(2)` the request log: `fileutil.RotatingFile` serializes every writer on one mutex held ACROSS the syscall and the rotation stall, so a slow volume used to cost every CONCURRENT request, not just the one being logged. Unlike syslog and logstore, the queue is a shock absorber and NOT a load shedder — the JSONL file is the durable audit record, so a full queue BLOCKS the caller (the pre-async behavior, never worse) and counts `Backpressure()`; no entry is ever dropped. Single drainer ⇒ the file stays FIFO. `Sync()` drains on demand (called by `ReadPersistent` so admin reads keep read-your-writes, and by `Close()` so shutdown loses nothing). See `internal/reqlog/persist.go` and `persist_test.go`.

## Process-log writes are ASYNC (`internal/logsink`)

[Original lines 201–201](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L201-L201) · `claude-main-L201-L201`

<!-- BEGIN preserved-block: claude-main-L201-L201 -->
- **Process-log writes are ASYNC (`internal/logsink`)**: `setupLogger` wraps the composed destination (`io.MultiWriter(os.Stdout, *fileutil.RotatingFile)`, or the `jsonLogWriter` pair in JSON mode) in `logsink.Writer`, so `logger.Printf` enqueues on a bounded channel and ONE drain goroutine owns the writers. `handleRequest` emits a line per proxied request (POLICY_ALLOW / POLICY_BLOCK / POLICY_DROP / POLICY_DEFAULT_DENY), and BOTH underlying writers were unbuffered behind mutexes held ACROSS the syscall — `log.Logger`'s own, and `fileutil.RotatingFile`'s (which also spans the remove/rename/reopen rotation stall) — so every request in the process serialized on two write(2)s. Measured (4-core, the verbatim POLICY_ALLOW line): the sink cost 2798 ns/op serial and **3204 ns/op at 4x parallel** — it got SLOWER as cores were added, i.e. a throughput ceiling, not a constant cost. Same contract as `internal/reqlog`: the queue is a shock absorber, NOT a load shedder — a full queue **BLOCKS** the caller (exactly the pre-change behavior, never worse) and counts `Backpressure()`; no line is ever dropped, and the single drainer keeps the log strictly FIFO. The drain loop flushes as soon as the queue empties, so an idle process still gets one write(2) per line (no added visibility delay) while a backlogged one amortizes the syscall. `logCloser` (returned by `setupLogger`, run last in the shutdown sequence) flushes before closing the file, and **`logger.Fatalf` is banned in favour of `logFatalf`** (logger.go) — `log.Logger.Fatalf` os.Exits immediately and would discard the queued line explaining why the process is exiting. The residual trade-off is that an ABRUPT death (SIGKILL/OOM) can lose the in-flight batch. Saturation is exported as `culvert_logsink_backpressure_total`. Pinned by `logger_async_test.go` (no loss, FIFO, flushing closer, JSON mode), `logsink_benchgate_test.go` (`TestBenchGate_LogSinkDecouplesCaller` — 64 lines against a 20 ms-per-write sink must return in ≪ 64x20 ms) and `internal/logsink/logsink_bench_test.go` (`TestBenchGateWriteAllocs`, 0 allocs/op).
