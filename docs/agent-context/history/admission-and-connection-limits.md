## A cluster rate-limit broadcast EXPIRES, and the DP→CP audit queue COUNTS what it drops (CHAOS-61, `security.go` + `cluster_ratelimit_freshness.go` + `internal/audit`)

[Original lines 182–182](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L182-L182) · `claude-main-L182-L182`

<!-- BEGIN preserved-block: claude-main-L182-L182 -->
- **A cluster rate-limit broadcast EXPIRES, and the DP→CP audit queue COUNTS what it drops (CHAOS-61, `security.go` + `cluster_ratelimit_freshness.go` + `internal/audit`)**: cluster-wide rate limiting is gossip — each DP reports hot IPs, the CP aggregates the fleet, and `AllowClusterAware` denies on `localCount + remoteCount >= limit`. `clusterCounts.Apply` is reached from EXACTLY ONE place, the gossip loop's SUCCESS branch (`rateLimitGossipLoop`); a failed `SyncRateLimits` logs and `continue`s. So the last broadcast FROZE in the map and was enforced for the rest of the process lifetime: an IP whose cluster-wide total was at or above `limit` when the CP went away — an ordinary NAT/corporate egress address, exactly the kind that gets hot — was thereafter denied on that node with `localCount == 0`. **A total blackhole for that client, on a healthy proxy, cleared only by the CP returning or a restart**, and indistinguishable in the log from a client genuinely sending too fast (`RATE_LIMITED <ip>` names the IP and nothing else). **The fix is ARITHMETIC, not posture**: `RemoteCounts` is by its own definition the total *in the current window*, so a broadcast received at `T` describes timestamps in `[T-W, T]` and at `now > T+W` every one of them has aged out — its correct contribution is zero, and serving the frozen value is a WRONG answer, not a conservative one. `clusterCountStore` stamps every applied broadcast (`appliedAtNano`, an atomic OUTSIDE the mutex so the hot path rules a broadcast stale with one load and NO lock — exactly the case where the map is not being replaced and every request would otherwise queue on the RWMutex for a value that cannot apply; `Apply` stores the stamp AFTER releasing the write lock, so a reader that sees the new stamp necessarily sees the new map). **`FreshCount(ip, now, maxAge)` is the ONLY read accessor — there is deliberately no unconditional `Get`**, so the frozen-count path cannot be reintroduced by a future caller. Three rules hold. **(1) The max-age is DERIVED from the live limiter** (`clusterRemoteCountMaxAge(rl.Window())`), never a second constant that could drift permissive against an operator-configured window. **(2) A NEGATIVE age is STALE, not fresh** — `age >= maxAge` alone reads a future stamp (clock rollback) as brand new and honours the broadcast for however far back the clock went, AND it disagreed with `clusterRateLimitFreshness`, which reports the same condition as stale; two answers to one question is the defect, so both now fail toward the LOCAL decision (caught by this sweep's own gate against the first version of the fix). **(3) Freshness is EVALUATED, never latched** (derived from the stamp on every read, the `ca_health.go` `Usable()` discipline), so recovery needs no clearing path and a wedged gossip loop still reports the truth. **The CP had been applying this exact reasoning in the other direction all along** — `rateLimitAggregator.ClusterTotalsExcluding` prunes a node that has not reported for two minutes so a dead DP's counts stop suppressing fleet traffic — so the rule existed on one side of the link and not the other, and the side that lacked it is the one that decides allow/deny on live traffic. Surfaces: `culvert_cluster_ratelimit_{remote_stale,broadcast_age_seconds,stale_episodes_total}` (emitted ONLY on a node where cluster rate limiting is ARMED — a `0` on a standalone proxy is indistinguishable from a healthy clustered node and the paging rule is `== 1`; the socks5/cluster_ca gauge precedent). **ARMED needs BOTH halves of what the request path requires** — `clusterRateLimitEnabled` (the DP gossip loop is running, so `AllowAuto` dispatches to the cluster-aware path) AND `rl.Enabled()` (`AllowClusterAware` returns true immediately when the limiter is off, before `FreshCount` is ever reached). The first version checked only the cluster flag, and `rateLimitGossipLoop` sets that unconditionally while skipping every RPC when the limiter is off — which is the DEFAULT posture (`Configure` enables only for a limit > 0) — so no broadcast could ever be applied and every freshness surface reported a permanent, un-clearable degradation on a node that is not rate limiting at all: the gauge pinned at 1, an episode counted, a warning logged, a banner shown. That is this same note's emission rule broken in its own file, applied to "is gossip running" but not to "is anything being decided" (Codex review, PR #1346). An un-armed node is therefore never `Stale` — staleness is a statement about ENFORCEMENT, not about the age of a value nobody reads — while `Applied`/`Age` stay honest so the surface remains diagnostic rather than blank, five read-only fields on `GET /api/cluster/rate-limits`, a Cluster-panel banner, and ONE log line per TRANSITION in each direction (the loop ticks every 5s; a per-tick line would report an hour-long outage 720 times). **No new alert event** — a stale broadcast is always the CP link, which already alerts and already carries the `/ready cp_poll` row; a second name for one root cause is two pages for one action. The degradation while it holds is that the cluster-wide limit becomes a PER-NODE limit (a client can use the limit on each node rather than once across the fleet) — bounded by the outage, and the correct trade against denying a client on expired data. **The same sweep closed the DP→CP audit push queue's silent drop**: the 1000-entry cap is correct (a DP that cannot reach its CP must not grow it unbounded) but it dropped with no counter, metric or log line — three hundred lines below this package's own documented contract for the durable path — and because `Requeue` PREPENDS the events that just failed to send while the trim keeps the newest, the first thing discarded is the OLDEST unsent history, i.e. the beginning of whatever happened during the outage (CWE-778). Both writers now go through one `trimPendingLocked` chokepoint so neither can drop without charging `PendingDrops()`; surfaced as `culvert_audit_cluster_push_drops_total` and `auditClusterPushDrops` on `/healthz` when non-zero. Non-zero means the CENTRALIZED trail has a gap; the node's local JSONL file is unaffected. Gates: `cluster_ratelimit_freshness_chaos_test.go` (17) — every DEFECT gate verified failing against the pre-fix tree, with `FreshBroadcastStillSuppresses`/`BroadcastAppliesForTheWholeWindow` as CONTROLS (the cheapest way to pass every defect gate is to stop consulting remote counts at all, which would silently delete the distributed rate limiter). Deliberately left: HA-1's config-staleness posture is unchanged; none of the four auxiliary DP loops back off or jitter (WK-13/HA-11, registered); `pollConfig` double-increments `failCount` (it increments, then `backoff` increments again, so the ceiling arrives in 3 failures not 6 and failover fires after 2) — recorded, not changed inside a sweep about something else. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §30 (CHAOS-61) and `docs/operator/cluster-rate-limit-freshness.md`.

## The IP filter's per-request gate is LOCK-FREE and FLAT in entry count (`security.go`)

[Original lines 239–239](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L239-L239) · `claude-main-L239-L239`

<!-- BEGIN preserved-block: claude-main-L239-L239 -->
- **The IP filter's per-request gate is LOCK-FREE and FLAT in entry count (`security.go`)**: `ipf.Allowed` is the FIRST gate on every proxied request (`handleRequest`, `socks5.go`), reached before the rate limiter, authentication, or policy. It took a process-wide `sync.RWMutex` read lock to reach its decision — including in the DEFAULT posture, where the filter is DISABLED and the lock guarded a `mode` string that never changes. `RWMutex.RLock` is an atomic read-modify-write on one shared word, so this was not a constant cost but a **throughput CEILING**, and the rate limiter sitting beside it in the same file already showed the right shape (`enabled atomic.Bool` probed BEFORE any lock). Measured (4-core Xeon, n=6, `BenchmarkIPFilterAllowed_*`): the disabled path cost **18.8 ns at GOMAXPROCS=1, 59.2 at 2, 65.0 at 4** — four cores bought **1.16x** the throughput of one, for a feature that is switched off. Two further defects rode along: every enabled-mode call spent **1 alloc / 16 B** (`net.ParseIP` + `net.IP.String()` to build a map key), and the CIDR side was a **linear scan** at ~14 ns per configured prefix — 105.9 ns at 1 CIDR, 317.9 at 16, 1042 at 64, **3785 at 256**, i.e. **3.8 µs of CPU per request** inside the request goroutine for an ordinary enterprise allowlist. `Allowed` now reads an immutable `ipFilterView` through an `atomic.Pointer` (the `internal/threatfeed` pattern): **2.3 / 1.2 / 0.6 ns** disabled (flat, scaling near-linearly: 3.8x from 1→4 cores), **0 allocs** in every posture, and the CIDR axis is **FLAT — ~55 ns at 1, 16, 64 and 256 prefixes (69.6x at 256)**. **Three invariants make it safe.** (1) The `mu`-guarded fields stay the AUTHORITATIVE write-side state, so `Add`/`Remove`/`ClearAll`/`List`/`Mode` keep their exact prior semantics — including `Remove`'s pre-existing raw-string keying, which is preserved rather than quietly fixed — and every mutator rebuilds and publishes a derived view before releasing the lock. **A mutator added without a `publishView()` call is a silent SECURITY failure, not a perf one** (a revoked allowlist entry that keeps admitting, a removed blocklist entry that keeps denying), pinned per mutator by `TestIPFilterView_EveryMutatorRepublishes`. (2) Membership is bucketed by PREFIX LENGTH — the address is masked to each DISTINCT length present and probed against a `map[netip.Prefix]struct{}` — so cost tracks the number of distinct lengths (bounded at 33 v4 / 129 v6, 2–5 in any real config) instead of the number of prefixes. (3) `prefixFromIPNet` **mirrors `net.networkNumberAndMask`**, and that is the subtle part: a network address `To4()` accepts is an IPv4 network however many bytes it is STORED in, and a 16-byte mask is re-read as its low four bytes, so `::ffff:10.0.0.0/104` behaves exactly like `10.0.0.0/8` and matches the plain address `10.0.0.1`. A naive "16 bytes means IPv6" reading gets that wrong in the FAIL-OPEN direction for a blocklist — it was written that way first and `TestIPFilterView_DifferentialAgainstLegacy` caught it. That differential test (a verbatim copy of the old `net.ParseIP` + linear-`Contains` algorithm as the oracle, over hand-picked divergence shapes plus 300 randomized filters) is the correctness spine, since the change also swaps PARSERS (`netip.ParseAddr` for `net.ParseIP`); zoned addresses are the one known divergence and are explicitly rejected to keep net's verdict, and 4-in-6 probes are `Unmap`ped for the same reason. `oddNets` carries any non-contiguous-mask `IPNet` on a linear fallback — unreachable via `net.ParseCIDR`, present so the representation change can never silently drop an entry from a security filter. **Publishing is per-MUTATION, so a LIST must be loaded through `AddAll`** — `publishView` rebuilds the whole derived view, so an `Add` loop is O(N²) (measured: 46 ms at 1k entries, 857 ms at 4k, 3.27 s at 8k, extrapolating to minutes at 100k against this list's `maxSnapIPList` cap of **2,000,000**), which would stall a boot or a snapshot apply on a legitimate enterprise allowlist. `AddAll` takes the lock ONCE, appends in one pass and publishes ONCE (8k entries: 3.27 s → 2.31 ms), returning the rejected entries so callers log them AFTER the lock is released rather than under it; all five bulk callers use it (startup `connlimit_startup.go`, `admin_settings` restore, config-version rollback — whose `List`+`Remove` clear loop is now the equivalent O(1) `ClearAll` — config import, and the CP→DP snapshot apply). `Add` still publishes per call because a single admin edit must be live immediately. Caught in review by Codex on PR #1207 and pinned by `TestBenchGate_IPFilterBulkLoadIsLinear` (ratio gate: 4x the entries must cost ≤8x — linear is ~4x, quadratic ~16x, measured 3.31x post-fix and 17.97x pre-fix) plus `TestIPFilterAddAll_MatchesAddLoop`. Gates: `TestBenchGate_IPFilterAllowedTakesNoLock` is **structural** (holds the write lock, requires `Allowed` to answer anyway — deterministic on any hardware, under `-race`, at any load), `TestBenchGate_IPFilterAllowedIsFlatInCIDRCount` is a **ratio** gate (1.01x measured, bound 4x, ~35x if the linear scan returns), and `TestBenchGate_IPFilterAllowedAllocsFree` pins 0 allocs across five postures.

## The per-IP connection limiter is SHARDED (`internal/connlimit`)

[Original lines 240–240](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L240-L240) · `claude-main-L240-L240`

<!-- BEGIN preserved-block: claude-main-L240-L240 -->
- **The per-IP connection limiter is SHARDED (`internal/connlimit`)**: `Acquire` + a deferred `Release` run on EVERY proxied request (`handleRequest`, `socks5.go`), not once per TCP connection — so on a keep-alive connection the pair is paid per request. Behind one process-wide `sync.Mutex` that was **three exclusive lock acquisitions per request** (Acquire; Release's lookup; Release's delete when the count returns to zero) on one cache line, so every request in the process serialised there regardless of which client sent it. Same shape as the `internal/threatfeed` and `internal/logsink` findings: not a constant cost but a **throughput CEILING**. Measured (4-core Xeon, distinct client IPs, `BenchmarkAcquireRelease_EnabledParallel`, n=12) the per-op cost ROSE with core count — **103 ns at GOMAXPROCS=1, 187 ns at 2, 294 ns at 4**, i.e. four cores bought 1.4x the throughput of one. Sharded (64 shards, `maphash.String` over the IP with a per-limiter random seed) it is **flat in core count — 119/131/103 ns — and four cores buy 4.6x (8.4M → 39.0M ops/s), 2.9x the old four-core ceiling**, widening on the 16/32-core hardware the appliance ships to. Three things are deliberate and recorded rather than papered over: (1) **GOMAXPROCS=1 got 15% SLOWER** — two `maphash.String` calls at ~5.5 ns, one in Acquire and one in Release (the FNV-1a loop the rate limiter uses was built and measured at 6.9 ns, ~3 ns/request worse, and not carried); a single-core box with one client is the one shape a gateway is never in. (2) Sharding spreads DISTINCT clients, so a **single NAT egress is unchanged** — `BenchmarkAcquireRelease_SingleIPParallel` pins that rather than claiming a win. (3) Shards are **padded to a cache line** (mutex + map header is 16 B, so four unpadded shards share a line): at n=10 the padding looked like noise (p=0.28), at n=25 it is decisive (−21% geomean, p≤0.005) — measured, not assumed. `maxPerIP` moved from lock-guarded to `atomic.Int64` (nothing serialises it against Acquire any more, and nothing needs to — `Enable` never touches a counter, and it still publishes the cap BEFORE the enabled flag so a reader seeing `enabled` never reads a stale cap). Every pre-existing invariant is transposed PER SHARD unchanged — the TOCTOU guard around the increment, the `cur == ctr` entry-identity check on the reject path, the `≤0` delete, and the unconditional-accounting contract that closes the #503 fail-closed/fail-open pair. **The one behavioural difference is confined to `ActiveIPs()`** (the admin API's `activeIPs` gauge): it is now a sum of per-shard snapshots — exact when quiescent, able to land between two consistent states under concurrent traffic. Gate: `TestBenchGate_DistinctIPsDoNotShareALock` holds ONE shard's lock and requires an Acquire/Release for an IP on a DIFFERENT shard to complete anyway — **structural, not timing-based** (the scaling-ratio gate was built first and rejected: its margin is too thin under `-race` on a shared runner, and a gate that can flake gets muted), with `TestBenchGate_SameShardStillSerialises` as its control so a passing gate cannot mean the lock simply stopped being taken. Both, plus `TestShard_CapIsPerIPNotPerShard` (two IPs colliding onto one shard share a lock but must NOT share a budget) and `TestShard_DistributionIsNotDegenerate`, were verified failing against a simulated collapse back to a single lock.

## The per-IP rate limiter's sliding window is a RING, so its cost is flat in the configured limit (`security.go`, `clientBucket`)

[Original lines 242–242](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L242-L242) · `claude-main-L242-L242`

<!-- BEGIN preserved-block: claude-main-L242-L242 -->
- **The per-IP rate limiter's sliding window is a RING, so its cost is flat in the configured limit (`security.go`, `clientBucket`)**: `RateLimiter.Allow` runs on EVERY proxied request (`handleRequest`, `socks5.go`) and its window maintenance was a filter-and-copy over the whole bucket (`valid := b.timestamps[:0]` … `if t.After(cutoff)`), so the per-request cost was proportional to the bucket's occupancy — which the accept test bounds by `security.rate_limit`. **That made an operator's policy setting the price of the gate**, and it was paid while HOLDING the shard mutex, so it did not merely cost its own request: it blocked every other IP hashing to the same shard (1/64 of the process's traffic). The shape is self-amplifying in exactly the wrong direction — a source already at its cap keeps sending, and every one of those requests walks the full window — so a flood degraded the gateway hardest precisely when the limiter was the control doing the work (the same lesson as the `HasSubscriber` alert-gate finding). Measured on a 4-core Xeon @2.80GHz at half occupancy (medians of n=3, `security_ratelimit_window_bench_test.go`, which benchmarks the VERBATIM pre-change algorithm in the same run so the comparison stays reproducible in-tree): **172 ns → 24.6 ns at 60 rpm, 1.38 µs → 22.2 ns at 600, 13.2 µs → 22.8 ns at 6 000, and 133 µs → 22.4 ns at 60 000** — i.e. flat, where it used to be linear. End to end, `Allow` across 256 IPs each sitting at their cap is now ~145–170 ns/op and **0 allocs/op** at both 600 and 6 000 rpm, at 1 and 4 cores. The old scan did two things linearly that neither needs to be: stamps are **appended in non-decreasing order**, so the expired entries are always a PREFIX — the survivors need no predicate test, and the copy back to index 0 existed only because a slice has no other way to drop a head. A ring drops the head by advancing an index, so each stamp is examined exactly once over its lifetime (amortized O(1)). **Three things are deliberate.** (1) The ring **grows LAZILY** (doubling, clamped to the limit) exactly as `append` did — pre-sizing to the limit is simpler and is NOT done: at 10k tracked IPs a 6 000/min policy would become ~1.4 GB of resident buckets. (2) `Allow` reads `time.Now()` BEFORE the shard lock, so arrival order is not stamp order and an inverted stamp would make prefix-expiry stop early; `add` therefore **clamps a new stamp up to the newest present**, restoring the ordering invariant by construction. The alternative — moving the clock read inside the lock — was built and measured and costs **~45% of the end-to-end gate at 4 cores (153 → 230 ns/op)** because it lengthens the critical section 1/64 of all traffic serialises on. The clamp's give-up is bounded (the gap between the clock read and the lock, microseconds, against a window in seconds) and lands **fail-CLOSED**: a clamped stamp expires no later than its true arrival, so the window can never admit past the limit. (3) `ExportHotDeltas` drops the expired prefix rather than counting past it — same verdict, less left for the next `Allow`. This is a COST change, not a POLICY change: `TestRateLimitWindow_DifferentialAgainstLegacy` pins the accept/reject verdict AND the occupancy against a verbatim copy of the filter-and-copy form over 300 randomized (limit, window, arrival-gap) shapes, with `TestRateLimitWindow_ExpiryBoundaryMatchesLegacy` covering the one verdict randomness cannot reach (a stamp landing exactly ON the cutoff — where a half-step-wrong predicate widens the window by one request per period). Gate: `TestBenchGate_RateLimitWindowIsFlatInConfiguredLimit` is a **RATIO** gate (60 vs 6 000 rpm in one run — machine-independent, no re-baselining; 0.91x measured, 84x against the reintroduced scan, bound 4x) plus `TestBenchGate_RateLimitWindowIsAllocationFree`; both were verified FAILING against the reintroduced defect, and the differential was verified failing against both a wrapped-ring growth bug and the boundary off-by-one. **The sibling finding on this path — `IsExempt` — is now CLOSED; see the next bullet.**

## The rate-limit exempt check is LOCK-FREE and FLAT in the exempt-CIDR count, and `prefixSet` is now ONE implementation serving both per-request IP gates (`security.go`, `rlExemptView` + `prefixSet`)

[Original lines 243–243](https://github.com/KidCarmi/Culvert/blob/3fcc07e7ab5d1e3bd4d19e6cadc8bb63b682f3af/CLAUDE.md#L243-L243) · `claude-main-L243-L243`

<!-- BEGIN preserved-block: claude-main-L243-L243 -->
- **The rate-limit exempt check is LOCK-FREE and FLAT in the exempt-CIDR count, and `prefixSet` is now ONE implementation serving both per-request IP gates (`security.go`, `rlExemptView` + `prefixSet`)**: `IsExempt` is the FIRST decision inside `Allow`/`AllowClusterAware`, so once an operator configures a rate limit it runs on 100% of proxied traffic (`handleRequest`, `socks5.go`) ahead of the sharded limiter. It took a process-wide `exemptMu.RLock` and then ran a LINEAR `net.IPNet.Contains` scan, which made the length of the operator's exempt list the price of the gate — and the exempt list exists precisely so that a monitoring or management range can bypass the limiter, so configuring it was the thing that made every OTHER client's request more expensive. Measured on a 4-core Xeon @2.80GHz (medians of n=3, `security_ratelimit_exempt_bench_test.go`, which benchmarks the VERBATIM pre-change shape in the SAME RUN via the `_Legacy` arms over `oracleIsExempt` — the `security_ratelimit_window_bench_test.go` convention, so the comparison is machine-independent and reproducible in-tree rather than a pair of numbers from a commit message): **59.7 ns → 3.06 ns with no exemptions, 304 ns → 66.3 ns at 16 CIDRs, 1013 ns → 64.3 ns at 64, and 3.95 µs → 63.9 ns at 256 (61.8x)** — i.e. FLAT (60–66 ns from 1 to 256 prefixes) where it used to cost ~15 ns per configured CIDR. The HIT paths move with it: a single-IP exemption 29.6 → 16.4 ns, and a CIDR hit at 256 prefixes **3907 → 65.5 ns (59.7x)**. End to end the whole `Allow` gate at four cores goes **1176 ns → 279 ns at 256 exempt CIDRs (4.2x)** and is now flat across exempt-list size (192/281/279 ns at 0/16/256) where it was 303/330/1176 — the exempt scan had been ~74% of the entire rate-limit gate. Three things are deliberate. **(1) The read path is an `atomic.Pointer[rlExemptView]` load, and the same republish contract applies as to `ipFilterView`**: a mutator added without `publishExemptViewLocked()` is a silent SECURITY failure — a revoked exemption that keeps bypassing the limiter — pinned per mutator by `TestRLExemptView_EveryMutatorRepublishes`, with `TestRLExemptView_MutatorInventoryIsComplete` failing when a new exempt-surface method appears unclassified. The view never ALIASES `exemptNets`, which matters because `RemoveExemption` compacts that slice IN PLACE (`filtered := r.exemptNets[:0]`) — safe under the old read lock, a data race without the derived copy (pinned under `-race` by `TestRLExemptView_ConcurrentReadersAndMutators`). **(2) The single-IP set is DELIBERATELY still keyed and probed by the RAW string**, not canonicalised to a `netip.Addr` the way `ipFilterView.singles` is: `AddExemption` stores `net.ParseIP(entry).String()`, so today an IPv4-MAPPED probe misses a plain-v4 exemption, and canonicalising both sides would make it HIT — which WIDENS an exemption, i.e. hands a client a rate-limit bypass it does not have. This is a COST change, not a POLICY change; pinned by `TestRLExemptView_MappedProbeStaysNonExempt` and by a differential test against a verbatim `legacyIsExempt` over hand-picked divergence shapes plus 300 randomized taxonomies. **(3) `AddExemptions` is the bulk-load primitive and its two call sites are not optional.** Publishing per entry makes a bulk load O(N²), and this list's snapshot cap is `maxSnapRateLimitExempt` (10,000), reached by the boot `admin_settings` restore (`admin_settings.go`) and by config import (`ui_config.go`) — both of which were `AddExemption` loops. Measured: per-entry publishing costs **2.99 s** to load 10,000 entries against **4.2 ms** linear, so shipping the view without the bulk primitive would have traded a per-request win for a ~700x BOOT STALL on a legitimate config. Same trap, same shape and same fix as `IPFilter.AddAll` (Codex, PR #1207); pinned by `TestBenchGate_RateLimitExemptBulkLoadIsLinear` (ratio gate, 4x the entries must cost ≤8x — measured 4.2–5.2x post-fix, 16.1x against the reintroduced per-entry publish). **The CIDR machinery is now `prefixSet`, extracted and shared by `ipFilterView` and `rlExemptView` rather than copied**: `prefixFromIPNet`'s family normalisation mirrors `net.networkNumberAndMask` in a way that is easy to get wrong in the FAIL-OPEN direction (a `::ffff:10.0.0.0/104` entry must behave exactly like `10.0.0.0/8`, including matching plain `10.0.0.1`), and a second copy is how that protection rots — the same reasoning that moved the badger recovery engine into `internal/storeguard`.
