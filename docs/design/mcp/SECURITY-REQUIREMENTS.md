# MCP Security Gateway — Security Requirements

Canonical **requirement-ID registry** for the PR-0 package. IDs are stable and referenced by
[`THREAT-MODEL.md`](THREAT-MODEL.md), [`TEST-TRACEABILITY-MATRIX.md`](TEST-TRACEABILITY-MATRIX.md),
[`ABUSE-CASES.md`](ABUSE-CASES.md) and [`IMPLEMENTATION-SLICES.md`](IMPLEMENTATION-SLICES.md).

**All requirements are `Status: Proposed`** (PR-0 is design-only; nothing is implemented). Normative
keywords **MUST / MUST NOT / SHOULD / MAY** are used deliberately. "Gate" names the slice or CI gate that
must be green before the requirement is considered satisfied. Every requirement carries: statement,
rationale, threat IDs, control owner, implementation owner, verification method, evidence required.

Column key per table: **ID · Normative statement · Rationale · Threats · Owner (Control / Impl) ·
Verification · Evidence · Gate**. Status is `Proposed` for all rows unless noted.

## MCP-PROTO — Protocol kernel (framing, bounds, version negotiation, state)

New family added by the PR-1 remediation (`PR1-READINESS-REMEDIATION.md`, finding H-2). These are the
**PR-1 Protocol-Kernel** normative limits that PR-1's acceptance criteria reference; they replace the
former undefined "protocol bounds" acceptance item and take over the *structural* parse-time bounding that
was previously conflated into `MCP-INSP-001` (semantic input inspection, PR-7) and `MCP-OPS-002` (runtime
listener/rate bounds, PR-5). The protocol kernel ships **no public listener** (PR-1); these requirements
are verified against the parser/framing/adapter code and a test harness, not a deployed endpoint.

**Numeric values are an open implementation decision ([`OPEN-DECISIONS.md`](OPEN-DECISIONS.md) D-14).**
Each limit below is a **required configurable bound** with a **safe-default** and a **hard-cap** obligation;
this package does **not** fix production default numbers without evidence.

| ID | Normative statement | Rationale | Threats | Owner (Control/Impl) | Verification | Evidence | Gate |
|---|---|---|---|---|---|---|---|
| MCP-PROTO-001 | The kernel **MUST** decode each message with a single strict JSON/JSON-RPC decoder; duplicate object keys **MUST** be rejected (or resolved by one documented, tested canonical rule), and the message forwarded downstream **MUST** be exactly the message the kernel validated (no parser differential). | A parse differential lets downstream policy see a different message than was validated → auth/policy bypass. | MCP-T-057,058,065 | Sec / Eng | Differential + malformed corpus + duplicate-key fixtures | Single-parse equivalence proof; duplicate-key rejected/canonicalized | PR-1 |
| MCP-PROTO-002 | Every inbound message **MUST** be classified as exactly one of request / response / notification per the negotiated version; ambiguous/invalid classification **MUST** be rejected with a defined error; unknown/unsupported **methods** and unadvertised/unreviewed **capabilities/extensions** **MUST** be rejected, never best-effort dispatched. | No implicit trust of unknown methods/capabilities. | MCP-T-059 | Sec / Eng | Classification + unknown-method + unsupported-extension tests | Correct class per fixture; unknown rejected | PR-1 |
| MCP-PROTO-003 | The kernel **MUST** track outstanding request IDs per session in a **bounded** table, validate ID type per spec (integer/string/null edge cases), and reject/ignore any **response** whose `id` cannot be correlated to an outstanding request in the **same** session; duplicate/absent IDs **MUST NOT** cause cross-correlation. **Correlation applies to responses only.** A JSON-RPC **notification** is one-way and carries **no top-level `id`** by definition, so it **MUST NOT** be subjected to outstanding-request correlation — doing so would reject every valid notification (cancellation, progress, list-changed). Notifications are instead validated independently: a notification that **does** carry a top-level `id` is a classification error and **MUST** be rejected (`MCP-PROTO-002`); its method token is validated per `MCP-PROTO-002`/`MCP-PROTO-014`; and it is subject to the same size/rate bounds as a request (`MCP-PROTO-006`/`008`). Where a notification references another message in its **params** (e.g. a cancellation naming a request `id`), that **param-level** reference **MUST** be resolved only against outstanding requests in the **same** session and **MUST NOT** be able to cancel or affect another session's request. | Prevent response mis-correlation / cross-response leakage and an unbounded ID table (queue vector). | MCP-T-060,071 | Sec / Eng | ID-correlation + edge-case tests | Bounded table; mis-correlation rejected | PR-1 |
| MCP-PROTO-004 | If batch messages are supported, per-element bounds and a maximum batch size **MUST** apply and amplification **MUST** be bounded; if unsupported, batch **MUST** be explicitly rejected with a defined error — never silently split or partially processed. | Batch amplification / reject-bypass. Support decision is D-14. | MCP-T-061 | Sec / Eng | Batch-policy tests | Batch bounded or explicitly rejected | PR-1 |
| MCP-PROTO-005 | Message framing **MUST** be unambiguous; truncated/partial messages **MUST** be detected and rejected after a **bounded** partial-frame buffer; the kernel **MUST NOT** block indefinitely on a partial frame. | Framing ambiguity + partial-frame buffering exhaustion. | MCP-T-062,073 | Sec / Eng | Framing + truncation + partial-frame tests | Truncated rejected; partial buffer bounded | PR-1 |
| MCP-PROTO-006 | The kernel **MUST** enforce configurable maximum **request/envelope size, JSON nesting depth, object-field and array-element counts, string length, and method-name length**, each with a safe default and a hard cap; exceeding any limit **MUST** produce a defined error and bounded cleanup. | Parse-time resource exhaustion (oversized/depth/field/string). | MCP-T-063 | Sec / Eng | Limit tests + fuzz | Each limit enforced; oversized rejected | PR-1 |
| MCP-PROTO-007 | Numeric values **MUST** be parsed into bounded types with defined overflow/precision behavior; pathological number encodings **MUST NOT** cause unbounded work or precision-driven differentials. | Numeric overflow / pathological encodings. | MCP-T-064 | Sec / Eng | Number edge-case fixtures | Overflow/precision defined; bounded work | PR-1 |
| MCP-PROTO-008 | The kernel **MUST** bound active request IDs / in-flight protocol operations per client/session, the parser memory attributable to one session, and (where enforceable) a per-message parsing time/work budget; exceeding a budget **MUST** fail closed for that session with cleanup. | Per-session resource budget (parse-time slow-input / memory). | MCP-T-073,063 | SRE / Eng | Resource-budget assertions under fuzz/load harness | Budgets enforced; session fails closed | PR-1 |
| MCP-PROTO-009 | No hostile input **MUST** cause a panic, unrecovered error, or uncontrolled allocation in the kernel; parse/adapter/framing/cancellation code **MUST** be fuzzed and **MUST** return a bounded error instead. | Crash-resistance. | MCP-T-074 | Sec / Eng | Fuzz (panic/crash detection) + race | No panic/crash on corpus; bounded error | PR-1 |
| MCP-PROTO-010 | The kernel **MUST** negotiate a protocol version from a finite, reviewed **allowlist** once at session establishment; a version outside the allowlist **MUST** be rejected (no best-effort interpretation, no silent downgrade); the negotiated version **MUST** be attached to session/decision context. | Version-negotiation confusion / downgrade. Allowlist content is D-1. | MCP-T-066,067 | Sec / Eng | Version-conformance fixtures (D-1-gated) | Allowlisted accepted; others rejected; version recorded | PR-1 |
| MCP-PROTO-011 | Each version adapter **MUST** normalize wire messages to one internal, version-agnostic representation such that downstream stages never branch on version; adapters **MUST** be proven equivalent (same normalized output for equivalent inputs) and **MUST NOT** introduce differential behavior. | Version-adapter differential. | MCP-T-068 | Sec / Eng | Adapter-equivalence fixtures (D-1-gated) | Equivalent normalized output; no differential | PR-1 |
| MCP-PROTO-012 | The protocol kernel **MUST** maintain a per-session, **immutable, opaque session context** (a protocol-layer handle that carries **no resolved identity** — identity resolution/binding is out of PR-1 scope, see `MCP-ID-008`). Lifecycle transitions **MUST** be validated (no out-of-order establishment); a cancellation **MUST** free correlation state, **MUST NOT** bypass an already-issued decision, and cancel-and-retry **MUST NOT** be a bypass; a reconnect **MUST** re-run the `MCP-INSP-008` Origin/Host check and **MUST NOT** replay/resume trust; duplicate completions **MUST** be rejected. | Protocol lifecycle, cancellation races, duplicate completion, reconnect replay — the *protocol-state* half of MCP-T-069, kept free of identity so PR-1 stays identity-agnostic. | MCP-T-069,070,071,072 | Sec / Eng | Protocol-lifecycle + cancellation-race + reconnect tests (no identity resolution) | Immutable opaque session context; races handled; reconnect re-validated | PR-1 |
| MCP-PROTO-013 | Every exceeded limit / rejected message **MUST** be handled by message class. For a message classified as a **request**, the kernel **MUST** emit a defined, bounded JSON-RPC error that leaks no internal state (no stack traces, paths, or credentials). For a message classified as a **notification**, the kernel **MUST NOT** emit any wire response — notifications are one-way, so replying both breaks conformance and turns a cheap notification flood into **reply amplification**; the rejection is instead recorded (decision event + metric) and the resources released. For a message classified as a **response** that is rejected (uncorrelated, malformed, or over-limit), the kernel **MUST NOT** emit any wire response either — answering a response creates a response-to-response feedback loop. Cleanup here is **asymmetric and the asymmetry is security-relevant**: the kernel **MUST** release the resources allocated to the **offending message itself** (buffers, partial parse state), but **MUST NOT** release an **outstanding-request** entry on the strength of an ID taken from a message it just rejected. An outstanding-request entry **MUST** be released **only after successful, trustworthy, same-session correlation**; otherwise it **MUST** be retained for its bounded timeout / session cleanup. Releasing on a partially decoded or untrusted ID would let a peer **delete a legitimate in-flight request's state by naming its ID in a deliberately malformed response** — a remote state-deletion primitive, and strictly worse than the bounded retention it would replace. An **uncorrelated** response has, by definition, no entry to release (`MCP-PROTO-003`). Only when the message cannot be parsed or classified at all may a single bounded error be emitted with `id: null`, and that path **MUST** itself be rate-bounded so it cannot become an amplification vector. The **cleanup guarantee is unconditional but SCOPED**: every rejected message, of any class, **MUST** deterministically release all resources allocated to **the offending message itself** (buffers, partial parse state, per-message allocations). It **MUST NOT** be read as session-wide cleanup: unrelated **session correlation state — in particular an outstanding-request entry the clause above protects — MUST NOT be released** on the strength of a rejected message. "Unconditional" qualifies *that the offending message is always cleaned up*, not *that everything reachable from its session is*. | Bounded, non-leaky error + deterministic cleanup. | MCP-T-057,062,063,074 | Sec / Eng | Error-shape + cleanup/leak tests | Bounded error; resources released | PR-1 |
| MCP-PROTO-014 | **UTF-8 / protocol-token handling.** (1) Invalid UTF-8 in any decoded string **MUST** be rejected. (2) Protocol **method names** and other spec-defined protocol tokens **MUST** be compared **exactly** (byte-for-byte, no normalization folding) against the supported-version allowlist. (3) Until D-1 proves that a supported protocol version permits non-ASCII method tokens, **non-ASCII protocol method names MUST be rejected**. (4) Opaque **user/server/tool identifiers** **MUST** follow their **field-specific** canonicalization rules and **MUST NOT** be globally Unicode-normalized by the protocol kernel unless the selected protocol specification explicitly requires it. This control does **not** detect, collapse, or prevent homoglyph/confusable attacks — if a later approved profile permits Unicode identifiers, confusable handling requires an **explicit field-level policy and dedicated tests** (out of scope here). | Make identifier handling explicit and safe without overstating it: invalid UTF-8 and non-ASCII/normalization-sensitive method tokens can bypass allowlist/dispatch or create a parser differential; exact comparison + non-ASCII rejection is the accurate protocol-layer control (NFC is **not** a confusable defense). | MCP-T-057,065 | Sec / Eng | Invalid-UTF-8 rejection tests; exact method-token comparison tests; non-ASCII-method-name rejection (D-1-gated); test that opaque identifiers are **not** globally normalized by the kernel | Invalid UTF-8 rejected; method tokens compared exactly; non-ASCII method names rejected pending D-1; opaque identifiers untouched by kernel-level normalization | PR-1 |

| MCP-AUTH-002 | The token audience **MUST** identify Culvert (the MCP resource); tokens for other audiences **MUST** be rejected. | No confused-audience acceptance. | MCP-AUTH-003 | Tokens **MUST** be audience-restricted to Culvert **through the authorization flow**, not by a bespoke in-token claim. (b) As the protected resource, Culvert **MUST** verify the resulting audience restriction on every request — `aud` for JWT access tokens (RFC 9068), or the introspection response's `aud` (and resource/`scope` metadata where the AS returns it) for opaque tokens (RFC 7662) — and **MUST** reject any token whose audience names the upstream business MCP server or any other non-Culvert service (ADR-0024 §D-2 items 2–3). Culvert **MUST NOT** require a non-standard resource-indicator claim inside the token. | MCP-AUTH-004 | Tokens **MUST** be short-TTL and expiry **MUST** be enforced. | Bound the stolen-token window. Repo enforces exp (`auth_oidc_flow.go:653-659`). | MCP-T-001 | Sec / Eng | Expiry tests | Expired-token rejection | PR-3 |
| MCP-AUTH-005 | The client token **MUST NOT** be forwarded unchanged upstream (no passthrough). | Isolate agent token from upstream privilege. Precedent only (`proxy.go:46-73`); net MCP impl required. | MCP-T-005 | Sec / Eng | Upstream-capture test | Upstream request carries no client token | PR-4 |
| MCP-AUTH-006 | The gateway **MUST** implement anti-replay / token-abuse defense as a layered posture — TLS every request, short TTL, audience/resource restriction, issuer/sig/exp/tenant/scope validation, introspection/revocation where applicable, client/session correlation + rate limits + anomaly signals, and **sender-constrained tokens (mTLS or DPoP) for high-risk or externally reachable profiles**. | MCP-AUTH-007 | Session/token binding **MUST** prevent cross-user session confusion. | One caller's session cannot serve another's identity. | MCP-T-008 | Sec / Eng | Cross-session tests | No identity bleed across concurrent sessions | PR-3 |

| MCP-EVENT-002 | Loss of authentication/deny/configuration/high-risk events **MUST NOT** occur silently. For the **critical write / destructive / configuration-publication / credential** action classes the decision event **MUST be durably committed — queue admission is NOT a commit; the local encrypted spool MUST CONFIRM the write (a full disk, `fsync` error or encryption-key failure is a commit FAILURE and MUST fail closed) — **BEFORE that class's own irreversible action**, because a fail-closed guarantee evaluated after the side effect is unimplementable: nothing remains to deny. **The irreversible action is class-specific and each class MUST be gated at its own:** *write / destructive* ⇒ **before the upstream call**; *configuration publication* ⇒ **before the snapshot is signed, pushed or applied** (`MCP-CPDP-001/002`, DFD-10); *credential issue / rotation / revocation / selection for a high-risk operation* ⇒ **before any broker-side materialization** — non-mutating credential **planning** (choosing identity and scope) MAY precede the commit, but **minting, rotating or revoking MUST NOT**; *state-affecting Management operation* ⇒ before the state change **and before the signed snapshot that mutation publishes is signed, pushed or applied** (DFD-3 — the approved Management mutation carries the configuration-publication class's irreversible action as well as its own). Gating only the upstream call leaves the configuration and credential classes ungated, since neither needs an upstream call to cause its side effect. The **outcome** event is emitted separately after execution and is **not** the fail-closed gate. If the decision event cannot be durably committed the operation **MUST NOT run** and **MUST fail closed AND** the system **MUST** enter the defined degraded mode with alerting (and increment an integrity-protected loss/degradation counter). **For an authentication-failure or authorization-denial event** (whose triggering request is already denied, so there is no operation to "fail closed"): if that denial event cannot be durably persisted, the system **MUST** enter the **critical degraded state**, alert, increment the integrity-protected loss counter, and **block new write/high-risk *allowed* operations until critical-event durability is restored** (unless an explicitly approved emergency policy states otherwise) — ADR-0024 §D-5 / EVENT-MODEL §4a. Read-only/low-risk classes may proceed only under an explicit degraded-mode policy with alarm + counter + bounded retry, never silently. | Critical-event durability — fail-closed and degraded-mode-with-alert are both required for critical write classes; a lost denial event triggers a durability lockout on subsequent write/high-risk operations rather than a fail-closed on the already-denied request. | MCP-T-044 | SRE/Sec / Eng | Saturation tests **per critical class, each asserting the ABSENCE OF EVERY IRREVERSIBLE ACTION DOWNSTREAM OF THAT FLOW'S COMMIT GATE — not only the action the class is NAMED after** (a flow can carry more than one class's side effect: DFD-3's approved Management mutation both changes Management state **and** publishes a signed snapshot; DFD-5's `WAL` precedes **both** broker materialization and the upstream call — asserting only the eponymous action passes an implementation that leaves that one record untouched while performing the other) — observing the error alone passes against a design that acts first and reports failure after: (a) write/destructive → **no upstream call occurred AND no broker-side materialization occurred**; (a4) spool-commit failure specifically (full disk / `fsync` error / encryption-key failure, **not** queue saturation) → same fail-closed outcome, proving the gate is a confirmed commit and not mere enqueueing; all with fail closed **and** degraded+alert; (b) **lost auth-failure/authz-denial event → critical degraded state + subsequent write/high-risk operations blocked until durability returns** | Zero critical loss; fail-closed + degraded + alert on every critical class **with every irreversible action on that class's flow proven not to have happened** (no upstream call **and** unchanged credential state / no config revision-or-push / **no Management state change and nothing signed or pushed**); denial-event loss → lockout of new write/high-risk ops until restored | PR-8 |

## Summary

**Total requirements: 91** across 16 namespaces (MCP-PROTO 14, MCP-AUTH 8, ID 8, SERVER 3, TOOL 6,
POLICY 7, CRED 6, INSP 9, EVENT 6, CPDP 3, HA 2, CONNECT 4, MGMT 4, PRIVACY 3, SUPPLY 4, OPS 4). The
MCP-PROTO family was added by the PR-1 remediation (finding H-2); the follow-up remediation added
`MCP-PROTO-014` (UTF-8/Unicode identifier handling), `MCP-INSP-009` (PR-5 listener binding, split from the
PR-1 `MCP-INSP-008` primitive), and `MCP-ID-008` (PR-3 identity binding, split from `MCP-PROTO-012`). All
`Status: Proposed`.
Every requirement maps to ≥1
threat ID (except supply-chain/ops posture requirements that are cross-cutting), a verification method, an
evidence expectation and a release gate. Uniqueness and threat-coverage are validated in
[`TEST-TRACEABILITY-MATRIX.md`](TEST-TRACEABILITY-MATRIX.md) and the Phase 5 consistency checks.
