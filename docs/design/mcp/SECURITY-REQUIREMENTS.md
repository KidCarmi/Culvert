## MCP-PROTO — Protocol kernel (framing, bounds, version negotiation, state)

New family added by the PR-1 remediation (`PR1-READINESS-REMEDIATION.md`, finding H-2). These are the
**PR-1 Protocol-Kernel** normative limits that PR-1's acceptance criteria reference; they replace the
former undefined "protocol bounds" acceptance item and take over the *structural* parse-time bounding that
was previously conflated into `MCP-INSP-001` (semantic input inspection, PR-7) and `MCP-OPS-002` (runtime
listener/rate bounds, PR-5). The protocol kernel ships **no public listener** (PR-1); these requirements
are verified against the parser/framing/adapter code and a test harness, not a deployed endpoint.

**Numeric values are an open implementation decision ([`OPEN-DECISIONS.md`](OPEN-DECISIONS.md) D-14).**
Each limit below is a **required configurable bound** with a **safe-default** and a **hard-cap** obligation;
this package does **not** fix production default numbers without evidence.

| MCP-PROTO-001 | The kernel **MUST** decode each message with a single strict JSON/JSON-RPC decoder; duplicate object keys **MUST** be rejected (or resolved by one documented, tested canonical rule), and the message forwarded downstream **MUST** be exactly the message the kernel validated (no parser differential). | A parse differential lets downstream policy see a different message than was validated → auth/policy bypass. | MCP-T-057,058,065 | Sec / Eng | Differential + malformed corpus + duplicate-key fixtures | Single-parse equivalence proof; duplicate-key rejected/canonicalized | PR-1 |
| MCP-PROTO-002 | Every inbound message **MUST** be classified as exactly one of request / response / notification per the negotiated version; ambiguous/invalid classification **MUST** be rejected with a defined error; unknown/unsupported **methods** and unadvertised/unreviewed **capabilities/extensions** **MUST** be rejected, never best-effort dispatched. **The two halves are ORDERED around negotiation:** the *envelope* decision (request / response / notification, plus `MCP-PROTO-003` ID correlation) is version-independent and MAY precede version negotiation, but **method and capability admission MUST occur AFTER the negotiated version is established** (`MCP-PROTO-010/011`) and be evaluated against **that version's** allowlist. Rejecting an unknown method before negotiation cannot implement "per the negotiated version": it refuses a method that is valid in the version about to be negotiated, and checks a version-specific method against the wrong allowlist — including on the initial handshake, where no version is established yet. **The handshake therefore needs a version-INDEPENDENT bootstrap admission BEFORE negotiation:** on an un-negotiated session the only admissible method is the `initialize` handshake that *supplies* the version, and any other method **MUST** be rejected **before** version/capability fields are interpreted or negotiation state is mutated — otherwise the kernel must either read those fields from a not-yet-admitted arbitrary method, or have no admitted handshake with which to establish a version at all (DFD-15 `CLASS` → `STRUCT` → `BOOT` → `VER` → `ADMIT`). | No implicit trust of unknown methods/capabilities. | MCP-T-059 | Sec / Eng | Classification + unknown-method + unsupported-extension tests | Correct class per fixture; unknown rejected | PR-1 |
| MCP-PROTO-003 | The kernel **MUST** track outstanding request IDs per session in a **bounded** table, validate ID type per spec (integer/string/null edge cases), and reject/ignore any **response** whose `id` cannot be correlated to an outstanding request in the **same** session; duplicate/absent IDs **MUST NOT** cause cross-correlation. **Correlation applies to responses only.** A JSON-RPC **notification** is one-way and carries **no top-level `id`** by definition, so it **MUST NOT** be subjected to outstanding-request correlation — doing so would reject every valid notification (cancellation, progress, list-changed). | MCP-PROTO-013 | Every exceeded limit / rejected message **MUST** be handled by message class. For a message classified as a **request**, the kernel **MUST** emit a defined, bounded JSON-RPC error that leaks no internal state (no stack traces, paths, or credentials). For a message classified as a **notification**, the kernel **MUST NOT** emit any wire response — notifications are one-way, so replying both breaks conformance and turns a cheap notification flood into **reply amplification**; the rejection is instead recorded (decision event + metric) and the resources released. For a message classified as a **response** that is rejected (uncorrelated, malformed, or over-limit), the kernel **MUST NOT** emit any wire response either — answering a response creates a response-to-response feedback loop. Cleanup here is **asymmetric and the asymmetry is security-relevant**: the kernel **MUST** release the resources allocated to the **offending message itself** (buffers, partial parse state), but **MUST NOT** release an **outstanding-request** entry on the strength of an ID taken from a message it just rejected. An outstanding-request entry **MUST** be released **only after successful, trustworthy, same-session correlation**; otherwise it **MUST** be retained for its bounded timeout / session cleanup. Releasing on a partially decoded or untrusted ID would let a peer **delete a legitimate in-flight request's state by naming its ID in a deliberately malformed response** — a remote state-deletion primitive, and strictly worse than the bounded retention it would replace. An **uncorrelated** response has, by definition, no entry to release (`MCP-PROTO-003`). Only when the message cannot be parsed or classified at all may a single bounded error be emitted with `id: null`, and that path **MUST** itself be rate-bounded so it cannot become an amplification vector. The **cleanup guarantee is unconditional but SCOPED**: every rejected message, of any class, **MUST** deterministically release all resources allocated to **the offending message itself** (buffers, partial parse state, per-message allocations). It **MUST NOT** be read as session-wide cleanup: unrelated **session correlation state — in particular an outstanding-request entry the clause above protects — MUST NOT be released** on the strength of a rejected message. "Unconditional" qualifies *that the offending message is always cleaned up*, not *that everything reachable from its session is*. A rejection carried on the **transport / initialize path** **MUST** additionally be **terminal**: it **MUST NOT** open or hold a legacy SSE stream, and its HTTP status **MUST** follow the terminal-status, no-pre-negotiation-stream posture owned by `MCP-PROTO-017` and evidenced in [`TRANSPORT-FALLBACK-EVIDENCE.md`](TRANSPORT-FALLBACK-EVIDENCE.md). | Bounded, non-leaky error + deterministic cleanup. | MCP-T-057,062,063,074 | Sec / Eng | Error-shape + cleanup/leak tests | Bounded error; resources released | PR-1 |
| MCP-PROTO-014 | **UTF-8 / protocol-token handling.** (1) Invalid UTF-8 in any decoded string **MUST** be rejected. (2) Protocol **method names** and other spec-defined protocol tokens **MUST** be compared **exactly** (byte-for-byte, no normalization folding) against the supported-version allowlist. (3) Until D-1 proves that a supported protocol version permits non-ASCII method tokens, **non-ASCII protocol method names MUST be rejected**. (4) Opaque **user/server/tool identifiers** **MUST** follow their **field-specific** canonicalization rules and **MUST NOT** be globally Unicode-normalized by the protocol kernel unless the selected protocol specification explicitly requires it. This control does **not** detect, collapse, or prevent homoglyph/confusable attacks — if a later approved profile permits Unicode identifiers, confusable handling requires an **explicit field-level policy and dedicated tests** (out of scope here). | Make identifier handling explicit and safe without overstating it: invalid UTF-8 and non-ASCII/normalization-sensitive method tokens can bypass allowlist/dispatch or create a parser differential; exact comparison + non-ASCII rejection is the accurate protocol-layer control (NFC is **not** a confusable defense). | MCP-T-057,065 | Sec / Eng | Invalid-UTF-8 rejection tests; exact method-token comparison tests; non-ASCII-method-name rejection (D-1-gated); test that opaque identifiers are **not** globally normalized by the kernel | Invalid UTF-8 rejected; method tokens compared exactly; non-ASCII method names rejected pending D-1; opaque identifiers untouched by kernel-level normalization | PR-1 |
| MCP-PROTO-015 | **Peer-role, requestor-scoped protocol state.** The kernel **MUST** be parameterized by **peer role** (client-facing vs upstream-server-facing) so **one** kernel implementation — one parser/framing/classification/version-adapter/bounds/cleanup — serves **both** untrusted legs; there **MUST NOT** be a second, unspecified decoder for upstream bytes. Outstanding-request / correlation / cancellation state **MUST** be keyed by at least `(session, requestor-role/direction, request-id)` with **independent per-requestor ID-uniqueness**. One direction **MUST NEVER** resolve, complete, cancel, delete, overwrite or release the other direction's state; the same JSON-RPC `id` **MAY** be outstanding concurrently in **both** directions; a cancellation references only a request issued in the **same direction** by the **owning requestor**; the `initialize` request **MUST NOT** be cancelled; a post-response cancellation is a tolerated **late race**, not a duplicate-completion fault. A peer-role method registry (`MCP-PROTO-016`) may differ in **admission** per leg, but the **security parser MUST NOT diverge**. | The design modelled the client→server envelope only; a single session-keyed table mis-correlates by construction (both peers legitimately mint `id:1`), and an unspecified second decoder for upstream bytes reintroduces the very parser differential `MCP-PROTO-001` prevents — across the two legs (#925). | MCP-T-076,059,060,069 | Sec / Eng | Requestor-direction correlation + same-id-both-directions + opposite-direction-cancellation-rejected + initialize-not-cancellable + late-cancel-tolerated fixtures; upstream-leg hostile corpus through the SAME kernel (differential assertion) | Correlation keyed by (session, direction, id); no cross-direction release; one kernel proven over both legs | PR-1 |
| MCP-PROTO-016 | **Admitted-method registry (Culvert-reviewed, not version-derived).** Culvert **MUST** admit protocol methods only from a Culvert-reviewed registry ([`MCP-OPERATION-REGISTRY.md`](MCP-OPERATION-REGISTRY.md)), **not** "whatever the negotiated version contains". | MCP-PROTO-017 | **Legacy-transport exclusion and no pre-negotiation held stream.** Culvert V1 **MUST** host **no** legacy `2024-11-05` HTTP+SSE transport pair — no SSE endpoint that emits an `endpoint` event, no paired legacy POST endpoint, no compatibility alias, and **no** configuration switch / profile flag / "allow-unknown transport era" option that could enable either (an explicit supported-transport **decision**, not an omission). The kernel/listener **MUST NOT** allocate or hold any SSE stream **before** a valid negotiated session — or other explicitly authorized stream context — exists: a GET without that context **MUST** return the spec-sanctioned terminal **`405`** (never an empty or indefinitely-held `text/event-stream`), and every security-motivated `400`/`404`/`405` rejection **MUST** be terminal such that a client's spec-mandated follow-on GET receives `405` and **zero** streams are retained. **N rejected clients MUST leave zero retained streams** (a hard invariant, not a connection-count bound; listener-side load assertion at PR-5). Preferring a `200` `initialize` **counter-offer** over a `4xx` hard reject avoids both the spec `4xx` legacy-probe trigger and the SDK catch-any app-fallback. All status/transport facts are bound to [`TRANSPORT-FALLBACK-EVIDENCE.md`](TRANSPORT-FALLBACK-EVIDENCE.md); the **sessionless / first-request** absent-`MCP-Protocol-Version` ruling is **D-1 (OPEN)** and `2025-03-26` **MUST NOT** be silently admitted. | A security-motivated `4xx` on the initialize/transport path is exactly what recruits a spec-conformant (or catch-any) SDK client into the legacy `2024-11-05` HTTP+SSE probe; if a stream is then opened/held awaiting an `endpoint` event Culvert never emits, each rejected client leaves an **unauthenticated, pre-initialize, indefinitely-held stream** (self-amplifying, MCP-T-042 class). A degraded state **MUST** carry a **scope** no wider than `(one node/DP runtime) × (one MCP capability) × (the affected durable partition)`; it **MUST NOT** propagate to another node, capability or tenant automatically, and **fleet-wide escalation MUST NOT be an automatic runtime side effect**. **The state and its scope MUST survive process restart**, reconstructed at startup from **integrity-protected local metadata** plus spool state; **a restart MUST NOT clear, erase or bypass it**, and **ambiguous or corrupt recovery metadata MUST fail toward the narrow LOCAL `critical-durability-degraded` state** — never toward `normal`, never toward a fleet-wide state. `critical-durability-degraded` **MAY** exit **only** when **all four** hold: (1) durable storage is writable; (2) critical reserved capacity is above the **reserve recovery watermark** — `P-CRIT` free bytes ≥ `reserve_recovery` × `event_critical_reserve_bytes`, a fraction **of the reserve, never of the spool**, so every accepted configuration has a **reachable** exit (a spool-relative watermark admits configurations that can never be satisfied, i.e. a permanent lockout on healthy storage); (3) a recovery/health marker is **durably committed and read back** (commit-confirmed, not enqueued); (4) the **in-process** backlog of accepted-but-not-yet-commit-confirmed critical records is within the **derived** bound `(100% − reserve_recovery)` of the reserve — derived rather than separately configured so it cannot contradict (2), and observed by a different probe than (2) so a spool with free space but unflushed in-process records does not clear the state — and exit **MUST** occur **within one bounded probe interval** thereafter. **No state, transition or configuration may permit a critical operation to run in a degraded domain without a durable event.** | A degraded state with no bounded exit is an outage; one that a restart clears is advisory, not a control; one with no scope is a fleet-wide amplifier.
