# MCP Configuration Surface Matrix

**Status: PR-0 design artifact (Proposed).** Every field in this document is a **PROPOSED** design
field for the two MCP capabilities described in [`BLUEPRINT.md`](BLUEPRINT.md) and
[`RECOMMENDED-ARCHITECTURE.md`](RECOMMENDED-ARCHITECTURE.md). None of these fields exist in the
repository today (**[FACT]** grep for an MCP/JSON-RPC listener returns zero hits — see
[`VERIFIED-REPOSITORY-CONTEXT.md`](VERIFIED-REPOSITORY-CONTEXT.md)). Nothing in this document should be
read as describing shipped behavior.

## Purpose

This matrix exists so that **no MCP configuration field is ever proposed, reviewed, or implemented
without a complete cross-surface plan.** The repository's GUI-parity mandate
(`CLAUDE.md`:123 — *"Every new CLI flag or config option MUST have a corresponding admin API endpoint
AND a UI panel/section so the user can manage it from the GUI. CLI-only features are not
acceptable"*) already forbids CLI-only configuration for the existing Secure Web Gateway (SWG)
product. This document extends that mandate, field-by-field, to the two proposed MCP capabilities and
adds the additional surfaces MCP introduces that SWG config never had to reason about (durable
decision-event pipelines, CP→DP catalog/credential revisions, per-tenant overrides, secret-adjacent
credential-profile metadata).

**A PR that introduces a new MCP config field without a corresponding row in this matrix — and,
starting at PR-1, a corresponding row in the real `configSurfaces` registry described below — is
incomplete.** The purpose of a design-time matrix is to make that incompleteness visible in review,
before the field exists in code where an anti-drift test would otherwise have to catch it.

## The anti-drift pattern this surface must follow

**[FACT]** Culvert already solved this exact problem once, for the SWG product, and the solution is a
hard architectural precedent MCP configuration MUST reuse rather than reinvent:

- `config_surfaces.go` (`configSurfaces`, lines 104–455) is a **declarative registry** — one
  `configSurfaceRow` per logical setting — that states, for every field, which of five surfaces it
  lives on and with what semantics:
  1. **Export/import** (`apiConfigExport`/`apiConfigImport`) — the full backup/restore surface.
  2. **Version-rollback** (`captureConfigBackup`/`applyConfigBackup`/`diffConfigs` in
     `configversion.go`) — a curated subset with per-field nil-skip/`[]`-wipe semantics distinct from
     export/import.
  3. **Restart durability** (`/data/admin_settings.json`, gated by `*Saved` sentinel booleans).
  4. **CP→DP sync** (`ConfigSnapshot`, `controlplane_snapshot.go`) — pushed to enrolled nodes, subject
     to `validateConfigSnapshot` DoS caps.
  5. **Snapshot-cap validation** — the per-slice/map size bound enforced before a snapshot is ever
     applied.
- The registry is **enforced, not aspirational**: `config_surfaces_test.go` reflection-walks the real
  `configBackup`, `AdminSettings`, and `ConfigSnapshot` structs and fails the build if any struct field
  is unclaimed by a registry row, or if a registry row's binding doesn't resolve to a real field
  (forward **and** reverse parity — the same two-directional pattern as the `uiRoutes`/C1 layer for
  admin API routes). Adding a config field means: add the struct field, add or extend a registry row,
  and the tests enumerate every remaining place the field still needs to be wired.

**MCP config MUST follow this pattern, not bypass it.** Concretely, when MCP configuration is
implemented starting at PR-1/PR-2:

- Every field in this matrix that reaches `Admin API` = Yes and `GUI panel` = Yes eventually needs a
  `configBackup`/`AdminSettings`/`ConfigSnapshot` struct field (as applicable) and a matching
  `configSurfaces` row. **Skipping the registry row is not an option that passes CI** — the parity
  tests are reflection-based, not opt-in.
- MCP introduces surfaces the existing five don't fully cover (durable decision-event export target,
  per-tenant override maps, credential-profile *metadata* propagation). Where an MCP field doesn't map
  cleanly onto one of the five existing surfaces, PR-1/PR-2 MUST either extend `config_surfaces.go`'s
  taxonomy (a new `fieldKind`/surface column) or introduce a parallel MCP-specific registry with the
  same enforced-parity property — never an unregistered ad hoc field. This decision is intentionally
  left open; see [`OPEN-DECISIONS.md`](OPEN-DECISIONS.md).
- The two MCP capabilities keep **separate registry rows and, if a parallel registry is chosen,
  separate registries** — a Management MCP field and a Gateway MCP field are never the same row, even
  when conceptually parallel (e.g. "listener bind address" exists twice, never once, shared).

## Doctrine reminder (do not merge the two capabilities)

Per [`BLUEPRINT.md`](BLUEPRINT.md) and [`RECOMMENDED-ARCHITECTURE.md`](RECOMMENDED-ARCHITECTURE.md),
"one Culvert platform; shared Control Plane services; SEPARATE enforcement engines and trust
boundaries":

- **Capability A — Culvert Management MCP Server** (`mcp_mgmt` namespace): `AI Client →
  /mcp/management → Culvert management`. Read-only by default; tenant-scoped; RBAC-gated; redacted;
  rate-limited; audited. No raw secrets, no command execution, no unrestricted log export, no
  production mutation until a plan→validate→approve→apply control exists (**MCP-MGMT-001**).
- **Capability B — MCP Security Gateway** (`mcp_gateway` namespace): `AI Agent → /mcp/gateway/{server-id}
  → Approved MCP Server → Enterprise System`. Owns identity, tool discovery/fingerprinting, policy
  evaluation, inspection, credential brokering, enforcement, and durable decision events.

Every row below is tagged `Capability = Mgmt` or `Capability = Gateway`. No row is shared. Where a
capability legitimately has **no** field for a requested category (e.g. Management MCP has no
outbound credential broker because it never touches upstream enterprise credentials), that is recorded
as an explicit `N/A` row rather than silently omitted, so the matrix is auditable against the full
category checklist.

### Backward-compatibility convention

Unless a row overrides it: **every field is additive, carries an `omitempty` JSON tag on the wire
struct, and an older binary that doesn't recognize the field ignores it and falls back to its
pre-existing (safe) behavior.** This directly mirrors the repo's existing precedent for
`decryptprofile.OnInspectError`: *"an additive persisted profile field (`omitempty`) that degrades to
fail-close on downgrade (old binary ignores the unknown key)"* (`CLAUDE.md`, Adaptive decryption
exclusion). For MCP this means: a downgraded/older Gateway node that doesn't understand a new
inspection-limit or policy field must fail closed (deny/quarantine), never silently widen behavior —
the same asymmetry `MCP-CRED-006`'s broker failure matrix already requires for credentials. Rows where
the safe direction on downgrade is anything other than "ignore and keep prior safe default" say so
explicitly in their `Backward compatibility` cell (marked `Override`).

### Secret handling

Per **MCP-CRED-004** (*"Secrets MUST NOT appear in logs, metrics, traces, errors or decision
events"*) and **MCP-EVENT-003** (*"Events MUST NOT store raw tokens, upstream secrets, private keys,
complete raw arguments or complete raw outputs by default"*), **no field in this matrix carries secret
material.** Credential-profile fields carry only profile IDs, environment/server/tool-class/
resource-scope metadata, and provider references (Vault path, KMS key ID, workload-identity binding) —
never the resolved secret value, never a ciphertext blob synced over `ConfigSnapshot`. This mirrors the
existing durability precedent: `/data/admin_settings.json` is `0600`, and where secret-adjacent
material genuinely must persist, `internal/secret`'s KEK/provider containment model
(`ADR-0007-secret`, cited as reusable prior art in
[`AUTH-AND-CREDENTIAL-MODEL.md`](AUTH-AND-CREDENTIAL-MODEL.md) §7.2) is the intended containment layer
— not a new ad hoc encryption scheme. `internal/redaction` (fail-closed `DataClass`) is the intended
reuse target for output/event redaction profiles referenced below.

### Implementation sequence reference

`PR-1` Protocol kernel · `PR-2` Registry & catalog · `PR-3` Identity principal · `PR-4` Credential
broker · `PR-5` Observe runtime · `PR-6` Policy engine · `PR-7` Inspection · `PR-8` Durable decision
events · `PR-9` API & GUI · `PR-10` CP/DP & HA · `PR-11` Shadow & canary · then a separate
**Production Qualification** gate (no PR-12).
