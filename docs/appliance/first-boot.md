# Culvert appliance — first boot and the operator journey

This is the customer-facing sequence from import to an enforcing gateway. Each
step says what the appliance does automatically and what the operator does.
The mechanics behind steps 4–6 are `scripts/install.sh` (unchanged) driven by
[`appliance/provision/culvert-firstboot.sh`](../../appliance/provision/culvert-firstboot.sh).

## The nine steps

### 1. Import the OVA
[`hypervisor-install.md`](hypervisor-install.md). Verify the `.ova.sha256` and
`build-info.json` first.

### 2. Configure resources and network
Accept the defaults (2 vCPU / 4 GB / 40 GB thin) or size up. Map the single NIC.
Set the OVF properties: an **SSH public key** (`public-keys`) for the `culvert`
administrator, optionally a console `password`, and `culvert.net.*` for a
static address. Nothing else is required.

### 3. Boot and discover the address
Power on and watch the VM console. Boot sequence:

1. systemd regenerates `/etc/machine-id`; cloud-init (OVF datasource via
   `guestinfo.ovfEnv`, or the OVF ISO on VirtualBox) sets the hostname,
   installs the SSH key, sets the console password, generates fresh SSH host
   keys (ed25519 + ecdsa), configures DHCP, grows `/` to the disk size.
2. `culvert-firstboot.service` runs (after cloud-init and Docker):
   `ovf` → `console` → `images` → `install` → `complete`, each recorded in
   `/var/lib/culvert-appliance/state/<step>.done`.
3. The console banner (`/etc/issue.d/50-culvert.issue`, refreshed every
   minute by `culvert-issue.timer`) shows the version, **management URL**,
   proxy URL and state: `provisioning (running)` → `services running — setup
   pending` → `setup complete …` → `ready to enforce`.

Address discovery: console banner, vSphere VM summary (open-vm-tools), or your
DHCP server's lease table (hostname `culvert-appliance` unless set).

### 4. Storage initialisation (automatic)
`images`: `docker load` of the pre-baked `culvert.tar.gz` / `clamav.tar.gz`
(`/var/lib/culvert-appliance/images/`); the loaded proxy image's identity is
compared with the manifest's pinned index digest and the step fails if it
differs. `install`: `install.sh` creates `/srv/culvert` (compose files and
maintenance-agent packaging extracted from the image's `/app/deploy` bundle)
and starts the stack; Docker creates the `proxy-data`, `clamav-db` and
`culvert-backups` volumes on the appliance disk. **The ClamAV sidecar downloads
~250 MB of signatures on this first start** — the proxy waits for it (compose
`depends_on: service_healthy`, up to 330 s); if the download stalls because
outbound access is missing, `install.sh` fails and the step is retried
(see "If first boot fails").

### 5. Identity and secrets (automatic, per instance)
Generated on the appliance and never shipped:
* `/srv/culvert/.env` — `CULVERT_CA_PASSPHRASE` and `CULVERT_LOG_PASSPHRASE`
  (40-char random; `install.sh` non-interactive default), written once and
  **never overwritten** on re-runs (`env_put` keeps existing values).
* The SSL-inspection Root CA (`/data/ca.bundle` in `proxy-data`, encrypted
  with that passphrase) and the admin-session signing key — generated by the
  proxy on its first start.
* SSH host keys and machine-id (cloud-init/systemd), the console credential
  (see step 3 / "Console access").

Back up `/srv/culvert/.env` together with any backup of the data volume: a
restored volume without the original passphrase cannot decrypt the CA
(`install.sh` warns about exactly this case).

### 6. Enrol the first administrator
Browse to `https://<address>:9090`. The admin UI serves a **self-signed**
certificate at this point (accept the warning once). The setup wizard
(`/api/setup/*`) creates the first admin account — there is no default
password.

The wizard asks for the per-instance **setup token**. First boot mints it
(32 hex characters), `install.sh` persists it in `/srv/culvert/.env` as
`CULVERT_SETUP_TOKEN`, and it is shown on the VM console at the end of
provisioning and by `sudo culvert-status` (root only, while setup is
pending). The proxy refuses `POST /api/setup/complete` without the matching
`X-Culvert-Setup-Token` header (403; wrong tokens count towards the login
lockout), so whoever reaches port 9090 first on the network cannot claim the
appliance — the credential is on the console/SSH path, which is the one the
operator already controls. It is a one-time gate: once the first admin exists
`/api/setup/complete` is closed regardless of the token. `culvert-status`
moves from `setup pending` to `setup complete`.

### 7. Management TLS
Replace the self-signed admin-UI certificate with one from your PKI:
* **Preferred — admin UI → Certificates → upload UI certificate/key** (`POST
  /api/certs/upload`, target `ui`). The pair is persisted in the `proxy-data`
  volume (`ui_tls_custom.go`) and survives restarts and release upgrades
  without touching compose.
* **Alternative — files + flags:** place the pair on the appliance, bind-mount
  it and add `"-tls-cert", "/etc/culvert/tls/ui.crt", "-tls-key",
  "/etc/culvert/tls/ui.key"` to the proxy `command` in
  `/srv/culvert/docker-compose.yml` (the flags are `-tls-cert`/`-tls-key`, or
  `proxy.tls_cert`/`proxy.tls_key` in `config.yaml`; `main.go`). Note the
  maintenance agent recreates the proxy from `docker-compose.yml` plus at most
  one override file (`compose_override_file`, used for the agent socket), so
  prefer the UI upload.

Clients that will be SSL-inspected must trust the appliance **Root CA**
(admin UI → Certificates → download CA); that is a separate certificate from
the management TLS one.

### 8. Policy and enforcement check
Create at least one access rule (default is deny), point a test client at
`http://<address>:8080` (or the PAC at `http://<address>:8080/proxy.pac`) and
confirm the decision in Live Feed. `culvert-status` reports **ready to
enforce** when `/ready` is 200 with `policy_loaded=ok`, `policy_posture=ok`
and the CA row `ok`.

What the fresh appliance enforces, and why:
* **Policy posture is default-DENY.** `install.sh` is run with
  `CULVERT_INSTALL_DEFAULT_ACTION=deny`, which persists `CULVERT_DEFAULT_ACTION=deny`
  into `/srv/culvert/.env`; the proxy applies it only when `config.yaml` sets no
  `default_action`, and a choice saved later in the admin UI wins. Without it an
  empty rulebase is **allow** (passthrough) — the gateway would forward
  everything until the first rule was written.
* **Proxy authentication is `defaultAuthOutcome=Exempt`** (unmatched traffic is
  not challenged for credentials) until you configure an identity source. The
  appliance ships no directory binding, so a `Default` (require-auth) posture
  would have no backend to answer and every client would be refused with 407 —
  default-deny on the policy side is what keeps the open auth posture safe: a
  request that is not authenticated is still not *allowed* unless a rule says
  so. Switch to `Default` from Authentication → Default outcome once LDAP/OIDC
  is enrolled; `policy_posture` and the `setup_complete` readiness rows do not
  change.

### 9. Reboot and verify
`sudo reboot` from the console or SSH. After boot the stack starts on its own
(`restart: unless-stopped`), `culvert-firstboot` does **not** re-run
(`complete.done` present), and `culvert-status` must show the same state as
before. This is also the moment to take the first VM snapshot/backup.

## Console access and SSH

* Console user: `culvert`. Credential precedence at first boot:
  * OVF/cloud-init `password` supplied → that password; `sudo` asks for it.
  * otherwise an SSH `public-keys` key supplied → the password stays **locked**
    and first boot installs `/etc/sudoers.d/95-culvert-keyonly`
    (`NOPASSWD`): the SSH private key *is* the per-instance credential, and a
    sudo rule demanding a password nobody was given is a lockout, not a
    control (the same posture as Ubuntu cloud images). To return to
    password-gated sudo: `sudo passwd culvert && sudo culvert-sudo-policy
    require-password` (it refuses while the account has no usable password, so
    the switch can never strand you). `culvert-sudo-policy status` shows which
    policy is in force; `culvert-status` prints it too.
  * otherwise a **one-time random password** is printed on the VM console once
    and must be changed at first login. It is never written to disk. First boot
    records that a mint is in progress before it sets the password; a boot that
    dies between setting it and printing it mints a *new* one on the next run
    instead of treating the never-shown password as a credential.
* SSH: `AllowUsers culvert`, keys only, no root, no passwords, no forwarding
  (`/etc/ssh/sshd_config.d/50-culvert.conf`). Inject keys via the OVF
  `public-keys` property or cloud-init `user-data`. To add a key later:
  console login → `sudo tee -a /home/culvert/.ssh/authorized_keys`.
* Host firewall (nftables): inbound 22/8080/9090 only (`hypervisor-install.md`).

## Required outbound access

First boot and routine operation need outbound **HTTPS (443)** to:

| Host | Why | When |
|------|-----|------|
| `database.clamav.net` (via `clamav/clamav` freshclam CDN, may redirect) | ClamAV signature database | first start (~250 MB) and daily refresh |
| `catalog.culvertlabs.com` | signed release catalog (`CULVERT_RELEASE_CATALOG_URL` default) | at proxy start + every ~6 h; Release Management |
| `ghcr.io` (+ `pkg-containers.githubusercontent.com`) | proxy image pulls for day-2 upgrades | upgrades only (the pilot image is pre-baked) |
| `fulcio.sigstore.dev`, `rekor.sigstore.dev`, `tuf-repo-cdn.sigstore.dev` | cosign verification of the proxy image before the host-root maintenance agent is installed (`install.sh` trust gate) and of upgrade images | first boot, upgrades |
| `github.com`, `objects.githubusercontent.com` | signed-release download fallback for the maintenance agent (only if the image bundle cannot be trusted) | fallback only |
| `archive.ubuntu.com`, `security.ubuntu.com` (HTTP/HTTPS) | guest-OS security updates | daily (unattended-upgrades) |
| `download.docker.com` | Docker engine updates (`culvert-os-update docker`) | operator-driven |
| threat-feed and category-feed origins (URLhaus, OpenPhish, the UT1 tarball, the signed SaaS feed) | content filtering data | periodic — see `docs/operator/threat-feed-freshness.md` |
| NTP | the catalog's `expires_at` is checked against the local clock | always |

If Sigstore is unreachable at first boot, the proxy still starts; only the
maintenance agent (Release Management → "Agent unreachable") is skipped, and
`install.sh` says so. Re-run `sudo systemctl restart culvert-firstboot` once
egress is fixed (idempotent), or `cd / && sudo bash
/opt/culvert-appliance/bin/culvert-install.sh` with the same environment the
first-boot service sets (`CULVERT_DIR=/srv/culvert`,
`CULVERT_PROXY_SEED_REF=ghcr.io/kidcarmi/culvert:v1.0.259`,
`CULVERT_INSTALL_ASSUME_DOCKER=1`). Air-gapped operation is not qualified.

## If first boot fails

* `sudo culvert-status` names the failed state; `sudo journalctl -u
  culvert-firstboot` and `/var/log/culvert-firstboot.log` carry the
  `install.sh` output.
* The service retries on failure every 2 minutes (up to 5 times per hour);
  `sudo systemctl restart culvert-firstboot` resumes at the first undone step.
  Completed steps are never repeated and established secrets never regenerated.
* Common cause: no outbound HTTPS (ClamAV download → compose `--wait` timeout).
  Fix egress, then restart the service.
* **Maintenance agent not installed** (`culvert-status` → `Maintenance agent:
  NOT installed (<reason>)`; Release Management shows *Agent unreachable*): the
  proxy is complete, but `install.sh` could not verify the image signature it
  trusts the host-root agent from (Sigstore/cosign or GitHub unreachable at
  first boot). This is recorded in `state/agent.pending`, never claimed as
  done, and `systemctl restart culvert-firstboot` does **not** retry it
  (`complete.done` is present, so the unit's condition fails). Fix egress,
  then run the explicit repair: `sudo culvert-firstboot --repair-agent`. It
  re-runs `install.sh` under the first boot's exact environment (idempotent;
  nothing in `.env` is rewritten), re-verifies the unit + enabled state +
  binary, and clears the pending record only on that evidence.

## Cloning / templating an appliance

Do **not** clone a booted appliance as-is: the clone would share the
machine-id, SSH host keys and — because application state is kept — the Root
CA, admin accounts and `.env` secrets. Run `sudo culvert-appliance-reset-identity
&& sudo poweroff` first; the clone regenerates machine-id, host keys, the
cloud-init instance and re-runs the `ovf`/`console` first-boot steps while
keeping `/srv/culvert` and the data volume. Rotate the Root CA and admin
credentials on the clone if it must not share trust with the original. For a
fresh identity *and* fresh application state, import the OVA again instead.
