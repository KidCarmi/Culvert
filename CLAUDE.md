# Culvert

Enterprise-grade open-source HTTP/HTTPS/SOCKS5 forward proxy written in Go.
Single binary, zero runtime dependencies.

non-commit is provable only with a complete ring, no reset, absence AND a moved fence — and, round 2, HISTORY CONTINUITY: the GET's durable `historyIncarnation` epoch identity — rotated by profile delete/recreate and by a history reset — must equal the one the marker was dispatched in, else the operation stays unresolved and the re-send is refused on both sides (`409 history_incarnation_mismatch`); "currently active" is derived from the committed revision's `storeRevision` + spec digest against the authoritative active store, never from `activeN`; and, round 3, the epoch is a DURABLE TRANSITION OF THE OBSERVED ACTIVE IDENTITY — `LifecycleStore.ObserveActive` runs on every lifecycle read/operation and ROTATES `historyIncarnation` on an observed rewind or same-revision spec replacement by ANY writer (replace import, config rollback, CP→DP snapshot), evidence preserved; `expectedActiveSpecDigest` is an independent publish/rollback fence; a profile delete records `DeletePending` durably BEFORE the active delete and a recreate mints its epoch BEFORE the active create; an identity that could not be made durable is reported "" and the frontend withholds dispatch; and, round 4, ONE PAC WRITER TRANSACTION BOUNDARY — every writer of the active profile store (lifecycle publish/rollback, CRUD, config import, config-version rollback, CP→DP snapshot apply) builds its candidate AND commits it under `pacProfilesAPIMu` (bulk writers via `pacProfilesWriterLock`; lock order `objectReferenceMutationGate` → `configRollbackMu` → `pacProfilesAPIMu`, taken last), and the lifecycle commit is additionally a store-GENERATION compare-and-swap (`ProfileStore.SetIfGeneration`, `409 concurrent_write` when a writer outside the boundary intervened — nothing written); a profile create is a RECOVERABLE two-write transition (`PrepareCreate` records `CreatePending` + `PreparedIncarnation` beside untouched evidence → active create → `FinalizeCreate`; a refused create withdraws, a crash is finished at the next access/boot); and, round 5, A REFUSAL IS TERMINAL ONLY ONCE DURABLE AND A COMMIT IS ATTRIBUTED BY WRITER IDENTITY, NEVER BY CONTENT — the profiles file carries PER-PROFILE provenance `profileWriteIds` (round 6 — profile id → identity of the writer that last CHANGED that profile, co-written in the same atomic write: the lifecycle commit stamps its operationId on its target via `ProfileStore.CommitIfGeneration`, the same generation CAS plus the identity; any other writer stamps a fresh random id on each profile whose content it changed and PRESERVES the provenance of every profile it left untouched, so a pool-only or unrelated-profile write never erases a commit's provenance; a document-level identity was NOT sufficient — it was replaced by any unrelated write and a genuine commit was then reconciled as refused); `pacClassifyReconcile` attributes a content-level "committed" verdict to an intent ONLY when the TARGET PROFILE's provenance (`ProfileWriteID`) is its operationId (another writer's identical content ⇒ the durable `concurrent_write` refusal, an unknown identity ⇒ ambiguous, never a guessed commit); `pacWriteConflict` answers `409 concurrent_write` only after the decision record persisted, else the NON-TERMINAL `500 outcome_unknown` + `detail: refusal_not_durable` (the browser keeps its marker, the pending intent stays the durable truth, reconciliation settles it as the same refusal and a repeat of the operationId replays it); and, round 7, AN UNRESOLVED LIFECYCLE INTENT IS SETTLED DURABLY BEFORE ANYONE CHANGES ITS PROFILE — `pacSettlePendingBeforeWrite` runs in every writer (CRUD, config import, config-version rollback, CP→DP snapshot) under `pacProfilesAPIMu` immediately before its write: for every profile whose PRESENCE or content the writer changes — removed, content-changed, and (round 8) candidate-only ADDED, the deterministic union of `pacChangedProfileIDs`; an absent profile can still carry a durable pending first-publish intent — a pending intent is reconciled node-locally (a genuine commit ⇒ durable COMMITTED + history revision; a non-writer ⇒ durable aborted/refused/ambiguous) and the durable truth is re-read; an intent still pending is NOT settled and the writer is refused (CRUD `503 lifecycle_unsettled`) or deferred (import `pac_profiles_not_applied`, rollback error, snapshot next sync) with nothing written — historical authorship is never inferred from current content or the current last writer, and untouched profiles/pools are never blocked); see Architecture Notes); the 2F-F Upstream surface at `/app/network/upstream` — `frontend/src/features/network/upstream/` + `src/api/upstream.ts` — is a typed client over the frozen 2F-C/2F-D upstream v2 contract (`ui_upstream.go`): the credential-free read model through fail-closed decoders (an entry carrying credential material is REFUSED, never rendered), bounded structured refusals rendered as server facts (never re-worded), create fenced on the DOCUMENT revision, update/delete/credential on the ENTRY revision, T2 replace (password once, body only) and T3 clear (exact entry id retyped), admin-only mutations with a complete viewer posture, and NO client-side persistence (the read model is the only truth); the real-binary journeys found that `upstreamMutate` wrote the status before the Content-Type so every 2xx mutation answer was sniffed `text/plain` — corrected (type set before `WriteHeader`), pinned by `upstream_mutation_content_type_red_test.go`; and the FRONTEND invariant behind it (2F-F correction round): a 2xx whose media type, JSON or ACTION-SPECIFIC evidence cannot be verified is UNPROVEN — never a success, never a failure — the ceremony closes, the page latches, every mutation and the probe are blocked, the read model is re-read once (a transport death requires the operator's Refresh) and the latch clears only after a genuine read-back; every mutation wrapper binds its 2xx to the action (`entry` identity/authority/state, `deleted`, `ok`+`summary`), and a refusal is a verdict only with its contracted status + typed allowlisted facts (`REFUSAL_CONTRACT`), no server string ever rendered; ## Key Environment Variables

- `CULVERT_CA_PASSPHRASE` — CA private key encryption passphrase (required for SSL inspect)
- `CULVERT_DATA_DIR` — startup-scoped override of the persisted-state root (`dataDir`, default `/data`: admin settings, object stores, PAC profiles, CDR state, config versions, audit/log stores, backup/restore/prepare-downgrade). The defaults that were historically literal `/data/...` values — the config-version store, `registry_settings.json`, the CDR certs root and `cdr_enabled` marker, the alert retry queue, the CDR store files, the reset-password roster default — are re-bound to the effective root by `rebindDataDirPaths` in the same step (PR-C1b), so an override moves ALL persisted state, never part of it. Unset/blank ⇒ `/data`, byte-identical to a build without the override; otherwise an ABSOLUTE, cleaned, non-root path (a relative path or `/` is FATAL at boot — booting on the default while the operator asked for another root would persist state where nobody looks). Read ONCE in `main()` before flag parsing and before any one-shot command (`applyDataDirFromEnv`, `data_dir.go`), so every consumer sees one value for the life of the process; logged once at startup when overridden. Env-only and startup-scoped — a recorded GUI-parity deferral of the same class as the HA-lease endpoints (the root cannot be moved by the process persisting into it). Added in the Batch 2 PR correction round (PR-C1): the real-binary browser smoke depended on a writable `/data`, which a CI runner's unprivileged user does not have, so every `/data`-backed mutation answered `persist_failed`/503 while root-run qualification passed; `frontend/scripts/e2e-smoke.sh` now gives each appliance instance its own root under the harness tmp dir (hermetic on any host, for any user).
- `CULVERT_C2_ENFORCE` — C2 metadata-driven RBAC mode. Default = enforce (fail-closed). Set to `false`/`0`/`no`/`off` to revert to shadow (log-only) mode without rebuild. Read once at startup.
- `CULVERT_EXPERIMENTAL_UI` — arms the new React/TypeScript admin frontend (`frontend/`, ADR-FE-001) at `/app/` + `/assets/`. Default OFF (unset ⇒ both routes 404, byte-identical to a build without the feature); the legacy `static/index.html` keeps serving `/` regardless. Read once at startup (`ensureFrontendV2`, `ui.go`); no YAML/CLI equivalent — development/preview flag only, not yet a supported production surface (see `docs/design/FRONTEND-MIGRATION-PLAN.md`). Report-only `frontend_v2` row on `/ready` when armed.
- `CULVERT_CLUSTER_GRPC_COMPRESSION` — opt-in gzip on the CP↔DP config-sync gRPC stream. Default **off** (fail-safe): only `true`/`1`/`yes`/`on` enable it. When off, the raised `maxClusterGRPCMsgSize` (128 MiB) frame alone carries a full ConfigSnapshot uncompressed (a 2 M-host blocklist ≈ 60 MiB), so large snapshots sync without compression. ## Code Conventions

- **Package**: Everything is `package main` (flat layout)
- **Go version**: 1.26 (go.mod; bumped from the prior 1.25.12 govulncheck pin as a side effect of the go.etcd.io/etcd/server/v3 v3.7.1 dependency update, which raised its own minimum Go requirement)
- **Logging**: Use `logger.Printf()`, never `log.Printf()` or `fmt.Printf()`
- **User input in logs**: Wrap with `sanitizeLog(s)` and use `%q` format verb (CWE-117 prevention; sanitizeLog's leading `strings.ReplaceAll` is the sanitiser CodeQL recognises — it is the FIRST statement and therefore on every return path, and it must stay that way: see the single-pass note in Architecture Notes)
- **CodeQL compliance**: For values that flow through objects (e.g. `rl.Limit()`, `added.Priority`), inline `strings.ReplaceAll` or `fmt.Sprintf` + `strings.ReplaceAll` at the call site so CodeQL sees the sanitiser
- **SSRF guards**: Inline `url.Parse` + scheme check + `isPrivateHost()` before outbound HTTP requests so CodeQL can verify the guard; do not rely solely on wrapper functions like `validateExternalURL()`
- **HTTP contexts**: Use `http.NewRequestWithContext()`, never bare `http.NewRequest()`; use `HandshakeContext()` not `Handshake()`; use `DialContext()` not `DialTimeout()`
- **Errors**: Return `fmt.Errorf("context: %w", err)` for wrapping
- **Concurrency**: Use `sync.RWMutex` for read-heavy stores, `atomic` for counters
- **Security**: SSRF checks via `isPrivateHost()` before any outbound dial
- **Tests**: Test files use `_test.go` suffix, same package (whitebox)
- **Lint suppressions**: Use `//nolint:errcheck` with reason comment; `// #nosec G402` for gosec
- **GUI parity**: Every new CLI flag or config option MUST have a corresponding admin API endpoint AND a UI panel/section so the user can manage it from the GUI. CLI-only features are not acceptable — the admin must have full control from the web interface.
- **API pattern**: Admin API handlers follow `apiXxx(w, r)` naming, registered through `register*Routes` helpers and represented in `uiRoutes` metadata (`ui_routes_meta.go`). Use `requireRole(w, r, "admin")` for write operations, `requireRole(w, r, "viewer")` for reads — handler-level RBAC stays as defense-in-depth even with C2 active.
- **UI pattern**: SPA panels in `static/index.html` use `data-view="name"` attributes. New panels need a nav-item in the sidebar, a view div, and JS load/render functions.
- **Config versioning**: Config-mutating API handlers must call `saveConfigVersion(actor, action)` after `auditEvent()` to create automatic snapshots.
- **Range iteration**: Use index-based range (`for i := range slice`) for large structs (PolicyRule 240 bytes, EnrolledNode 176 bytes) to avoid `rangeValCopy` gocritic warnings.
- **gosec G117**: Avoid struct field names or JSON tags matching secret patterns (e.g. `secret`, `password`, `token`). Rename to non-matching names (e.g. `SessionHMAC` instead of `SessionSecret`).
- **gosec G124**: When cookies use dynamic `Secure` flag (e.g. `isSecureRequest(r)`), suppress with `// #nosec G124 -- dynamic Secure flag`.
- **Cyclomatic complexity**: Keep functions under cyclop threshold of 15. Extract helpers for complex switch/if chains.
- **`upstreamTransport` is read-only after publication**: the shared upstream `*http.Transport` is owned by `upstream_transport.go` (P5.3 / S6). Read via `getUpstreamTransport()`. Mutate via `swapUpstreamTransport(update)` only — the update closure builds a NEW `*http.Transport` (use `cloneTransport` + `cloneTLSConfig`) and MUST NOT mutate its input. Direct field assignment on a loaded transport (`getUpstreamTransport().Proxy = …`, including the local-variable bind form `t := getUpstreamTransport(); t.Proxy = …`) is forbidden — it races against the proxy hot path's reads.

## Architecture Notes

- **Default deny**: Policy engine defaults to deny when no rule matches (Zero Trust)
- **SSL inspect**: MITM via on-the-fly leaf certs signed by internal CA (ECDSA P-256)
- **Adaptive decryption exclusion (fail-open + auto-learn)**: `internal/autoexclude` — a volatile, bounded, TTL-bounded in-memory cache of hosts SSL inspection could not decrypt, so subsequent CONNECTs bypass (PAN-OS-style local decryption-exclusion cache). Opt-in per decryption profile via `OnInspectError=="fail-open"`. **SCOPED KEY (policy isolation, not just host):** every entry is keyed by `(scopeID, host)` where `scopeID` is the matched decryption-profile's identity — a host learned under one fail-open profile is consulted ONLY for sessions matched to that same profile, so one fail-open rule/profile/tenant can never create a bypass consumed by another. `resolveSSLAction` consults the cache ONLY when the matched rule opts into fail-open AND within that profile's scope (gated read — a fail-close rule never populates OR consults, so hosts on fail-close rules are un-poisonable and behavior is byte-identical when unused). **SECURITY-GENERATION FENCING (PR2, `roadmap/PR2-autoexclude-security-generation-fencing.md`):** the profile ID is stable across edits, so each entry ALSO records a `securityGen` — a deterministic fingerprint (`decryptprofile.computeSecurityGen`, `SecurityGen()`) over ONLY the security-effective fields (`OnInspectError`, `CertVerification`, `OnUnsupported`, `MinTLSVersion`, `MaxTLSVersion`, `InspectHTTP2`; identity/timestamps/`StallTimeoutSecs` are EXCLUDED so a rename never invalidates). `Observe`/`Contains` are `(scopeID, gen, host)`: a gen MISMATCH is a miss (re-inspect), so a security-relevant same-ID profile edit invalidates learned entries immediately while a rename preserves them. The gen is PRECOMPUTED at store-write time and returned by the hot-path accessors (`FailOpenScope`/`FailOpenScopeByID` now return `(id/scope, gen, ok)`), so the CONNECT path never hashes (benchgate-pinned zero-alloc). It NARROWS the `(scopeID,host)` boundary to `(scopeID,gen,host)`, never broadens it; `scopeID` stays PURE for metrics/audit. The gen is a pure function of the synced fields — never persisted/synced, recomputed identically on every node (CP→DP) and across restarts. **Tightened classifier (`classify{Origin,Client}InspectFailure`, autoexclude_resolve.go):** an origin controls its own TLS alerts, so only NARROW signals learn — origin leg: `client_cert_required` (specific `certificate_required` TLS-1.3 alert; the ONLY reason permitted to LIVE-RESCUE the triggering session) and `unsupported_params` (only the client-side `server selected unsupported protocol version` string — a genuine per-origin version mismatch; the host-independent `no supported versions satisfy` config error and the server-side `no cipher suite` string are deliberately NOT matched; LEARN-ONLY, never rescues); client leg: a specific cert-rejection alert (`client_pinned`, learn-only). Generic/origin-emitted alerts (`handshake failure`, `no application protocol`), cert-verify failures (untrusted/expired/mismatch — a Block signal + the poisoning vector), and EOF/RST/timeout/wrapped errors NEVER learn (fail-closed default). A host is excluded only after a CONFIRM-COUNT of DISTINCT client-evidence tokens (default 2) within a window — the token is the AUTHENTICATED IDENTITY when available, else the client IP (IPv6 collapsed to /64 for single-host churn; IPv4 RAW — a /24 would over-collapse a NAT fleet; NAT/DHCP limitation documented). `client_pinned` gets a shorter TTL (1h vs 12h). Only `client_cert_required` on the strip path live-RESCUES the current session (confirm-count-exempt) via `handleTunnelBypass` (its own inline `isPrivateHost`+`ssrfControl` re-dial); everything else — `unsupported_params`, the native-H2 path, client-pinning — is learn-only (self-heal on the next session after the confirm-count). Promotion fires a SCOPED audit event (actor = triggering client IP) + `fireAlert` + metrics (`culvert_decrypt_autoexclude_{total{reason,scope},hit_total{scope},active{scope},pending}` — F6 labels `hit_total`/`active` by profile scope, same capped label set folding overflow to `_other_`; the process total is `sum()`-able and also on `/api/decryption/health`); pending map is independently bounded (`maxPending`). The learned ENTRIES are VOLATILE — off every config surface (cleared on restart, never CP→DP synced). The five ENGINE PARAMETERS (`confirmN`/`ttl`/`pinnedTTL`/`window`/`maxEntries`) are runtime-tunable (F10, PRs #747/#749/#752/#753): DURABLE in `admin_settings.json` (sentinel `AutoExcludeTunablesSaved`) but node-local — OFF export/import, version-rollback, and CP→DP (AdminDurable-only `configSurfaces` rows, pinned by `config_surfaces_test.go`). `Cache.Reconfigure` applies changes in-place under the mutex (forward-only: active entries keep their expiry; lowering `maxEntries` deterministically evicts oldest-first to exactly the cap). `OnInspectError` is an additive persisted profile field (omitempty) that degrades to fail-close on downgrade (old binary ignores the unknown key). Admin surface: `/api/decryption-exclusions` (GET viewer list+Stats+fail-open footprint+per-scope rule blast-radius / DELETE operator evict-one `?scope=&host=`·clear-all) + `GET/PUT /api/decryption-exclusions/tunables` (GET viewer = defaults+bounds ONLY, current values stay on the Stats surface as the single source of truth; PUT admin = full-set `zero⇒default`, `confirmN`≥2, `maxEntries`≤262144, persist-before-apply: validate→persist target→apply infallible Reconfigure, no rollback branch) + the Decryption Exclusions SPA panel (incl. the admin-only Cache Tuning section). Engine tests use an injected clock; `swapAutoExclude` isolates the global singleton per test (the PR3d fence-pollution class). See `docs/operator/decryption-auto-exclusions.md` and `roadmap/auto-exclusion-cache-plan.md`.
- **The shutdown sequence is BOUNDED end to end, in three phases with a durability RESERVE (CHAOS-56, `main_shutdown.go` + `runtime_shutdown.go`)**: SIGTERM runs 17 ordered hooks, and until CHAOS-56 the sequence was bounded only by the container's `stop_grace_period`. Three of Culvert's per-request sinks are ASYNCHRONOUS by design (`internal/logsink`, `internal/reqlog`, `internal/syslog`), and each header documents the same residual — an abrupt death loses the in-flight batch, the ORDERLY path flushes — so three durability contracts were delegated to a sequence that could not guarantee it reached the flush. **The unbounded hook is gRPC `GracefulStop`, and NOT for the reason it looks like.** grpc-go bounds the IDLE case with a 5s GOAWAY ping-ack timer (measured 6.005s end to end on v1.83.1 against a silent HTTP/2 peer — the "half-open peer waits out the ~15-minute TCP retransmit budget" story is WRONG, and measuring it is what found the real one), but `outgoingGoAwayHandler` closes the transport only when `len(t.activeStreams) == 0`; with a live stream it arms NO timer, and `GracefulStop` blocks in `for len(s.conns) != 0`. Two ordinary faults produce a stream that never finishes and neither surfaces an error: a handler blocked in `write(2)` on a wedged volume (`Enroll`/`RenewCert` persist, `PushAuditEvents` appends to a `RotatingFile`) and a peer that stops reading a large `GetConfig` response (TCP zero-window persist retries indefinitely). Reaching the grace means SIGKILL, which skips the cluster-store flush, the request-log queue drain, a clean badger close (an unclean one is exactly the torn `MANIFEST` CHAOS-50's boot-path quarantine exists for — a hung shutdown MANUFACTURES the corruption the previous sweep had to survive) and the log-sink flush **holding the lines that say why**. Six rules now hold. **(1) Three phases, and the FLUSH reserve is carved out UP FRONT** — `shutdownFlushBoundary` (105) splits the late registry via `partitionAt` into DRAIN hooks (best-effort; abandoning one costs a client retry) and FLUSH hooks (durable; abandoning one costs durability or a quarantined store), and the reserve is measured from the START of the flush phase, so a drain that overran its own share still cannot spend it. **(2) Every phase carries a REAL deadline** (`defaultShutdownBudget`: Total 45s, Early 12s, Flush 10s) — the early phase used to run under `context.Background()`, pinned as correct by a test that was pinning the DEFECT (`TestRunShutdownSequence_EarlyCtxHasNoDeadline_LateCtxDoes`, since inverted), and the late ctx was ADVISORY: `RunAll` never consulted it and most hooks cannot (`syslog`/`badger`/`logstore`/`reqlog`/`audit`/`logCloser` take no ctx; the tunnel drain took one and ran its own timer its comment calls "independent of the parent ctx", so the real worst case was 30s + 15s + the closers against a documented 30s). **(3) Every hook runs under a WATCHDOG, and the RESERVE IS RECURSIVE** (`hookBudget`): a hook may take what is left of its phase MINUS `shutdownHookMinSlice` (1s) for every hook still BEHIND it, then one shared `shutdownHookGrace` (3s) before it is abandoned, so the envelope stays `Total + 2×grace` = 51s, inside the 60s compose grace and pinned to it by a cross-artifact gate that parses `docker-compose.yml`. **The grace is SHARED BY THE PHASE, and only a clamp makes that true** (SEC-SHUT-1, `2026-09-04` review): `RunAll` folds it into ONE phase HORIZON (`phaseEnd + grace`) and `hookBudget` measures every hook's slice against THAT, so the phase can never cross it (a slice is always <= the time remaining to it) while every hook still gets its own non-zero slice. Merely CLAMPING the abandon instant is not enough and was the first, rejected shape: it bounded the total but handed a later hook an ALREADY-EXPIRED watchdog, so it could be abandoned before its goroutine entered `h.stop` — and since `main` exits as soon as the sequence returns, `request-log-close`/`audit-log-close`/`log-closer` then never ran at all (measured: a ZERO-length window for flush hooks 4-6), starving exactly the closers the reserve protects (Codex P1, PR #1311). It was first charged PER HOOK, on the reasoning that `hookBudget` hands an overrunning hook's unused SLICE to the hooks behind it — true, but the grace is added ON TOP of each hook's deadline and is never charged against the phase's remaining time, so only the slice is conserved and each stalled hook cost a further full grace. The overrun therefore grew with hook count (1.0/1.4/2.4/3.4/3.7 graces at 1/3/6/9/10 stalled hooks), and on the shipped constants the full sequence measured **59.2s against the 51s the gate computes and the 60s compose grace — one further durable closer took it to 60.0s**. The cross-artifact gate could not see it because it validates the `Total + 2×grace` FORMULA, not the behaviour; the behaviour is now pinned in hook count by `shutdown_envelope_test.go` (7 gates: three regression, verified failing against the original per-hook grace, plus TWO controls that fail against the clamp-only shape (durable closers must have COMPLETED when `RunAll` returns, and each late hook's execution window must clear `shutdownHookMinSlice/4` — a merely-positive assertion passed against the defect, since an expired ctx returns in tens of ns), a healthy-path control, and an unbounded-phase boundary). `runShutdownHook` also waits for the hook goroutine to signal ENTRY before arming the watchdog, so an already-due watchdog cannot race the runtime's scheduling of the goroutine. **Do not re-arm the grace per hook, and do not widen `Total` or `stop_grace_period` instead — that hides the symptom and leaves the bound uncomputable from the constants.** **Do not collapse this back to one deadline per phase.** The first shipped shape did, with the recorded rationale "a stalled hook is abandoned, and the flush hooks are safe because they have their own reserved phase" — which is FALSE: the flush reserve protects flush hooks from a stuck DRAIN, never from EACH OTHER, so `syslog-close`/`community-db-close` stalling on a wedged volume burned the whole reserve and `request-log-close`/`audit-log-close`/`log-closer` were started and abandoned against an already-past deadline (Codex P1 — SD-2b reproduced inside the fix for SD-2b). The hook RECEIVES the deadline the watchdog enforces, so a ctx-aware hook winds down instead of being abandoned; a fast hook hands its unused share to the next, so a legitimately slow close still gets almost the whole phase (control-gated). An abandoned hook is NAMED in a line emitted AT THE POINT OF ABANDONMENT, never from the phase-end aggregate: the last flush hook closes the log sink, so a phase-end line on the flush phase is enqueued into a channel nobody drains (the same reason `runShutdownSequence` emits its completion line BEFORE the flush phase — the pre-existing `logger.Println("Stopped.")` after it was already being swallowed). Abandoning is never worse than the SIGKILL it replaces, which abandons the same hook PLUS everything behind it. **(4) Panics are CONTAINED** — same direction as CHAOS-55's recovery loop, opposite to CHAOS-24's HA keepalive, for the reason recorded there: a shutdown hook holds no authority containment would extend. **(5) `StopControlPlaneGRPC` is bounded** (`gracefulStopBounded`, `cpGRPCGracefulStopBudget` 8s — above the measured 6.0s idle drain so an unresponsive fleet still completes gracefully), then a force-close; force-closing is safe because an interrupted unary RPC is retried by the caller's own sync loop. **grpc-go's `stop(graceful bool)` is hostile to being raced in TWO ways and the obvious wrapper hits both — do not "simplify" this back.** (a) It ends with `s.handlersWG.Wait()`, so `GracefulStop` does not return until every HANDLER returns — the very handler being escaped — so the goroutine must NOT be joined (draft one did). (b) That `handlersWG.Wait()` runs while HOLDING `s.mu` (`stop` takes the lock with `defer Unlock` before the conns wait; `s.cv.Wait()` releases it only while waiting), so when the last conn is removed both stops contend and, if the GRACEFUL one wins, it parks forever holding the mutex and a SYNCHRONOUS `srv.Stop()` blocks on it unboundedly — the original fault rebuilt inside its own fix. Which one wins is pure timing: draft two passed every targeted run AND the full suite and failed only under `-race`. So `Stop()` is issued on its OWN goroutine and the function returns. What it therefore guarantees is narrower than "the server is stopped": the LISTENERS are closed (grpc-go closes them before the conns wait), and the transport force-close is best-effort + asynchronous — which is why the hook watchdog is the only HARD bound on this hook and the two are NOT redundant. The gate's TOLERANCE is part of the gate: a generous "returns eventually" bound would have made draft two a flake rather than a failure. **(6) A SECOND SIGTERM/SIGINT force-exits** with status 1 after `flushLogSink()` — `signal.Notify` takes the runtime's default terminate behaviour away and nothing read `quit` again, so the second signal was swallowed and the only escalation left was SIGKILL. The watcher re-checks the disarm via `shouldEscalate` before exiting: Go picks UNIFORMLY among ready select cases, so a signal pending at the instant `stopEscalation` ran made a COMPLETED shutdown exit 1 half the time (Codex P2). That tie cannot be scheduled from a test, so the decision is its own function and is pinned deterministically rather than by a probabilistic race gate. Gates: `shutdown_chaos_test.go` (17) — four defect gates verified failing against their reintroduced pre-fix shapes, a permanent DEFECT PROOF (`BareGracefulStopIsUnboundedOnAWedgedStream`) so a future grpc-go change cannot let the bounded gate quietly prove less than it claims, and three CONTROLS (a watchdog that abandoned everything, or a drain clamped to nothing, would pass the defect gates while being far worse than the defect). Worse, the fault a caller cannot handle: a corrupt `.sst` makes `badger.Open` **PANIC from a goroutine badger spawns** (`created by … newLevelsController`), so `recover()` at the call site never fires and returning the error instead of exiting would have fixed nothing. `catdb.OpenResilient` is the boot-path entry point (**direct `catdb.Open` is for callers that already know the directory is sound**): a **per-attempt, flock-OWNED poison marker** — a SIBLING of the store, armed around every attempt and cleared however it returns — turns "a previous process died inside `badger.Open`" into a signal the next boot acts on, and the directory is quarantined **before** badger touches it. A marker counts as poison only when its **flock can be taken**, which the kernel permits only once its owner is gone; it is per-attempt rather than a single shared path because a shared one cannot survive concurrency (a second booting process would clear a still-live opener's breadcrumb, and if that opener then panicked the next boot would walk into the corrupt store again — the crash loop persisting through its own remedy). Four rules keep the rename safe and must not be relaxed: (1) it **moves aside, never deletes** (`.corrupt.<unixnano>`, the CHAOS-05/07 convention, pruned to ONE copy); (2) the DIRECTORY flock — badger's own lock — is **held ACROSS the rename, not probed and released before it** (`rename(2)` does not consult flocks, so probing leaves a window in which a concurrent boot's live store is renamed away); the invariant is carried by the TYPE — `quarantineDir` takes the `*heldLock` as a required argument and refuses a released one (`errStoreLockNotHeld`); (3) a live opener's marker is NEVER touched and a skipped quarantine leaves the breadcrumbs for the next boot; (4) returned errors are matched against the ENVIRONMENTAL deny-list (lock held, ENOTDIR, EACCES, EROFS, ENOSPC, EMFILE, EIO) **before** the corruption allow-list, and anything unrecognised DEGRADES — the fail-safe default is to leave the disk alone. The outcome is reported ONCE, after it is known (a quarantine followed by a failed replacement open is a FAILURE, not a recovery — reporting the quarantine first emitted two contradictory alerts). Note for anyone extending this: **none of these faults are reachable via `errors.Is`** (badger wraps with `y.Wrapf`, no `Unwrap`), so the fault → message table is itself a test (`TestClassifyOpenError_EmpiricalBadgerMessages`) and a badger upgrade that rewords them fails the build rather than silently stopping recovery. `loadCommunityFeedDB` degrades to `communityDB = nil`, which every consumer already nil-guards — byte-identical to running without `-cat-feed-db`. Visibility reuses existing vocabulary: the `state_file_corrupt` alert (same operator action, no second dialect), a `category_feed_db` operator-contract row, and `culvert_catfeeddb_{available,recovered,quarantined_copies}`. **Deliberately NOT on `/readyz`** — Layer-1-only categorisation is a fully serving node, and failing readiness would pull a healthy gateway out of rotation over a degraded cache. The machinery itself now lives in **`internal/storeguard`** (CHAOS-62 extracted it verbatim so `internal/logstore` could reuse it — see the next bullet); `catdb/resilient.go` is a thin adapter with an EMPTY `storeguard.Policy`, and its 21 recovery gates run unchanged against the extracted engine. **Do not re-inline or re-copy the engine**: the fault → message table is empirical and is pinned by a test precisely so a badger upgrade that rewords a message fails the build, and a second copy is how that protection rots. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §§19/31 and `docs/operator/category-store-recovery.md`.
- **A damaged request-history store must never kill the process, and an encryption error must never quarantine it (CHAOS-62, `internal/logstore/resilient.go` + `internal/storeguard`)**: `logstore.OpenTTL` carries the identical uncatchable-panic exposure as the category store above — re-measured against THIS store's options (encryption on, 128 MiB value log) a corrupt `.sst` still panics from a goroutine badger spawns. It was WORSE in two ways the CHAOS-50 register row (R-E) recorded backwards as "bounded by being opt-in". Opt-in means the toggle is DURABLE in `admin_settings.json` and re-applied by `LoadAdminSettings` on every boot, so one unclean kill is a self-latching **unattended crash loop** with no admin UI left to turn the setting off; and it means `enableLogStore` is reachable from the **LIVE admin API** (`ui_config.go`), so a damaged store kills a gateway carrying production traffic the moment an admin flips a switch — no error the handler could return, because the process is gone. `openLogStore` now goes through `logstore.OpenResilientTTL`; the caller DEGRADES (history off — the posture of a node that never had the toggle on), never exits. **The classifier is a per-store `storeguard.Policy` because of this store, and a Policy can only ever SUBTRACT** (there is deliberately no field for ADDING corruption signals — widening destruction from a call site is how a shared safety mechanism becomes an unsafe one): badger reports a CHANGED PASSPHRASE, a LOST SALT and real KEYREGISTRY damage with the SAME error on a keyed store, and CHAOS-50's table lists that message as corruption on the explicit rationale *"this store is never opened with a key"* — true there, false here — so reusing it unmodified would move a HEALTHY store aside over an ordinary config change. The exemption is expressed at BOTH layers on purpose (structurally on `ErrEncMismatch`, textually on the raw badger message) so a future change to `OpenTTL`'s error rewrite cannot silently re-arm that quarantine. Real KEYREGISTRY damage therefore does not self-heal — a recorded owner trade: of the four postures the only unacceptable one is destroying intact history to fix a configuration mistake. **`EncKey` mints a salt ONLY when there is no store it could lock us out of** (`storeHasContent`; an unreadable directory answers TRUE — refuse rather than overwrite key material on a guess): it used to mint and WRITE a fresh salt whenever the `<dir>.salt` sidecar was unreadable or short, which on the READ path destroyed the only value that could ever decrypt an existing store, surfaced as an error indistinguishable from a passphrase change, and so made the operator's remedy "purge" — the same rule `internal/alerts` already adopted as SEC-WHSIGN-1 (*a failed decrypt never mints a key*). It now returns `ErrSaltUnusable`, sidecar untouched, and the API gives that its OWN 409 naming its own REVERSIBLE remedy (restore one file) rather than inheriting the mismatch's irreversible "purge". The salt is a SIBLING of the store dir, so a quarantine leaves it in place — required in both directions: the replacement store keeps working AND the quarantined copy stays decryptable, so the evidence is readable evidence. Visibility mirrors CHAOS-50 exactly (no second dialect): `request_history` operator-contract row, `culvert_logstore_{available,recovered,quarantined_copies}`, the existing `state_file_corrupt` alert, outcome reported ONCE after it is known. **Deliberately NOT on `/readyz`** — history is a queryable convenience over traffic that is ALSO in `internal/reqlog` and `internal/audit`, both independent of this store. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §31 and `docs/operator/request-history-recovery.md`.
- **The public admin-login endpoint bounds its username BEFORE any durable write (CHAOS-63, `login_input_bounds.go`)**: `apiAuthLogin` (`/api/auth/login`) is on `uiAuthMiddleware`'s PUBLIC allowlist and bounded nothing, so the caller's chosen `body.User` reached four retaining sinks — the tier-1 and tier-2 `internal/lockout` map keys (which `Cleanup` deliberately cannot sweep before `lockout.Window` = 10 min elapses), the 500-entry audit ring, the DURABLE audit JSONL, and the `auth_lockout` alert payload. The only limits in front of the handler are `securityMiddleware`'s 1 MiB body cap and the 60-mutating-POST/min per-IP API limiter, so ONE unauthenticated client commits **~60 MiB/min of chosen bytes** into a compliance record that is a `fileutil.RotatingFile(path, 50)` keeping exactly ONE archive (100 MB total, `rotating.go` removes the previous `.1` before renaming) — the entire retained audit trail rotated away in **under two minutes**, and ~1 GB of heap parked for ten. Measured by the gate: **4,195,672 bytes into the audit file from 8 requests.** `internal/audit`'s own header names this outcome (CWE-778/A09:2021) and its `writeErrors` counter CANNOT see it: **every one of these writes SUCCEEDS**, so `storage_write_failed`, the `audit_log_persistence` contract row and `culvert_audit_write_errors_total` all stay green while the record is destroyed. Four rules now hold. **(1) The bound is at the ENTRY POINT** — `rejectOversizeLoginUser` refuses `len(body.User) > maxUsernameLen` (256, the same constant `proxy_portal.go` already applies to Proxy-Authorization) and returns BEFORE the limiter, the credential check and the alert, so a rejected attempt creates no state at all. **A CONFIGURED account is NEVER refused, however long its name** (`cfg.LoginNameConfigured`, a non-retaining probe that MUST mirror `VerifyUIUser`'s own roster-or-legacy resolution — pinned by `TestChaos63_LoginNameConfiguredMatchesVerifyUIUser`, because a divergence is an admin lockout). The first draft claimed no real account could carry such a name, since `apiSetupComplete` and the user-creation API cap at 64; that is FALSE — `-user`/`auth.user` reach `cfg.SetAuth` and `--reset-password` reaches `cfg.SetUIUser`, and neither store bounds the name (`validateAuthStartupCredentials` validates only the password), so an over-long username can already be a valid persisted admin and refusing it would have locked that operator out of the admin UI on upgrade (Codex review, PR #1320). `warnOversizeConfiguredUsernames` (auth_startup.go) warns at boot and is deliberately NOT fatal — the stores never bounded the name, so failing the boot would brick an appliance whose config was legal when written. 400 not 401 is deliberate for a name that exists nowhere: a username's LENGTH is not a secret. The narrow cost is that, past the bound only, 400-vs-401 says "no such account" to a caller who already guessed the exact over-long name — a far better trade than refusing a real admin. **(2) `internal/lockout` carries the structural half** — `MaxUsernameKeyLen`/`boundUsername` clamp at EVERY public entry point (`Check`, `CheckPair`, `RecordFailure`, `RecordPairFailure`, `RecordSuccess`, `AttemptsLeft`, `ResetUser`). **The clamp is INJECTIVE** (rune-safe prefix + a SHA-256 digest of the WHOLE name), and that is a SECURITY property: because a configured over-long name is exempt from the rejection above, it reaches this limiter, so a plain truncation would let an attacker who knew that admin's first 256 bytes submit an ordinary ≤256-byte name clamping to the SAME key and drive the tier-2 account lock against them — lockout-as-DoS, the exact defect the two-tier design (RISK-012) exists to prevent (pinned by `TestBoundUsername_IsInjective`). Applying the clamp at only SOME entry points is worse than not applying it: `Check` and `RecordFailure` disagreeing about the key splits one attacker's failures across two counters and silently WEAKENS the lock while passing any byte-size assertion (pinned by `TestOversizeUsername_CheckAndRecordAgree`, with `TestBoundedNames_BehaviourUnchanged` as the control that an ordinary lockout is untouched). The package's `Cleanup` doc claimed the maps were bounded "against an unbounded-memory DoS" — true on the ENTRY-COUNT axis, never true on the KEY-SIZE axis. **(3) The attempt is still AUDITED** (`auth.login.rejected`, actor truncated via `truncateForAudit` with a self-describing `…[truncated, N bytes]` marker, real length in the detail): bounding the bytes must not delete the evidence that the admin plane is being probed, and the entry is O(1) at the same rate the ordinary `auth.login.fail` entry would have cost, so it adds no ring-eviction capacity the endpoint did not already have. **(4) The rejection is VISIBLE** — `culvert_login_oversize_rejected_total` is the operator's only signal (the caller just gets a 400), and the log line is rate-limited to one per minute with the magnitude in the counter, because a mitigation for a write-amplification defect must not be one itself. **Deliberately NOT done:** no byte cap inside `internal/audit` (the sink cannot tell attacker bytes from a legitimate `auditEventDiff` before/after payload — whole policy objects are marshalled there on purpose — so a cap would destroy real compliance evidence to fix an input-validation defect); no hard entry-count cap on the lockout maps (evicting at a cap evicts a REAL lock — an owner trade-off, recorded as open register row AU-17, now ~4000x smaller per key). Gates: `login_input_bounds_test.go` (10) + `internal/lockout/lockout_keybound_test.go` (9); seven defect gates verified failing against their reintroduced pre-fix shapes. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §32 and `docs/operator/admin-login-input-bounds.md`.
- **Audit-log write loss is COUNTED, never silent (`internal/audit`)**: the JSONL file is the DURABLE compliance record — the in-memory ring holds only the newest `MaxRing` (500) entries and is wiped on restart — so `Add` must never discard a persist failure. Every entry that does not reach the file is charged to `WriteErrors()` (write error, **short write with a nil error** — the truncated-JSON-line case an `io.Writer` seam can produce — and the defensive marshal branch); only the FIRST failure is logged (a failing disk fails every write; the counter carries the magnitude), matching `internal/reqlog`'s contract. The audit log is an append-only `fileutil.RotatingFile`, NOT a `fileutil.AtomicWrite`, so the CHAOS-45 durable-write chokepoint observer never sees it — `storage_health.go`'s `init` therefore wires `audit.SetWriteFailureObserver(noteStorageWriteFailure)` explicitly to reach the same plane (degraded operator-contract row, rate-limited log, `storage_write_failed` alert, path redaction). **The observer MUST NOT call `Add`**, directly or transitively: re-entering `Add` from it recurses without bound on a persistently failing disk (the production observer is audit-free by construction; a panicking observer is contained so audit loss can never take down the admin plane it records). Persistence stays best-effort — a failing disk must not make an admin change fail — but it is surfaced on `/api/stats` (`auditLogWriteErrors`), `/metrics` (`culvert_audit_write_errors_total`), `/healthz` (added only when non-zero; never fails the probe) and the dashboard, where audit loss outranks request-log loss. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §13 (register item ST-8).
- **An OCSP response is a verdict only when it is BOUND, FRESH and AFFIRMATIVE — and the check does not reach inspected HTTPS (CHAOS-65, `internal/ocsp/ocsp.go` + `ocsp_coverage.go`)**: every input this engine acts on is written by **the party being checked** — the responder URLs come out of the peer's own AIA extension, so the peer picks which responder is asked, how many, and therefore what comes back — and nothing in the pipeline treated that as hostile. **(1) The response was not BOUND to the certificate under test.** `cryptoocsp.ParseResponse(b, issuer)` is `ParseResponseForCert(b, nil, issuer)`, which takes `Responses[0]` and NEVER compares the serial (`x/crypto@v0.56.0/ocsp/ocsp.go:509-528`); the signature is verified, which is a far lower bar than it sounds, because a genuine CA-signed `good` about any OTHER certificate of the same issuer is obtained by asking that CA about any live cert and keeping the bytes. The peer names the responder, so the peer serves that reply, and a **revoked certificate is accepted — a complete revocation bypass by its own subject, needing no network position.** Now `ParseResponseForCert(respBytes, leaf, issuer)`; **never call `ParseResponse` here.** **(1b) BINDING THE RESPONSE IS ONLY HALF — THE SIGNER MUST BE BOUND TO AN AUTHORITY TOO, and getting that wrong defeated (1) entirely** (Codex review, PR #1369): `ParseResponseForCert` verifies an embedded responder certificate by asking ONLY whether the ISSUER signed it, never whether it carries RFC 6960 §4.2.2.2's `id-kp-OCSPSigning`. **The peer's own leaf is by definition a certificate the issuer signed, and the peer holds its private key** — so the peer signs a fresh `good` about its OWN serial, embeds its own leaf as the responder, serves it from the responder URL in its own AIA, and a REVOKED certificate is accepted needing no response from anybody else, which is strictly EASIER than the borrowed-response vector (1) closed. `responderAuthorized` now admits exactly two signers: the issuer itself, and a delegate the issuer signed that carries the OCSP-signing EKU and is inside its own validity window. **`ExtKeyUsageAny` is deliberately REFUSED** — honouring it re-admits every ordinary leaf the issuer ever signed, i.e. the whole attack; and **refusing every embedded certificate is NOT the fix** (delegated responders are ordinary and widely deployed — pinned as a CONTROL). The delegate's own revocation status is deliberately unchecked: that is the infinite regress RFC 6960 §4.2.2.2.1 answers with `id-pkix-ocsp-nocheck`. The lesson, which this note had already written and only half applied: *"the peer picks the responder, so the peer picks the answer"* was answered for WHICH CERTIFICATE the response is about and not for WHO WAS ALLOWED TO SAY SO — binding an assertion to its subject is worth nothing until the signer is bound to an authority. **(2) There was NO freshness check.** `ThisUpdate`/`NextUpdate` were parsed and never read, `CreateRequest(leaf, issuer, nil)` sends no nonce, and OCSP rides plaintext HTTP — so a `good` captured before revocation replayed forever, and fixing (1) does not close it (a pre-revocation response for the CORRECT certificate binds perfectly). `responseFresh` requires `ThisUpdate` not in the future and `now` inside `NextUpdate`, with a `maxResponseAge` 24h ceiling when `NextUpdate` is absent (RFC 6960 §2.4 permits omitting it, which without a ceiling is an unbounded replay window). Skew is tolerated **5 min in BOTH directions**, reusing `caClockSkewTolerance`'s value rather than inventing a second one: a clock rollback is a fault, not an attack, and must not take revocation checking down. **(2b) THE CACHE MUST NOT OUTLIVE THE AUTHORIZATION IT IS BUILT ON** (Codex review): freshness was checked at receipt and then thrown away — every confirmed verdict was cached for the fixed 1h `cacheTTL`, so a `good` whose `NextUpdate` was a minute out kept admitting the certificate for another 59 minutes after the responder stopped vouching for it, i.e. (2)'s replay window closed on the wire and reopened in the cache. `cacheResult` now takes the response's own deadline (`responseValidUntil` = `NextUpdate`+skew, else `ThisUpdate`+`maxResponseAge`) and uses the EARLIER of that and `cacheTTL`; a verdict already at its deadline is not cached at all. Same shape as (1b): a rule enforced at one layer and not carried to the next. **(2c) AND THE CACHE MUST NOT OUTLIVE ITS SIGNER EITHER** (Codex review round 3): two checks bound a verdict at PARSE time — `responseFresh` bounds the ASSERTION, `responderAuthorized` bounds the SIGNER — and (2b) carried only the first into the cache. A delegated responder valid for another THIRTY SECONDS could sign a `good` whose `NextUpdate` was a day out, so the handshake that parsed it cached the verdict and later handshakes kept admitting the certificate for the rest of the cache TTL, while a re-parse of those identical bytes would have refused them as an unauthorized responder. `responseValidUntil` now takes the issuer and caps at the EARLIER of the response deadline and the delegate's `NotAfter`+skew, MIRRORING `responderAuthorized`'s branch structure exactly (the issuer-signed branch takes no signer cap, because that branch applies no window check — capping there would expire verdicts the parser still accepts and buy nothing). **This was the THIRD instance of one pattern in this sweep** — (1) bound the response to its subject, (1b) the signer to an authority, (2b) the assertion's deadline into the cache, (2c) the signer's — so the rule to carry forward is: *a check that runs at parse time governs a value that outlives the parse*; for every validity rule, settle what caches the result and for how long IN THE SAME CHANGE. **(3) A verdict is `Good` or `Revoked` or it is NOT A VERDICT.** `unknown` used to be a pass while a responder that could not be REACHED failed closed — two postures for one question; under the CA/Browser Forum baseline requirements a CA must not answer `good` for a certificate it never issued, so `unknown` is exactly the answer a mis-issued or forged certificate draws. An unbindable response, a stale one, an unauthorized signer and an `unknown` are each discarded under their own counter and fall through to the EXISTING fail-closed path with its existing 2-min `indeterminateTTL` — no new posture, no second dialect (CHAOS-53's rule for the scan sidecar). **(4) The verdict cache is keyed by RFC 6960's CertID** (`certKey` = SHA-256 over issuer subject + issuer SPKI + serial), not the serial alone: a serial is unique only WITHIN an issuer, and the dangerous direction of that collision admits a genuinely REVOKED certificate from a different CA off another CA's cached `good`, with no responder query at all — ordinary, not exotic, wherever two enterprise CAs with sequential serials are trusted. **(5) The responder URL is an SSRF sink** and was reached with `http.DefaultClient` and no guard at all, which also follows up to ten redirects: scheme allow-list + `ssrf.PrivateHost` INLINE at the call site (so CodeQL sees it, repo convention), `ssrf.SafeDialContext` under it to close the rebinding window, and `CheckRedirect` refusing outright — a guard on the first URL alone is bypassed by a `302`. Deliberately **not** `http.DefaultClient`: it shares the process-wide default transport, follows redirects, and honours `HTTP(S)_PROXY`, none of which is wanted for a request whose URL the peer chose; the consequence (responder queries are DIRECT and do not traverse a parent proxy) is a behaviour change recorded in the runbook. **(6) The work is an ENVELOPE, not a per-step allowance** — `maxResponders` 4 inside ONE `queryBudget` 5s, where the budget is deliberately the OLD per-responder timeout so the ordinary one-responder certificate is unchanged and only the worst case shrinks. `leaf.OCSPServer` used to be walked in full under a per-responder 5s timeout on the REQUEST goroutine inside a TLS handshake, holding the client conn, an FD and a per-IP `connlimit` slot: 200 blackholed responders parked it ~17 minutes AND aimed 200 outbound POSTs at hosts the attacker named (CHAOS-58's rule, one subsystem over). **(6b) AN ACCUSATION IS CHARGED ONLY WHEN IT IS DEMONSTRABLE** (Codex review): every `ParseResponseForCert` error used to charge `notForCertTotal`, whose metric help and RED panel banner both read *"something is answering with borrowed responses"* — so an HTML 502 from a broken responder raised a standing claim of attack on a surface whose whole job is to be believed. `noteUnusableResponse` charges `not_for_certificate` only when the response parses, its signature verifies against the issuer, and the serial is someone ELSE's; everything else is `malformed`. **The second parse is required and a string match would not do**: the library checks the serial BEFORE verifying any signature, so its serial-mismatch error alone proves nothing about who signed. A multi-status response that cannot be re-parsed counts as `malformed` — an UNDERCOUNT of the accusation, the only direction it may err in. **(6c) REVOKED WINS OVER GOOD — a Good does NOT short-circuit the responder loop** (Codex review round 2): the pre-CHAOS-65 loop walked every responder and returned revoked if ANY said so; the rewrite added `case Good: return` to save queries, so the FIRST responder decided — and **the peer writes the AIA list AND its order**, which hands the verdict back to the party being checked, this note's own finding reintroduced by the change that bounded the loop (it also accepts a certificate during ordinary responder replication lag). A Good is now remembered with the EARLIEST deadline among the Good answers (that is what the cache may rely on) and the loop continues; only Revoked short-circuits. **A cost change must not quietly move a security posture** — diff the CONTROL FLOW against what it replaced, not just the happy-path outputs. **(6e) AND AN SSRF REFUSAL IS COUNTED ONLY WHEN IT IS ONE** (Codex review round 4): `ssrf.PrivateHostContext` has THREE outcomes — allowed, refused-as-private, and COULD-NOT-DETERMINE (DNS failure, or this query's own budget expiring mid-lookup) — and the call site read any error as the middle one, so an ordinary resolver outage inflated `responder_blocked`, whose runbook tells the operator the responder RESOLVED INTO A PRIVATE RANGE and sends them down a different remediation. Neither guard branch wrapped a sentinel, so the fix is at BOTH layers: `ssrf.ErrBlocked` (previously documented as the connect-time `Control` sentinel only) now wraps the PRE-FLIGHT refusal too — one identity meaning *we refused this destination as private*, at whichever layer decided it — while the resolution-failure branch deliberately does NOT wrap it; the call site charges `blockedTotal` only on `errors.Is(err, ssrf.ErrBlocked)`, and a resolution failure takes NO `response_rejected_total` reason (no response existed to reject; it is already accounted by the fail-closed path). **This is the SECOND accusation-counter defect in this one sweep** — (6b) was the same mistake on `not_for_certificate` — and both came from treating a multi-cause error path as one thing because it arrives as one value. The standing rule: *a counter an operator is told to act on is charged only from evidence supporting the specific claim its runbook makes*, and a guard that can fail for more than one reason must SAY which rather than leave the call site to guess. **(6d) A DIAL-TIME SSRF REFUSAL IS COUNTED** (Codex review round 2): `ssrf.SafeDialContext` catches a responder host that answers public to the pre-flight `ssrf.PrivateHost` check and private to the dial — the DNS-rebinding case the dialer exists for — but its `ErrBlocked` landed in the generic transport branch, so the guard's own success moved neither `responderBlockedTotal` nor the `responder_blocked` metric reason. `errors.Is(err, ssrf.ErrBlocked)` now charges it. **(7) Misses are SINGLE-FLIGHTED per CertID** (leader/follower, the `hostIPCache`/`jwksCache` shape): 24 concurrent handshakes used to produce 24 queries, amplifying client rate 1:1 onto a responder that is by hypothesis already the slow dependency. **No follower timer** (it would release the follower to start exactly the query being collapsed), the leader publishes on EVERY exit path INCLUDING a panic, and the flight's defaults are the **fail-closed** verdict so a dead leader leaves followers denied rather than admitted. `resolve` ALSO re-checks the cache before opening a flight (lock order `flightMu` → `mu`, the only order this file takes): the caller's lookup happened earlier, so a handshake descheduled while the leader finished would otherwise open a NEW flight and query again for a verdict already cached — defeating the collapsing during exactly the cold-cache burst it exists for (Codex review). **(8) THE CONTROL IS NOT ON THE PATH THAT HANDSHAKES, and this is REPORTED, not fixed (register row CA-6b / OCSP-8).** `ConfigureTLSConfigOCSP` has exactly two call sites (`mtls_ocsp_startup.go`, the `/api/ocsp` toggle) and both target `upstreamOpTLSCfg` behind the shared upstream `*http.Transport` — which for a forward proxy means an `https://` PARENT PROXY handshake and nothing else, since the plain-HTTP path never negotiates TLS to an origin. Every inspected HTTPS request goes through `upstreamInspectTLSConfig` (`proxy_tunnel.go`), which builds its own `tls.Config` with no callbacks. So revocation is not checked on the one path where this appliance validates an origin certificate on a client's behalf, while the banner, the panel and the API all say "enabled" and every counter reads zero — *"found nothing wrong"* and *"never consulted"* are the same scrape. **Do not close this by simply attaching the callbacks**: that makes EVERY inspected HTTPS request depend on reaching an external responder, FAIL-CLOSED, on networks where outbound port 80 to arbitrary hosts is exactly what egress policy forbids — a fleet-wide HTTPS outage arriving the moment someone ticks a checkbox, and reachable from the LIVE admin API. It needs a soft posture designed alongside it (observe-only counters, or fail-open-and-alert). What shipped instead is visibility: `ocspCoverage()` with a STRUCTURAL gate comparing each claim against the `tls.Config` the named path actually builds (it pins the AGREEMENT, not the gap — whoever wires the inspect path finds the test failing and updates the claim in the same change), a WARNING from both enable paths, a panel banner, `coverage`/`uncheckedEnforcingPaths` on `GET /api/ocsp`, and `culvert_ocsp_path_checked{path}`. Surfaces: `culvert_ocsp_{enabled,revoked_total,fail_closed_total,cache_entries,response_rejected_total{reason},responders_truncated_total,singleflight_joined_total,path_checked{path}}` — **emitted ONLY when the checker is enabled** (the socks5/cluster_ca/dns rule: a flat zero from every appliance that never turned it on is indistinguishable from a broken one). - **Log sanitisation is ONE pass, and the leading `strings.ReplaceAll` is load-bearing (`sanitizeLog` in proxy.go, `obs.Sanitize` in internal/obs)**: `sanitizeLog` is the most-called sanitiser in the tree (~377 call sites) and it is on the REQUEST path — `handleRequest` emits one `POLICY_*` line per proxied request that passes FIVE values through it (rule name twice, host, matched conditions, identity), and the tunnel/relay/block paths add more. It used to scan every string FOUR times: `strings.ReplaceAll` for `\n`, then `\r`, then `\t`, then a separate scalar `containsControl` pass, plus a FIFTH full copy pass on a hit. The first three were redundant with the fourth **by construction** — `\n` (0x0A), `\r` (0x0D) and `\t` (0x09) are all `< 0x20`, and every branch mapped its match to the SAME byte, `'_'` — so the whole function was only ever computing *"every byte `< 0x20` or `== 0x7F` becomes `'_'`, length preserved"*, a single predicate one pass decides. Measured (Go 1.26, 4-core Xeon, n=3x1M): rule name 15 B **56.8 -> 28.0 ns**, hostname **59.1 -> 28.5**, identity **60.6 -> 28.3**, conditions 57 B **103.5 -> 55.0**, long URL 270 B **266.8 -> 201.9**, empty **39.7 -> 15.7**, control-carrying 28 B **340 -> 147 ns and 4 -> 2 allocs**; the five calls behind one `POLICY_ALLOW` line go **463 -> 284 ns**, i.e. ~180 ns of CPU off every allowed request. The clean path stays allocation-free, as before. **The surviving newline `ReplaceAll` is NOT vestigial and must stay the FIRST statement** (and therefore on every return path): it is the barrier CodeQL's `go/log-injection` query recognises, and CodeQL runs on PRs touching `proxy.go` and `internal/**`, so removing it risks turning every `logger.Printf(..., sanitizeLog(x))` in the tree into a CWE-117 alert. It is also the cheapest of the four scans (`strings.Count` uses a SIMD `IndexByte`), so keeping it costs ~3 ns and buys the whole convention. A SWAR (8-bytes-per-word) control scan was built and measured — ~60 ns better on 270-byte inputs, nothing on the short strings that dominate — and deliberately thrown away rather than carried: a word-at-a-time bit trick is the wrong kind of clever for the function whose bug class is log injection. `internal/obs.Sanitize` is a deliberate independent COPY (its own comment records why: delegating across a package boundary risks losing CodeQL's recognition) and got the identical treatment plus its own proof. Equivalence is exact, not approximate, and is pinned by a differential test against a VERBATIM copy of the four-scan implementation (hand-picked divergence shapes incl. the C0/DEL boundary bytes, 20k randomized boundary-weighted inputs) plus a fuzz target — ~5.2M executions found no divergence. **The SIZE of the win is hardware-dependent and the spread is wide** — it is governed by how expensive `strings.ReplaceAll`'s per-call overhead is RELATIVE to the scalar control-byte scan, which differs by an order of magnitude between CPUs (the two removed calls: ~24 ns each on the dev box, ~3 ns each on the CI runner), so the same commit improves the 57-byte shape by 47% on one and 10% on the other. The DIRECTION never changes — this form strictly does less work — and the allocation halving is hardware-independent. Gates: `proxy_sanitizelog_test.go` + `internal/obs/sanitize_test.go` (correctness), `proxy_sanitizelog_bench_test.go` (before/after, both forms timed in ONE run so the comparison stays reproducible), `proxy_sanitizelog_benchgate_test.go` (0 allocs on the clean path; <=2 on the scrub path; plus the scan-count gate). **The scan-count gate is STRUCTURAL — an AST assertion that `sanitizeLog` makes exactly ONE `strings.ReplaceAll` call and that it is the FIRST statement — and it was a same-run timing RATIO first.** That ratio was argued to be machine-independent because both forms were timed together; CI falsified it on the first run (0.57 on the dev box vs 0.90 on the runner for identical code, against a 0.80 bound), for the reason above: a same-run ratio cancels the clock, not the instruction mix. Any bound loose enough for both machines is too loose to catch a reintroduction (the CI control measured 1.00). This is the same wall `internal/connlimit`, `internal/threatfeed` and the latency histogram hit, with the same recorded conclusion — *a gate that can flake gets muted* — and the structural form is strictly better here anyway: deterministic under any load or `-race`, AND it pins the CodeQL barrier's POSITION, which no timing gate can observe. It carries its own CONTROL, running the same predicate against the verbatim pre-change `legacySanitizeLog` and requiring it to be REJECTED, so a selector typo that matches nothing cannot pass forever.

- **Destination-host DNS resolution is BOUNDED, SINGLE-FLIGHTED and STALE-SERVING (CHAOS-64 — the resolver half of the CHAOS-60 bullet below, sharing one `hostIPCache`; `geoip.go` + `dns_health.go`)**: a `DestCountry` policy rule puts the customer's resolver on the critical path of every request that misses one process-wide cache — `matchDestNorm` calls `geo.LookupCached` on the REQUEST goroutine, once per such rule, and that needs an IP before it can ask for a country. `policy.go`'s own comment names the hazard and drops the evaluation lock because of it, which is the right fix for the LOCK and no fix at all for the REQUEST. An expired negative is a MISS. Two invariants keep that safe: a **failed refresh never overwrites a still-servable positive** (a negative is served as FRESH for its TTL, so without the guard the refresh introduced by the fix would itself take geo dark for exactly the window the stale answer existed to cover), and `finishFlight` is **DEFERRED on every leader path** (otherwise a panic inside the resolution leaves followers blocked forever on a flight nobody completes — a bounded resolver fault turned into a permanent request-plane hang no upstream `recover()` can undo). - **Request-log persistence is ASYNC (`internal/reqlog`)**: `Add` rings the entry in memory and enqueues it on a bounded channel; ONE drain goroutine owns the JSONL file, encodes with a reused `json.Encoder` into a `bufio.Writer`, and flushes as soon as the queue drains (so an idle proxy still gets one `write(2)` per entry — no added durability delay — while a backlogged one amortizes the syscall across the batch). Unlike syslog and logstore, the queue is a shock absorber and NOT a load shedder — the JSONL file is the durable audit record, so a full queue BLOCKS the caller (the pre-async behavior, never worse) and counts `Backpressure()`; no entry is ever dropped. Single drainer ⇒ the file stays FIFO. `Sync()` drains on demand (called by `ReadPersistent` so admin reads keep read-your-writes, and by `Close()` so shutdown loses nothing). Measured (4-core, the verbatim POLICY_ALLOW line): the sink cost 2798 ns/op serial and **3204 ns/op at 4x parallel** — it got SLOWER as cores were added, i.e. a throughput ceiling, not a constant cost. Same contract as `internal/reqlog`: the queue is a shock absorber, NOT a load shedder — a full queue **BLOCKS** the caller (exactly the pre-change behavior, never worse) and counts `Backpressure()`; no line is ever dropped, and the single drainer keeps the log strictly FIFO. The drain loop flushes as soon as the queue empties, so an idle process still gets one write(2) per line (no added visibility delay) while a backlogged one amortizes the syscall. `logCloser` (returned by `setupLogger`, run last in the shutdown sequence) flushes before closing the file, and **`logger.Fatalf` is banned in favour of `logFatalf`** (logger.go) — `log.Logger.Fatalf` os.Exits immediately and would discard the queued line explaining why the process is exiting. The residual trade-off is that an ABRUPT death (SIGKILL/OOM) can lose the in-flight batch. Saturation is exported as `culvert_logsink_backpressure_total`. Pinned by `logger_async_test.go` (no loss, FIFO, flushing closer, JSON mode), `logsink_benchgate_test.go` (`TestBenchGate_LogSinkDecouplesCaller` — 64 lines against a 20 ms-per-write sink must return in ≪ 64x20 ms) and `internal/logsink/logsink_bench_test.go` (`TestBenchGateWriteAllocs`, 0 allocs/op).
- **Relay pattern**: All tunnel relays (CONNECT, WebSocket, SOCKS5) wait for BOTH goroutines; CloseWrite unblocks peers. Shared `relayCounted`/`bidiRelayCounted` (proxy_tunnel.go) do the byte-counted bridge for the WS + CONNECT-bypass paths. Every raw relay is idle-bounded via `idleCopyCounted` (CHAOS-03): read deadlines armed at half of `tunnelIdleTimeout` (default 1h) around `io.CopyBuffer` — preserving the TCP↔TCP kernel-splice fast path — with a shared per-tunnel activity stamp so bytes in EITHER direction keep both goroutines alive, and a hard close of both conns on idle (the peer relay may be blocked in a deadline-less Write that only a close unblocks). Only READ deadlines are used: read timeouts are resumable on `tls.Conn`; a write timeout would corrupt TLS state.
- **Every hijacked tunnel is registered with the shutdown drain, and the drain can END the wait (CHAOS-57, `proxy_tunnel_drain.go`)**: `drainActiveTunnels` waits on ONE number — `activeConns` — and Culvert has SEVEN hijacked-tunnel classes. Four never touched it: both non-TLS inspect fallbacks (strip + native), WebSocket, and SOCKS5. A hijacked conn is invisible to `http.Server.Shutdown` BY CONSTRUCTION, and `socks5Server.Stop` waits only for the ACCEPT LOOP while every session runs in a detached `go handleSOCKS5(conn)` (a deferral `socks5_shutdown_test.go`'s own header records). So for those four classes nothing waited and nothing closed them — they ran until process exit and the kernel reset them. Three silent consequences: **one fault, two postures** (a CONNECT tunnel got 15 s of grace on SIGTERM; a WebSocket or SSH-over-SOCKS5 session on the same node at the same instant got none, decided only by which `recordActiveConn` call site the path happened to pass); **the accounting for every severed tunnel was destroyed** (`recordTunnelClose*` runs only AFTER both relay goroutines drain, so every graceful shutdown dropped the bytes + duration of every in-flight raw tunnel from the request log, the JSONL export, the SIEM feed and the dashboard totals — systematic across a rolling fleet upgrade); and **the drain's own evidence undercounted** ("Draining 0 active tunnel(s)" on a node severing hundreds of sessions; `activeConns` is also the dashboard field an operator sizes FD budgets from). **Counting alone would have been the WRONG fix and this is the load-bearing part**: long-lived is what WebSocket and SOCKS5 are FOR, so a drain that waits on them with no way to END the wait hits its deadline on EVERY shutdown of a node carrying one — a guaranteed 15 s per node across a fleet upgrade — and severs them anyway; the operator pays the window and gets nothing. So the registry holds BOTH legs and the drain deadline force-closes them (mirroring PR3d's `forceCloseH2InspectTunnels` rather than inventing a second mechanism): each relay's `io.Copy` returns, its parent runs `recordTunnelClose*`, and the accounting lands while the FLUSH hooks (order ≥ 110) are still ahead. Force-closing is never worse than the SIGKILL it replaces — that abandons the same conns AND the accounting. Five rules hold. **(1) `registerDrainableTunnel` OWNS the `activeConns` accounting for its class** — a caller must NOT also call `recordActiveConn`, or the drain waits on a count that never reaches zero and spends the whole window on every shutdown forever after; release is idempotent (`sync.Once`), because a negative gauge makes `active <= 0` true permanently and restores the original blindness by accident. **(2) The map key is the ENTRY POINTER, never a conn**: two tunnels can legitimately hold the same conn value (the strip-path fallback registers `rawClient` while the inspect path registers the `tls.Conn` wrapping it), and a conn-keyed registry lets one release evict the other's registration — measured, it evicts BOTH. **(3) The backstop closes CONNS, not contexts** — `idleCopyCounted` sits in `io.CopyBuffer`, which returns only on a read/write error, and the peer direction may be parked in a deadline-less Write nothing but a close can end; entries are LEFT in the map (the relay's own release removes them; deleting here races a concurrent release into a double decrement). **(4) The settle is a CEILING clamped to the phase budget** (`tunnelForceCloseSettle`, 2 s) and is SKIPPED on the `ctx.Done()` branch — the budget is already spent there, lingering would take time from the hooks behind us, and losing that accounting is exactly the pre-change behaviour, never worse. **(5) An inspected-H2 tunnel appears in BOTH registries** and that is deliberate, not double-counting: this registry owns the single `activeConns` increment while `culvert_h2_inspect_active` measures the GOAWAY-capable subset; both backstops fire at the same deadline and a second `Close` is a no-op. Surfaces: `culvert_tunnels_active{class}` (five classes; the label names are a monitoring contract, pinned by test) + `culvert_tunnel_drain_forced_total`, and a per-class breakdown in the drain's log line — when the drain times out, WHICH kind of session held the node decides the remedy. A **PX-4 residual** closed alongside: `relayPlaintextInspectFallback` was the ONE relay goroutine in the tree with no panic guard (every other raw relay has carried one since CHAOS-24), so a panic there killed an in-line security appliance and dropped every OTHER in-flight tunnel with it. Gates: `proxy_tunnel_drain_chaos_test.go` (15) — every defect gate verified failing against its reintroduced pre-fix shape, plus CONTROLS for the two cheapest wrong fixes (force-closing at drain START passes every defect gate while being strictly worse than the defect; a quiet node must still shut down instantly). **A SHUTDOWN FENCE (`fenceTunnelEstablishment`, hook order 94) refuses NEW long-lived tunnels before the drain looks, and the ordering IS the correctness argument** — after the listeners stop (80/90) so a session the drain could still cover is never refused needlessly, before the drain (100) so nothing establishes behind its back. It exists because **the HTTP paths have a synchronization barrier before the drain and SOCKS5 has none**: `proxySrv.Shutdown` (90) waits for every in-flight request, so a CONNECT/WS either completes or hijacks-and-registers before the drain; `socks5Server.Stop` (80) waits only for the ACCEPT LOOP (each session is a detached `go handleSOCKS5(conn)`), so a session accepted just before Stop can sit in its 30s negotiation deadline plus a 10s dial and register up to ~40s later. Since `drainActiveTunnels` returns IMMEDIATELY when `activeConns <= 0` — exactly a node whose SOCKS5 sessions are all still negotiating — the drain, the backstop and the FLUSH hooks could all complete before the handler sent `0x00 success` and established a tunnel nothing would ever close or account for: PX-8 surviving inside its own fix (Codex review, PR #1288). The fix REFUSES rather than registering earlier: registering at handler entry would make the drain wait on sessions that may never become tunnels and would redefine `culvert_tunnels_active` from live tunnels to attempts, whereas a `0x01` reply is protocol-correct and lets the client retry against another node instead of receiving a success and a tunnel that dies seconds later. The check sits AFTER the dial and immediately BEFORE the reply, so the check-to-register window is microseconds, not a 10s dial. `culvert_tunnel_fence_refused_total` counts refusals; `resetTunnelDrainRegistryForTest` must clear the fence (a leaked fence refuses every SOCKS5 session in every later test). Deliberately left: `go trackDestinationCountry` still unguarded, and tunnels are cut rather than migrated — draining a node before a restart stays the operator's job. - **An unusable webhook signing secret is PRESERVED and REPORTED, never blanked away (SEC-WHSIGN-1, `internal/alerts`)**: webhook HMAC secrets are AES-GCM encrypted at rest (RISK-003) under a NODE-LOCAL key file (`<dataDir>/.alert_webhook_key`) that is deliberately never archived — the same rule that excludes `.kek` files, since a key must not share a tarball with the material it unwraps. `alert_webhooks.json` IS archived, so restoring a backup onto a fresh volume is the reachable way to hold a secret that cannot be unwrapped (an unreadable key file at boot — permissions, or an EMFILE window — gets there too). Three rules hold. **(1) The in-memory cleartext is still dropped** (never sign with a value that failed authentication), so `deliverAttempt` emits no `X-Culvert-Signature`. **(2) The on-disk ciphertext is KEPT** in the unexported `Webhook.sealedSecret` and written back VERBATIM by `save()`; re-encrypting the blanked cleartext persisted `""` and destroyed recoverable key material, and because `save()` rewrites the WHOLE list that was triggered by an unrelated add/edit/delete/toggle — the code's own "no data loss on a transient key-read failure" comment was not upheld. Restoring the original key file now recovers signing without re-entry. **(3) The state is VISIBLE.** `List()` blanks `Secret`, so "no secret was ever configured" and "the secret is unusable and deliveries are UNSIGNED" used to serialise identically — a monitoring blind spot where a receiver that verifies the HMAC silently stops accepting this node's security alerts, and quiet looks like healthy. `List()` now reports a DERIVED read-only `SigningDegraded` (`signing_degraded`), the `alert_webhook_signing` operator-contract row warns (counts only — no name, URL or ciphertext on that viewer-role surface), and the Alert Webhooks panel badges it. The status is derived and NEVER accepted from a caller or from the file (`Add`/`Update`/`Init` all clear it) and is never persisted. Delivery stays fail-OPEN-but-loud (unsigned, badged) rather than refusing to deliver: silence is worse than a visible authenticity failure on the alerting channel — recorded owner decision. **(4) A failed DECRYPT never mints a key** (`webhookSecretKey(dir, create)`; `create` is true only on the encrypt path). Minting on read meant the restore case wrote a fresh key as a side effect of failing to decrypt, so the preserved ciphertext and every later write sat under DIFFERENT keys and the documented "restore the original key file" recovery would break exactly the secrets the operator had already re-entered (Codex review, PR #1222). Creation now happens on the first encrypt — an explicit operator action — which also stops a failed read from attempting a write on a read-only or full volume. The operator remedy is therefore ORDERED and both surfaces say so: restore the original key file FIRST if you still have it (no re-entry needed), otherwise re-enter each secret, and never restore the old key AFTER re-entering. - **DPI scan ReDoS budget is enforced ONCE PER SCAN, not per pattern (`internal/scanner`)**: `ContentScanner.Scan` runs on every SSL-inspected response body (`safeDPIScan`, proxy_tunnel.go). `re.Match` is not interruptible, so the per-match ReDoS deadline needs a goroutine to abandon — and that harness (goroutine + channel + timer) used to be paid PER PATTERN: measured 6 allocs/448 B each, so a 20-pattern policy charged 120 allocs/9.0 KB and a 50-pattern policy 300 allocs/22.4 KB to every inspected body. - **The per-minute time series is SHARDED on its current minute (`store.go`)**: `tsRecordResult` runs on EVERY proxied request via `recordStats` — HTTP, CONNECT, WebSocket, SOCKS5 alike. It took ONE process-wide `sync.Mutex` and, while HOLDING it, read the clock (`tsAdvance`'s `time.Now`) before bumping three counters, so every request in the process serialised on one lock across a vDSO clock read. Same class as the `internal/threatfeed`, `internal/connlimit`, IP-filter and latency-histogram findings. **The header this replaces recorded the opposite conclusion and the way it was reached is the lesson**: an RLock+atomic fast path had been benchmarked, measured FLAT, and read as "every request bumps the SAME current-minute bucket, so the shared cache line, not the mutex, is the bound". Both halves were wrong — `RWMutex` cannot help a path that MUTATES, so a flat result said nothing about the bound; and the shared cache line is inherent only while the counter stays shared. The measurement that settles it is not ns/op at one core but how ns/op MOVES with core count (4-core box, Go 1.26, ns/op, GOMAXPROCS 1 / 4): mutex with the clock inside it **85.5 / 178.6**; clock hoisted out 83.1 / 144.9; lock-free but counters still shared 78.9 / 62.2; lock-free and SHARDED **85.9 / 38.1**; `time.Now().Unix()/60` alone — the irreducible floor — 64.8 / **16.6**. Read the floor first: at four cores the old path spent 162 of its 179 ns NOT doing the work. In the real code `tsRecordResult` went **172.6 → 36.1 ns/op at four cores** (four cores had been delivering 5.8M records/s against 11.4M on ONE core — adding cores SUBTRACTED throughput — and now deliver 27.7M, **4.8x the old ceiling**), and the whole `recordStats` fan-out **275.8 → 131.2 ns/op**. There is NO low-concurrency price — one core came out AHEAD too (142.9 → 130.0), because dropping the lock/unlock pair and collapsing the verdict pair into a single atomic add together cost less than picking a shard. **Those fan-out figures are TIGHT-LOOP numbers and are not the ones to quote** — `store_stats_bench_test.go`'s methodology note (added by the topHosts work, #1357) records that a tight `recordStats` loop is not the production duty cycle, because speeding one component only raises the arrival rate at the next contended one. The MARGINAL cost, `BenchmarkRequestCycle` in isolated processes (n=5, medians, ns of fan-out per request), is the number a gateway pays and is also where the two sharding changes COMPOSE: sharded topHosts alone **129 / 490** at GOMAXPROCS 1 / 4 — cores made it WORSE, the ceiling had simply moved to the other component — versus **111 / 87** with the time series sharded too, i.e. it FALLS with core count and is 5.6x cheaper at four cores. The bimodality that note warns about shows up in exactly the arm that still has a contended component (main's 4-core WithStats spread 755–784 ns across five runs; this branch's 364–371). Only the CURRENT minute is hot, so only it is sharded — the 60-bucket ring is untouched and still mutex-guarded; requests accumulate into `live` (`tsShardCount` 64, cache-line padded), a `rollover` folds them into the bucket they belong to, and readers (`tsGet` — the SSE dashboard tick, `/api/stats`, the history-store disk estimate) sum the shards in, moving work read-ward exactly as the sharded histogram does. **`record` has no key to shard on** — a request contributes to a global count, not a per-IP or per-host slot — so the index comes from `math/rand/v2`'s per-P generator (aliased `mrand`; this file's `rand` is `crypto/rand`), NOT a shared atomic round-robin counter, which would reintroduce the very cache line being removed. **THE INVARIANT IS CONSERVATION, NOT INSTANT ATTRIBUTION**: a request descheduled between reading `liveMin` and incrementing lands in the NEXT minute's accumulator, an at-most-one-bucket shift on a 60-minute sparkline; nothing is ever lost, because `foldLiveLocked` **SWAPS** each shard to zero rather than reading-then-zeroing, so a late increment is carried into the following fold. That distinction is not theoretical — a read-then-zero fold loses counts on every run of `TestTimeSeries_ConservedAcrossRollover`, which counts writers rather than fixing a total in advance and so is exact regardless of scheduling. **But whole-window conservation is NOT sufficient, and that is the sharp edge**: `/api/timeseries` hands the dashboard three PARALLEL arrays, so the invariant is also PER BUCKET (`allowed[i]+blocked[i] == buckets[i]`). The first shipped shape carried a separate `total`/`allowed`/`blocked` triple, so a writer took TWO independent adds and the fold THREE independent swaps — a fold landing between a writer's two adds banked its total in the OLD bucket and its verdict in the NEW one, a permanent per-bucket mismatch that conserved the window total perfectly and so passed every window-sum test (Codex review, PR #1286). A request's counters therefore live in ONE word: the allow/block pair is PACKED (`verdicts`, allowed high 32 bits / blocked low 32) and a verdict is a SINGLE atomic add, with unverdicted records (`tsRecord`) on their own `plain` word — each writer touches exactly one, so the fold's two swaps are independent BY CONSTRUCTION. The packing is also FASTER (one add, not two), which is why one core came out ahead. The 32-bit halves bound one shard between two folds, i.e. one wall-clock minute: 4.29e9 requests on one shard ≈ 4.6 billion req/s process-wide, unreachable, and an idle shard accumulates nothing. **Do not unpack this back into a counter triple.** Pinned by `TestTimeSeries_PerBucketVerdictsStayConsistent` (verified failing 3/3 against the split-counter shape, while `ConservedAcrossRollover` passed throughout — the two gates are not redundant). `tsGet` sums the shards WITHOUT draining (a read that drained would report traffic once and show zero on the next dashboard poll) and still does not advance the ring, so an idle proxy reports the window as it stood at the last request — unchanged. `advanceLocked` carries over the old `tsAdvance` verbatim, including first-record (`lastMin == 0`) and clock-went-backwards (`diff <= 0`). Gates (`store_timeseries_shard_test.go`): `TestBenchGate_TimeSeriesRecordTakesNoLock` is **structural, not timing-based** — it HOLDS `ts.mu` and requires the record path to complete anyway, so a return to serialising fails deterministically on any hardware, under any load, with or without `-race` (a scaling-ratio gate was rejected for the same reason connlimit's and the histogram's were: a gate that can flake gets muted) — with `TestTimeSeriesShards_DistributionIsNotDegenerate` as its CONTROL, because a no-lock gate would also pass if every request piled onto one shard. Both were verified failing against the reintroduced pre-fix shape. The two gates that depend on not crossing a wall-clock minute retry instead of failing, so a real rollover can never be reported as a regression.
- **Per-request tracing setup pays no canonicalisation and ONE CSPRNG draw (`proxy.go` `setupRequestTracing` + `connlimit.go`)**: `setupRequestTracing` is the SECOND statement in `handleRequest` — ahead of the connection limiter, the IP filter and authentication — so it runs on 100% of proxied traffic on every protocol. On the end-to-end proxy benchmark it was **13.8% of every allocation `handleRequest` made** (alloc_objects at `memprofilerate=1`, `BenchmarkPerfQual_ProxyHTTPForward/rules=100`: 13,228 of 96,072 objects), and more than half of that bought nothing at all. **(1) `"X-Request-ID"` is not the CANONICAL MIME spelling.** Every `Header.Get`/`Set`/`Del` routes its key through `textproto.CanonicalMIMEHeaderKey`, which has a fast path that scans for already-canonical input and returns it verbatim, and a slow path that copies the key into a `[]byte`, rewrites the casing and ALLOCATES the result. The fix is BYTE-IDENTICAL on the wire, not merely compatible: `Set` already stored under `CanonicalMIMEHeaderKey(key)`, so the map key — and therefore what `Header.Write` emits — was `X-Request-Id` before the change too; only the re-derivation is removed. **(2) The two IDs were drawn and encoded separately.** `crypto/rand.Read` carries ~27 ns of fixed per-call cost on top of ~2.5 ns/byte, so draws of 8 and 24 bytes cost 131 ns where one draw of 32 costs 106 ns, and each generator allocated its own string. `generateTraceIDs` lays both IDs end to end in one stack buffer, converts ONCE and returns slices of that single string (slicing a string is free — the two header values share one 71-byte backing array): 250 ns / 2 allocs → 190 ns / 1 alloc. The IDs are cut from DISJOINT bytes (request ID 0:8, trace-id 8:24, parent-id 24:32), so sharing a draw does not correlate them and the request ID is not recoverable from the traceparent a downstream origin receives. Measured on a 4-core Xeon @2.8GHz, median of n=7: fresh request (client sent neither header) **969 → 584 ns/op, 8 → 4 allocs**; already-traced request (client sent both) **320 → 164 ns/op, 3 → 1 alloc**; 4x parallel **362 → 213 ns/op**. Gates: `proxy_tracing_test.go` (7 — the differential, the layout check through the production `parseTraceparent` consumer, uniqueness, sanitisation, the only-what-is-missing arm) + `TestBenchGate_RequestTracingAllocs` (bounds are the exact measured steady state, no headroom) and `TestBenchGate_RequestTracingBeatsLegacy` (the before/after saving, measured in ONE run so it is machine-independent). - **The request-latency histogram is SHARDED (`metrics.go`)**: `latencyHist.Observe` runs on EVERY proxied request (`recordRequestTelemetry`, proxy.go) — HTTP, CONNECT, WebSocket alike. It was documented as "lock-free", which is not the same thing as contention-free: it wrote three atomics per observation onto two shared cache lines, and the first was a compare-and-swap **LOOP** over ONE process-wide accumulator. A CAS loop under contention does not merely serialise — every losing core retries, and the retries generate the coherence traffic that makes the next round lose — so the metric got MORE expensive per request the more cores carried traffic, on 100% of traffic. Same class as the `internal/threatfeed`, `internal/logsink` and `internal/connlimit` findings. Median of n=15 on a 4-core box: **20.6 / 179.6 / 292.3 ns/op at 1 / 2 / 4 cores before** (four cores delivered 3.4M observations/s against 49M/s on ONE core — adding cores SUBTRACTED throughput) → **18.3 / 40.7 / 30.3 ns/op after**, flat in core count, **9.6x** the old four-core ceiling and slightly better at one core, so there is no low-concurrency price. The absolute "before" number is load-sensitive BY CONSTRUCTION (a contended CAS loop degrades further the busier the box is — a quieter run of the same benchmark measured 15.0 / 125.5 / 158.9 → 13.6 / 16.6 / 12.0); quote the SHAPE, not the constant. Two changes, both cost-only — every rendered number is the same number: (1) counters split across `histShardCount` (128) cache-line-padded `histShard`s, summed at scrape (a scrape is once per scrape interval against a per-request write path, so moving work read-ward is the correct direction); (2) the separate `total` field is GONE — the count is the sum of the bucket counters, which removes an atomic write AND makes `_count` exactly equal the `+Inf` bucket as the Prometheus exposition format requires (the old shape bumped `total` BEFORE the bucket, so a scrape landing between the two rendered `_count` one greater than `+Inf`). **The sum stays a float64 CAS, now per shard, and that is load-bearing:** an integer-NANOSECOND accumulator is a single atomic add and measured ~0.4 ns/op cheaper serially and ~2.9 ns/op cheaper at four cores, but int64 nanos overflow after 9.2e9 seconds of ACCUMULATED latency — about **107 days** of uptime for a 10k req/s gateway averaging 100 ms — and a wrapped sum exports a NEGATIVE, non-monotonic `_sum` to Prometheus and OTLP (caught in review on PR #1200; pinned by `TestHistogramSumDoesNotOverflowAtHighAggregateLatency`, which is written to fail against the integer form). Sharding is what removed the contention; the accumulator's TYPE never had to change to get it, and per-shard partial sums are ~128x smaller than the old global one so float64 precision is better than before, not worse. **Do not re-derive this as an integer accumulator.** The bits live in a `uint64` with `atomic.CompareAndSwapUint64`, NOT the pre-sharding `int64`: `math.Float64bits` speaks uint64, so the int64 field cost a `uint64<->int64` conversion on every read and write, each carrying a `// #nosec G115` that golangci-lint does NOT honour (those lines only survived because the lint gate runs `--new-from-rev` and predated them — the suppression was never load-bearing, the grandfathering was). The unsigned field removes both conversions and both suppressions. A non-finite guard is also new: one NaN observation used to poison `_sum` permanently. **`Observe` has no key to shard on, so the shard is derived from the observation itself** (splitmix64 over the float bits): latencies come from `time.Since`, so the low mantissa bits are nanosecond noise and spread well (4096 realistic samples fill all 128 shards, min 19 / max 49 / mean 32, none empty). A caller observing a CONSTANT value collapses to one shard and scales as the old code did — **never worse** — and that limitation is pinned as a CONTROL test rather than hidden. `snapshot()`/`Count()` are the read accessors (otlp.go and the histogram tests go through them). Gate: `TestBenchGate_ObservationsDoNotShareOneCounter` is **structural, not timing-based** — it requires realistic observations to touch many distinct shards, so a collapse back to one counter set fails deterministically on any hardware, under any load, with or without `-race` (the scaling-ratio gate was rejected for the same reason connlimit's was: a gate that can flake gets muted), with `TestBenchGate_ConstantObservationsCollapseToOneShard` as its control. `newHistogram` rejects more than `maxHistogramBuckets` (12) bounds rather than silently truncating. Full suite in `metrics_histogram_shard_test.go`.
- **Destination-category resolution is per-SCAN, not per-rule (`policy_hostcat.go`)**: `Evaluate` already hoists the request-invariant work out of its rule loop (normalized host, parsed client IP, one `scanNow` clock read). The host→category fusion is the same class of value — it depends on the HOST, not the rule — and is by far the most expensive: `catStore.LookupHost` (which every `DestCategoryGroup` rule reaches via `lookupHostCategory`) deliberately walks every host pattern in the taxonomy instead of the lowercase index, so it can report the admin's configured pattern verbatim for the URL-lookup API — O(patterns), lowercasing + concatenating per pattern — and `communityDB.Lookup` opens a **BadgerDB read transaction per domain label** on a feed-backed deployment. Run per rule, that fixed cost was multiplied by the rule count: measured on a 12-category / 480-pattern taxonomy against an uncategorized host, a category-group scan cost **205 µs at 10 rules, 1.01 ms at 50, and 4.03 ms at 200 — per request**, with 91% of the profile in `LookupHost`. `hostCatScratch` resolves each host-only tier at most once per scan (**−89.7% / −97.8% / −99.3%**; −96.8% at 4x parallel; allocation counts unchanged — the scratch stays on the stack, and non-category scans are statistically unchanged). - **Host→category resolution is INDEXED in both directions (`internal/urlcat`)**: the store has always carried a forward index (`index`/`adminIndex`: category → lowercase host set) giving `MatchesHost` an O(labels) probe, but the REVERSE direction — `LookupHost`/`LookupHostAdmin`, host → category — was a nested scan over every host pattern of every category. Clean traffic is the WORST case — an uncategorized destination cannot short-circuit, so it walks all of them. Measured on the SHIPPED default taxonomy alone (657 patterns / 27 categories): ~24 µs per lookup, and a 20-rule category posture cost **~497 µs of pure CPU per request** in `Evaluate` (1 rule 24.5 µs, 5 rules 126 µs). `hostIndex`/`adminHostIndex` now map a lowercase pattern → the `patternRef` (entry position, host position) of the FIRST entry declaring it, and `lookupIn` probes only the keys that can match (the host, then the remainder after each `.`): 325 ns / 1.3 µs / 4.6 µs for the same 1/5/20 rules (**−98.7% to −99.1%**), flat in taxonomy size (~80 ns at 5657 patterns vs 252 µs before), still 0 allocs/op. **The winner is unchanged, and that is the load-bearing part**: the old loop returned the first `(entry, host)` position whose lowercased pattern matched, so taking the MINIMUM position over the matching keys is the same result — including the case where a LESS specific pattern in an EARLIER category outranks a more specific one in a later category, which a plain most-specific-suffix walk silently inverts. `matchedBy` stays the admin's verbatim configured pattern (hence the index resolves back through `s.entries`). The memo is now REVISION-KEYED and LAZY: writers only bump the monotonic `rev` (`invalidateFingerprintLocked`, O(1)), and `ContentFingerprint()` serves the cached `{rev, fp}` while `rev` matches, else computes under the READ lock, single-flighted through `fpMu` (lock order `fpMu` → `s.mu`). Freshness stays exact because `rev` advances inside the writer's critical section — a reader that can see new content necessarily sees the advanced revision — and `rev` is monotonic, so a revision names exactly one content state. Pinned by `urlcat_fingerprint_cost_test.go` (ratio cost gate, warm-memo freshness gate, concurrent two-state gate) alongside the value contract in `urlcat_fingerprint_test.go`. Pinned by `internal/urlcat/urlcat_lookup_index_test.go` (differential test against the verbatim pre-index scan: hand-picked divergence shapes, 200 randomized taxonomies, mutation tracking, the whole shipped taxonomy, and a race-detector reader/mutator run) and `urlcat_lookup_bench_test.go` + `BenchmarkPolicyEvaluate_CategoryGroupRules` (policy_bench_test.go). - **Threat-feed lookups are LOCK-FREE (`internal/threatfeed`)**: `CheckDomain` runs on EVERY proxied request and `CheckURL` additionally on every plain-HTTP one (`preDispatchBlocked`, proxy.go), and both used to take `tf.mu.RLock` **twice** — once inside `Enabled()`, once for the map probe. `sync.RWMutex.RLock` is an atomic read-modify-write on one shared word, so every request wrote the same cache line purely to read tables that in steady state never change. That is not a constant cost but a **throughput ceiling**: measured (4-core Xeon, 100k entries) `CheckDomain` cost **100.6 ns/op serial but 211.7 ns/op at 4x parallel** — it got 2.2x SLOWER as cores were added, on a per-request path, exactly when a gateway is busiest (same shape as the `internal/logsink` finding). The three lookups now read an immutable `readView` published via `atomic.Pointer` (**88.8 ns serial / 22.6 ns at 4x parallel — 3.9x near-linear scaling, 9.4x the old parallel figure**; `CheckURL` parallel 284→187 ns). **The contract is one line and it is load-bearing: a map reachable from a PUBLISHED readView is never mutated in place.** Every writer of `enabled`/`urls`/`domains`/`domainAllowlist` installs a REPLACEMENT map and calls `publishLocked()` before releasing `tf.mu` — `AddDomainAllowlist`/`RemoveDomainAllowlist`/`SeedForTest` were converted from in-place edits to copy-then-swap for exactly this reason (admin-rate paths; the allowlist is tens of entries). **Adding a mutator without a `publishLocked()` call is a silent SECURITY failure, not a perf one** — a synced threat entry that never blocks, or a revoked allowlist exemption that keeps suppressing hits — so it is pinned per mutator by `TestReadView_EveryMutatorRepublishes`; the no-in-place-mutation half is enforced by the race detector via `TestReadView_ConcurrentReadersAndWriters`. The view ALIASES the maps (publishing a 500k-entry sync is one pointer store, not a copy), and taking it ONCE also fixed a latent consistency hole: the old shape dropped the lock between the `Enabled()` probe and the table probe, so a concurrent `Sync` could be observed half-applied. The regression gate (`TestBenchGate_LookupsTakeNoFeedLock`) is deliberately **structural, not timing-based** — it holds the write lock and requires the lookups to complete anyway; the scaling-ratio gate was built first and rejected because its margin narrows to 1.35x under `-race`, too thin for a per-PR runner. Still-locked (cold, correct): `DomainAllowlisted`, `DomainAllowlist`, `saveToDisk`, `Stats`, the export/cluster surfaces.
- **The blocklist read lock is SHARDED, not a read view (`internal/blocklist/hotread.go`)**: `Store.IsBlocked` runs on EVERY proxied destination — plain HTTP, CONNECT, WebSocket and SOCKS5 all reach it through `preDispatchBlocked`, before any policy work begins — and it took ONE process-wide `sync.RWMutex` read lock to reach its verdict. Same finding as `internal/threatfeed` above: `RLock` is an atomic read-modify-write on one shared word, so every request in the process wrote the same cache line purely to read maps that in steady state never change. Measured (4-core Xeon, 100k-entry feed-backed store, one wildcard, an ordinary 33-byte CDN host that MISSES — what every ALLOWED request pays; medians of n=7, aggregate Mlookups/s, `BenchmarkIsBlockedScaling` vs `BenchmarkIsBlockedScaling_Baseline` at `-cpu 1,2,4`): default no-exceptions posture **9.01 / 6.25 / 6.58 before → 8.60 / 10.21 / 16.43 after (2.50x at four cores)**; with exceptions configured **3.47 / 3.34 / 3.52 → 3.55 / 6.01 / 11.08 (3.15x)**. The finding is the BEFORE row: not that the store was slow but that it was **CAPPED** — four cores delivered *less* throughput than one, because each added core only contributed more traffic to the single contended line. **The instrument is deliberately NOT this repo's `atomic.Pointer` read view, and that choice is measured.** threatfeed and IPFilter replace their large maps wholesale and mutate only small ones incrementally; this store is the opposite — `exact`/`wildcards` are LARGE (a feed-backed deployment runs to 10^6 hosts) and are mutated INCREMENTALLY by `ApplyDelta` on every cluster delta sync, plus `Add`/`AddManual`/`Remove` and the pruning paths. A copy-on-write publish costs 0.65 ms/437 KB at 10k, 12 ms/3.5 MB at 100k and **190 ms/56 MB at 1M**, so a view would have traded a read-side ceiling for a per-delta-sync stall and a GC-pressure regression, and the admin bulk-delete handler (`ui_policy.go` loops `bl.Remove`) would have become O(hosts x blocklist-size) — the exact O(N^2) trap IPFilter had to add `AddAll` to escape. Sharding the READ side instead removes the contention with **zero write amplification: every one of the 15 mutator bodies is byte-identical** and writers keep true exclusive access, which also means this change structurally cannot carry the view's failure class — there is no view, so there is no mutator that can forget to publish one. `hotRW` gives readers one of 64 cache-line-padded `sync.RWMutex` shards (index from `rand.Uint64`, per-P and lock-free since Go 1.22; there is no key to shard on, so the goal is only to spread readers across lines) while `Lock` takes EVERY shard in ascending order — readers hold at most one shard, so the ordering is total and deadlock is impossible. Cold admin/persist readers share shard 0 and are unchanged. **The trade, both directions:** a writer now pays 1.52 us instead of 24 ns (62x — just the shard count), against callers that already do far more work and run at admin/feed rate; and at ONE core the read path is ~5% slower (8.60 vs 9.01 Mops/s) from the added `rand.Uint64` — recorded rather than papered over, exactly as `internal/connlimit` recorded its own, because a single-core gateway is the one shape a forward proxy is never in. Gates: `TestHotRW_WriteLockExcludesHotReaders` (the mutual-exclusion contract, deterministic because a writer holds every shard so the reader's draw cannot matter) and `TestHotRW_ConcurrentReadersAndMutators` (every real mutator against the real hot path under `-race` — the two that catch a writer which stops taking all shards; both verified failing against that injected defect), plus `TestBenchGate_HotReadsSpreadAcrossShards`, which is **structural, not timing-based** (it counts distinct shards reached, so a collapse back to one lock fails on any hardware, under any load, with or without `-race` — the scaling-ratio gate was rejected for the same reason connlimit's and the histogram's were). **A parallel benchmark on this path must give each worker its OWN sink**: the serial form (`benchBlocked = st.IsBlocked(...)`) is correct serially and ruinous under `RunParallel`, where every worker then writes one shared cache line per iteration — that false sharing became the bottleneck being measured and flattened the sharded store to the baseline's throughput, hiding the entire finding until a pure-CPU control proved the box scales 4.0x.
- **GeoIP policy**: Fails closed on cache miss (unknown country = rule does not match)
- **The GeoIP policy accessor is CACHE-ONLY, and the enforcement path owns its own warmer (CHAOS-60, `geoip.go` + `geoip_resolve_health.go`)**: deciding a country-scoped rule needs TWO cached facts — host→IP (`resolvedHostCache`) and IP→country (`internal/geoip`) — and `matchDestNorm` reads both through `geo.LookupCached` inside the request goroutine, which holds the client connection and a per-IP `connlimit` slot while it runs. **`LookupCached` blocked.** It called `resolveHost`, which on a miss called `net.LookupHost` — **no context, no deadline, no way to abandon**, running to the system resolver's full budget (`resolv.conf` timeout × attempts × nameservers, 10–40 s on a blackholed resolver) — before policy evaluation could continue, and before the plain-HTTP path's `upstreamRequestTimeout` is even armed (the CONNECT path has no overall budget at all). The register recorded this path as SAFE (row WK-3, ✓, *"never blocks on DB/DNS"*); the claim was true when written and was invalidated by the host→IP cache being added in FRONT of the blocking call without removing it — the cache made the common path fast, which is why nothing noticed the miss path. There was no single-flight either, and the negative entry that suppresses the next lookup is written only when a lookup RETURNS, so in exactly the window where lookups do not return nothing suppresses the next one: measured pre-fix, **50 concurrent misses for one host → 50 resolver invocations**, i.e. the proxy amplifies client request rate 1:1 (×2 for the A/AAAA pair) into queries at an already-failing resolver. **The second half is worse and is a security finding**: after resolving, the country is read from a cache whose ONLY populator on the request path was `trackDestinationCountry` — a best-effort DASHBOARD sampler that runs on the ALLOW branch only, after the decision, behind a 256-slot drop-on-full semaphore whose own comment says samples are dropped rather than queued. Country-scoped **enforcement** therefore depended on a telemetry goroutine having won a slot on an earlier request; saturate it (or block the first request, so the sampler never runs) and every country rule silently stops matching, with the rule's hit counter reading exactly like "no traffic matched this rule". Four rules now hold. **(1) The accessor never resolves**: `resolveHostCached` answers from an IP literal or a live entry, a miss returns `("", false)` — the fail-closed answer the call site already documented — and arms a warm; "unknown, nothing cached" and "resolved to nothing usable" are DISTINCT returns because only the first is worth warming (a negative-cached host is governed by its 30 s TTL, never by the request rate). **(2) The warm is bounded by a SEMAPHORE (`geoWarmSem`, 64, drop-on-full), deliberately NOT by a context deadline** — under the cgo resolver a cancelled lookup returns to the caller while the OS thread stays blocked in `getaddrinfo`, so a deadline would release the slot without releasing the thread, converting a bounded goroutine pool into an unbounded THREAD pool; holding the slot for the TRUE duration of the call is what makes the bound real. A queue was rejected for the usual reason: it converts a resolver outage into unbounded memory and unbounded staleness. **(3) Misses are SINGLE-FLIGHTED and the host is CLAIMED BEFORE A POOL SLOT IS TAKEN** (`hostIPCache.begin`/`finish`, the `jwksCache` leader-publishes-to-followers shape). The ORDER is load-bearing and was wrong in the first version of this fix (Codex P1): a pre-CHECK (`resolving`) with the actual claim left to the goroutine (`begin` runs inside `resolveHost`) means concurrent evaluations for ONE uncached host all pass the check, all take a slot, and all but one park as followers HOLDING those slots for the resolver's full delay — so one popular destination drains the 64-slot pool and every unrelated host's warm is dropped and its country rule left unresolved, i.e. the GEO-2 degradation re-entered through the fix for GEO-2. `begin` is now called SYNCHRONOUSLY in the caller before any slot is taken; a non-leader returns having touched nothing, and a leader that cannot get a slot HANDS THE CLAIM BACK (`finish` with nil, deliberately WITHOUT a cache write — nothing was learned and a negative entry would suppress the retry for a full TTL over a transient shortage). `finish` is idempotent (`sync.Once`) so every hand-back path can call it unconditionally. The slot is released to the channel it was TAKEN from (`sem` is captured, not re-read), so a goroutine outliving a swap cannot release into a channel it never acquired. **(4) The warm fills BOTH caches** (`geoip.LookupByIP`, not just the resolver) — that is what removes the dependency on the dashboard sampler, and why it also fires on the country-half miss (host cached, IP never geolocated), the shape that was otherwise permanently undecidable on a saturated node. Surfaces (emitted ONLY when a GeoIP DB is loaded — the socks5/cluster_ca rule: a flat `0` on a node with no GeoIP is indistinguishable from one whose geo rules stopped enforcing): `culvert_geo_{warm_total,warm_dropped_total,warm_failed_total,warm_saturated,warm_inflight}` plus **`culvert_geo_policy_unresolved_total`**, the first signal an operator has ever had that a geo rule is evaluating against an unknown country (a low rate is expected — one per host per cache lifetime; a rate tracking request rate means enforcement is not converging). - **Periodic feeds back off, jitter, and report their freshness (CHAOS-59, `internal/feedsched` + `threatfeed_health.go`)**: Culvert ships THREE periodic feed loops and only the newest — the signed SaaS feed's `saasFeedScheduler` — scheduled itself correctly. The two older ones (`internal/threatfeed`, `internal/feedsync`) were bare `time.NewTicker`s that DISCARDED the round's outcome, which fails in three directions at once. **Cadence:** a ticker has no notion of failure, so a failed round waited a FULL interval — 6 h for threat intel, **24 h** for the UT1 category feed — and the triggering fault is a DNS blip, a 503, or a restarted upstream proxy, not an exotic one. **Cold start:** `Start` syncs immediately when the on-disk DB is empty (fresh install, re-image, replaced volume, a §19 quarantine), so a node whose FIRST round failed enforced with an EMPTY threat database — not stale intelligence, NONE — for up to six hours while `/health`, `/ready`, `/metrics` and the dashboard all reported a healthy gateway. **Fleet:** a ticker fires at a fixed offset from process start, so nodes that boot together sync together FOREVER against public third-party origins shared by every deployment (abuse.ch, openphish.com, and a 50+ MB tarball on `raw.githubusercontent.com`); the ordinary answer to that is rate-limiting of the customer's egress IP, which PRODUCES the failure the absent backoff then holds the whole fleet at — a closed loop where the scheduler manufactures the outage it cannot recover from. **And none of it was visible, because the WK-5 carry-forward fix consumed its own detector**: `culvert_threat_feed_entries` is held at its last-good value BY DESIGN, so after that fix a feed dead for three weeks exported metrics byte-identical to one that synced ten minutes ago, and the sole surviving difference (`threat_feed_sync_ok`) reached ONE role-gated admin JSON blob nothing scrapes. `internal/feedsched` is the shared cadence engine, deliberately shaped like the `saasFeedScheduler` rather than invented: interval±**stable per-node jitter** (drawn ONCE — re-rolling per tick lets nodes drift back into phase and makes the cadence untestable) after a clean round, bounded exponential backoff after a failed one (threat feed 5 min→1 h, category feed 15 min→2 h), reset by the first success, waits INTERRUPTIBLE so shutdown never sits out a retry, and a **panicking round charged as a FAILED round** (contained at the iteration per `internal/obs`'s rule, so a hostile feed body backs off instead of hot-looping). **BOTH the retry floor and the ceiling are CLAMPED to the live interval** and that is load-bearing: a ceiling above the interval means a failing feed attempts LESS often than a healthy one, turning the recovery mechanism into an extra delay — a caller cannot express that shape. The invariant holds at EVERY interval: a retry is never later than the configured cadence. Retries are unbounded in COUNT and bounded in RATE, which does not violate "avoid infinite retries" for CHAOS-55's reason (never silent — counted, classified, alerted past the threshold) and because a feed that STOPPED retrying would freeze intelligence permanently on one transient error. - **A directory that ACCEPTS and then STALLS is bounded, not hung (CHAOS-58, `auth_ldap.go`)**: CHAOS-47's provider-wide cooldown is armed from `noteVerifyError`, i.e. by the error `verify()` RETURNS — so it can only see a fault that returns. `LDAPAuth.verify` dialed with a 10s dialer timeout and then ran up to four blocking operations (StartTLS, service bind, search, user bind) with NO deadline: go-ldap's `Conn` defaults to `requestTimeout: 0` and its message loop arms a timer only `if requestTimeout > 0`, so `Bind`/`Search` waited on a bare `<-msgCtx.responses`. - **Credential verification is a BOUNDED, observable resource (CHAOS-57, `internal/authcost` + `auth_cost_health.go`)**: Culvert authenticates on EVERY proxied request, and when the credential is a local account that means one `bcrypt.CompareHashAndPassword` at `bcrypt.DefaultCost` — **~80 ms of exclusive CPU**, measured. That constant is a property of the DATA PATH, not of a login form, and nothing bounded it. **The cheap branch is the WRONG-username branch**: `verifyAuthWithSnapshot` ran an unconditional comparison against `dummyBcryptHash` whenever the username did not match (RISK-008's timing equaliser — it exists for a good reason), and that branch sat BEFORE the result cache and never populated it, so a flood of DISTINCT usernames was a guaranteed miss every time — no credential, no valid username, no knowledge of the deployment. The three front-door limiters that could have capped the arrival rate all ship DISABLED (`-rate-limit` defaults to 0, connlimit disabled, no IP filter), and nothing capped CONCURRENCY, so N simultaneous requests put N goroutines into bcrypt at once. Measured on the 4-core reference box: **79.6 ms/attempt vs 1.5 µs for a cached auth (51,631x amplification); 66 req/s — ~13 KB/s on the wire — consumed 100% of all four cores; other CPU work degraded 15.6x under 64 attacker connections.** The arithmetic generalises without a benchmark: **12.5 × GOMAXPROCS requests/second saturates the machine.** `internal/authcost` now governs it with two fail-closed bounds and one fairness rule: a **GLOBAL CEILING** of `GOMAXPROCS/2` (floored at 1 — half, not all, because the gateway's real work must keep running while somebody authenticates; a ceiling equal to GOMAXPROCS bounds the fault without preventing the outage, and this is the bound that holds against a DISTRIBUTED flood); a **PER-CLIENT CEILING of 1** on how many slots one source holds AT ONCE (without it the global ceiling contains the CPU but not the OUTAGE — one source occupies every slot and denies everyone else). **A client at its cap WAITS for its own earlier verification; it is NOT refused on the spot** — getting that wrong was the engine's first shape and a self-inflicted outage: a single workstation opening its ordinary parallel connection pool, all of whose cached results expired together, had **five of six VALID credentials DENIED** with no attacker present (measured on the real auth path; it surfaced as a CI determinism failure and not locally, because whether one client's parallel requests overlap depends on machine load). Waiting costs fairness nothing — the cap still bounds what a source HOLDS at any instant — and only changes what happens to the excess: serialised behind its predecessor (~80 ms each) instead of rejected. Parked waiters count against the SAME bounded waiter budget as the global queue, and the wait is bounded, so a burst deeper than roughly `maxWait / verification cost` (about a dozen from one client) still ends in a refusal. **The lesson: "one source, one slot" is a correct FAIRNESS rule and an incorrect ADMISSION rule** — fairness is about what a client may HOLD, admission about what happens to the rest; conflating them turns a bound into a denial; and a **BOUNDED WAIT (1 s) with a BOUNDED QUEUE (8× the ceiling)** so a legitimate synchronised burst is absorbed rather than refused — **the queue is capped because an unbounded one converts a CPU-exhaustion vector into a goroutine-and-memory one, and trading one exhaustion for another is not a fix.** **THE ORDER OF THE CALL SITE IS A SECURITY CONTRACT, not style** (`verifyAuthFrom`, store.go): (1) the cache is consulted FIRST and UNCONDITIONALLY, ahead of the username comparison — this changes no verdict (entries are only ever stored for the configured username, so a wrong username was always a miss) and costs the same one HMAC + map probe either way, but it means a client riding a warm cache never consumes a slot, without which a legitimate high-rate deployment would be throttled by a bound on work it is not doing; (2) **admission is decided BEFORE the username is compared and must not depend on it** — gating only the branch that reaches the real hash (the obvious fix, and the one written first) makes "over budget" FAST for a wrong username and SLOW for a wrong password, handing back exactly the username-enumeration oracle RISK-008 removed, so the bound would have been bought with the vulnerability it protects; (3) refusal is a DENY (fail closed — the cost of a spurious refusal is a 407 the client retries); (4) the slot is held across BOTH branches and released by `defer` so a panic inside bcrypt cannot leak it. Pinned by `TestChaos57_AdmissionDecisionIsUsernameIndependent`, verified failing against the asymmetric shape. **The result cache's EVICTION POLICY is a security control too**: it is populated by UNAUTHENTICATED requests (negative results are cached, deliberately) and used to drop **one arbitrary LIVE entry** at capacity, so a flood of distinct passwords under a known username displaced OTHER clients' cached positives — measured gone by a 2×-capacity flood, after which the victim paid a full bcrypt on EVERY request, landing the attacker's amplification on legitimate traffic. `internal/authstate`'s policy is ported: entries are attributed to a client key and eviction takes the **oldest entry of the client holding the MOST** (ties by oldest entry then client key — deterministic, never map order), so a flooding source evicts ITSELF and a single-entry client is untouchable until every other client is down to one. The bucket index also removes the pre-fix O(cache) expired-entry scan (64 µs per insertion under the process-wide auth mutex); **compaction keys on `len(keys)`, NOT the un-consumed window** — the trap `internal/authstate` documents, where a window-based test never fires under a sustained flood and the backing array grows with request count. The bounds are **CONSTANTS derived from GOMAXPROCS** with NO config surface (and therefore no GUI-parity obligation — recorded deferral, same class as `jwksStaleMaxAge`): a knob here could only widen a DoS window, and headroom is large and checkable (successful results cache for 5 min, so the sustained uncached rate is `active users / 300 s` ≈ 1.7/s for 500 users against ~25/s on four cores). External providers (LDAP/OIDC) BYPASS the governor — they run no bcrypt, and charging them a slot would bound the wrong resource and let a slow directory starve local authentication (their plane is CHAOS-47's `authProbeGate`). Surfaces: `culvert_auth_verify_{total,refused_total{reason},waited_total,inflight,max_concurrent,queued,saturated}` + `culvert_auth_cache_evictions_total`, the `credential_verification` operator-contract row (counts and bounds only — the client key is admin-scoped), a rate-limited `AUTH_VERIFY_REFUSED`/`AUTH_VERIFY_RECOVERED` log pair, and a fire-once-per-episode `auth_verify_saturated` alert. **Recovery requires BOTH halves of the evidence** — a FAST-PATH admission AND no refusal for `authCostRecoveryQuiet` (5s). Neither alone suffices: a queued admission proves the ceiling was still full, and a fast admission proves only that a slot was free AT THAT INSTANT. Clearing on a fast admission alone (the first shape, a Codex P1) meant that under a sustained flood — where every in-flight bcrypt releases its slot, so some arrival wins the fast path roughly once per comparison while its siblings keep being refused — the episode **restarted every ~80 ms and could NEVER reach `authCostDegradedAfter`**: the contract row flapped, an `AUTH_VERIFY_RECOVERED` line was emitted per comparison, and **`auth_verify_saturated` would never have fired for the primary attack the governor exists to expose**. This is NOT a retreat to recovery-on-elapsed-time (the `ca_health.go`/`storage_health.go` rule): elapsed time alone still clears nothing, an admission is still required, so a gateway nobody authenticates against stays reported as refusing rather than declared healthy by silence. **The lesson, twin to the per-client one: the evidence must match the claim** — "a slot was free" and "refusals have stopped" are different propositions, and the signal was keyed on the one easier to observe. **A SECOND finding inside the fix, caught in self-review:** moving the cache lookup ahead of the username comparison made a LATENT non-injective cache key reachable — `cacheKey` hashed `user + ":" + pass`, so `("admin","a:b")` and `("admin:a","b")` collide. That was unreachable while the cache was consulted only AFTER the username matched (every reachable key shared the same prefix); consulted earlier with a CALLER-CHOSEN username it is an **AUTHENTICATION BYPASS** — with a colon anywhere in the configured password, a re-split of it hits the cached positive and authenticates as a caller-controlled subject. `cacheKey` now LENGTH-FRAMES each field. The lesson generalises: **a reordering is not a refactor when a downstream invariant is holding the old order up** — the hash was safe only because of the ordering, and nothing recorded that, because at the time it was a coincidence rather than a dependency. Gates: 15 in `internal/authcost` + 19 in `auth_cost_chaos_test.go`; eleven defect gates verified failing against the shape each replaces. Deliberately left: **AU-3e**, a PRE-EXISTING username-enumeration oracle reached by REPETITION (a negative for the correct username is cached, one for a wrong username is not, so repeating the same wrong pair is ~1.5 µs vs ~80 ms) — reported, not fixed, because closing it changes a security control's behaviour and deserves its own review; the admin-UI login path (bounded by `loginLimiter` instead); and PX-6 (the front-door limiters still ship disabled — the governor bounds the flood's COST, not its arrival). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §25 and `docs/operator/credential-verification-cost.md`.
- **Interactive-login callback state is bounded FAIRLY, not randomly (`internal/authstate`)**: the OIDC PKCE store (`globalPKCEStore`) and the SAML AuthnRequest store (`globalSAMLStateStore`) hold verifier/nonce/relay state for logins that have not happened yet, and they are populated by **UNAUTHENTICATED** requests — `resolveCaptivePortalURL` mints an entry on the proxy's no-credentials path (`proxy.go`, Default arm, gated only by the quarantined `browserRedirectEligibleLegacy` User-Agent heuristic), `resolveSSOPortalURL` does it on the SSORequired arm, and the public `/auth/select` page does it per render. Both stores are hard-capped at 1000. **The eviction policy is therefore a security control, not housekeeping.** Both previously evicted "one arbitrary entry" — a single-key map range, i.e. a uniformly random LIVE entry — so an anonymous client looping requests through the proxy destroyed other users' in-flight state at one entry per request and every real callback came back `invalid or expired state`: a remotely triggerable, unauthenticated **denial of SSO authentication** for the whole gateway (it failed CLOSED — no bypass — which is exactly why it was silent). Entries are now attributed to a CLIENT KEY (`authStateClientKey` → `realClientIP`, so X-Forwarded-For counts only from a configured trusted proxy; IPv6 collapsed to /64 because one host owns a whole /64; IPv4 RAW), and eviction always takes the OLDEST entry of the client holding the MOST — ties broken by oldest entry, then by client key, so the victim never depends on Go map order. **A flooding source therefore evicts ITSELF**: displacing one honest single-entry login now needs as many distinct client keys as the cap, not one host with a for-loop. TTL, cap, single-use `Pop`, and the fail-closed callback are byte-identical — fairness decides only WHO is evicted, never what is admitted. Two implementation invariants the tests pin: the per-client key list compacts on **total slice length**, not on the un-consumed window (a window-based test never fires while a client sits at the cap, so the backing array would grow with total request count — a memory leak reachable by the same flood), and eviction is **deterministic** (`TestEvictionIsDeterministic`). Surfaced on `/metrics` as `culvert_login_state_{entries,clients}` + `culvert_login_state_evictions_total{store="oidc_pkce"|"saml"}` — a climbing eviction counter is the operator's only signal that logins are being displaced before they can be redeemed. - **The IP filter's per-request gate is LOCK-FREE and FLAT in entry count (`security.go`)**: `ipf.Allowed` is the FIRST gate on every proxied request (`handleRequest`, `socks5.go`), reached before the rate limiter, authentication, or policy. It took a process-wide `sync.RWMutex` read lock to reach its decision — including in the DEFAULT posture, where the filter is DISABLED and the lock guarded a `mode` string that never changes. `RWMutex.RLock` is an atomic read-modify-write on one shared word, so this was not a constant cost but a **throughput CEILING**, and the rate limiter sitting beside it in the same file already showed the right shape (`enabled atomic.Bool` probed BEFORE any lock). (3) `prefixFromIPNet` **mirrors `net.networkNumberAndMask`**, and that is the subtle part: a network address `To4()` accepts is an IPv4 network however many bytes it is STORED in, and a 16-byte mask is re-read as its low four bytes, so `::ffff:10.0.0.0/104` behaves exactly like `10.0.0.0/8` and matches the plain address `10.0.0.1`. A naive "16 bytes means IPv6" reading gets that wrong in the FAIL-OPEN direction for a blocklist — it was written that way first and `TestIPFilterView_DifferentialAgainstLegacy` caught it. Caught in review by Codex on PR #1207 and pinned by `TestBenchGate_IPFilterBulkLoadIsLinear` (ratio gate: 4x the entries must cost ≤8x — linear is ~4x, quadratic ~16x, measured 3.31x post-fix and 17.97x pre-fix) plus `TestIPFilterAddAll_MatchesAddLoop`. - **The per-IP rate limiter's sliding window is a RING, so its cost is flat in the configured limit (`security.go`, `clientBucket`)**: `RateLimiter.Allow` runs on EVERY proxied request (`handleRequest`, `socks5.go`) and its window maintenance was a filter-and-copy over the whole bucket (`valid := b.timestamps[:0]` … `if t.After(cutoff)`), so the per-request cost was proportional to the bucket's occupancy — which the accept test bounds by `security.rate_limit`. **That made an operator's policy setting the price of the gate**, and it was paid while HOLDING the shard mutex, so it did not merely cost its own request: it blocked every other IP hashing to the same shard (1/64 of the process's traffic). The shape is self-amplifying in exactly the wrong direction — a source already at its cap keeps sending, and every one of those requests walks the full window — so a flood degraded the gateway hardest precisely when the limiter was the control doing the work (the same lesson as the `HasSubscriber` alert-gate finding). Measured on a 4-core Xeon @2.80GHz at half occupancy (medians of n=3, `security_ratelimit_window_bench_test.go`, which benchmarks the VERBATIM pre-change algorithm in the same run so the comparison stays reproducible in-tree): **172 ns → 24.6 ns at 60 rpm, 1.38 µs → 22.2 ns at 600, 13.2 µs → 22.8 ns at 6 000, and 133 µs → 22.4 ns at 60 000** — i.e. flat, where it used to be linear. End to end, `Allow` across 256 IPs each sitting at their cap is now ~145–170 ns/op and **0 allocs/op** at both 600 and 6 000 rpm, at 1 and 4 cores. The old scan did two things linearly that neither needs to be: stamps are **appended in non-decreasing order**, so the expired entries are always a PREFIX — the survivors need no predicate test, and the copy back to index 0 existed only because a slice has no other way to drop a head. A ring drops the head by advancing an index, so each stamp is examined exactly once over its lifetime (amortized O(1)). **Three things are deliberate.** (1) The ring **grows LAZILY** (doubling, clamped to the limit) exactly as `append` did — pre-sizing to the limit is simpler and is NOT done: at 10k tracked IPs a 6 000/min policy would become ~1.4 GB of resident buckets. (2) `Allow` reads `time.Now()` BEFORE the shard lock, so arrival order is not stamp order and an inverted stamp would make prefix-expiry stop early; `add` therefore **clamps a new stamp up to the newest present**, restoring the ordering invariant by construction. The alternative — moving the clock read inside the lock — was built and measured and costs **~45% of the end-to-end gate at 4 cores (153 → 230 ns/op)** because it lengthens the critical section 1/64 of all traffic serialises on. The clamp's give-up is bounded (the gap between the clock read and the lock, microseconds, against a window in seconds) and lands **fail-CLOSED**: a clamped stamp expires no later than its true arrival, so the window can never admit past the limit. (3) `ExportHotDeltas` drops the expired prefix rather than counting past it — same verdict, less left for the next `Allow`. This is a COST change, not a POLICY change: `TestRateLimitWindow_DifferentialAgainstLegacy` pins the accept/reject verdict AND the occupancy against a verbatim copy of the filter-and-copy form over 300 randomized (limit, window, arrival-gap) shapes, with `TestRateLimitWindow_ExpiryBoundaryMatchesLegacy` covering the one verdict randomness cannot reach (a stamp landing exactly ON the cutoff — where a half-step-wrong predicate widens the window by one request per period). Gate: `TestBenchGate_RateLimitWindowIsFlatInConfiguredLimit` is a **RATIO** gate (60 vs 6 000 rpm in one run — machine-independent, no re-baselining; 0.91x measured, 84x against the reintroduced scan, bound 4x) plus `TestBenchGate_RateLimitWindowIsAllocationFree`; both were verified FAILING against the reintroduced defect, and the differential was verified failing against both a wrapped-ring growth bug and the boundary off-by-one. **The sibling finding on this path — `IsExempt` — is now CLOSED; see the next bullet.**

Quietly retrying until a live peer DIES and then taking over would make a node of unknown state age authoritative, which is precisely `haPromoteFreshnessWindow`'s judgement, so recovery routes to it rather than around it: an observed foreign holder is LATCHED (loop exits, this process never acquires again) and its disposition MIRRORS the shipped S4/S2 decision — resync from the recorded ex-standby, else keep the read-only leader role + CRITICAL alert. **The poll interval is capped BELOW the lease TTL (`recoveryPollCeiling`) and that is a CORRECTNESS bound, not tuning:** a free lease proves nobody holds it now, not that nobody held it since we last looked, and etcd keeps a holder's key for ≥1 TTL after it stops renewing — so looking at least once per TTL makes a completed-and-vanished peer tenure impossible to miss between two SUCCESSFUL observations (HA-19; the residual blind-partition case is recorded for an owner, and the shipped resume path already shares it). **(d) Panic containment lands the OPPOSITE way from `leaseRenewRound`**, and the contrast is the point: containing a keepalive panic is dangerous because it would extend authority the node is no longer confirming (CHAOS-24), whereas here there is NO authority to extend, so containing and backing off is strictly fail-closed. ## Admin UI / Control Plane

The admin API is wired in three layers — `startUI()` only composes them, never registers routes itself.

**Route registration**
- `startUI()` MUST NOT contain `mux.HandleFunc` calls. All routes are registered through per-domain `register*Routes(mux, ...)` helpers (e.g. `registerPolicyRoutes`, `registerSecurityRoutes`).
- `uiRoutes` in `ui_routes_meta.go` is the **single source of truth** for route metadata. Adding a route means: (1) register it via a `register*Routes` helper, (2) add a corresponding `uiRouteMetadata` entry to `uiRoutes`.
- Metadata is **method-aware** via `Methods []uiRouteMethod`. Each entry declares `Method`, `MinRole`, `Mutating`, `AuditExpected`, plus an optional note. `MethodAny` (`"*"`) is the catch-all when a handler intentionally treats every method the same.

**Middleware chain (outer → inner)**

```
uiIPGuardMiddleware → securityMiddleware → uiAuthMiddleware → uiMetadataEnforcement → mux
```

- `uiAuthMiddleware` owns the public-route allowlist and injects `uiRoleKey{}` into the request context.
- `uiMetadataEnforcement` (C2) reads that role and gates the request against per-method `MinRole` from `uiRoutes`. **Active by default** — fail-closed.
- `securityMiddleware` still owns CSRF, body-limit, and rate-limit decisions based on the HTTP method. The `Mutating` flag in metadata is **informational only**; it does not alter middleware behavior.

**Kill switch**
- `CULVERT_C2_ENFORCE=false` (or `0`/`no`/`off`) reverts C2 to shadow mode (log-only, never blocks). Read once at startup; admin-API runtime mutation is intentionally not supported.

**AuditExpected (C2c)**
- Pure observability. After a 2xx/3xx response, if metadata says `AuditExpected=true` and no `auditEvent`/`auditEventDiff` ran, the middleware emits one `C2: audit missing ...` log line and increments `c2AuditMissingTotal`. Failed requests, hijacked responses, and public routes are skipped. C2c **never** blocks a request.

**Role-divergence detector (C4 — REPORT-ONLY)**
- Pure observability. When the C2 middleware admits a request whose per-method `MinRole` is *lower* than what the handler-level `requireRole` ultimately demands (e.g. `apiIdPRouter` declares `MethodAny=viewer` but `apiIdPItem`'s PUT branch calls `requireRole(RoleAdmin)`), C4 increments `c2RoleDivergenceTotal` and emits one `C2: role divergence ...` log line. The middleware injects the C2-evaluated `MinRole` into the request context; `requireRole`'s failure branch reads that value and compares against the role it just rejected.
- C4 **never** blocks, allows, or alters the response. The handler's existing `requireRole` writes the 403 itself; C4 only observes the decision after the fact. Defense-in-depth (invariant #6) is preserved; the handler is still the real backstop.
- Audit ring is intentionally untouched — divergence events are governance observability, not admin-action audit. They flow out via the structured logger and the C3 governance endpoint only.

**Governance surface (C3)**
- `GET /api/governance/control-plane` (admin-only) exposes route inventory, C2 mode, the six C2 counters, derived health (four axes), and the parity-test pyramid (D0/C1/C1.5/C2/C2c/C4). Read-only and side-effect-free; no Prometheus exposure, no AST replay, no schema mutation. The kill switch stays env-only and read-once.
- C3 health severity policy (`deriveGovernanceHealth`):
  - `missing_meta > 0` → `metadata_parity = drift`, status = `drift`. C1 reverse-parity should make this impossible at runtime, so any non-zero value is genuine governance/config drift.
  - `no_policy > 0` → `metadata_parity = warn`, status ≥ `warn`. The counter can be triggered by a client sending a method the route does not accept (e.g. PATCH against a GET-only route, scanner probes); reserving drift for `missing_meta` keeps the indicator from flipping to drift on benign client traffic.
  - `audit_missing > 0` → `audit_completion = warn`, status ≥ `warn`.
  - `enforce_denied > 0` while `mode = shadow` → `enforce_consistency = drift`, status = `drift` (the kill-switch contract is read-once at startup).
  - `role_divergence > 0` → `role_divergence = warn`, status ≥ `warn`. Triggered legitimately by viewers probing admin-only sub-actions on dynamic dispatchers; reserved for warn rather than drift to avoid noise on benign client traffic.
- The six C2 counters surfaced by C3 (one-line definitions):
  - `would_deny` — session role was below the per-method `MinRole`. Increments in BOTH shadow and enforce modes; tracks the policy decision regardless of action.
  - `enforce_denied` — request actually got a 403 from the metadata-driven gate. Stays at zero in shadow mode; in enforce mode it moves in lock-step with `would_deny`.
  - `missing_meta` — request path resolved through the mux but had no matching `uiRoutes` entry (the static `/` catch-all absorbs unknown paths, so this is rare in practice). Soft-fail; never blocks a request.
  - `no_policy` — path matched a `uiRoutes` entry but the HTTP method had no exact policy and no `MethodAny` fallback. Soft-fail; never blocks a request. Triggered both by genuine drift and by clients sending unsupported methods (see severity policy above).
  - `audit_missing` — successful request (2xx/3xx) on an `AuditExpected=true` route did not emit an `auditEvent`/`auditEventDiff` call (C2c observability).
  - `role_divergence` — handler-level `requireRole` rejected a request whose C2-evaluated `MinRole` was strictly lower (i.e. metadata was more permissive than the handler's actual contract). Increments at most once per request, on the failure branch of `requireRole`. Observability only; never blocks.

### Admin UI / Control Plane Invariants

These are non-negotiable for any change touching the admin API:

1. **No route without metadata.** Every `mux.HandleFunc` path must have a matching `uiRoutes` entry. C1 forward/reverse parity tests enforce this.
2. **Metadata must never be more permissive than handler behavior.** If the handler enforces admin, metadata cannot say viewer. C1.5 AST parity tests enforce this for directly detectable handler behavior; dynamic/delegated handlers must be documented and reviewed.
3. **Resolution order: specific method > MethodAny > soft-fail.** Don't use `MethodAny` to paper over a method-specific contract.
4. **Missing metadata / no method policy must NEVER block requests.** Both are soft-fail in shadow and enforce mode — they log + count, the handler-level `requireRole` remains the real backstop.
5. **Public routes are owned by `uiAuthMiddleware` only.** C2 stays out (`RolePublic` is documentation, not enforcement). Don't add public-route gates to C2.
6. **Do not remove handler-level `requireRole`.** C2 is an additional gate, not a replacement. Defense-in-depth is the contract.
7. **C2 must never allow what the handler denies.** If they ever disagree, the handler wins by design — C2's role is to add denials, never to widen access.

### Testing Guarantees

Each layer has its own test suite — keep them green when modifying the admin API.

- **D0** (`d0_*_test.go`) — route/auth/security baseline invariants: route inventory pinned at the canonical count, auth allowlist, CSRF, body-limit, and rate-limit checks.
- **C1** (`ui_routes_meta_test.go`) — bidirectional route/metadata parity layer: forward (every `uiRoutes` entry has a matching `mux.HandleFunc`) and reverse (every `mux.HandleFunc` has a matching `uiRoutes` entry), source-scan based.
- **C1.5** (`ui_routes_meta_audit_test.go`) — AST-walk parity between metadata `MinRole`/`Mutating` and the per-method behavior of each handler (`requireRole` calls, method switches).
- **C2** (`ui_metadata_enforcement_test.go`) — middleware enforcement: shadow mode is silent, enforce mode returns 403, kill switch toggles correctly, missing-meta and no-policy stay soft-fail.
- **C2c** (`ui_metadata_enforcement_test.go` — `TestC2c_*`) — audit-completion observability: warns on success without audit, silent on failure / hijacked / public / `AuditExpected=false`, never blocks the request.
- **C4** (`ui_metadata_divergence_test.go` — `TestC4_*`) — report-only role-divergence detector: increments `c2RoleDivergenceTotal` and emits a structured log line when the handler's `requireRole(R)` rejects a request whose C2-evaluated `MinRole` was strictly lower. Tests cover the canonical viewer-on-admin-route case via `apiIdPRouter`, the parity case (no event), the C2-stricter case (no event), and the response-decision invariance proof (C4 cannot change the 403 the handler already wrote).

### Test-authoring pitfalls

- **Audit ring saturation.** The in-memory audit ring is bounded at `maxAuditLogs = 500`. Tests MUST NOT assert on `len(auditGet())` deltas (e.g. `len(after) == len(before)+1`) because under `-count=2 -shuffle=on` the cumulative suite saturates the ring and `len()` stops growing — adding a new entry evicts the oldest. The determinism gate (`QA · Determinism`) re-runs the suite shuffled to flush these out. Instead, assert on entry **content**: scan `auditGet()` for an entry matching a unique discriminator (`Actor` IP from a TEST-NET-2 reserved range, plus `Action`/`Object`, plus a baseline `TS` captured before the call). See `security_feedsync_audit_test.go` for the canonical pattern.
