# Culvert

Enterprise-grade open-source HTTP/HTTPS/SOCKS5 forward proxy written in Go.
Single binary, zero runtime dependencies.

## Key Environment Variables

- `CULVERT_CA_PASSPHRASE` — CA private key encryption passphrase (required for SSL inspect)
- `CULVERT_C2_ENFORCE` — C2 metadata-driven RBAC mode. Default = enforce (fail-closed). Set to `false`/`0`/`no`/`off` to revert to shadow (log-only) mode without rebuild. Read once at startup.
- `CULVERT_EXPERIMENTAL_UI` — arms the new React/TypeScript admin frontend (`frontend/`, ADR-FE-001) at `/app/` + `/assets/`. Default OFF (unset ⇒ both routes 404, byte-identical to a build without the feature); the legacy `static/index.html` keeps serving `/` regardless. Read once at startup (`ensureFrontendV2`, `ui.go`); no YAML/CLI equivalent — development/preview flag only, not yet a supported production surface (see `docs/design/FRONTEND-MIGRATION-PLAN.md`). Report-only `frontend_v2` row on `/ready` when armed.
- `CULVERT_CLUSTER_GRPC_COMPRESSION` — opt-in gzip on the CP↔DP config-sync gRPC stream. Default **off** (fail-safe): only `true`/`1`/`yes`/`on` enable it. When off, the raised `maxClusterGRPCMsgSize` (128 MiB) frame alone carries a full ConfigSnapshot uncompressed (a 2 M-host blocklist ≈ 60 MiB), so large snapshots sync without compression. Enabling it makes the DP send every RPC gzip-encoded — safe **only after every CP in the fleet runs a build that registers the gzip codec** (the CP always accepts + echoes gzip but never requires it, so this is a CP-first migration; a DP-first flip against an un-upgraded/rolled-back CP would fail every RPC with `Unimplemented`). Startup-scoped, read once (recorded GUI-parity deferral — same class as the HA-lease endpoints and `-cluster-insecure`). The resolved value is surfaced read-only on `GET /api/cluster/status` (`grpcCompressionEnabled`) and the Cluster panel, same status-only precedent as the HA Fencing Lease card, so an operator can confirm the effective setting without SSH.
- `CULVERT_RELEASE_CATALOG_TRUST_KEYS` — JSON array of **public** ed25519 release-catalog trust roots (`[{"key_id","alg":"ed25519","public_key":"<base64>"}]`) that EXTEND the baked roots (`bakedReleaseTrustKeysJSON`, linker-injected at official-build time). Public keys only — never private signing material.
- `CULVERT_RELEASE_CATALOG_VERIFY` — release-catalog signature mode. Default = enforce whenever any trust root (baked or configured) is present; with no roots and no override Release Management is DISABLED (unsigned catalogs are never auto-trusted). Set to `permissive` (accept unsigned; still reject a present-but-invalid signature) or `disabled` (skip verification) only as a deliberate, logged **break-glass**. Read once at startup.
- `CULVERT_RELEASE_CATALOG_URL` — **operator OVERRIDE** of the catalog origin (M1-2 product revision: the appliance has a CANONICAL BUILT-IN default, `https://catalog.culvertlabs.com/release-catalog` — a normal customer configures nothing). Set it only for air-gapped deployments, internal mirrors, staging/test, or regional/private distribution; empty/unset ⇒ the baked default; `off`/`none`/`disabled` ⇒ NO outbound fetch (the trust-SAFE opt-out — verification stays fully enforced on any on-disk catalog, so silencing the fetch never requires relaxing `CULVERT_RELEASE_CATALOG_VERIFY`), surfaced as `catalog_url_source:"disabled"`. **The origin never affects trust** — verification (baked roots + pinned identity, enforce mode) is identical for default and overridden origins, and changing the URL cannot change trusted signing identities/roots. Effective origin host + source (`default`/`override`/`disabled`) + refresh cadence + last-refresh outcome surfaced read-only on `/api/releases` (`catalog_origin`, `catalog_url_source`; the full URL is shown only for the public default — an override may carry presigned credentials) and in the admin Release Management panel. A boot-time seed failure is folded into `last_refresh` as trigger `startup` (immediate visibility, no ~6h blind window). SSRF guard still rejects private-IP origins (recorded constraint for internal mirrors). In enforce mode, the Control Plane fetches + verifies the signed catalog at startup (signature + freshness + rollback, read-only) and atomically installs it into `<dataDir>/release_catalog/`; any failure leaves the existing catalog untouched (fail closed). Verification is in the binary (`release_autoseed.go`); the installer only forwards the env (never bakes a default). Auto-seed never runs in break-glass permissive/disabled. Read once at startup.
- `CULVERT_RELEASE_REFRESH_INTERVAL` — periodic production catalog-refresh cadence (M1-2). Go duration (default `6h`, ±10% jitter, min clamp `1m`); the loop runs only when a catalog origin is in effect AND in enforce mode, drives the SAME verified auto-seed seam as the manual `POST /api/releases/catalog-refresh` (shared `refreshStatus`; fail-closed — a failed tick leaves the catalog untouched), and stops on shutdown. When the refresh loop does NOT run (fetch disabled via `off`/`none`/`disabled`, or break-glass verify modes), a standalone detection-only stale watchdog (CHAOS-23, `runCatalogStaleWatchdogLoop`) ticks at the same resolved cadence so `release_catalog_stale` stays live at runtime — exactly one watchdog driver per process (`startReleaseDetectionLoop`). Unset/typo ⇒ default (fail-safe: a typo must not disable the freshness loop). Env-only (CULVERT_RELEASE_* family precedent); cadence + `last_refresh` surfaced read-only on `/api/releases`. **M1-3 detection rides this loop** (`release_alerts.go`): alerts `release_catalog_stale` (installed catalog expires <30d — the 180-day freshness watchdog), `release_catalog_refresh_failing` (3 consecutive failures), `release_catalog_recovered` — each fires ONCE per threshold crossing (RT-H2 latches on `releaseManager` under `statusMu`; reset on restart, documented); stale is also evaluated once at startup via `deferStartupAlert`. Metrics: `culvert_release_catalog_refresh_total{result}` + scrape-time `culvert_release_catalog_expires_in_seconds` (omitted when no catalog). `/api/releases` adds `expires_in_days`; the Release panel shows it with warn color inside the 30d threshold. Thresholds are constants (recorded deferral).
- `CULVERT_RELEASE_SIGSTORE_IDENTITY` — OPTIONAL operator override for the pinned **keyless** (Sigstore-identity) trust policy (P2b), JSON `{"issuer","san_regex"}`. Unset ⇒ the baked official identity (issuer = the GitHub Actions OIDC issuer; SAN anchored to a tagged release of this repo's workflow). Break-glass / fork-mirror only; env-only (GUI-parity deferral, same as the other `CULVERT_RELEASE_*` vars). Read once at startup.
- `CULVERT_RELEASE_SIGSTORE_TRUSTED_ROOT` — OPTIONAL path to a custom Sigstore TUF `trusted_root.json` (P2b). Unset ⇒ the baked embed (`trusted_root.json`, the REAL Sigstore public-good root as of P2b-2a, so the keyless scheme is ACTIVE by default — see the P2b-2a Architecture Note below; point this at an empty file to deactivate). **PUBLIC** trust material only — never private signing keys. Read once at startup.
- `CULVERT_MCP_DISTRIBUTION_TRUST_KEYS` — PR-12 DP verify-trust for the signed MCP CP/DP distribution path (`initMCPDistribution`, `mcp_distribution_startup_config.go`). JSON array of **PUBLIC** ed25519 roots in the SAME shape as `CULVERT_RELEASE_CATALOG_TRUST_KEYS`: `[{"key_id","alg":"ed25519","public_key":"<base64-raw-32-byte-key>"}]`. PUBLIC material only (a private signing key is never provisioned to a DP). Unset or empty ⇒ MCP CP/DP distribution stays DISABLED (no DP applier is composed, `applySnapshotMCP` is a no-op, a received ConfigSnapshot is byte-identical to the pre-PR-10 SWG snapshot). A present-but-invalid value fails CLOSED to disabled (never composes an applier that trusts nothing or the wrong key). When a valid trust store is provisioned, the shim composes the Gateway and Management DP appliers (physically isolated, durable state under `<dataDir>/mcp_distribution/`, `Recover` at startup, then rollout reconciliation), so a signed rollout envelope reaches the durable rollout commit path and an executing-mode transition fails closed at the execution-dependency gate. Env-only crypto trust with a recorded GUI-parity deferral (same precedent as the `CULVERT_RELEASE_*` trust-key vars and the HA-lease endpoints); effective composition state (`dp_composed`, `dp_compose_reason`, PUBLIC `dp_trust_key_ids`) is surfaced READ-ONLY on `GET /api/mcp/distribution`. Read once at startup.

## Code Conventions

- **Package**: Everything is `package main` (flat layout)
- **Go version**: 1.26 (go.mod; bumped from the prior 1.25.12 govulncheck pin as a side effect of the go.etcd.io/etcd/server/v3 v3.7.1 dependency update, which raised its own minimum Go requirement)
- **Logging**: Use `logger.Printf()`, never `log.Printf()` or `fmt.Printf()`
- **User input in logs**: Wrap with `sanitizeLog(s)` and use `%q` format verb (CWE-117 prevention; sanitizeLog uses strings.ReplaceAll which CodeQL recognises)
- **CodeQL compliance**: For values that flow through objects (e.g. `rl.Limit()`, `added.Priority`), inline `strings.ReplaceAll` or `fmt.Sprintf` + `strings.ReplaceAll` at the call site so CodeQL sees the sanitiser
- **SSRF guards**: Inline `url.Parse` + scheme check + `isPrivateHost()` before outbound HTTP requests so CodeQL can verify the guard; do not rely solely on wrapper functions like `validateExternalURL()`
- **HTTP contexts**: Use `http.NewRequestWithContext()`, never bare `http.NewRequest()`; use `HandshakeContext()` not `Handshake()`; use `DialContext()` not `DialTimeout()`
- **Errors**: Return `fmt.Errorf("context: %w", err)` for wrapping
- **Concurrency**: Use `sync.RWMutex` for read-heavy stores, `atomic` for counters
- **Security**: SSRF checks via `isPrivateHost()` before any outbound dial
- **Tests**: Test files use `_test.go` suffix, same package (whitebox)
- **Lint suppressions**: Use `//nolint:errcheck` with reason comment; `// #nosec G402` for gosec
- **GUI parity**: Every new CLI flag or config option MUST have a corresponding admin API endpoint AND a UI panel/section so the user can manage it from the GUI. CLI-only features are not acceptable — the admin must have full control from the web interface.
- **API pattern**: Admin API handlers follow `apiXxx(w, r)` naming, registered through `register*Routes` helpers and represented in `uiRoutes` metadata (`ui_routes_meta.go`). Use `requireRole(w, r, "admin")` for write operations, `requireRole(w, r, "viewer")` for reads — handler-level RBAC stays as defense-in-depth even with C2 active.
- **UI pattern**: SPA panels in `static/index.html` use `data-view="name"` attributes. New panels need a nav-item in the sidebar, a view div, and JS load/render functions.
- **Config versioning**: Config-mutating API handlers must call `saveConfigVersion(actor, action)` after `auditEvent()` to create automatic snapshots.
- **Range iteration**: Use index-based range (`for i := range slice`) for large structs (PolicyRule 240 bytes, EnrolledNode 176 bytes) to avoid `rangeValCopy` gocritic warnings.
- **gosec G117**: Avoid struct field names or JSON tags matching secret patterns (e.g. `secret`, `password`, `token`). Rename to non-matching names (e.g. `SessionHMAC` instead of `SessionSecret`).
- **gosec G124**: When cookies use dynamic `Secure` flag (e.g. `isSecureRequest(r)`), suppress with `// #nosec G124 -- dynamic Secure flag`.
- **Cyclomatic complexity**: Keep functions under cyclop threshold of 15. Extract helpers for complex switch/if chains.
- **`upstreamTransport` is read-only after publication**: the shared upstream `*http.Transport` is owned by `upstream_transport.go` (P5.3 / S6). Read via `getUpstreamTransport()`. Mutate via `swapUpstreamTransport(update)` only — the update closure builds a NEW `*http.Transport` (use `cloneTransport` + `cloneTLSConfig`) and MUST NOT mutate its input. Direct field assignment on a loaded transport (`getUpstreamTransport().Proxy = …`, including the local-variable bind form `t := getUpstreamTransport(); t.Proxy = …`) is forbidden — it races against the proxy hot path's reads.

## CI Pipelines

Lane architecture (authority: `roadmap/CI-REDESIGN.md`). **The required merge
checks are `✅ Fast PR Gate — APPROVED` and `✅ Deep PR Gate — APPROVED`** —
if a PR is red, look at those two first. The QA/Security gate check names on
PRs are pass-through shells kept for branch-protection continuity; both run
fully on main pushes (and the Security gate on tags + weekly cron).

- `pr-fast-gate.yml` — **Lane A, required on every PR**: fmt/vet/build (+arm64 compile, static assert, tidy check), diff-scoped golangci-lint, THE single full `-race` run owning both coverage contracts (55% global + per-file floors), benchgate, govulncheck+gosec, gitleaks (even docs-only PRs), path-gated maint-agent checks, advisory traffic smoke
- `pr-deep-gate.yml` — **Lane B, required-if-triggered** (diff-classified): build-image-once → trivy scan + compose validation, hadolint, staticcheck, determinism (any `*_test.go` change), go-licenses on dep changes, packaging (shellcheck/visudo/systemd)
- `ci.yml` — main/tag path: build, compose smoke, multi-arch docker publish + cosign, catalog gate, auto-tag (waits for BOTH gate approvals on the SHA before tagging), release + SLSA provenance. Workflow name `CI` is load-bearing (`publish-catalog-pages.yml` triggers on it — do not rename)
- `qa-gate.yml` / `security-release-gate.yml` — full functional QA / 10-check security scan on main pushes, tags (security), and weekly cron (security); pass-through on PRs
- `codeql.yml` — CodeQL SAST: main pushes, weekly, and PRs touching the proxy/security/release surface
- `code-review.yml` — advisory PR DX: reviewdog inline lint, PR-size, conventional commits
- Nightly/weekly: `fuzz-nightly.yml` (Mon/Wed/Fri coverage-guided fuzzing), `proxy-nightly-e2e.yml` (load), `proxy-weekly-stress.yml`, `proxy-ui-e2e.yml` (playwright), `auth-idp-interop.yml`, `install-lifecycle-e2e.yml` + `maint-agent-*-e2e.yml` (installer/agent e2e — nightly + installer-surface PRs)

## Architecture Notes

- **Default deny**: Policy engine defaults to deny when no rule matches (Zero Trust)
- **SSL inspect**: MITM via on-the-fly leaf certs signed by internal CA (ECDSA P-256)
- **Adaptive decryption exclusion (fail-open + auto-learn)**: `internal/autoexclude` — a volatile, bounded, TTL-bounded in-memory cache of hosts SSL inspection could not decrypt, so subsequent CONNECTs bypass (PAN-OS-style local decryption-exclusion cache). Opt-in per decryption profile via `OnInspectError=="fail-open"`. **SCOPED KEY (policy isolation, not just host):** every entry is keyed by `(scopeID, host)` where `scopeID` is the matched decryption-profile's identity — a host learned under one fail-open profile is consulted ONLY for sessions matched to that same profile, so one fail-open rule/profile/tenant can never create a bypass consumed by another. `resolveSSLAction` consults the cache ONLY when the matched rule opts into fail-open AND within that profile's scope (gated read — a fail-close rule never populates OR consults, so hosts on fail-close rules are un-poisonable and behavior is byte-identical when unused). **SECURITY-GENERATION FENCING (PR2, `roadmap/PR2-autoexclude-security-generation-fencing.md`):** the profile ID is stable across edits, so each entry ALSO records a `securityGen` — a deterministic fingerprint (`decryptprofile.computeSecurityGen`, `SecurityGen()`) over ONLY the security-effective fields (`OnInspectError`, `CertVerification`, `OnUnsupported`, `MinTLSVersion`, `MaxTLSVersion`, `InspectHTTP2`; identity/timestamps/`StallTimeoutSecs` are EXCLUDED so a rename never invalidates). `Observe`/`Contains` are `(scopeID, gen, host)`: a gen MISMATCH is a miss (re-inspect), so a security-relevant same-ID profile edit invalidates learned entries immediately while a rename preserves them. The gen is PRECOMPUTED at store-write time and returned by the hot-path accessors (`FailOpenScope`/`FailOpenScopeByID` now return `(id/scope, gen, ok)`), so the CONNECT path never hashes (benchgate-pinned zero-alloc). It NARROWS the `(scopeID,host)` boundary to `(scopeID,gen,host)`, never broadens it; `scopeID` stays PURE for metrics/audit. The gen is a pure function of the synced fields — never persisted/synced, recomputed identically on every node (CP→DP) and across restarts. **Tightened classifier (`classify{Origin,Client}InspectFailure`, autoexclude_resolve.go):** an origin controls its own TLS alerts, so only NARROW signals learn — origin leg: `client_cert_required` (specific `certificate_required` TLS-1.3 alert; the ONLY reason permitted to LIVE-RESCUE the triggering session) and `unsupported_params` (only the client-side `server selected unsupported protocol version` string — a genuine per-origin version mismatch; the host-independent `no supported versions satisfy` config error and the server-side `no cipher suite` string are deliberately NOT matched; LEARN-ONLY, never rescues); client leg: a specific cert-rejection alert (`client_pinned`, learn-only). Generic/origin-emitted alerts (`handshake failure`, `no application protocol`), cert-verify failures (untrusted/expired/mismatch — a Block signal + the poisoning vector), and EOF/RST/timeout/wrapped errors NEVER learn (fail-closed default). A host is excluded only after a CONFIRM-COUNT of DISTINCT client-evidence tokens (default 2) within a window — the token is the AUTHENTICATED IDENTITY when available, else the client IP (IPv6 collapsed to /64 for single-host churn; IPv4 RAW — a /24 would over-collapse a NAT fleet; NAT/DHCP limitation documented). `client_pinned` gets a shorter TTL (1h vs 12h). Only `client_cert_required` on the strip path live-RESCUES the current session (confirm-count-exempt) via `handleTunnelBypass` (its own inline `isPrivateHost`+`ssrfControl` re-dial); everything else — `unsupported_params`, the native-H2 path, client-pinning — is learn-only (self-heal on the next session after the confirm-count). Promotion fires a SCOPED audit event (actor = triggering client IP) + `fireAlert` + metrics (`culvert_decrypt_autoexclude_{total{reason,scope},hit_total{scope},active{scope},pending}` — F6 labels `hit_total`/`active` by profile scope, same capped label set folding overflow to `_other_`; the process total is `sum()`-able and also on `/api/decryption/health`); pending map is independently bounded (`maxPending`). The learned ENTRIES are VOLATILE — off every config surface (cleared on restart, never CP→DP synced). The five ENGINE PARAMETERS (`confirmN`/`ttl`/`pinnedTTL`/`window`/`maxEntries`) are runtime-tunable (F10, PRs #747/#749/#752/#753): DURABLE in `admin_settings.json` (sentinel `AutoExcludeTunablesSaved`) but node-local — OFF export/import, version-rollback, and CP→DP (AdminDurable-only `configSurfaces` rows, pinned by `config_surfaces_test.go`). `Cache.Reconfigure` applies changes in-place under the mutex (forward-only: active entries keep their expiry; lowering `maxEntries` deterministically evicts oldest-first to exactly the cap). `OnInspectError` is an additive persisted profile field (omitempty) that degrades to fail-close on downgrade (old binary ignores the unknown key). Admin surface: `/api/decryption-exclusions` (GET viewer list+Stats+fail-open footprint+per-scope rule blast-radius / DELETE operator evict-one `?scope=&host=`·clear-all) + `GET/PUT /api/decryption-exclusions/tunables` (GET viewer = defaults+bounds ONLY, current values stay on the Stats surface as the single source of truth; PUT admin = full-set `zero⇒default`, `confirmN`≥2, `maxEntries`≤262144, persist-before-apply: validate→persist target→apply infallible Reconfigure, no rollback branch) + the Decryption Exclusions SPA panel (incl. the admin-only Cache Tuning section). Engine tests use an injected clock; `swapAutoExclude` isolates the global singleton per test (the PR3d fence-pollution class). See `docs/operator/decryption-auto-exclusions.md` and `roadmap/auto-exclusion-cache-plan.md`.
- **The shutdown sequence is BOUNDED end to end, in three phases with a durability RESERVE (CHAOS-56, `main_shutdown.go` + `runtime_shutdown.go`)**: SIGTERM runs 17 ordered hooks, and until CHAOS-56 the sequence was bounded only by the container's `stop_grace_period`. Three of Culvert's per-request sinks are ASYNCHRONOUS by design (`internal/logsink`, `internal/reqlog`, `internal/syslog`), and each header documents the same residual — an abrupt death loses the in-flight batch, the ORDERLY path flushes — so three durability contracts were delegated to a sequence that could not guarantee it reached the flush. **The unbounded hook is gRPC `GracefulStop`, and NOT for the reason it looks like.** grpc-go bounds the IDLE case with a 5s GOAWAY ping-ack timer (measured 6.005s end to end on v1.83.1 against a silent HTTP/2 peer — the "half-open peer waits out the ~15-minute TCP retransmit budget" story is WRONG, and measuring it is what found the real one), but `outgoingGoAwayHandler` closes the transport only when `len(t.activeStreams) == 0`; with a live stream it arms NO timer, and `GracefulStop` blocks in `for len(s.conns) != 0`. Two ordinary faults produce a stream that never finishes and neither surfaces an error: a handler blocked in `write(2)` on a wedged volume (`Enroll`/`RenewCert` persist, `PushAuditEvents` appends to a `RotatingFile`) and a peer that stops reading a large `GetConfig` response (TCP zero-window persist retries indefinitely). Reaching the grace means SIGKILL, which skips the cluster-store flush, the request-log queue drain, a clean badger close (an unclean one is exactly the torn `MANIFEST` CHAOS-50's boot-path quarantine exists for — a hung shutdown MANUFACTURES the corruption the previous sweep had to survive) and the log-sink flush **holding the lines that say why**. Six rules now hold. **(1) Three phases, and the FLUSH reserve is carved out UP FRONT** — `shutdownFlushBoundary` (105) splits the late registry via `partitionAt` into DRAIN hooks (best-effort; abandoning one costs a client retry) and FLUSH hooks (durable; abandoning one costs durability or a quarantined store), and the reserve is measured from the START of the flush phase, so a drain that overran its own share still cannot spend it. **(2) Every phase carries a REAL deadline** (`defaultShutdownBudget`: Total 45s, Early 12s, Flush 10s) — the early phase used to run under `context.Background()`, pinned as correct by a test that was pinning the DEFECT (`TestRunShutdownSequence_EarlyCtxHasNoDeadline_LateCtxDoes`, since inverted), and the late ctx was ADVISORY: `RunAll` never consulted it and most hooks cannot (`syslog`/`badger`/`logstore`/`reqlog`/`audit`/`logCloser` take no ctx; the tunnel drain took one and ran its own timer its comment calls "independent of the parent ctx", so the real worst case was 30s + 15s + the closers against a documented 30s). **(3) Every hook runs under a WATCHDOG, and the RESERVE IS RECURSIVE** (`hookBudget`): a hook may take what is left of its phase MINUS `shutdownHookMinSlice` (1s) for every hook still BEHIND it, then one shared `shutdownHookGrace` (3s) before it is abandoned, so the envelope stays `Total + 2×grace` = 51s, inside the 60s compose grace and pinned to it by a cross-artifact gate that parses `docker-compose.yml`. **Do not collapse this back to one deadline per phase.** The first shipped shape did, with the recorded rationale "a stalled hook is abandoned, and the flush hooks are safe because they have their own reserved phase" — which is FALSE: the flush reserve protects flush hooks from a stuck DRAIN, never from EACH OTHER, so `syslog-close`/`community-db-close` stalling on a wedged volume burned the whole reserve and `request-log-close`/`audit-log-close`/`log-closer` were started and abandoned against an already-past deadline (Codex P1 — SD-2b reproduced inside the fix for SD-2b). The hook RECEIVES the deadline the watchdog enforces, so a ctx-aware hook winds down instead of being abandoned; a fast hook hands its unused share to the next, so a legitimately slow close still gets almost the whole phase (control-gated). An abandoned hook is NAMED in a line emitted AT THE POINT OF ABANDONMENT, never from the phase-end aggregate: the last flush hook closes the log sink, so a phase-end line on the flush phase is enqueued into a channel nobody drains (the same reason `runShutdownSequence` emits its completion line BEFORE the flush phase — the pre-existing `logger.Println("Stopped.")` after it was already being swallowed). Abandoning is never worse than the SIGKILL it replaces, which abandons the same hook PLUS everything behind it. **(4) Panics are CONTAINED** — same direction as CHAOS-55's recovery loop, opposite to CHAOS-24's HA keepalive, for the reason recorded there: a shutdown hook holds no authority containment would extend. **(5) `StopControlPlaneGRPC` is bounded** (`gracefulStopBounded`, `cpGRPCGracefulStopBudget` 8s — above the measured 6.0s idle drain so an unresponsive fleet still completes gracefully), then a force-close; force-closing is safe because an interrupted unary RPC is retried by the caller's own sync loop. **grpc-go's `stop(graceful bool)` is hostile to being raced in TWO ways and the obvious wrapper hits both — do not "simplify" this back.** (a) It ends with `s.handlersWG.Wait()`, so `GracefulStop` does not return until every HANDLER returns — the very handler being escaped — so the goroutine must NOT be joined (draft one did). (b) That `handlersWG.Wait()` runs while HOLDING `s.mu` (`stop` takes the lock with `defer Unlock` before the conns wait; `s.cv.Wait()` releases it only while waiting), so when the last conn is removed both stops contend and, if the GRACEFUL one wins, it parks forever holding the mutex and a SYNCHRONOUS `srv.Stop()` blocks on it unboundedly — the original fault rebuilt inside its own fix. Which one wins is pure timing: draft two passed every targeted run AND the full suite and failed only under `-race`. So `Stop()` is issued on its OWN goroutine and the function returns. What it therefore guarantees is narrower than "the server is stopped": the LISTENERS are closed (grpc-go closes them before the conns wait), and the transport force-close is best-effort + asynchronous — which is why the hook watchdog is the only HARD bound on this hook and the two are NOT redundant. The gate's TOLERANCE is part of the gate: a generous "returns eventually" bound would have made draft two a flake rather than a failure. **(6) A SECOND SIGTERM/SIGINT force-exits** with status 1 after `flushLogSink()` — `signal.Notify` takes the runtime's default terminate behaviour away and nothing read `quit` again, so the second signal was swallowed and the only escalation left was SIGKILL. The watcher re-checks the disarm via `shouldEscalate` before exiting: Go picks UNIFORMLY among ready select cases, so a signal pending at the instant `stopEscalation` ran made a COMPLETED shutdown exit 1 half the time (Codex P2). That tie cannot be scheduled from a test, so the decision is its own function and is pinned deterministically rather than by a probabilistic race gate. Gates: `shutdown_chaos_test.go` (17) — four defect gates verified failing against their reintroduced pre-fix shapes, a permanent DEFECT PROOF (`BareGracefulStopIsUnboundedOnAWedgedStream`) so a future grpc-go change cannot let the bounded gate quietly prove less than it claims, and three CONTROLS (a watchdog that abandoned everything, or a drain clamped to nothing, would pass the defect gates while being far worse than the defect). Deliberately left: no unclean-shutdown breadcrumb (the one signal a SIGKILL cannot destroy — recorded as SD-5), no shutdown metrics (a process that is exiting is never scraped again; the log is the record, which is only true because the envelope now guarantees the flush), and `HAState.Stop()`'s `wg.Wait()` stays an unbounded join now covered by the early phase's watchdog. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §24 and `docs/operator/graceful-shutdown.md`.
- **The SOCKS5 accept loop backs off, classifies, and reports (CHAOS-54, `socks5.go` `serve` + `socks5_health.go`)**: `socks5Server.serve` is the ONLY hand-rolled accept loop in the data plane — the proxy port, admin UI, PAC endpoint and MCP gateway all run under `net/http.Server.Serve` and the control plane under gRPC, both of which back off on accept failure and stop on an unrecoverable error. This loop did neither: any `Accept` error other than `net.ErrClosed` was logged and retried IMMEDIATELY, forever. `accept(2)` returns EMFILE/ENFILE straight out of `internal/poll.FD.Accept` without blocking (only EINTR/ECONNABORTED are retried in the runtime, only EAGAIN waits), so a descriptor incident measured **7,681,156 accept attempts in 300 ms** with one `logger.Printf` each — a pinned core, ~40 MB/s into a `fileutil.RotatingFile` capped at 50 MB with ONE archive (so the entire retained process log, INCLUDING the cause of the exhaustion, was overwritten in ~2 s), and — because `internal/logsink` BLOCKS a producer on a full queue and `handleRequest` writes one POLICY_* line per proxied request through that same sink — added latency to every HTTP request on a node whose SOCKS5 listener nobody was using. Self-amplifying: FD exhaustion is the recorded terminal state of WK-11 (leaked alert sockets) and PX-6 (no global connection cap). Four rules now hold and must not be relaxed. **(1) Backoff is net/http's exact schedule** (5 ms doubling to a 1 s ceiling, `nextSOCKS5AcceptBackoff`), reset on an OBSERVED successful accept — copied rather than invented because it is the schedule every other listener in this process already follows, and its ceiling is deliberately below the 2 s `socks5-listener-stop` shutdown budget. **(2) The sleep is INTERRUPTIBLE**: `Stop` closes a `stopping` channel (via `sync.Once`) BEFORE `ln.Close()`, so shutdown never waits out a backoff; measured worst case at the ceiling 107 µs, pinned by `TestChaos54_StopIsPromptDuringAcceptBackoff` (a many-trial gate — where `Stop` lands inside a non-interruptible sleep is uniform, so one trial passes a broken build a quarter of the time). **(3) Only a socket that is GONE stops the loop**: `socks5AcceptFatal` matches EBADF/ENOTSOCK/EINVAL/EFAULT/ENOTCONN via `errors.As` (never string matching — net wraps as `*net.OpError{*os.SyscallError{syscall.Errno}}` and the text is platform-specific), closes the listener so clients get connection-refused instead of hanging against a bound-but-never-accepting port, and records DOWN. An UNRECOGNISED error is deliberately NOT fatal — backed off to 1/s, retrying an unknown error costs nothing, while misclassifying a transient fault as fatal is a customer-visible outage; that does not violate "avoid infinite retries" because the retry is never silent. **(4) Degradation is a DURATION, not a count** (`socks5AcceptDegradedAfter` 30 s): the ceiling is reached in ~1.3 s and paging on that would page on every transient spike. Logging is rate-limited (onset immediately, then ≤1 line per 30 s, then one recovery line naming the suppressed count — signal in the log, magnitude in the counter) and the loop carries a panic guard that reports DOWN (the CHAOS-24 objection to recovering in a worker goroutine does not apply when the recovery path is the loudest state the subsystem can produce). Recovery clears ONLY on an observed successful accept, never on elapsed time. **Degraded and down carry SEPARATE fire-once latches** (`alerted` vs `downAlerted`) — a shared one swallowed the page for a dead listener whenever it had already been degraded, silencing the more urgent of two states that point at opposite actions (storage_health.go's "two failures must not share a rate gate" rule). Surfaces: `socks5_listener` operator-contract row, report-only `/readyz socks5` row (absent when unconfigured; FIXED detail strings — `/readyz` is unauthenticated on the proxy port and an error count + reason would fingerprint a resource-exhausted node), `/healthz socks5` field, `culvert_socks5_{listener_up,accept_errors_total,accept_degraded,accept_backoff_seconds}` (emitted only when configured — `up 0` on a node that never had SOCKS5 is indistinguishable from a dead listener and the paging rule is `== 0`), and a fire-once-per-episode `socks5_listener_down` alert whose Detail carries a BOUNDED reason class (`Dispatch` dedups on `event + ":" + Detail`; a raw accept error embeds the listener address — the WK-12/RS-5 defect). **`net.ErrClosed` is NOT by itself a shutdown signal** — it says the listener is gone, and `Stop` is only one way that happens; the loop checks whether `stopping` was actually closed (`Stop` closes it BEFORE `ln.Close()`, so the check is race-free in the direction that matters) and otherwise records DOWN, because returning silently would leave every probe green on a dead listener — PX-18 in miniature, reintroduced inside the change that closed it (Codex review, PR #1208). Gates: `socks5_accept_chaos_test.go` (18). Still open on this path and deliberately untouched: SOCKS5 never consults the policy engine (no category/GeoIP/schedule rules, no default-deny), plus PX-1/PX-5/PX-6/PX-7/PX-8. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §22 and `docs/operator/socks5-listener-health.md`.
- **A damaged Layer-2 category store must never stop the boot (CHAOS-50, `internal/catdb/resilient.go`)**: the community category store is a BadgerDB directory opened on the BOOT path and enabled by DEFAULT in the shipped `docker-compose.yml` (`-cat-feed-db /data/catfeeddb`, on a service with `restart: unless-stopped`). It used to `logFatalf` on any open failure, so one torn `MANIFEST` after an unclean container kill was an unattended CRASH-LOOP — no proxy, no admin UI, no health endpoint, recoverable only by shell access — over the ONE store on that path holding no authoritative state (it is a cache of a downloadable feed; `feedsync.Start` re-syncs an empty store immediately). Worse, the fault a caller cannot handle: a corrupt `.sst` makes `badger.Open` **PANIC from a goroutine badger spawns** (`created by … newLevelsController`), so `recover()` at the call site never fires and returning the error instead of exiting would have fixed nothing. `catdb.OpenResilient` is the boot-path entry point (**direct `catdb.Open` is for callers that already know the directory is sound**): a **per-attempt, flock-OWNED poison marker** — a SIBLING of the store, armed around every attempt and cleared however it returns — turns "a previous process died inside `badger.Open`" into a signal the next boot acts on, and the directory is quarantined **before** badger touches it. A marker counts as poison only when its **flock can be taken**, which the kernel permits only once its owner is gone; it is per-attempt rather than a single shared path because a shared one cannot survive concurrency (a second booting process would clear a still-live opener's breadcrumb, and if that opener then panicked the next boot would walk into the corrupt store again — the crash loop persisting through its own remedy). Four rules keep the rename safe and must not be relaxed: (1) it **moves aside, never deletes** (`.corrupt.<unixnano>`, the CHAOS-05/07 convention, pruned to ONE copy); (2) the DIRECTORY flock — badger's own lock — is **held ACROSS the rename, not probed and released before it** (`rename(2)` does not consult flocks, so probing leaves a window in which a concurrent boot's live store is renamed away); the invariant is carried by the TYPE — `quarantineDir` takes the `*heldLock` as a required argument and refuses a released one (`errStoreLockNotHeld`); (3) a live opener's marker is NEVER touched and a skipped quarantine leaves the breadcrumbs for the next boot; (4) returned errors are matched against the ENVIRONMENTAL deny-list (lock held, ENOTDIR, EACCES, EROFS, ENOSPC, EMFILE, EIO) **before** the corruption allow-list, and anything unrecognised DEGRADES — the fail-safe default is to leave the disk alone. The outcome is reported ONCE, after it is known (a quarantine followed by a failed replacement open is a FAILURE, not a recovery — reporting the quarantine first emitted two contradictory alerts). Note for anyone extending this: **none of these faults are reachable via `errors.Is`** (badger wraps with `y.Wrapf`, no `Unwrap`), so the fault → message table is itself a test (`TestClassifyOpenError_EmpiricalBadgerMessages`) and a badger upgrade that rewords them fails the build rather than silently stopping recovery. `loadCommunityFeedDB` degrades to `communityDB = nil`, which every consumer already nil-guards — byte-identical to running without `-cat-feed-db`. Visibility reuses existing vocabulary: the `state_file_corrupt` alert (same operator action, no second dialect), a `category_feed_db` operator-contract row, and `culvert_catfeeddb_{available,recovered,quarantined_copies}`. **Deliberately NOT on `/readyz`** — Layer-1-only categorisation is a fully serving node, and failing readiness would pull a healthy gateway out of rotation over a degraded cache. `internal/logstore` shares the same uncatchable-panic exposure and is recorded, not fixed (its content is request history with retention semantics). See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §19 and `docs/operator/category-store-recovery.md`.
- **The public admin-login endpoint bounds its username BEFORE any durable write (CHAOS-58, `login_input_bounds.go`)**: `apiAuthLogin` (`/api/auth/login`) is on `uiAuthMiddleware`'s PUBLIC allowlist and bounded nothing, so the caller's chosen `body.User` reached four retaining sinks — the tier-1 and tier-2 `internal/lockout` map keys (which `Cleanup` deliberately cannot sweep before `lockout.Window` = 10 min elapses), the 500-entry audit ring, the DURABLE audit JSONL, and the `auth_lockout` alert payload. The only limits in front of the handler are `securityMiddleware`'s 1 MiB body cap and the 60-mutating-POST/min per-IP API limiter, so ONE unauthenticated client commits **~60 MiB/min of chosen bytes** into a compliance record that is a `fileutil.RotatingFile(path, 50)` keeping exactly ONE archive (100 MB total, `rotating.go` removes the previous `.1` before renaming) — the entire retained audit trail rotated away in **under two minutes**, and ~1 GB of heap parked for ten. Measured by the gate: **4,195,672 bytes into the audit file from 8 requests.** `internal/audit`'s own header names this outcome (CWE-778/A09:2021) and its `writeErrors` counter CANNOT see it: **every one of these writes SUCCEEDS**, so `storage_write_failed`, the `audit_log_persistence` contract row and `culvert_audit_write_errors_total` all stay green while the record is destroyed. Four rules now hold. **(1) The bound is at the ENTRY POINT** — `rejectOversizeLoginUser` refuses `len(body.User) > maxUsernameLen` (256, the same constant `proxy_portal.go` already applies to Proxy-Authorization) and returns BEFORE the limiter, the credential check and the alert, so a rejected attempt creates no state at all. **A CONFIGURED account is NEVER refused, however long its name** (`cfg.LoginNameConfigured`, a non-retaining probe that MUST mirror `VerifyUIUser`'s own roster-or-legacy resolution — pinned by `TestChaos58_LoginNameConfiguredMatchesVerifyUIUser`, because a divergence is an admin lockout). The first draft claimed no real account could carry such a name, since `apiSetupComplete` and the user-creation API cap at 64; that is FALSE — `-user`/`auth.user` reach `cfg.SetAuth` and `--reset-password` reaches `cfg.SetUIUser`, and neither store bounds the name (`validateAuthStartupCredentials` validates only the password), so an over-long username can already be a valid persisted admin and refusing it would have locked that operator out of the admin UI on upgrade (Codex review, PR #1320). `warnOversizeConfiguredUsernames` (auth_startup.go) warns at boot and is deliberately NOT fatal — the stores never bounded the name, so failing the boot would brick an appliance whose config was legal when written. 400 not 401 is deliberate for a name that exists nowhere: a username's LENGTH is not a secret. The narrow cost is that, past the bound only, 400-vs-401 says "no such account" to a caller who already guessed the exact over-long name — a far better trade than refusing a real admin. **(2) `internal/lockout` carries the structural half** — `MaxUsernameKeyLen`/`boundUsername` clamp at EVERY public entry point (`Check`, `CheckPair`, `RecordFailure`, `RecordPairFailure`, `RecordSuccess`, `AttemptsLeft`, `ResetUser`). **The clamp is INJECTIVE** (rune-safe prefix + a SHA-256 digest of the WHOLE name), and that is a SECURITY property: because a configured over-long name is exempt from the rejection above, it reaches this limiter, so a plain truncation would let an attacker who knew that admin's first 256 bytes submit an ordinary ≤256-byte name clamping to the SAME key and drive the tier-2 account lock against them — lockout-as-DoS, the exact defect the two-tier design (RISK-012) exists to prevent (pinned by `TestBoundUsername_IsInjective`). Applying the clamp at only SOME entry points is worse than not applying it: `Check` and `RecordFailure` disagreeing about the key splits one attacker's failures across two counters and silently WEAKENS the lock while passing any byte-size assertion (pinned by `TestOversizeUsername_CheckAndRecordAgree`, with `TestBoundedNames_BehaviourUnchanged` as the control that an ordinary lockout is untouched). The package's `Cleanup` doc claimed the maps were bounded "against an unbounded-memory DoS" — true on the ENTRY-COUNT axis, never true on the KEY-SIZE axis. **(3) The attempt is still AUDITED** (`auth.login.rejected`, actor truncated via `truncateForAudit` with a self-describing `…[truncated, N bytes]` marker, real length in the detail): bounding the bytes must not delete the evidence that the admin plane is being probed, and the entry is O(1) at the same rate the ordinary `auth.login.fail` entry would have cost, so it adds no ring-eviction capacity the endpoint did not already have. **(4) The rejection is VISIBLE** — `culvert_login_oversize_rejected_total` is the operator's only signal (the caller just gets a 400), and the log line is rate-limited to one per minute with the magnitude in the counter, because a mitigation for a write-amplification defect must not be one itself. **Deliberately NOT done:** no byte cap inside `internal/audit` (the sink cannot tell attacker bytes from a legitimate `auditEventDiff` before/after payload — whole policy objects are marshalled there on purpose — so a cap would destroy real compliance evidence to fix an input-validation defect); no hard entry-count cap on the lockout maps (evicting at a cap evicts a REAL lock — an owner trade-off, recorded as open register row AU-16, now ~4000x smaller per key). Gates: `login_input_bounds_test.go` (10) + `internal/lockout/lockout_keybound_test.go` (9); seven defect gates verified failing against their reintroduced pre-fix shapes. See `roadmap/CHAOS-ENGINEERING-REVIEW.md` §25 and `docs/operator/admin-login-input-bounds.md`.

Refusing costs no availability: `x509.CreateCertificate` ignores the parent's window, so the cert was unusable from birth, and because `Enroll` accepts an unauthenticated caller (`VerifyClientCertIfGiven`) the operator's *re-enroll* recovery used to return a dead certificate WITH a success response. `clampNodeCertValidity` clamps node certs to the issuer on both ends (unclamped they overclaimed by up to a YEAR vs the leaf case's 24h, so every expiry surface in the fleet reported validity that did not exist); `clusterCARenewalWindow` (30d) is ONE constant shared by the CA's rotation window and the clamp horizon, so on a healthy fleet the clamp is unreachable. **(3) The shared rotation loop's start condition must not be owned by one of its CAs**: `StartCAAutoRotation` drives both trust roots and was started only `if certMgr.Ready()`, so an inspection-CA load failure silently disabled cluster-CA rotation + overlap cleanup for what is a 10-year certificate. It is now unconditional (both halves already no-op when their CA is absent). - **Request-log persistence is ASYNC (`internal/reqlog`)**: `Add` rings the entry in memory and enqueues it on a bounded channel; ONE drain goroutine owns the JSONL file, encodes with a reused `json.Encoder` into a `bufio.Writer`, and flushes as soon as the queue drains (so an idle proxy still gets one `write(2)` per entry — no added durability delay — while a backlogged one amortizes the syscall across the batch). Request goroutines must never marshal or `write(2)` the request log: `fileutil.RotatingFile` serializes every writer on one mutex held ACROSS the syscall and the rotation stall, so a slow volume used to cost every CONCURRENT request, not just the one being logged. Unlike syslog and logstore, the queue is a shock absorber and NOT a load shedder — the JSONL file is the durable audit record, so a full queue BLOCKS the caller (the pre-async behavior, never worse) and counts `Backpressure()`; no entry is ever dropped. Single drainer ⇒ the file stays FIFO. `Sync()` drains on demand (called by `ReadPersistent` so admin reads keep read-your-writes, and by `Close()` so shutdown loses nothing). See `internal/reqlog/persist.go` and `persist_test.go`.
- **Process-log writes are ASYNC (`internal/logsink`)**: `setupLogger` wraps the composed destination (`io.MultiWriter(os.Stdout, *fileutil.RotatingFile)`, or the `jsonLogWriter` pair in JSON mode) in `logsink.Writer`, so `logger.Printf` enqueues on a bounded channel and ONE drain goroutine owns the writers. `handleRequest` emits a line per proxied request (POLICY_ALLOW / POLICY_BLOCK / POLICY_DROP / POLICY_DEFAULT_DENY), and BOTH underlying writers were unbuffered behind mutexes held ACROSS the syscall — `log.Logger`'s own, and `fileutil.RotatingFile`'s (which also spans the remove/rename/reopen rotation stall) — so every request in the process serialized on two write(2)s. Measured (4-core, the verbatim POLICY_ALLOW line): the sink cost 2798 ns/op serial and **3204 ns/op at 4x parallel** — it got SLOWER as cores were added, i.e. a throughput ceiling, not a constant cost. Same contract as `internal/reqlog`: the queue is a shock absorber, NOT a load shedder — a full queue **BLOCKS** the caller (exactly the pre-change behavior, never worse) and counts `Backpressure()`; no line is ever dropped, and the single drainer keeps the log strictly FIFO. The drain loop flushes as soon as the queue empties, so an idle process still gets one write(2) per line (no added visibility delay) while a backlogged one amortizes the syscall. `logCloser` (returned by `setupLogger`, run last in the shutdown sequence) flushes before closing the file, and **`logger.Fatalf` is banned in favour of `logFatalf`** (logger.go) — `log.Logger.Fatalf` os.Exits immediately and would discard the queued line explaining why the process is exiting. The residual trade-off is that an ABRUPT death (SIGKILL/OOM) can lose the in-flight batch. Saturation is exported as `culvert_logsink_backpressure_total`. Pinned by `logger_async_test.go` (no loss, FIFO, flushing closer, JSON mode), `logsink_benchgate_test.go` (`TestBenchGate_LogSinkDecouplesCaller` — 64 lines against a 20 ms-per-write sink must return in ≪ 64x20 ms) and `internal/logsink/logsink_bench_test.go` (`TestBenchGateWriteAllocs`, 0 allocs/op).
- **Relay pattern**: All tunnel relays (CONNECT, WebSocket, SOCKS5) wait for BOTH goroutines; CloseWrite unblocks peers. Every raw relay is idle-bounded via `idleCopyCounted` (CHAOS-03): read deadlines armed at half of `tunnelIdleTimeout` (default 1h) around `io.CopyBuffer` — preserving the TCP↔TCP kernel-splice fast path — with a shared per-tunnel activity stamp so bytes in EITHER direction keep both goroutines alive, and a hard close of both conns on idle (the peer relay may be blocked in a deadline-less Write that only a close unblocks). Only READ deadlines are used: read timeouts are resumable on `tls.Conn`; a write timeout would corrupt TLS state.

- **The plain-HTTP forward path uses the transport, never an `http.Client` (`proxy_http.go`)**: a forward proxy must never follow a redirect — a 3xx belongs to the client — so `handleHTTP` built a per-request `http.Client` whose only jobs were `CheckRedirect: ErrUseLastResponse` and a timeout, and then paid for the redirect machinery anyway: `Client.do` installs it unconditionally BEFORE the first round trip, long before `CheckRedirect` is consulted. - **An unusable webhook signing secret is PRESERVED and REPORTED, never blanked away (SEC-WHSIGN-1, `internal/alerts`)**: webhook HMAC secrets are AES-GCM encrypted at rest (RISK-003) under a NODE-LOCAL key file (`<dataDir>/.alert_webhook_key`) that is deliberately never archived — the same rule that excludes `.kek` files, since a key must not share a tarball with the material it unwraps. `alert_webhooks.json` IS archived, so restoring a backup onto a fresh volume is the reachable way to hold a secret that cannot be unwrapped (an unreadable key file at boot — permissions, or an EMFILE window — gets there too). Three rules hold. **(1) The in-memory cleartext is still dropped** (never sign with a value that failed authentication), so `deliverAttempt` emits no `X-Culvert-Signature`. **(2) The on-disk ciphertext is KEPT** in the unexported `Webhook.sealedSecret` and written back VERBATIM by `save()`; re-encrypting the blanked cleartext persisted `""` and destroyed recoverable key material, and because `save()` rewrites the WHOLE list that was triggered by an unrelated add/edit/delete/toggle — the code's own "no data loss on a transient key-read failure" comment was not upheld. Restoring the original key file now recovers signing without re-entry. **(3) The state is VISIBLE.** `List()` blanks `Secret`, so "no secret was ever configured" and "the secret is unusable and deliveries are UNSIGNED" used to serialise identically — a monitoring blind spot where a receiver that verifies the HMAC silently stops accepting this node's security alerts, and quiet looks like healthy. `List()` now reports a DERIVED read-only `SigningDegraded` (`signing_degraded`), the `alert_webhook_signing` operator-contract row warns (counts only — no name, URL or ciphertext on that viewer-role surface), and the Alert Webhooks panel badges it. The status is derived and NEVER accepted from a caller or from the file (`Add`/`Update`/`Init` all clear it) and is never persisted. Delivery stays fail-OPEN-but-loud (unsigned, badged) rather than refusing to deliver: silence is worse than a visible authenticity failure on the alerting channel — recorded owner decision. **(4) A failed DECRYPT never mints a key** (`webhookSecretKey(dir, create)`; `create` is true only on the encrypt path). Minting on read meant the restore case wrote a fresh key as a side effect of failing to decrypt, so the preserved ciphertext and every later write sat under DIFFERENT keys and the documented "restore the original key file" recovery would break exactly the secrets the operator had already re-entered (Codex review, PR #1222). Creation now happens on the first encrypt — an explicit operator action — which also stops a failed read from attempting a write on a read-only or full volume. The operator remedy is therefore ORDERED and both surfaces say so: restore the original key file FIRST if you still have it (no re-entry needed), otherwise re-enter each secret, and never restore the old key AFTER re-entering. - **DPI scan ReDoS budget is enforced ONCE PER SCAN, not per pattern (`internal/scanner`)**: `ContentScanner.Scan` runs on every SSL-inspected response body (`safeDPIScan`, proxy_tunnel.go). `re.Match` is not interruptible, so the per-match ReDoS deadline needs a goroutine to abandon — and that harness (goroutine + channel + timer) used to be paid PER PATTERN: measured 6 allocs/448 B each, so a 20-pattern policy charged 120 allocs/9.0 KB and a 50-pattern policy 300 allocs/22.4 KB to every inspected body. Most operator patterns carry a literal prefix and match in a few hundred ns (`ghp_…` 158 ns/8 KiB), so the guard cost more than the work it guarded. `patternSet.scan` now walks the whole list in ONE worker: **7 allocs/480 B flat at 1/10/20/50 patterns** (−92% ns/op at 50 patterns, −29% on the 4-core parallel mix, throughput 14.0→19.5 MB/s). **The per-pattern budget is preserved exactly** — the worker stamps the start of each match and the parent charges the fired timer against the pattern actually running, extending it when that match still has budget (`budgetRemaining`); a whole-scan budget would have been equally fast but would fail closed on a large body with many individually-fine patterns, i.e. block legitimate traffic. Timeout stays fail-closed (S17), and the budget is enforced from BOTH sides so an overrun can never be forgotten: the parent catches a match still RUNNING past budget, while the worker times each match it COMPLETES (a descheduled parent would otherwise re-arm against the next pattern's stamp and silently admit the overrun — `TestMatch_WorkerCatchesItsOwnOverrun`). - **The request-latency histogram is SHARDED (`metrics.go`)**: `latencyHist.Observe` runs on EVERY proxied request (`recordRequestTelemetry`, proxy.go) — HTTP, CONNECT, WebSocket alike. It was documented as "lock-free", which is not the same thing as contention-free: it wrote three atomics per observation onto two shared cache lines, and the first was a compare-and-swap **LOOP** over ONE process-wide accumulator. A CAS loop under contention does not merely serialise — every losing core retries, and the retries generate the coherence traffic that makes the next round lose — so the metric got MORE expensive per request the more cores carried traffic, on 100% of traffic. Same class as the `internal/threatfeed`, `internal/logsink` and `internal/connlimit` findings. Median of n=15 on a 4-core box: **20.6 / 179.6 / 292.3 ns/op at 1 / 2 / 4 cores before** (four cores delivered 3.4M observations/s against 49M/s on ONE core — adding cores SUBTRACTED throughput) → **18.3 / 40.7 / 30.3 ns/op after**, flat in core count, **9.6x** the old four-core ceiling and slightly better at one core, so there is no low-concurrency price. The absolute "before" number is load-sensitive BY CONSTRUCTION (a contended CAS loop degrades further the busier the box is — a quieter run of the same benchmark measured 15.0 / 125.5 / 158.9 → 13.6 / 16.6 / 12.0); quote the SHAPE, not the constant. Two changes, both cost-only — every rendered number is the same number: (1) counters split across `histShardCount` (128) cache-line-padded `histShard`s, summed at scrape (a scrape is once per scrape interval against a per-request write path, so moving work read-ward is the correct direction); (2) the separate `total` field is GONE — the count is the sum of the bucket counters, which removes an atomic write AND makes `_count` exactly equal the `+Inf` bucket as the Prometheus exposition format requires (the old shape bumped `total` BEFORE the bucket, so a scrape landing between the two rendered `_count` one greater than `+Inf`). **The sum stays a float64 CAS, now per shard, and that is load-bearing:** an integer-NANOSECOND accumulator is a single atomic add and measured ~0.4 ns/op cheaper serially and ~2.9 ns/op cheaper at four cores, but int64 nanos overflow after 9.2e9 seconds of ACCUMULATED latency — about **107 days** of uptime for a 10k req/s gateway averaging 100 ms — and a wrapped sum exports a NEGATIVE, non-monotonic `_sum` to Prometheus and OTLP (caught in review on PR #1200; pinned by `TestHistogramSumDoesNotOverflowAtHighAggregateLatency`, which is written to fail against the integer form). Sharding is what removed the contention; the accumulator's TYPE never had to change to get it, and per-shard partial sums are ~128x smaller than the old global one so float64 precision is better than before, not worse. **Do not re-derive this as an integer accumulator.** The bits live in a `uint64` with `atomic.CompareAndSwapUint64`, NOT the pre-sharding `int64`: `math.Float64bits` speaks uint64, so the int64 field cost a `uint64<->int64` conversion on every read and write, each carrying a `// #nosec G115` that golangci-lint does NOT honour (those lines only survived because the lint gate runs `--new-from-rev` and predated them — the suppression was never load-bearing, the grandfathering was). The unsigned field removes both conversions and both suppressions. A non-finite guard is also new: one NaN observation used to poison `_sum` permanently. **`Observe` has no key to shard on, so the shard is derived from the observation itself** (splitmix64 over the float bits): latencies come from `time.Since`, so the low mantissa bits are nanosecond noise and spread well (4096 realistic samples fill all 128 shards, min 19 / max 49 / mean 32, none empty). A caller observing a CONSTANT value collapses to one shard and scales as the old code did — **never worse** — and that limitation is pinned as a CONTROL test rather than hidden. `snapshot()`/`Count()` are the read accessors (otlp.go and the histogram tests go through them). Gate: `TestBenchGate_ObservationsDoNotShareOneCounter` is **structural, not timing-based** — it requires realistic observations to touch many distinct shards, so a collapse back to one counter set fails deterministically on any hardware, under any load, with or without `-race` (the scaling-ratio gate was rejected for the same reason connlimit's was: a gate that can flake gets muted), with `TestBenchGate_ConstantObservationsCollapseToOneShard` as its control. `newHistogram` rejects more than `maxHistogramBuckets` (12) bounds rather than silently truncating. Full suite in `metrics_histogram_shard_test.go`.

- **Host→category resolution is INDEXED in both directions (`internal/urlcat`)**: the store has always carried a forward index (`index`/`adminIndex`: category → lowercase host set) giving `MatchesHost` an O(labels) probe, but the REVERSE direction — `LookupHost`/`LookupHostAdmin`, host → category — was a nested scan over every host pattern of every category. - **Identity-backend availability (CHAOS-47, `auth_backend_health.go`)**: the legacy LDAP and OIDC proxy-auth backends cache authentication OUTCOMES (5 min / 2 min) so a per-request-auth gateway does not re-bind or re-introspect per request. **Only an AUTHORITATIVE answer from a reachable backend is cacheable** — wrong password, inactive token, user not found, not in the required group. A failure to REACH the backend (dial refused, STARTTLS error, service-account bind failure, search error, introspection transport error, non-200 from the introspection endpoint, malformed body) is NOT: the request still fails closed, but caching it kept denying valid credentials for a full TTL *after* the backend recovered, per credential. `verify`/`introspect` therefore return an error reserved for infrastructure failure; `(false, nil)` means the backend answered "no". TTL, cap, single-use `Pop`, and the fail-closed callback are byte-identical — fairness decides only WHO is evicted, never what is admitted. - **The IP filter's per-request gate is LOCK-FREE and FLAT in entry count (`security.go`)**: `ipf.Allowed` is the FIRST gate on every proxied request (`handleRequest`, `socks5.go`), reached before the rate limiter, authentication, or policy. It took a process-wide `sync.RWMutex` read lock to reach its decision — including in the DEFAULT posture, where the filter is DISABLED and the lock guarded a `mode` string that never changes. `RWMutex.RLock` is an atomic read-modify-write on one shared word, so this was not a constant cost but a **throughput CEILING**, and the rate limiter sitting beside it in the same file already showed the right shape (`enabled atomic.Bool` probed BEFORE any lock). Measured (4-core Xeon, n=6, `BenchmarkIPFilterAllowed_*`): the disabled path cost **18.8 ns at GOMAXPROCS=1, 59.2 at 2, 65.0 at 4** — four cores bought **1.16x** the throughput of one, for a feature that is switched off. Two further defects rode along: every enabled-mode call spent **1 alloc / 16 B** (`net.ParseIP` + `net.IP.String()` to build a map key), and the CIDR side was a **linear scan** at ~14 ns per configured prefix — 105.9 ns at 1 CIDR, 317.9 at 16, 1042 at 64, **3785 at 256**, i.e. **3.8 µs of CPU per request** inside the request goroutine for an ordinary enterprise allowlist. `Allowed` now reads an immutable `ipFilterView` through an `atomic.Pointer` (the `internal/threatfeed` pattern): **2.3 / 1.2 / 0.6 ns** disabled (flat, scaling near-linearly: 3.8x from 1→4 cores), **0 allocs** in every posture, and the CIDR axis is **FLAT — ~55 ns at 1, 16, 64 and 256 prefixes (69.6x at 256)**. **Three invariants make it safe.** (1) The `mu`-guarded fields stay the AUTHORITATIVE write-side state, so `Add`/`Remove`/`ClearAll`/`List`/`Mode` keep their exact prior semantics — including `Remove`'s pre-existing raw-string keying, which is preserved rather than quietly fixed — and every mutator rebuilds and publishes a derived view before releasing the lock. **A mutator added without a `publishView()` call is a silent SECURITY failure, not a perf one** (a revoked allowlist entry that keeps admitting, a removed blocklist entry that keeps denying), pinned per mutator by `TestIPFilterView_EveryMutatorRepublishes`. (2) Membership is bucketed by PREFIX LENGTH — the address is masked to each DISTINCT length present and probed against a `map[netip.Prefix]struct{}` — so cost tracks the number of distinct lengths (bounded at 33 v4 / 129 v6, 2–5 in any real config) instead of the number of prefixes. (3) `prefixFromIPNet` **mirrors `net.networkNumberAndMask`**, and that is the subtle part: a network address `To4()` accepts is an IPv4 network however many bytes it is STORED in, and a 16-byte mask is re-read as its low four bytes, so `::ffff:10.0.0.0/104` behaves exactly like `10.0.0.0/8` and matches the plain address `10.0.0.1`. A naive "16 bytes means IPv6" reading gets that wrong in the FAIL-OPEN direction for a blocklist — it was written that way first and `TestIPFilterView_DifferentialAgainstLegacy` caught it. That differential test (a verbatim copy of the old `net.ParseIP` + linear-`Contains` algorithm as the oracle, over hand-picked divergence shapes plus 300 randomized filters) is the correctness spine, since the change also swaps PARSERS (`netip.ParseAddr` for `net.ParseIP`); zoned addresses are the one known divergence and are explicitly rejected to keep net's verdict, and 4-in-6 probes are `Unmap`ped for the same reason. `oddNets` carries any non-contiguous-mask `IPNet` on a linear fallback — unreachable via `net.ParseCIDR`, present so the representation change can never silently drop an entry from a security filter. **Publishing is per-MUTATION, so a LIST must be loaded through `AddAll`** — `publishView` rebuilds the whole derived view, so an `Add` loop is O(N²) (measured: 46 ms at 1k entries, 857 ms at 4k, 3.27 s at 8k, extrapolating to minutes at 100k against this list's `maxSnapIPList` cap of **2,000,000**), which would stall a boot or a snapshot apply on a legitimate enterprise allowlist. `AddAll` takes the lock ONCE, appends in one pass and publishes ONCE (8k entries: 3.27 s → 2.31 ms), returning the rejected entries so callers log them AFTER the lock is released rather than under it; all five bulk callers use it (startup `connlimit_startup.go`, `admin_settings` restore, config-version rollback — whose `List`+`Remove` clear loop is now the equivalent O(1) `ClearAll` — config import, and the CP→DP snapshot apply). `Add` still publishes per call because a single admin edit must be live immediately. Caught in review by Codex on PR #1207 and pinned by `TestBenchGate_IPFilterBulkLoadIsLinear` (ratio gate: 4x the entries must cost ≤8x — linear is ~4x, quadratic ~16x, measured 3.31x post-fix and 17.97x pre-fix) plus `TestIPFilterAddAll_MatchesAddLoop`. Gates: `TestBenchGate_IPFilterAllowedTakesNoLock` is **structural** (holds the write lock, requires `Allowed` to answer anyway — deterministic on any hardware, under `-race`, at any load), `TestBenchGate_IPFilterAllowedIsFlatInCIDRCount` is a **ratio** gate (1.01x measured, bound 4x, ~35x if the linear scan returns), and `TestBenchGate_IPFilterAllowedAllocsFree` pins 0 allocs across five postures.

- **The fencing lease has a way BACK (CHAOS-55, `ha_lease_recovery.go`)**: ADR-0005 has three exits from write authority (denied on promotion, denied on resume, self-fenced by the keepalive) and shipped a return path for exactly one. The other two dead-ended, and the mechanism is one sentence twice: **an unknown was treated as a decision.** `ha_lease.go`'s header states the rule for the other direction — *"leadership cannot be taken while the fence's state is unknown"* — and the promotion path obeys it exactly; the resume path broke it in reverse. **(1) HA-7:** `acquireLeaseForResume`'s 45 s budget (`haResumeGhostWait`) was spent ONLY on waiting out this node's own ghost lease, and a transport error returned false on the FIRST attempt — so the fault that actually happens, **boot ordering** (a host reboot starts culvert and etcd concurrently; seconds of `connection refused` is enough), got zero retries. `ResumeAsLeader` then asserted `role=leader, leaseEpoch=0`, and because `startLeaseKeepalive` no-ops on a zero epoch, NOTHING in the process ever called `Acquire` again: no issuance, no revocation sync, no snapshot a DP would accept, and `PromoteManually` refuses a node already roled `leader`, so a human restart was the ONLY lever. **(2) HA-16, worse:** with a recorded `standbyAddr`, ANY failed resume demoted to standby — including an unreachable backend. In a 2-node cluster restarting together the guess is symmetric: each stands by against the other, neither can sync (`verifyBundleEpoch` rejects a bundle with no live holder), `lastSyncOK` stays zero, and `leaseAutoPromote`'s freshness gate then refuses every promotion — **a permanently leaderless cluster from a few seconds of etcd being slow to boot.** Four rules now hold. **(a)** `resumeAcquireRound` classifies each round (`granted`/`foreign`/`ownGhost`/`unknown`/`raceRetryable`) and the resume retries the retryable ones — this alone covers the boot-order case with no read-only window — but under its OWN budget `haResumeUnreachableWait` (5s), NOT the ghost path's 45s: `ResumeAsLeader` runs inside `initCluster`, which `main.go` orders BEFORE the root CA, the policy engine, the proxy listener and the admin UI, so blocking here is time the DATA PLANE is not serving, and the fence governs control-plane writes only. Reusing the 45s budget would have traded a CP write outage for a data-path outage; anything longer is the background loop's job, which costs the boot nothing (pinned from both ends). **(b)** A longer outage arms a background re-acquire loop, bounded in RATE and never in ATTEMPTS (1 s→30 s, ±20% jitter — a fleet restarts together, so a fixed cadence aims a synchronised herd at the recovering etcd, the WK-13 shape). That does not violate "avoid infinite retries" for CHAOS-54's reason: the retry is never silent (first failure immediately, then ≤1 line/60 s, then a recovery line naming the suppressed count; magnitude in a counter), and the sleep is INTERRUPTIBLE so `Stop` never waits out a backoff. **(c) ONE ATOMIC ACQUIRE decides, and an AFFIRMATIVE foreign holder is LATCHED.** `Provider.Acquire` is a single transaction: it cannot succeed while anyone else holds the lease, and when it denies it reports the holder it saw. So a grant IS proof the fence was free and a denial carries the evidence — `acquireLeaseAttempt` surfaces that Status (the bool wrapper discarded it, which forced a second `Read` whose window let a foreign holder expire between the two calls and read back as free; Codex review of PR #1223). Quietly retrying until a live peer DIES and then taking over would make a node of unknown state age authoritative, which is precisely `haPromoteFreshnessWindow`'s judgement, so recovery routes to it rather than around it: an observed foreign holder is LATCHED (loop exits, this process never acquires again) and its disposition MIRRORS the shipped S4/S2 decision — resync from the recorded ex-standby, else keep the read-only leader role + CRITICAL alert. **The poll interval is capped BELOW the lease TTL (`recoveryPollCeiling`) and that is a CORRECTNESS bound, not tuning:** a free lease proves nobody holds it now, not that nobody held it since we last looked, and etcd keeps a holder's key for ≥1 TTL after it stops renewing — so looking at least once per TTL makes a completed-and-vanished peer tenure impossible to miss between two SUCCESSFUL observations (HA-19; the residual blind-partition case is recorded for an owner, and the shipped resume path already shares it). **(d) Panic containment lands the OPPOSITE way from `leaseRenewRound`**, and the contrast is the point: containing a keepalive panic is dangerous because it would extend authority the node is no longer confirming (CHAOS-24), whereas here there is NO authority to extend, so containing and backing off is strictly fail-closed. ## Admin UI / Control Plane

The admin API is wired in three layers — `startUI()` only composes them, never registers routes itself.

**Route registration**
- `startUI()` MUST NOT contain `mux.HandleFunc` calls. All routes are registered through per-domain `register*Routes(mux, ...)` helpers (e.g. `registerPolicyRoutes`, `registerSecurityRoutes`).
- `uiRoutes` in `ui_routes_meta.go` is the **single source of truth** for route metadata. Adding a route means: (1) register it via a `register*Routes` helper, (2) add a corresponding `uiRouteMetadata` entry to `uiRoutes`.
- Metadata is **method-aware** via `Methods []uiRouteMethod`. Each entry declares `Method`, `MinRole`, `Mutating`, `AuditExpected`, plus an optional note. `MethodAny` (`"*"`) is the catch-all when a handler intentionally treats every method the same.

**Middleware chain (outer → inner)**

```
uiIPGuardMiddleware → securityMiddleware → uiAuthMiddleware → uiMetadataEnforcement → mux
```

- `uiAuthMiddleware` owns the public-route allowlist and injects `uiRoleKey{}` into the request context.
- `uiMetadataEnforcement` (C2) reads that role and gates the request against per-method `MinRole` from `uiRoutes`. **Active by default** — fail-closed.
- `securityMiddleware` still owns CSRF, body-limit, and rate-limit decisions based on the HTTP method. The `Mutating` flag in metadata is **informational only**; it does not alter middleware behavior.

**Kill switch**
- `CULVERT_C2_ENFORCE=false` (or `0`/`no`/`off`) reverts C2 to shadow mode (log-only, never blocks). Read once at startup; admin-API runtime mutation is intentionally not supported.

**AuditExpected (C2c)**
- Pure observability. After a 2xx/3xx response, if metadata says `AuditExpected=true` and no `auditEvent`/`auditEventDiff` ran, the middleware emits one `C2: audit missing ...` log line and increments `c2AuditMissingTotal`. Failed requests, hijacked responses, and public routes are skipped. C2c **never** blocks a request.

**Role-divergence detector (C4 — REPORT-ONLY)**
- Pure observability. When the C2 middleware admits a request whose per-method `MinRole` is *lower* than what the handler-level `requireRole` ultimately demands (e.g. `apiIdPRouter` declares `MethodAny=viewer` but `apiIdPItem`'s PUT branch calls `requireRole(RoleAdmin)`), C4 increments `c2RoleDivergenceTotal` and emits one `C2: role divergence ...` log line. The middleware injects the C2-evaluated `MinRole` into the request context; `requireRole`'s failure branch reads that value and compares against the role it just rejected.
- C4 **never** blocks, allows, or alters the response. The handler's existing `requireRole` writes the 403 itself; C4 only observes the decision after the fact. Defense-in-depth (invariant #6) is preserved; the handler is still the real backstop.
- Audit ring is intentionally untouched — divergence events are governance observability, not admin-action audit. They flow out via the structured logger and the C3 governance endpoint only.

**Governance surface (C3)**
- `GET /api/governance/control-plane` (admin-only) exposes route inventory, C2 mode, the six C2 counters, derived health (four axes), and the parity-test pyramid (D0/C1/C1.5/C2/C2c/C4). Read-only and side-effect-free; no Prometheus exposure, no AST replay, no schema mutation. The kill switch stays env-only and read-once.
- C3 health severity policy (`deriveGovernanceHealth`):
  - `missing_meta > 0` → `metadata_parity = drift`, status = `drift`. C1 reverse-parity should make this impossible at runtime, so any non-zero value is genuine governance/config drift.
  - `no_policy > 0` → `metadata_parity = warn`, status ≥ `warn`. The counter can be triggered by a client sending a method the route does not accept (e.g. PATCH against a GET-only route, scanner probes); reserving drift for `missing_meta` keeps the indicator from flipping to drift on benign client traffic.
  - `audit_missing > 0` → `audit_completion = warn`, status ≥ `warn`.
  - `enforce_denied > 0` while `mode = shadow` → `enforce_consistency = drift`, status = `drift` (the kill-switch contract is read-once at startup).
  - `role_divergence > 0` → `role_divergence = warn`, status ≥ `warn`. Triggered legitimately by viewers probing admin-only sub-actions on dynamic dispatchers; reserved for warn rather than drift to avoid noise on benign client traffic.
- The six C2 counters surfaced by C3 (one-line definitions):
  - `would_deny` — session role was below the per-method `MinRole`. Increments in BOTH shadow and enforce modes; tracks the policy decision regardless of action.
  - `enforce_denied` — request actually got a 403 from the metadata-driven gate. Stays at zero in shadow mode; in enforce mode it moves in lock-step with `would_deny`.
  - `missing_meta` — request path resolved through the mux but had no matching `uiRoutes` entry (the static `/` catch-all absorbs unknown paths, so this is rare in practice). Soft-fail; never blocks a request.
  - `no_policy` — path matched a `uiRoutes` entry but the HTTP method had no exact policy and no `MethodAny` fallback. Soft-fail; never blocks a request. Triggered both by genuine drift and by clients sending unsupported methods (see severity policy above).
  - `audit_missing` — successful request (2xx/3xx) on an `AuditExpected=true` route did not emit an `auditEvent`/`auditEventDiff` call (C2c observability).
  - `role_divergence` — handler-level `requireRole` rejected a request whose C2-evaluated `MinRole` was strictly lower (i.e. metadata was more permissive than the handler's actual contract). Increments at most once per request, on the failure branch of `requireRole`. Observability only; never blocks.

### Admin UI / Control Plane Invariants

These are non-negotiable for any change touching the admin API:

1. **No route without metadata.** Every `mux.HandleFunc` path must have a matching `uiRoutes` entry. C1 forward/reverse parity tests enforce this.
2. **Metadata must never be more permissive than handler behavior.** If the handler enforces admin, metadata cannot say viewer. C1.5 AST parity tests enforce this for directly detectable handler behavior; dynamic/delegated handlers must be documented and reviewed.
3. **Resolution order: specific method > MethodAny > soft-fail.** Don't use `MethodAny` to paper over a method-specific contract.
4. **Missing metadata / no method policy must NEVER block requests.** Both are soft-fail in shadow and enforce mode — they log + count, the handler-level `requireRole` remains the real backstop.
5. **Public routes are owned by `uiAuthMiddleware` only.** C2 stays out (`RolePublic` is documentation, not enforcement). Don't add public-route gates to C2.
6. **Do not remove handler-level `requireRole`.** C2 is an additional gate, not a replacement. Defense-in-depth is the contract.
7. **C2 must never allow what the handler denies.** If they ever disagree, the handler wins by design — C2's role is to add denials, never to widen access.

### Testing Guarantees

Each layer has its own test suite — keep them green when modifying the admin API.

- **D0** (`d0_*_test.go`) — route/auth/security baseline invariants: route inventory pinned at the canonical count, auth allowlist, CSRF, body-limit, and rate-limit checks.
- **C1** (`ui_routes_meta_test.go`) — bidirectional route/metadata parity layer: forward (every `uiRoutes` entry has a matching `mux.HandleFunc`) and reverse (every `mux.HandleFunc` has a matching `uiRoutes` entry), source-scan based.
- **C1.5** (`ui_routes_meta_audit_test.go`) — AST-walk parity between metadata `MinRole`/`Mutating` and the per-method behavior of each handler (`requireRole` calls, method switches).
- **C2** (`ui_metadata_enforcement_test.go`) — middleware enforcement: shadow mode is silent, enforce mode returns 403, kill switch toggles correctly, missing-meta and no-policy stay soft-fail.
- **C2c** (`ui_metadata_enforcement_test.go` — `TestC2c_*`) — audit-completion observability: warns on success without audit, silent on failure / hijacked / public / `AuditExpected=false`, never blocks the request.
- **C4** (`ui_metadata_divergence_test.go` — `TestC4_*`) — report-only role-divergence detector: increments `c2RoleDivergenceTotal` and emits a structured log line when the handler's `requireRole(R)` rejects a request whose C2-evaluated `MinRole` was strictly lower. Tests cover the canonical viewer-on-admin-route case via `apiIdPRouter`, the parity case (no event), the C2-stricter case (no event), and the response-decision invariance proof (C4 cannot change the 403 the handler already wrote).

### Test-authoring pitfalls

- **Audit ring saturation.** The in-memory audit ring is bounded at `maxAuditLogs = 500`. Tests MUST NOT assert on `len(auditGet())` deltas (e.g. `len(after) == len(before)+1`) because under `-count=2 -shuffle=on` the cumulative suite saturates the ring and `len()` stops growing — adding a new entry evicts the oldest. The determinism gate (`QA · Determinism`) re-runs the suite shuffled to flush these out. Instead, assert on entry **content**: scan `auditGet()` for an entry matching a unique discriminator (`Actor` IP from a TEST-NET-2 reserved range, plus `Action`/`Object`, plus a baseline `TS` captured before the call). See `security_feedsync_audit_test.go` for the canonical pattern.
