⚠️ Stage-1 outcome ≠ Allow. Auth Policy rules decide how a client authenticates — they never allow traffic. Stage-2 policy still decides access and default-deny still applies. Creating, editing, deleting and reordering these rules requires the admin role.
  • Exempt — skips end-user authentication only, and only when the client presents no credentials. No identity is ever created. Stage-2 still decides.
  • CredentialRequired — returns a deterministic 407 credential challenge; the client must authenticate first. It does not allow traffic, and the Stage-2 decision applies only after the client authenticates.
  • SSORequired — requires an interactive browser SSO login first: a browser is redirected (302) to the IdP, while a non-browser or CONNECT client is failed closed (403). It does not allow traffic; Stage-2 still decides access only after an identity exists.

Decryption Profiles

A Decryption Profile is the "how to decrypt" object a policy rule references (the rule's match criteria are the "what"). It controls Inspect as HTTP/2 (removes the HTTP/1.1-downgrade anti-bot signal), upstream certificate verification, the TLS version floor/cap, and the per-stream stall bound.
Honest scope: native HTTP/2 does not change the TLS fingerprint — Google-class destinations that fingerprint the ClientHello or key on egress-IP reputation may still challenge; those need a Bypass rule or warmed dedicated egress. Best fit: business-critical H2 SaaS you must keep inspected.

TLS parameter negotiation only (version/cipher below floor).
Whole inspect-failure class (can't-decrypt / client cert / pinning). Drives auto-exclusion.

⚠ Fail-open disables SSL inspection for hosts it can't decrypt. After a confirm-count of distinct clients, an incompatible host is auto-excluded and later sessions bypass inspection until it expires (12h; 1h pinned). Untrusted/expired certs are never excluded — they stay blocked. Learning is scoped to this profile only.

How auto-exclusion works
Learns on a genuine can't-decrypt signal only — the origin requires a client certificate, an unsupported TLS version, or a pinned client rejects our forged cert; generic origin errors and cert-validation failures do not qualify (they stay a 502 / block). Only the client-cert-required case rescues the current session; everything else is learn-only, so the first connection to a never-before-seen incompatible host still fails and the next self-heals — add known pinned apps to the manual SSL Bypass list for guaranteed first-session success. The cache is volatile and per-node. Every learn is alerted, audited, and listed under Decryption Exclusions. Keep inspection-mandatory hosts on fail-close rules — those are never learned or bypassed.
Decryption Exclusions

These are hosts SSL inspection is currently OFF for — learned automatically because an inspected tunnel could not be established (unsupported TLS, the origin required a client certificate, or a pinned client rejected our certificate) under a rule whose Decryption Profile opts into fail-open. A host is only excluded after a confirm-count of distinct clients, and entries expire (12h; 1h for pinned). Each exclusion is scoped to the decryption profile that learned it — a host excluded under one profile is still inspected for rules using a different profile. An untrusted/expired origin certificate is never auto-excluded — that stays a block. This cache is volatile (cleared on restart, never synced between nodes) and is not part of config export/rollback. Every entry below means inspection coverage is reduced; evict any you don't expect.

The token + fingerprint pair come from the Sluice admin. Fingerprint is TOFU-pinned — a mismatch rejects the handshake even with a valid token. Sync to Leader

Fencing is configured at startup (--ha-etcd-endpoints / cluster.etcd_endpoints) and read once — this panel shows status only. With a lease armed, leadership and automatic failover are arbitrated by etcd; write authority requires a live lease. The Term tile above equals the epoch of the currently-held fencing lease (ADR-0005: term = a held lease's epoch). In a failure state where no lease is held — e.g. a leader that restarted and cannot reacquire the etcd lease, running read-only — the lease card shows epoch 0 while Term retains the last synced value, so the two can differ precisely when you are diagnosing a fencing problem.

This standby polls the leader every ~5s. The Sync to Leader tile shows the current consecutive-failure streak — it resets to 0 on every successful sync. At the configured threshold this standby stops waiting and either self-promotes (automatic failover / fencing lease) or, if automatic failover is off, stays read-only until an operator promotes it manually. Watching this tile climb is your early warning before that happens.

Use when the leader is down and automatic failover is off. Confirm the leader is truly gone first — promoting while the leader still serves causes split-brain.
