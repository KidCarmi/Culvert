# D1.0 — Persistent State Inventory Audit

**Status:** read-only inventory. No code changed; no migrations introduced.
**Scope:** map every artifact that survives a process restart and is relevant to install / upgrade / rollback. Output is the input to D1.1, not a fix list.
**Sources:** code search across the repo on branch `claude/review-claude-production-plan-ZCXER`. Where a fact could not be pinned with certainty from source, the field is marked `???` rather than guessed.

## Methodology

- Grep’d the tree for every disk-write primitive (`os.WriteFile`, `os.OpenFile` with `O_CREATE|O_WRONLY`, `os.Create`, `json.NewEncoder` paired with a file, `os.Rename`, `ioutil.WriteFile`).
- Cross-referenced startup readers (`os.ReadFile`, `os.Open` + decoder) against writer call sites.
- Walked `configversion.go` to determine which artifacts are captured in `configBackup` (i.e. what the rollback API can actually restore).
- Walked the `ConfigSnapshot` struct in `controlplane.go` to determine which artifacts are pushed to DPs.
- Anchored against state-bearing files explicitly named in `CLAUDE.md`: `store.go`, `ca.go`, `configversion.go`, `threatfeed.go`, `feedsync.go`, `enrollment.go`, `controlplane.go`, `nodegroup.go`, `bandwidth.go`, `hashcache.go`, `lockout.go`, `session.go`, `auth.go`, `bootstrap.go`, `update.go`, `update_cluster.go`, `config.go`, `events.go`, `logger.go`, `syslog.go`, `catdb.go`.

## Risk rubric

Risk is **upgrade/rollback risk**, not general operational risk.

| Rating | Triggers (any of) |
|--------|-------------------|
| **HIGH** | Non-atomic write of an artifact that is (a) written from a request-handling goroutine, OR (b) loss-of-quorum critical (RBAC, CA, cluster bootstrap), OR (c) the rollback mechanism itself. |
| **MEDIUM** | Non-atomic write of a non-critical artifact, OR atomic write but no payload version field on a schema that is mutated through the admin API, OR sidecars that can desync from a primary file across a crash. |
| **LOW** | Atomic write AND (in `configBackup` snapshot OR cluster-synced OR trivially regenerable). |
| **N/A** | Network sink, no on-disk persistence. |

## Recommended-next-test taxonomy

Used in the per-artifact `Next test` field. These are *candidates* — D1.1 picks one or two categories, not all.

- **A.** Cold-start (empty path) — assert sensible default, fail-closed where applicable.
- **B.** Atomic-write hardening — replace direct `os.WriteFile` with temp + rename + fsync.
- **C.** Sidecar consistency — assert primary + sidecars stay consistent across mid-write crash.
- **D.** Backup/restore round-trip — admin export → wipe → import → verify.
- **E.** Schema-version probe — feed file from future schema; assert graceful skip, never delete.
- **F.** Concurrent-writer race — fire N admin API writes; assert no corruption / no lost updates.
- **G.** Crash-during-write — kill -9 mid-write; assert recoverability or clear failure.

## D1.1 selection — what the data points to

You posed four candidates: cold-start tests, backup/restore tests, upgrade fixture tests, atomic-write hardening. The inventory makes the relative cost/benefit fairly clear.

**Atomic-write hardening (your option “atomic-write hardening”)** is where the data screams loudest. Seven HIGH-risk artifacts hinge on it, including the rollback mechanism itself — and three of the seven (`config_versions`, `cluster.json`, `bandwidth.json`) are written every time an admin clicks Save. Hardening these is **mechanical** (introduce a single `writeFileAtomic` helper, replace ~10 call sites), reviewable in isolation, and unblocks every other D1 workstream — fixture tests are pointless if the writer that produced the fixture is itself non-atomic.

**Cold-start tests** are the natural pair: cheap, no production code change, and they expose any startup paths that assume a file exists (CA bootstrap, UI users default admin, cluster store, enrollment). Together with hardening they form a small, defensible D1.1.

**Backup/restore tests** are valuable but presuppose backup endpoints that don’t exist yet for ~6 artifacts (UI users, cluster store, CA, threat feed, …). That’s a feature workstream more than a test workstream.

**Upgrade fixture tests** are highest-leverage long-term but lowest-leverage now: 14 artifacts have no version field, so a fixture from “v_old” is indistinguishable from a fixture from the current build. Designing fixtures is wasted effort until those schemas grow versions.

### Recommendation

**D1.1 = (a) atomic-write hardening for the seven HIGH-risk artifacts + (b) cold-start tests for everything in the inventory.** Defer backup/restore and fixture work to D1.2 / D1.3 once the two preconditions above are in place.

Tradeoff: this is a code-change workstream, not a pure test layer like D0/C1. If you want D1.1 to remain test-only, the second-best choice is **cold-start tests alone** (option “cold-start / empty-data tests”), which surfaces the same risks observationally without touching production code. The HIGH-risk atomicity gaps would then move to D1.2.

Two clarifying questions before you pick:

1. Is D1.1 allowed to ship code changes (atomic-write helper + ~10 call-site replacements)? If not, default to cold-start tests only.
2. For cold-start: do we want to assert *fail-closed* defaults (e.g. missing `ui_users.json` → no admin, UI in lockout) or *bootstrap* defaults (auto-create default admin)? The current code does the latter; the former is more aligned with the “Default deny” invariant in `CLAUDE.md`.
