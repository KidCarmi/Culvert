# P2 — Release Pipeline & Image Trust (keyless / Sigstore)

Status: PLAN. Decision recorded: **keyless OIDC/Sigstore** signing; start in
parallel with the P1.7 auto-seed PR (#499).

This realizes Phase 2 of `docs/operator/enterprise-release-catalog-plan.md`: move
catalog publication into the release process so no human hand-edits an official
catalog, sign images keyless, emit provenance, and gate releases in CI.

## The trust-model fork "keyless" forces (read first)

Phase 1 (shipped, #498) verifies the catalog with a **baked ed25519 public root**:
`index.json.sig` is a detached ed25519 signature over raw `index.json`, checked
against `bakedReleaseTrustKeysJSON` ∪ `CULVERT_RELEASE_CATALOG_TRUST_KEYS`.

"Keyless" (Sigstore) has **no long-lived key**: CI signs with an ephemeral key
bound to its OIDC identity via a Fulcio X.509 cert, logged in Rekor. Verification
trusts a **Fulcio root + an identity policy** (the GitHub Actions workflow
identity), not a fixed public key. These are different trust models:

| | Phase 1 (today) | Keyless (Sigstore) |
|---|---|---|
| Catalog trust root | baked ed25519 public key | Fulcio root + identity policy (+ Rekor) |
| `index.json.sig` | ed25519 detached envelope | Sigstore bundle (cert+sig+log entry) |
| Verifier | stdlib `ed25519.Verify` (tiny) | `sigstore-go` (heavy dep, TUF roots) |
| Offline/air-gap | trivial (key baked) | needs bundled Fulcio/Rekor/TUF roots |

So a fully-keyless **catalog** means a new in-binary Sigstore verifier and a
trust-root change to what Phase 1 just shipped. That is significant and
dependency-heavy (`sigstore-go` pulls a large tree; air-gap needs bundled roots).
**Image** signing keyless is cheap and needs no binary change.

### Recommended slicing (keeps each PR reviewable, defers the heavy change)

- **P2a (this plan): release pipeline + keyless IMAGE trust + CI gates.** No
  Control-Plane trust-model change. Concretely:
  - Release workflow resolves the pushed image digest after publish.
  - Catalog is **generated from release metadata** by a committed generator
    (`scripts/gen-release-catalog`), never hand-edited — including `expires_at`
    and a monotonic `catalog_version`.
  - `cosign sign` the image **keyless** (GitHub OIDC); push signature + a SLSA
    provenance attestation.
  - Catalog is signed for the CI gate with an **ephemeral ed25519 key minted in
    the workflow** (proves the existing verifier end-to-end) — this is a TEST
    signature for the gate, NOT an official trust root yet.
  - CI gates (release-blocking):
    - every catalog ref is `repo@sha256:<64hex>` (no tags),
    - catalog `list_digest` == the digest the workflow actually pushed,
    - catalog verifies with the workflow's ephemeral public key (round-trip),
    - `expires_at`/`catalog_version`/schema present and well-formed,
    - image signature verifies against the expected workflow identity (cosign),
    - provenance attestation exists for the release image.
  - Attach the catalog bundle (`index.json`, `index.json.sig`, manifests,
    `checksums.txt`) + provenance to the GitHub Release.
  - **No baked official root is shipped in P2a.** The CP still only trusts what an
    operator configures; P2a proves the *pipeline* is correct and tamper-evident.

- **P2b (separate, reviewed follow-up): migrate Control-Plane catalog trust to
  Sigstore identity.** Add the `sigstore-go` verifier path, make the "baked root"
  a pinned Fulcio root + GitHub workflow identity policy, bundle the offline
  roots for air-gap, and only then publish the official keyless-signed catalog the
  shipped CP trusts out of the box. This is the change that actually makes
  end-users update through Release Management, and it deserves its own security
  review because it revises the Phase 1 verifier.

This ordering means **P2a ships value with zero risk to the Phase 1 trust model**,
and the consequential trust-model migration (P2b) is isolated for its own review.

## P2a deliverables (files)

- `.github/workflows/release.yml` (new or extend `ci.yml` release job):
  `permissions: id-token: write, contents: write, packages: write`; build+push
  image, capture digest, `cosign sign`/attest keyless, run the catalog generator,
  run the gate, attach artifacts.
- `scripts/gen-release-catalog/` (Go, in `package main` under a `tools` build tag
  or a separate module-free script dir): deterministic generator from release
  metadata → `index.json` + manifests; refuses tags; stamps `expires_at`,
  `catalog_version`. Reuses the existing on-disk shapes.
- `scripts/sign-catalog`: minted-ephemeral-ed25519 signing for the CI gate
  (private key never leaves the runner job; public key is an output the gate
  verifies against — NOT committed, NOT baked).
- `release_pipeline_gate_test.go` (or a CI step invoking the existing loader):
  a Go test/gate that loads the generated bundle through `LoadVerifiedCatalog`
  with the gate's ephemeral public key and asserts the digest-match + ref-shape +
  freshness invariants. Reuses Phase 1 code so the gate can never drift from
  runtime verification.
- Docs: enterprise plan Phase 2 status; README note that official keyless catalog
  trust lands in P2b; no overclaiming.

## Non-goals (P2a)

- No `sigstore-go` in the binary, no Control-Plane trust-model change (that's P2b).
- No baked official root shipped (P2b, after the verifier exists).
- No air-gap bundle, no mirror, no agent changes.
- Legacy Docker updater untouched.

## Security invariants (P2a)

- No private key — ephemeral or otherwise — is committed, baked, or logged. The
  CI gate's ephemeral ed25519 private key lives only in the job and is discarded.
- The gate is **release-blocking**: a tag ref, a digest mismatch, a failed
  catalog/image-signature verification, or missing provenance fails the release.
- The catalog generator is deterministic and rejects mutable tags at generation
  time (defense-in-depth with the loader's `catalogValidateRepo`).
- Image signing uses GitHub OIDC (`id-token: write`), short-lived, identity-bound.

## Open decision for the user (P2b gate)

Before P2b: confirm migrating the Control-Plane catalog trust root from baked
ed25519 to **Sigstore identity** (Fulcio root + pinned `KidCarmi/Culvert`
release-workflow identity), accepting the `sigstore-go` dependency and the
requirement to bundle Fulcio/Rekor/TUF roots for offline/air-gap verification —
vs. keeping a baked ed25519 root signed by an OIDC-gated KMS (not fully keyless,
but tiny verifier + trivial air-gap). P2a is identical either way.

## Acceptance (P2a)

- A release run produces a generated catalog whose digest matches the pushed
  image, signs the image keyless, emits provenance, and the gate passes.
- Tampering (tag ref, wrong digest, mutated manifest, missing provenance) fails
  the release in CI.
