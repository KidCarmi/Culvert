# D1.6 — Runtime validation checklist

**Status: pending host-side validation. Required gate for D1.6c.**

D1.6a (PR #202) and D1.6b (PR #205) are merged on `main`. Both
slices passed CI (vet, race, determinism, golangci-lint, gosec,
staticcheck, shellcheck, visudo) and have ~120 unit / integration
tests using fake exec layers. The CI gate proves the agent is
*well-formed in isolation* — it does NOT prove that the
sudo + systemd + docker compose interaction works end-to-end on
a real Linux host.

This document captures the manual runtime validation that MUST be
completed before any D1.6c work begins.

## Test-host requirements

- Linux distribution: Ubuntu 22.04 LTS (jammy) **or** Ubuntu 24.04 LTS
  (noble). Other systemd-based distros are likely to work but are
  not part of the contract for this checklist.
- `systemd` ≥ 248.
- `sudo` ≥ 1.9 (so `visudo -c` and the `Cmnd_Spec` exact-arg matcher
  behave as documented).
- Docker Engine ≥ 24 with Compose v2 plugin (`docker compose ps`
  must work without invoking the legacy `docker-compose` binary).
- A working Culvert deployment via `docker-compose.yml` that the
  test operator can stop / start / restore against.
- A *disposable* state for the destructive steps (`restore commit`).
  Do NOT run the destructive steps against an in-use deployment.

## Pre-flight setup

Before running the checklist, do these once:

```sh
# Build agent
(cd cmd/culvert-maint && go build -o /tmp/culvert-maint .)

# Install (creates user/group, renders sudoers, installs unit)
sudo packaging/culvert-maint/install.sh /tmp/culvert-maint

# Edit /etc/culvert-maint/config.toml — at minimum set:
#   compose_project_dir, compose_file, allow_peers, health_base_url
# Re-run install.sh so the sudoers entry is re-rendered with the
# correct compose_path.
sudo packaging/culvert-maint/install.sh /tmp/culvert-maint

# Set CULVERT_BACKUP_PASSPHRASE for the agent process. The
# canonical place is the systemd unit drop-in:
#   /etc/systemd/system/culvert-maint.service.d/passphrase.conf
#       [Service]
#       Environment="CULVERT_BACKUP_PASSPHRASE=<dev-pass>"
# Reload + restart:
sudo systemctl daemon-reload
sudo systemctl start culvert-maint
```

## Runtime validation checklist

Every item below MUST pass. Capture journal output / curl responses
for each item; attach them to the D1.6c kickoff so the gate can be
reviewed.

The items are ordered to be runnable end-to-end in one session — each
step assumes the prior steps passed.

### Foundation (D1.6a surface)

1. **install.sh on clean Ubuntu 22.04 / 24.04 VM.** Fresh VM, no
   prior `culvert-maint` user or files. `install.sh` exits 0;
   creates the system user/group, installs binary at
   `/usr/local/bin/culvert-maint`, renders
   `/etc/sudoers.d/culvert-maint` with the absolute compose path
   (no `{compose_…}` placeholders), `visudo -c` validates, systemd
   unit installed.
2. **systemd service starts.** `sudo systemctl start culvert-maint`
   exits 0; `systemctl status culvert-maint` shows `active
   (running)`; journal shows the agent bound the UDS at
   `/run/culvert-maint.sock` mode 0660. No errors before the
   "listening on" log line.
3. **Unix socket API works under SO_PEERCRED.**
   - As the allowlisted user:
     `curl --unix-socket /run/culvert-maint.sock http://localhost/v1/health`
     returns 200 with `{"status":"ok","agent_version":"…"}`.
   - From a non-allowlisted user (e.g. `sudo -u nobody …`): same
     curl returns 403 (or refused). Journal logs the rejected UID.
4. **sudoers path-bound commands work under the systemd sandbox.**
   The agent runs as `culvert-maint` (non-root, no docker group).
   Confirm `/v1/status` succeeds — this is the canonical proof that
   the systemd unit's hardening directives do NOT block the
   sudoers-mediated `docker compose ps` invocation. If this step
   fails, none of the state-changing flows below can work.
5. **`docker compose ps` reaches `/v1/status`.** With the proxy
   stack actually running (`docker compose up -d` ahead of time):
   `curl --unix-socket /run/culvert-maint.sock http://localhost/v1/status | jq`
   returns `compose_stack_up: true` and the `proxy` service in
   `compose_services` with `state: "running"`.
5a. **Running-image digest reaches `/v1/status` (P1.1).** With the proxy
   stack running, the same `/v1/status` response carries a best-effort
   `running_image` object — `image_id` (the running container's
   `sha256:` config digest) and, for a pulled image, `repo_digests`
   (`repo@sha256:…`). It is digest-only and read-only (reuses the
   already-allowlisted `CaptureRunningProxyImage` — no sudoers change).
   It is OPTIONAL: absent when the stack is down or the capture did not
   complete, and its absence never changes the response code or sets
   `compose_error`. A locally-built (never-pushed) image legitimately
   reports `running_image` with an empty/omitted `repo_digests`.

### Backup surface (D1.6b)

6. **Encrypted backup through agent.** With
   `CULVERT_BACKUP_PASSPHRASE` set in the unit drop-in:
   ```sh
   FN=smoke-$(date -u +%Y%m%dT%H%M%SZ).tar.gz.enc
   curl --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/backups \
        -H 'Content-Type: application/json' \
        -d "{\"filename\":\"$FN\",\"encrypt\":true,\"passphrase_ref\":\"env:CULVERT_BACKUP_PASSPHRASE\"}"
   ```
   Returns 202 with `op_id`. Poll `/v1/operations/{op_id}` until
   `state: succeeded`. Backup file appears in `/backup` (the
   `culvert-backups` volume's mount in the cli container).
7. **`GET /v1/backups`.**
   `curl --unix-socket /run/culvert-maint.sock http://localhost/v1/backups | jq`
   returns 200 with a JSON array. The file from step 6 appears
   with `encrypted: true` and a non-zero `size_bytes`.

### Restore surface (D1.6b)

8. **Restore dry-run through agent.**
   ```sh
   curl --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/restores/dryrun \
        -H 'Content-Type: application/json' \
        -d "{\"path\":\"/backup/$FN\",\"mode\":\"full\",\"passphrase_ref\":\"env:CULVERT_BACKUP_PASSPHRASE\"}"
   ```
   Returns 202; op completes succeeded; the per-op log shows the
   cli's restore plan output. `/v1/status` still reports
   `compose_stack_up: true` (dryrun does NOT touch the stack).

### Cleanup surface (D1.6b)

9. **`cleanup dry-run`.**
   ```sh
   curl --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/cleanups \
        -H 'Content-Type: application/json' \
        -d '{"older_than":"720h","keep_last":3,"confirm":false}'
   ```
   Returns 202; succeeded; per-op log shows planned candidates
   (or "nothing to clean"). Argv must NOT contain `--confirm`.
   Filesystem unchanged.
10. **`cleanup --confirm`.** Same body but `"confirm":true`. Argv
    must contain `--confirm`. Op succeeds; any planned candidates
    are actually deleted; the per-op log shows the deletion log.

### Destructive flows (DISPOSABLE STACK ONLY)

11. **Restore commit on a disposable stack.** Have a known-good
    backup. Note: this rolls `/data` back to that backup and
    restarts the stack.
    ```sh
    curl --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/restores/commit \
         -H 'Content-Type: application/json' \
         -d "{\"path\":\"/backup/$FN\",\"mode\":\"full\",\"passphrase_ref\":\"env:CULVERT_BACKUP_PASSPHRASE\"}"
    ```
    Returns 202. `/v1/operations/{op_id}` eventually shows
    `state: succeeded` with 4 stages in canonical order:
    `stop_stack` → `run_cli_restore_commit` → `start_stack` →
    `health_check`. `/v1/status` reports `compose_stack_up: true`
    after the op completes.
12. **Restore failure triggers best-effort up.** Force a restore
    failure (e.g. submit `path` pointing at a corrupt or
    non-existent file under `/backup`):
    ```sh
    curl --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/restores/commit \
         -H 'Content-Type: application/json' \
         -d "{\"path\":\"/backup/does-not-exist.tar.gz.enc\",\"mode\":\"full\",\"passphrase_ref\":\"env:CULVERT_BACKUP_PASSPHRASE\"}"
    ```
    Op fails with `failure_reason: cli_error`. Op progress shows
    that `start_stack` STILL ran (best-effort). The per-op log
    contains the `recovery: running after earlier failure at
    stage=run_cli_restore_commit` note on `start_stack` and
    `health_check`. The compose stack is back up afterward.
13. **`health_check` runs after recovery.** Same scenario as #12 —
    confirm `/v1/operations/{op_id}` progress includes a
    `health_check` stage record (succeeded or failed; the
    important thing is it RAN). The per-op log shows the
    ready/health detail string.

### Lifecycle / contract (D1.6b)

14. **Idempotency retry returns the same `op_id`.**
    ```sh
    BODY='{"filename":"smoke-idempotency.tar.gz.enc","encrypt":true,"passphrase_ref":"env:CULVERT_BACKUP_PASSPHRASE","idempotency_key":"smoke-1"}'
    R1=$(curl -s --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/backups -H 'Content-Type: application/json' -d "$BODY")
    R2=$(curl -s --unix-socket /run/culvert-maint.sock -X POST http://localhost/v1/backups -H 'Content-Type: application/json' -d "$BODY")
    ```
    `R1` returns 202 with `deduped: false`. `R2` returns 200 with
    `deduped: true`. `R1.op_id == R2.op_id`.
15. **Lock conflict returns 409.** Submit two `backup.create`
    requests with DIFFERENT idempotency keys back-to-back; the
    second arrives while the first is still in flight (this is
    timing-sensitive — may need to use a slow backup target or a
    very large `/data` to reproduce reliably). Expected: HTTP 409
    with the holder's snapshot in the response body.
16. **Operation logs contain NO passphrase value.**
    ```sh
    sudo cat /var/lib/culvert-maint/operations/<op_id>.log | grep -F "$CULVERT_BACKUP_PASSPHRASE"
    ```
    Must return zero matches. (Replace `<op_id>` with the encrypted
    backup from step 6.) Same check against
    `/var/lib/culvert-maint/audit.jsonl`. Both files MUST mention
    `passphrase_ref` (the env reference) but NEVER the resolved
    value.
17. **Audit events are written correctly.**
    ```sh
    sudo tail -50 /var/lib/culvert-maint/audit.jsonl | jq -c
    ```
    For every successful op (steps 6, 7→read-only no audit, 8, 9,
    10, 11): exactly one `outcome:"started"` and one
    `outcome:"succeeded"` event with matching `op_id`, `actor`,
    `kind`. For step 12 (the failure): one `started` + one
    `failed` with `failure_reason: cli_error`. No event mentions
    the resolved passphrase value.

## D1.6c readiness gate

D1.6c work MUST NOT start until ALL of the following are true:

1. **Every item in the checklist above passes** on a real Linux VM
   (Ubuntu 22.04 or 24.04). The captured journal / curl / file-
   inspection output is attached to the D1.6c kickoff or recorded
   in a comment on this document's PR.
2. **Any runtime bugs surfaced by the checklist are fixed** on
   `main` (small follow-up PRs against D1.6a/b are acceptable;
   they should NOT carry D1.6c scope).
3. **The final D1.6b operational notes are updated if needed.**
   Concretely: if the checklist surfaces a behavior that the
   operator-facing docs (`docs/operator/docker-compose-backup-
   restore.md`, the agent's PR-body manual smoke checklist, the
   sudoers comment block) don't accurately describe, those docs
   are updated before the gate is considered passed.

The gate is binary — partial passes (e.g. "everything except step 11
because we don't have a disposable stack handy") DO NOT clear the
gate. D1.6c can be substantially more invasive (image pulls,
manifest inspection, rollback orchestration), and a runtime bug in
the D1.6b foundation surfacing during D1.6c work would be
expensive to root-cause.

## Future D1.6c scope placeholder

D1.6c will cover:

- **Upgrade check** (`POST /v1/upgrades/check`) — `docker compose
  pull` against the configured image, surface "newer image
  available" without committing.
- **Upgrade apply** (`POST /v1/upgrades/apply`) — pull → drain →
  swap → health-gated restart.
- **Image allowlist** — `image_allowlist` config key (regex,
  applied to the resolved image reference); the runner refuses to
  pull or run anything outside it.
- **Digest pinning** — accept and prefer `@sha256:…` references in
  the upgrade flow; surface drift between tag and digest.
- **Health-gated restart** — reuse the D1.6b `health_check`
  primitive for the post-swap verification; failure rolls forward
  into the rollback path rather than leaving the stack in a bad
  state.
- **Rollback path** (`POST /v1/rollbacks`) — explicit operator-
  triggered revert to the previously-running image (the one we
  pulled before the swap).
- **Failure recovery** — same `ContinueOnError` pattern as restore
  commit, so a failed apply still runs the rollback's recovery
  stages.

NOT in D1.6c (still deferred):

- GUI integration (D2).
- CP/API integration (D1.6d).
- Fleet / cluster orchestration (a separate slice; not on the
  D1.6 path at all).
- `.deb` / `.rpm` packaging (deferred until the agent contract
  has stabilised through D1.6c).
- Kubernetes / Helm charts.
- OVA images.
- Removal of the legacy `updater` sidecar (already documented as
  superseded by D1.6 in CLAUDE.md but not removed in code).

These items remain in their existing roadmap docs (`PHASES.md`,
`ROADMAP.md`, `roadmap-day2.md`) and are not blocked by D1.6c.
