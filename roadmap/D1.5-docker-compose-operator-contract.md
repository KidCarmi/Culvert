# D1.5 — Docker Compose Operator Contract

**Status:** design slice — no code, no compose changes, no user-facing operator docs in this slice.
**Audience:** maintainers, code reviewers, future D1.6 Maintenance Agent implementers.
**Implementation slice:** ships the `cli` service, the `culvert-backups` volume, `docs/operator/docker-compose-backup-restore.md`, the `docs/OPERATIONS.md § 4` deprecation update, and the `CLAUDE.md` architecture entry — none of which land here.

---

## 0. Why this exists

D1.3 + D1.4 shipped the CLI surface (`--backup`, `--restore`, `--cleanup-restore-leftovers`, `--encrypt`). What's still implicit is **how an operator drives those flags from a Docker Compose deployment**. Today's `docs/OPERATIONS.md` § 4 still recommends `tar -C /data -czf …` — pre-D1.3 guidance that bypasses the manifest, sha256, schema-version, and CA-bundle cross-validation that D1.3 introduced.

D1.5 is the authoritative operator contract that:

1. Pins the supported deployment shape (services, volumes, mounts).
2. Says exactly which operations are runtime-allowed and which require an offline maintenance window.
3. Locks down the canonical `docker compose` invocation for every backup/restore/cleanup action.
4. Defines the trust boundary that the future GUI and D1.6 Maintenance Agent must respect.

The forcing-function relationship with D1.6 is critical: the agent will perform exactly the sequences D1.5 specifies — nothing more, nothing less. Anything D1.5 does not sanction is unavailable from the GUI even after D1.6 lands.

## 1. Deployment layout

### 1.1 Services

The supported layout adds **one** new service to `docker-compose.yml`. Existing services are untouched.

| Service | Purpose | Lifecycle | Has docker.sock? |
|---|---|---|---|
| `proxy` | Main Culvert daemon (existing) | Long-running, `restart: unless-stopped` | **No** |
| `clamav` | AV sidecar (existing) | Long-running | No |
| `updater` | Legacy update sidecar (existing) | Long-running | Yes (legacy; superseded by D1.6 — see § 5) |
| **`cli`** *(new — landed by implementation slice)* | One-shot operator commands (`--backup`, `--restore`, `--cleanup-restore-leftovers`) | **Ephemeral** via `docker compose run --rm cli …` | No |

The `cli` service is **profile-gated** (`profiles: ["cli"]`) so `docker compose up -d` continues to start exactly the same set as today (no surprise side effects). Operators invoke it with `docker compose --profile cli run --rm cli <flags>`.

The image is identical to `proxy` — same registry pull, same binary. This eliminates version-skew between the daemon and its CLI: a backup taken with the cli service is, by construction, decoded by the same code path the daemon would have used.

**Approved:** profile-gated `cli` service is the canonical operator path. `docker compose exec proxy /app/culvert <flags>` is **not** the supported path — exec conflates the daemon and CLI lifecycles, is harder for the agent to reason about, and lets a one-shot crash escape into the running daemon container.

### 1.2 Volumes

| Volume | Mount | Lifecycle | Contract |
|---|---|---|---|
| `proxy-data` | `/data` (rw in `proxy` + `cli`; ro in `updater`) | Existing | **Product state**: identity, policy, audit, blocklists, request log, CA bundle, `cluster.json`, `config_versions/`, `ui_users.json`. **Never** contains backup archives. |
| `clamav-db` | `/var/lib/clamav` (in `clamav`) | Existing | ClamAV signatures only. |
| `updater-state` | `/state` (in `updater`) | Existing | Updater rollback metadata. |
| **`culvert-backups`** *(new — landed by implementation slice)* | `/backup` (rw in `cli` only) | New | **Backup archives only** (`*.tar.gz` / `*.tar.gz.enc`). |

Two consequences of mounting `/backup` only in `cli`:

1. **The long-running `proxy` container has no read or write access to backup archives at runtime.** A compromise of the proxy process cannot exfiltrate prior backups.
2. **Backups can be sourced from off-host storage** (NFS, S3-CSI, BitWarden Send, etc.) without exposing `/data` to that storage. The `cli` service is the only mount surface.

**Approved:** `/backup` defaults to a named volume (`culvert-backups`) for the supplied compose. Operators with off-host backup targets override it with a single line, e.g.:

```yaml
# Operator override: bind-mount /backup to a host directory
volumes:
  - ./backups:/backup
```

This is documented in the implementation slice's user-facing operator doc. The supplied compose stays portable.

### 1.3 Logs vs reports vs state

- **Operational logs** (`proxy.log`, `audit.jsonl`, `requests.log`) live under `/data`. Existing behavior — unchanged.
- **Backup archives** live under `/backup`. New.
- **Maintenance reports** (upgrade plan, post-restore health checks, agent action audit) — **deferred to D1.6**. The Maintenance Agent will own its own volume; D1.5 does not pre-allocate one.

### 1.4 Product state vs deployment config

D1.5 makes the distinction explicit so operators know what `--backup` covers and what they own out-of-band:

| Class | Examples | In `/data`? | In backup? |
|---|---|---|---|
| Product state | `ui_users.json`, `cluster.json`, `policy.json`, `ca.bundle`, `config_versions/`, blocklists, threat-feed cache | **Yes** | **Yes** (Tier 1 + Tier 2 per D1.3a) |
| Operational state | `proxy.log`, `audit.jsonl`, `hashcache.json`, `hit_counters.json` | Yes | **No** (Tier 3) |
| Deployment config | `docker-compose.yml`, `.env` files, host TLS termination, reverse-proxy config | **No** — operator's source control | No |
| Backup archives | `*.tar.gz.enc` | **No** — in `/backup` | No (don't back up backups) |

The contract: a clean, tested operator deployment can be reproduced from `docker-compose.yml` + the latest backup archive. Operational state is not preserved across restore — by design.

## 2. Runtime vs offline operations

| Operation | Mode | Why | Operator contract |
|---|---|---|---|
| `--backup` (unencrypted) | **Runtime** | Read-mostly walk of `/data`. Mid-rotation log files are Tier-3 (excluded). Manifest sha256 captures point-in-time content. | Allowed while `proxy` is up. |
| `--backup --encrypt` | **Runtime** | Same as above; encryption is in-process, no extra fs interaction. | Allowed while `proxy` is up. |
| `--restore <tar>` (dry-run) | **Runtime** | No writes. Tarball decoded in memory; cross-validates against current `/data`. | Allowed while `proxy` is up. |
| `--restore <tar> --confirm` (commit) | **Offline (mandatory)** | Performs `rename(/data, /data.bak.*)` + `rename(/data.staging.*, /data)`. Open file descriptors held by the daemon become invalid; admin actions during the swap would race. D1.3b.2b is documented offline-only. | **`docker compose down` → `run --rm cli --confirm` → `up -d`.** No exception. |
| `--list-restore-leftovers` | **Runtime** | Read-only Lstat walk of `/data`'s siblings. | Allowed any time. |
| `--cleanup-restore-leftovers` (dry-run) | **Runtime** | Read-only. | Allowed any time. |
| `--cleanup-restore-leftovers --confirm` | **Runtime** *(approved)* | Operates on **siblings** of `/data` only (`/data.bak.*`, `/data.staging.*`). The proxy holds no descriptors there. Re-Lstat TOCTOU guard at deletion time. | Allowed while `proxy` is up. |
| Image / binary upgrade | **Out of scope** | Owned by D1.6 Maintenance Agent. The legacy `updater` sidecar continues to function until D1.6 lands. | N/A for D1.5. |

### 2.1 Why cleanup-confirm is runtime-OK

The cleanup-confirm doctrine deserves its own sub-section because operators may default-assume parity with restore-commit. The D1.3c safety contract makes it safe under live load:

- **Sibling-only:** `os.ReadDir(parent_of_dataDir)` is non-recursive. `/data` itself can never be a candidate.
- **Exact regex:** `^<base>\.(bak|staging)\.<YYYYMMDDTHHMMSSZ>-<pid>$` is anchored. Names that don't match are silently ignored; near-misses (regex-shaped non-directory or symlink) emit `WARN` and are excluded.
- **Lstat at admission AND immediately before deletion:** the second Lstat is the TOCTOU re-check that catches a symlink swap injected between discovery and `os.RemoveAll`.
- **Never follows or deletes symlinks; never deletes files; only directories matching the exact regex.**
- **The proxy holds no file descriptors under `/data.bak.*` or `/data.staging.*`** — those directories are restore artifacts, never accessed by the daemon.

The combination is robust under live load. No operator-visible coordination with the `proxy` lifecycle is required.

## 3. Canonical Docker Compose commands

The following is the complete operator-facing surface for backup, restore, and cleanup. Each is a single command. All idempotent with respect to repeat invocations except the destructive ones, which fail closed on collision.

### 3.1 Create an unencrypted backup *(dev / lab only)*

```bash
docker compose --profile cli run --rm cli \
  --backup /backup/culvert-$(date -u +%Y%m%dT%H%M%SZ).tar.gz
```

Refuses to overwrite an existing path (D1.3a contract). Exit 0 on success.

Unencrypted backups are **dev / lab only**. They must not leave the host. The user-facing operator doc will say so explicitly.

### 3.2 Create an encrypted backup *(production default)*

```bash
docker compose --profile cli run --rm \
  -e CULVERT_BACKUP_PASSPHRASE \
  cli \
  --backup /backup/culvert-$(date -u +%Y%m%dT%H%M%SZ).tar.gz.enc \
  --encrypt
```

The bare `-e CULVERT_BACKUP_PASSPHRASE` form forwards the operator's existing shell env without echoing the value into argv (which would land it in `ps` and shell history). Operators source the passphrase from `.env` (chmod 0600, gitignored), a `pass`/`gopass` lookup, or a Docker secret (see § 4).

D1.4 contract: refuses to run without the env var (no TTY prompting in this slice), warns if the passphrase is shorter than 12 chars, refuses to overwrite an existing path.

### 3.3 Restore dry-run *(safe while proxy is up)*

```bash
docker compose --profile cli run --rm \
  -e CULVERT_BACKUP_PASSPHRASE \
  cli \
  --restore /backup/culvert-20260501T030000Z.tar.gz.enc
```

`CULVERT_BACKUP_PASSPHRASE` is required only if the backup is encrypted; magic-byte sniff decides. Prints the D1.3b.1 + D1.3b.2a plan (mode-aware delta, DP-reenrollment guard, TOTP rollback guard) and exits without writing to `/data`.

Optional flags mirror the D1.3b.2 CLI surface: `--mode {full|trust-root-only|state-only}`, `--accept-dp-reenrollment`, `--allow-counter-rollback`.

### 3.4 Restore commit *(destructive — proxy must be stopped)*

```bash
# 1. Stop the running stack.
docker compose down

# 2. Run the destructive commit in an ephemeral container.
docker compose --profile cli run --rm \
  -e CULVERT_BACKUP_PASSPHRASE \
  cli \
  --restore /backup/culvert-20260501T030000Z.tar.gz.enc \
  --confirm \
  --mode full

# 3. Bring the stack back up.
docker compose up -d
```

Step 2 will refuse without `--confirm` (dry-run by default), without the env var on an encrypted backup (fail closed), and on guard violations without the explicit acknowledgment flags. The previous `/data` is preserved at `/data.bak.<ts>-<pid>` per D1.3b.2b — clean it up with the cleanup command below once the new state is verified.

### 3.5 List restore leftovers

```bash
docker compose --profile cli run --rm cli \
  --list-restore-leftovers
```

Read-only inventory; safe any time.

### 3.6 Cleanup restore leftovers (dry-run, then commit)

```bash
# Dry-run — see what would be deleted.
docker compose --profile cli run --rm cli \
  --cleanup-restore-leftovers \
  --older-than 720h \
  --keep-last 3

# Execute — same flags + --confirm.
docker compose --profile cli run --rm cli \
  --cleanup-restore-leftovers \
  --older-than 720h \
  --keep-last 3 \
  --confirm
```

Safe while the proxy is up (cleanup operates on siblings of `/data`, never `/data` itself, per D1.3c contract).

## 4. Security posture

### 4.1 Trust boundary: no Docker socket in CP/GUI

D1.5 codifies the principle the D1.6 design already commits to: **no service that handles user requests gets `/var/run/docker.sock`**.

- `proxy`, `cli`: never mount `docker.sock`. Already true; D1.5 cements this as a contract violation if ever changed.
- `updater` *(legacy)*: continues to mount it until D1.6 deprecates the path. New deployments should plan for D1.6 rather than depending on the legacy updater for new features. See § 5.

Maintenance ops that require the socket — image pull, container recreate, volume snapshot — are **not** part of the D1.5 contract. They become the D1.6 Maintenance Agent's job.

### 4.2 Passphrase handling

Three operator-supported channels, ranked from least to most production-grade:

| Channel | Use case | Risks | Mitigation |
|---|---|---|---|
| Inline `-e VAR=value` on the command line | Throwaway tests | Lands in shell history and in `ps` for the parent shell | Don't use in production. The user-facing doc will warn. |
| Shell env + bare `-e VAR` (no value) | Standard operator workflow | History exposure unless the value was sourced from `.env` | `.env` chmod 0600, gitignored; `set +o history` for ad-hoc |
| Docker secret mounted, then `cat /run/secrets/x` to seed env | Production / multi-operator | Requires Swarm or Compose v2 secret support | Document for prod tier; not the default for the lab compose |

D1.5 mandates: **passphrases never appear in the committed `docker-compose.yml`.** The supplied compose file references `CULVERT_BACKUP_PASSPHRASE` symbolically only — never with a value. The user-facing doc + a `gitleaks` rule (existing in CI) cover the lint side.

### 4.3 Backup-file sensitivity

Even encrypted backups are sensitive: passphrase compromise = plaintext access to all of `/data` at the time of the snapshot. Contract:

- `/backup` directory mode = `0700`, owned by the container's runtime UID. The implementation slice will set this on volume creation.
- **Encrypted backups are the recommended default.** The user-facing doc will lead with the encrypted recipe.
- Unencrypted backups are documented as **dev / lab only** and the operator docs will say so explicitly.
- Off-host copy of encrypted backups is acceptable. Off-host copy of unencrypted backups is **not** recommended.
- Backup filename convention: `culvert-<UTC-RFC3339-ish>.tar.gz[.enc]`. Magic-byte sniff is authoritative; suffix is cosmetic.

### 4.4 Restore commit safety

- The contract requires `docker compose down` first. The CLI itself does not detect a running proxy on the same host — operator discipline + the documented `down → run --rm → up -d` sequence enforces this for the human-driven path.
- The D1.6 Maintenance Agent will eventually orchestrate this sequence and refuse to commit if a proxy on the same host is still listening on its admin port. That is an additional safety net; D1.5 does not gate on it.

### 4.5 Logging

- `--backup`, `--restore`, `--cleanup-restore-leftovers` print operator-facing status to stdout/stderr.
- The passphrase **never** appears in stdout/stderr/audit/log under any code path. D1.4 already enforces this for the in-process logger; D1.5 adds the operational rule that `docker compose logs cli` must not capture the passphrase env var. The bare `-e VAR` form satisfies this; inline `-e VAR=value` does not.

## 5. Future GUI / Agent alignment

D1.5 is the **operator contract**. D1.6 is the **agent contract that automates D1.5**. The relationship:

- The eventual admin GUI will not call `docker compose` directly. It will call the local Maintenance Agent over a unix-socket (per D1.6 design).
- The Maintenance Agent will perform exactly the sequences D1.5 specifies — `docker compose down` → `run --rm cli` → `up -d` — with progress streaming back to the CP and audit hooks for each step.
- This means D1.5 has a **forcing function** on D1.6's API surface: every operation in § 3 must have an agent-side counterpart, and the agent must refuse anything not in this list.
- Conversely, anything D1.5 does **not** sanction (arbitrary host shell, manual `docker exec`, image upgrade outside the agent) must remain unavailable from the GUI even after D1.6 lands.

The contract D1.5 establishes is what the agent is **allowed** to enforce — not just a suggestion the operator may follow. The agent will refuse out-of-contract operations.

### 5.1 Legacy `updater` sidecar

D1.5 does not touch the `updater` service in `docker-compose.yml`. Per approved decision:

- The `updater` sidecar is documented as **legacy / superseded by the future D1.6 Maintenance Agent**.
- It is **not removed** in this slice or in the D1.5 implementation slice.
- **No hard deprecation timeline** is introduced in D1.5. The deprecation path will be defined when D1.6 implementation lands.
- New deployments should plan for D1.6 rather than depending on the legacy updater for new features.

Until D1.6 ships, the legacy updater continues to work as today (containerized image pull/recreate/rollback via its own Docker socket mount). The trust-boundary principle in § 4.1 acknowledges this as a known exception that will be eliminated by D1.6.

## 8. Invariants summary

These are non-negotiable for any change touching the operator contract.

1. **The `cli` service is the only canonical operator path** for backup, restore, and cleanup. `docker compose exec proxy …` is not supported and not documented.
2. **`/backup` is mounted only in `cli`.** Never in `proxy`, never in `updater`.
3. **`docker.sock` is never mounted in any new service.** The legacy `updater` is the only carve-out, and it is documented as superseded by D1.6.
4. **Restore commit is offline-only.** `docker compose down` → `run --rm cli --confirm` → `up -d`.
5. **Backup, restore-dry-run, and cleanup (dry-run + confirm) are runtime-OK.**
6. **Encrypted backups are the production default.** Unencrypted is dev/lab only.
7. **Passphrases never appear in `docker-compose.yml`, in argv, or in `docker compose logs`.**
8. **Every operation D1.5 sanctions has an agent counterpart in D1.6; nothing else does.**

## 9. Open questions deferred to the implementation slice

1. Backup filename timestamp format — `date -u +%Y%m%dT%H%M%SZ` vs `date -u +%Y-%m-%dT%H:%M:%SZ`. The CLI doesn't care (filename is cosmetic), but the user-facing doc should pick one and stick with it. Lean: the dense form (`20260501T030000Z`) for filesystem-safety and easy sort/grep.
2. Default `culvert-backups` retention — purely an operator policy question (the cleanup CLI is already in their hands), but the user-facing doc should suggest a starting point. Lean: 30 days + last 3 always preserved.
3. Whether the supplied compose's `cli` entry should set `user:` to a non-root UID matching `proxy`. Depends on the image's existing user posture; settle when the implementation slice opens.

None of the above gate the design.
