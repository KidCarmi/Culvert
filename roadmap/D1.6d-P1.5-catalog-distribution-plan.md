# D1.6d / P1.5 — Release Catalog Distribution & Refresh (architecture)

**Status:** DESIGN ONLY. No code, no GUI, no agent changes, no dispatch. This is
the architecture for **how a verified release catalog reaches a running Control
Plane** and is kept current — the slice P1.2 explicitly deferred ("Reload =
construct a new `*Catalog`; the refresh slice will own swap semantics; not here"
— `roadmap/D1.6d-P1.2-release-catalog-runtime-plan.md` §1). It sits on top of:

- **P1.2 runtime** — `LoadCatalog` / `loadCatalogFromIndexBytes`, the
  `CatalogSource` interface, the symlink-refusing/bounded `dirCatalogSource`, and
  the **immutable, build-complete-or-nil `*Catalog`** (never partial).
- **P1.3 authenticity** — `LoadVerifiedCatalog`, the `TrustStore` (key ring +
  `enforce`/`permissive`/`disabled` modes), the detached `index.json.sig`
  envelope, and the **verify-before-parse** trust boundary.

> **Prime invariant (carried from #389 / P1.2 / P1.3):** the agent stays
> release-agnostic. Distribution and refresh are **100% Control-Plane-side**. The
> agent never fetches a catalog, never sees a signature, never knows a refresh
> happened — it still only ever receives a `repo@sha256:…` digest from a later
> dispatch slice.

> **The one thing this slice adds:** a **`CatalogHolder`** that publishes an
> *atomically swappable* verified `*Catalog`, fed by **pluggable providers**
> (local dir / HTTP / air-gap bundle) through a **stage → verify → atomic-publish**
> pipeline, with a **last-good on-disk cache** for restart durability. Nothing is
> ever served until it has passed the P1.3 trust boundary.

---

## 1. Scope & non-goals

**In scope (design only):** the source model, refresh model, scheduling,
staleness, local cache, startup behavior, atomic replacement, rollback, air-gap /
OVA delivery, the trust boundary, failure handling, the dependency graph, and the
recommended implementation slices.

**Explicit non-goals (deferred, by constraint):**
- **No code, no GUI, no admin API** (the operator surface is the final slice).
- **No agent changes, no upgrade dispatch** — this slice *produces and refreshes*
  the catalog; handing a resolved digest to the agent is the dispatch slice.
- **No CP→DP propagation** — the catalog stays CP-only (it is not added to
  `ConfigSnapshot`).
- **No new trust mechanism** — verification is exactly P1.3; this slice only
  decides *what bytes get fed to it, when, and what is published on success*.

## 2. The ten questions (direct answers)

| # | Question | Answer (elaborated in the noted section) |
|---|---|---|
| 1 | **Where does `index.json` come from?** | A **`CatalogProvider`** stages it into a local directory: `localDirProvider` (OVA seed / operator dir), `httpProvider` (online CP fetch), or `bundleProvider` (air-gap signed tarball). All converge on a staging dir read by the P1.2 `dirCatalogSource`. (§4, §5) |
| 2 | **How is it refreshed?** | A single CP-side **refresher** runs **stage → `LoadVerifiedCatalog` → atomic publish** on a jittered interval (online), on manual trigger, and once at startup. Air-gap/local refresh is **event-driven** (bundle import / dir change), not polled. (§6) |
| 3 | **What happens when refresh fails?** | **Keep the current live catalog**, log + counter + alert, discard the staging dir. Never serve a partial or unverified catalog. The last-good catalog continues to answer queries. (§9, §11) |
| 4 | **What happens when signature verification fails?** | Same as a failed refresh — the candidate is **rejected at the trust boundary and never published**. Verify failure is a distinct, higher-severity signal (probable tamper) than a fetch failure. (§10, §11) |
| 5 | **What catalog is used during startup?** | Load order: **(1) last-good on-disk cache → (2) OVA/seed dir → (3) none**. Each candidate is **re-verified** through P1.3 before it is published; the first that verifies wins. Online mode then kicks a background refresh. (§7) |
| 6 | **How does air-gap receive updates?** | The operator imports a **signed release bundle** (tarball: `index.json` + `index.json.sig` + manifests + image blobs). `bundleProvider` extracts it to staging; verification is **identical to online** — only the transport differs. (§8) |
| 7 | **How does OVA ship a bootstrap catalog?** | A **read-only seed catalog** is baked into the OVA image at a fixed path. It is the step-2 startup fallback and the day-0 catalog until a refresh/bundle replaces it. It is signed and verified like any other. (§7, §8) |
| 8 | **How does refresh avoid partial replacement?** | Build + verify happen **entirely off to the side** (staging); publication is a **single `atomic.Pointer[Catalog]` store** (in-memory) plus a **single `os.Rename`** (on-disk cache). Readers see whole-old or whole-new, never partial — the `*Catalog` is immutable and build-complete (P1.2). (§9) |
| 9 | **How is catalog rollback handled?** | The **last-good** verified catalog is always retained (in-memory + on-disk); a small ring of prior **verified** catalog snapshots is kept so an operator can pin/roll back to an earlier *valid* catalog. A *failed* refresh never replaces anything, so rollback is only for a valid-but-unwanted catalog. (§9.2) |
| 10 | **What is the trust boundary?** | **`LoadVerifiedCatalog` (P1.3) is the single trust boundary.** Everything before it — network, TLS, staging, the on-disk cache, the bundle tarball — is **untrusted**; the only bytes that ever become a live catalog are those that passed verification, and the cache is **re-verified on read**. (§10) |

## 3. Architecture (components)

```
                          ┌────────────────────────── Control Plane (this slice) ──────────────────────────┐
 source of truth          │                                                                                │
 ───────────────          │   ┌─────────────┐   stage    ┌───────────┐  verify (P1.3)   ┌──────────────┐   │
 online registry / CDN ──▶│   │  Catalog    │──────────▶ │  staging  │ ───────────────▶ │ LoadVerified │   │
 air-gap signed bundle ──▶│   │  Provider   │  (bytes)   │   dir     │  TrustStore gate │   Catalog    │   │
 OVA seed dir / op dir ──▶│   │ (3 impls)   │            └───────────┘                  └──────┬───────┘   │
                          │   └─────────────┘                                                  │ *Catalog  │
                          │         ▲                                                          ▼ (immutable)│
                          │   ┌─────┴───────┐   schedule / manual / startup     ┌──────────────────────┐   │
                          │   │  Refresher  │ ───────────────────────────────▶  │     CatalogHolder    │   │
                          │   │ (1 goroutine│                                    │  atomic.Pointer[Cat] │   │
                          │   │  + ticker)  │ ◀── on success: publish + persist  │  + persist last-good │   │
                          │   └─────────────┘                                    └───────────┬──────────┘   │
                          │                                                                  │ GetCatalog() │
                          │   on-disk cache (atomic rename) ◀── last-good bytes+sig          ▼ (lock-free)  │
                          │                                                     Resolve / Lookup / Current  │
                          │                                                     / List  (P1.2 query surface)│
                          └────────────────────────────────────────────────────────────────────────────────┘
```

- **`CatalogProvider`** (new) — `Stage(ctx) (stagingDir string, err error)`. Three
  impls: `localDirProvider`, `httpProvider`, `bundleProvider`. Each lands a
  **complete candidate** (index + sig + manifests) in a fresh staging dir. A
  provider does **no** trust work — it only moves bytes.
- **`CatalogHolder`** (new) — owns `atomic.Pointer[Catalog]`. `GetCatalog()` is a
  **lock-free** load on the read path (the P1.2 query methods run on the loaded
  pointer). `publish(*Catalog, meta)` does the atomic store + on-disk persist.
  This is the component P1.2 deferred ("the refresh slice will own swap
  semantics").
- **`Refresher`** (new) — the **single goroutine** this slice introduces. Drives
  `Provider.Stage → LoadVerifiedCatalog → CatalogHolder.publish` on a jittered
  interval (online), on a manual trigger, and once at startup. Owns staleness
  bookkeeping (`lastRefreshOK`, `lastRefreshAttempt`, last error).
- **on-disk cache** (new) — the restart-durability layer: the last-good
  **verified** `index.json` + `index.json.sig` + manifests, written via a
  staging-dir + `os.Rename` swap. Re-verified on the next startup read.
- **TrustStore / `LoadVerifiedCatalog`** (P1.3) — unchanged; the trust boundary.
- **`*Catalog` + query surface** (P1.2) — unchanged; immutable, published as-is.

## 4. Catalog source model

A **`CatalogProvider`** abstracts *where the bytes come from*; the verifier and
holder don't care which one ran. All three stage a **self-contained candidate**
(`index.json`, `index.json.sig`, `manifests/<ref>.json`) into a fresh temp dir,
which is then wrapped by the existing P1.2 `dirCatalogSource` (symlink-refusing,
bounded) and handed to `LoadVerifiedCatalog`.

| Provider | Transport | Use | Notes |
|---|---|---|---|
| `localDirProvider` | a local directory | OVA seed, operator-managed dir, the on-disk cache itself | Smallest; no network, no goroutine needed to *use* it. The P1.2 dir source already covers reads. |
| `httpProvider` | HTTPS GET of `index.json` + `.sig` + each `manifests/<ref>` | online CP refresh | **SSRF-guarded**: inline `url.Parse` + scheme check + `isPrivateHost()` before each dial (CLAUDE.md); `http.NewRequestWithContext`; bounded reads (`catalogMaxReadBytes`); the manifest list is taken from the *index*, but each `manifest_ref` is shape-validated (P1.2 §4.5) before fetch. |
| `bundleProvider` | a signed tarball (extracted) | air-gap | Extracts index/sig/manifests (and, for the image-bearing bundle, defers image `docker load` to the air-gap/dispatch slice). Path-traversal-safe extraction; bounded entry sizes. |

> **The source mode is config (read-once at startup for this slice).** One active
> provider at a time (`source.mode = local | http | bundle`). Runtime mode/URL
> changes are an admin-API concern for the final slice — named here, not built.

> **A provider never publishes.** Staging is untrusted scratch space; only
> `LoadVerifiedCatalog` success turns staged bytes into a live catalog (§10).

## 5. Control & data flow (one refresh)

```
1. Refresher fires (interval tick | manual | startup).
2. provider.Stage(ctx) → fresh staging dir with index.json[.sig] + manifests/.
   ── fetch/extract failure → STOP, keep current, log+count (§11 F-fetch).
3. src := dirCatalogSource(stagingDir)        // P1.2: symlink-refusing, bounded
4. cat, err := LoadVerifiedCatalog(src, trust) // P1.3: verify-before-parse
   ── verify/parse failure → STOP, keep current, log+count+ALERT (§11 F-verify).
5. persist: write staged bytes to cache-staging, fsync, os.Rename → cacheDir.
   ── persist failure → log; still publish in-memory (in-memory is authoritative).
6. holder.publish(cat): atomic.Pointer.Store(cat); update lastRefreshOK = now.
7. discard staging dir.
```

Steps 2–4 are **off to the side**; the live catalog keeps answering queries
throughout. Only step 6 makes the new catalog visible, and it is a single atomic
store of an already-complete object.

## 6. Refresh model & scheduling

- **One refresher goroutine** (the first the catalog layer introduces — P1.2
  forbade goroutines/timers in the loader on purpose; they live *here*).
- **Triggers:** (a) **startup** (once, synchronous enough to have a catalog before
  serving release queries — §7); (b) **interval** ticker, configurable (default
  e.g. 1h) with **jitter** to avoid thundering-herd against a shared registry;
  (c) **manual** (admin-API trigger, named for the final slice).
- **Online only.** `http` mode polls; `local`/`bundle` modes do **not** poll the
  network — they refresh on an **event** (a manual trigger, a bundle import, or a
  detected seed/dir change). Air-gap must never depend on a network tick.
- **Single-flight.** At most one refresh in flight; a trigger during a refresh is
  coalesced (no overlapping stage/verify, no swap races).
- **Backoff on repeated failure** (online): exponential with a cap, so a down
  registry doesn't hammer; the last-good catalog keeps serving meanwhile.
- **Read-once config** for mode + interval at startup (mirrors `CULVERT_C2_ENFORCE`
  / the P1.3 mode knob); runtime mutation is the final slice.

## 7. Startup behavior

The CP must reach a **verified** catalog (or a clearly "no catalog" state) before
it answers release queries, but **must still boot** if none is available — the
catalog is **not** on the proxy hot path, so its absence disables release
features without taking the proxy down.

```
startup:
  1. cache:  load last-good from cacheDir → LoadVerifiedCatalog → publish? 
             (re-verify! a cache file is untrusted bytes — §10)
  2. seed:   else load the OVA/operator seed dir → LoadVerifiedCatalog → publish?
  3. none:   else publish NOTHING. GetCatalog() returns "no catalog";
             release features report "catalog unavailable" (fail-closed: no
             releases offered, never an unverified one).
  4. online: regardless of 1–3, the refresher kicks an async refresh to advance
             to the freshest verified catalog.
```

- **The cache wins over the seed** when both verify (it is newer/operator-curated);
  the seed is the day-0 floor.
- **Re-verification at startup is mandatory.** A cache or seed that fails P1.3
  (tampered file, retired key, wrong mode) is **discarded**, not served. This is
  why the cache stores the `.sig` alongside the bytes.
- **`enforce` startup with only an unsigned seed** ⇒ no catalog (fail-closed), CP
  boots, release features disabled, loud log. `permissive` ⇒ the unsigned seed
  loads with a warning (migration).

## 8. Air-gap & OVA compatibility

- **OVA bootstrap catalog:** a **read-only, signed seed** baked into the image at
  a fixed path (e.g. `/usr/share/culvert/catalog-seed/`). It is the §7 step-2
  fallback and the day-0 catalog. Verified like any other source; the trust root
  is the **baked-in key ring** (P1.3 §4.2), so the OVA verifies its own seed
  **offline**.
- **Air-gap updates (the bundle):** the operator transfers a **signed release
  bundle** (tarball: `index.json` + `index.json.sig` + manifests + `docker save`
  image blobs). `bundleProvider` extracts the catalog parts to staging; the
  **catalog** is verified by the **same `index.json.sig` against the same trust
  root** — verification is identical to online, only the transport differs
  (parent plan §8). The **image blobs** are loaded into the local registry by the
  air-gap/dispatch slice, which must bind **loaded-image-digest ==
  authenticated `list_digest`** (P1.3 §7 — *not* covered by the index signature
  alone).
- **No network in air-gap.** Refresh is **event-driven** (bundle import), never a
  poll. Revocation/rotation reaches an air-gapped site only by shipping a new
  CP/OVA image (P1.3 §7) — there is no online CRL by design.
- **Offline `changelog_url` etc.** must have bundled equivalents (the GUI degrades
  to bundled notes) — a content concern for the GUI slice, noted here.

## 9. Catalog replacement atomicity & rollback

### 9.1 Atomic replacement

Two independent atomic operations, both performed only **after** verification:

1. **In-memory (authoritative for serving):** `atomic.Pointer[Catalog].Store(new)`.
   Because the `*Catalog` is **immutable and build-complete** (P1.2 returns
   nil-or-whole, never partial), a reader's `GetCatalog()` returns either the
   entire old or the entire new catalog — there is no torn read, no lock on the
   query path.
2. **On-disk (restart durability):** write staged bytes to a cache-staging dir,
   `fsync`, then **`os.Rename`** onto the canonical cache path (atomic within a
   filesystem). 

**Ordering:** persist (rename) **then** in-memory store. A crash between leaves
disk *ahead* of memory, but the process is dead — the next startup loads the
(newer, verified) disk cache, so the system converges. A persist failure after a
successful verify still does the in-memory store (memory is authoritative) and
logs; the next refresh re-persists.

> **No partial catalog is reachable.** Staging is separate; the swap is a single
> pointer store; disk is a single rename. There is no window in which queries see
> half a catalog or a mix of old/new releases.

### 9.2 Rollback

- **Last-good is always retained** (in-memory until the next successful publish;
  on-disk in `cacheDir`). A *failed* refresh never replaces it, so the common
  "bad update" case needs no explicit rollback — the bad candidate was simply
  never published.
- **Versioned snapshots (optional, bounded ring):** keep the last *N* **verified**
  catalogs as numbered snapshots (mirroring `configversion.go`'s
  `/data/config_versions/v{N}.json` pattern, e.g.
  `/data/catalog_versions/v{N}/`), so an operator can **pin / roll back to an
  earlier *valid* catalog** (a valid-but-unwanted refresh — e.g. a channel
  re-point they want to undo). Each snapshot retains its `.sig` so a rollback is
  itself re-verified before publish.
- Rollback is **publish-of-a-retained-verified-catalog**, reusing the exact §9.1
  atomic path — it is not a special code path that bypasses verification.

## 10. The trust boundary

```
   UNTRUSTED                                          │   TRUSTED
   ─────────                                          │   ───────
   network · TLS · CDN · staging dir · on-disk cache  │   published *Catalog
   · bundle tarball · provider bytes                  │   · query results
                                                      │
            stage bytes ──────────▶ LoadVerifiedCatalog (P1.3) ──────────▶ publish
                                    ▲ THE TRUST BOUNDARY
```

- **`LoadVerifiedCatalog` is the one and only trust boundary.** No provider,
  cache, or transport is trusted; the only bytes that become a live catalog are
  those that passed the P1.3 verify-before-parse gate.
- **The on-disk cache is untrusted and re-verified on read** (§7) — defense in
  depth: even though it was verified when written, a tampered cache file must not
  load. Storing the `.sig` alongside makes this a normal `LoadVerifiedCatalog`.
- **TLS authenticates the *transport*, not the *catalog*.** A correct HTTPS fetch
  from a compromised mirror still yields a catalog that must pass `index.json.sig`
  — TLS is not a substitute for the signature.
- **Enforcement mode is global and applies to every source** identically
  (startup, online refresh, bundle import). `disabled` (break-glass) is the only
  mode that skips the boundary and must carry the P1.3 §6.2 persistent signal.

## 11. Failure modes

All failures **keep the current live catalog** (or, at startup with no prior
catalog, leave the CP in the explicit "no catalog" state). A failed refresh is
**never** allowed to degrade or partially replace a good catalog.

| # | Condition | Behavior |
|---|---|---|
| F-fetch | Provider `Stage` fails (network down, 404, TLS error, bundle missing/oversize, traversal in tarball) | Keep current; log + `catalog_refresh_fail_total{reason}`; online backoff. Not an alert by itself (rollout/ops signal). |
| F-verify | `LoadVerifiedCatalog` rejects (bad/missing sig, untrusted key, tampered bytes) | Keep current; **higher-severity alert** (probable tamper) + counter; staging discarded. (Distinct from F-fetch.) |
| F-parse | Staged index/manifest malformed (P1.2 fail-closed) but signature somehow valid | Keep current; log + counter. (In `enforce` this means a validly-signed-but-malformed catalog — a producer bug; surfaces distinctly.) |
| F-empty | Provider stages an empty/zero-release catalog | Rejected by P1.2 (F10); keep current. |
| F-cache-corrupt | Startup cache fails re-verification | Discard cache, fall through to seed (§7); log. A tampered cache never loads. |
| F-seed-missing | No seed and no cache at startup | Publish nothing; CP boots; release features report "catalog unavailable"; loud log. |
| F-persist | Verified catalog can't be written to the on-disk cache (disk full, perms) | **Still publish in-memory** (authoritative); log; next refresh re-persists. Serving is unaffected. |
| F-stale | Last successful refresh older than a configured threshold | **Keep serving** the last-good catalog (do NOT fail-closed on age); surface staleness + optional warn/alert (§12). |
| F-concurrent | A trigger arrives mid-refresh | Coalesced by single-flight; no overlapping stage/verify, no swap race (§6). |
| F-bundle-image | Air-gap bundle's image blob ≠ authenticated `list_digest` | The **bundle/dispatch slice** rejects at image load (P1.3 §7); the catalog itself may still be valid, but dispatch must not deploy a mismatched image. (Out of this slice's publish path.) |

## 12. Staleness handling

- Track **`GeneratedAt()`** (from the index, P1.2) and **`lastRefreshOK`** (wall
  clock of the last successful publish). Expose both for the GUI/staleness display
  (final slice) and a `catalog_age_seconds` gauge.
- **Staleness never invalidates a valid catalog.** An air-gapped site may
  legitimately run a months-old catalog; failing closed on age would break it.
  Past a configurable `max_staleness`, **warn/alert** but keep serving.
- "Stale" is an **operator signal**, not a security control — security is the
  signature (§10), which is independent of age (the anti-rollback/freshness gap is
  explicitly out of P1.3/P1.5 scope; a stale validly-signed catalog still
  verifies — see P1.3 §1).

## 13. Dependency graph

```
config (source.mode, interval, urls, cacheDir, seedDir, trust_keys, verify_mode)
        │
        ▼
  CatalogProvider ──(stages bytes)──▶ staging dir
   ├─ localDirProvider                     │
   ├─ httpProvider (SSRF-guard, bounded)   │
   └─ bundleProvider (safe extract)        ▼
                                  dirCatalogSource (P1.2)  ◀── reuses symlink/bounded reads
                                           │
                                           ▼
                                  LoadVerifiedCatalog (P1.3) ◀── TrustStore (key ring + mode)
                                           │  ── TRUST BOUNDARY ──
                                           ▼
                                  loadCatalogFromIndexBytes (P1.2) → *Catalog (immutable)
                                           │
                          ┌────────────────┼─────────────────┐
                          ▼                ▼                 ▼
                 CatalogHolder      on-disk cache      catalog_versions ring
                 atomic.Pointer     (atomic rename)    (optional rollback)
                          │
        ┌─────────────────┼──────────────────────────┐
        ▼                 ▼                           ▼
   Resolve/Lookup/   GetCatalog()              Refresher goroutine
   Current/List      (lock-free read)          (schedule · manual · startup · backoff)
   (P1.2 surface)
                                  cross-cutting: logger.Printf · metrics culvert_* · alerts.go
```

**Edges that must not exist (anti-dependencies):**
- Provider → `*Catalog` (a provider must never construct a catalog; it stages
  bytes only — verification is the only path to a `*Catalog`).
- Query surface → Provider/Refresher (reads never trigger I/O; `GetCatalog()` is a
  pure atomic load).
- Anything here → agent / `ConfigSnapshot` / dispatch (CP-only, agent-agnostic).

## 14. Interaction with P1.2 & P1.3 (what is reused vs added)

- **P1.2 reused unchanged:** `dirCatalogSource` (the staging reader),
  `loadCatalogFromIndexBytes`, the immutable `*Catalog`, the whole query surface
  (`Resolve`/`Lookup`/`Current`/`List`/`GeneratedAt`), `catalogMaxReadBytes`. The
  catalog object is published *exactly as P1.2 builds it* — this slice never
  reaches inside it.
- **P1.2 promise honored:** P1.2 said "reload = construct a new `*Catalog`; the
  refresh slice owns swap semantics." This slice is that owner — it adds the
  goroutine, the ticker, and the atomic swap that P1.2 deliberately omitted.
- **P1.3 reused unchanged:** `LoadVerifiedCatalog`, `SignedCatalogSource`,
  `TrustStore`, the modes, the envelope. Every publish path (startup, online,
  bundle, rollback) goes through `LoadVerifiedCatalog` — there is no second,
  weaker loader.
- **P1.3 trust boundary is preserved end-to-end:** the cache and bundle are
  untrusted and re-verified; modes apply identically to every source.

## 15. Recommended implementation slices

Smallest-first; each is independently shippable and testable, and each preserves
the P1.2/P1.3 invariants.

| Slice | Delivers | Depends on | Notes |
|---|---|---|---|
| **P1.5a — Holder + atomic publish** | `CatalogHolder` (`atomic.Pointer[Catalog]`, `GetCatalog`, `publish`), startup load from a **single local dir** (seed/cache) via `LoadVerifiedCatalog`, manual "reload from dir". **No goroutine, no network.** | P1.2, P1.3 | The kernel. Proves atomic swap + re-verification + the "no catalog" boot state. |
| **P1.5b — Refresher + cache + staleness** | the refresher **goroutine** (interval + jitter + single-flight + backoff), the **on-disk last-good cache** (stage + `os.Rename`), `lastRefreshOK`/`GeneratedAt` staleness tracking, metrics/alerts. | P1.5a | Still local-dir source; introduces scheduling + durability. |
| **P1.5c — HTTP provider** | `httpProvider` (SSRF-guarded, bounded, `http.NewRequestWithContext`) for **online** refresh. | P1.5b | First network source; the dispatch/GUI slices can now show "update available." |
| **P1.5d — Air-gap bundle provider** | `bundleProvider` (safe tarball extract) + the **outer bundle signature** contract (P1.3 §7) + image-blob↔`list_digest` binding hand-off to the image-load/dispatch slice. | P1.5b | Offline updates; no polling. |
| **P1.5e — Rollback ring** | bounded `catalog_versions` snapshots + pin/rollback (re-verified publish), mirroring `configversion.go`. | P1.5a | Optional; valid-but-unwanted rollback. |
| **P1.5f — Operator surface** | admin API + GUI: source config, manual refresh, verify/staleness status, mode display (GUI-parity, per CLAUDE.md). | P1.5a–c | The final slice; runtime config mutation lands here. |

**Natural order after P1.5:** the CP→agent **dispatch** slice (`Resolve` →
`upgrades.apply` with the repo-bound `PinnedRef`, repo-equality per P1.2 §2.4),
then rollback-candidate computation, then the full release GUI.

## 16. Summary of decisions

| Question | Decision |
|---|---|
| **Source model** | `CatalogProvider` (local / http / bundle) stages a self-contained candidate into a temp dir; one active mode (config, read-once). |
| **Refresh** | One refresher goroutine: startup + jittered interval (online) + manual; single-flight; backoff. Air-gap/local are event-driven, never polled. |
| **Refresh failure** | Keep current live catalog; log + counter (+ alert for verify failures); discard staging. Never partial, never unverified. |
| **Verify failure** | Rejected at the P1.3 boundary; never published; higher-severity alert. |
| **Startup catalog** | cache → seed → none; every candidate re-verified; CP boots even with no catalog (release features fail-closed-unavailable). |
