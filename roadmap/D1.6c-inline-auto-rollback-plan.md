# D1.6c — Inline Auto-Rollback: Focused Implementation Plan

**Status:** PLAN ONLY. No code, no endpoint activation, no sudoers changes, no
data rollback, no GUI, no implementation. This document drives a later impl
slice; it must leave no ambiguity for it.

**Scope:** define exactly how `upgrades.apply` automatically performs an
**image** rollback when an upgrade becomes unhealthy *after restart*. It builds
on what is already live on `main`:

- `POST /v1/upgrades/check`, `POST /v1/upgrades/apply` (#361), and
  `POST /v1/rollbacks` (mode=image, #369).
- Image rollback already does `capture → pull → restart → health gate → verify`
  via `buildImageRollbackStages(targetRef)` (reusing `ComposePull` /
  `ComposeUpWithImage` / `CaptureRunningProxyImage`; **no sudoers/template** of
  its own).
- The release-UX direction (#363): the agent is a **low-level internal
  executor**.

> **Architectural invariant (from #363).** Auto-rollback is an **internal agent
> concern**. The agent already holds the prior digest in memory (apply's
> `capture_before`), so inline rollback is **fully self-contained** — it needs no
> CP call, no release/channel/version awareness, and no operator input. (This is
> the one structural difference from *standalone* rollback, where the CP supplies
> the target digest.) A future CP/GUI may *surface* the rollback outcome from the
> op result, but the agent must not gain release awareness.

---

## 0. The one-paragraph model

When an `upgrades.apply` restarts onto the new image and then **fails the health
gate or post-restart verify**, the same apply operation automatically re-pins the
proxy back to the **prior** running digest (captured before the upgrade) using the
**shared image-rollback stages**, all **inside the same op and the same
maintenance-lock tenure**. The operation's terminal **state stays `failed`** (the
upgrade the operator asked for did not succeed); the `failure_reason` and a
structured `result` tell the operator unambiguously whether the rollback ran and
whether it restored service.

---

## 1. Enable / Disable policy

- **Opt-out, on by default.** The apply request gains `rollback_on_failure bool`
  that **defaults to `true`** when omitted. Rationale: a failed upgrade that
  leaves the proxy down is the worst outcome; the safe default is to restore
  service automatically. An operator running a deliberate forward-only migration
  can pass `false`.
- **Always *attemptable*, never *forced*.** Even with `true`, rollback only fires
  when a valid prior digest was captured **and** the failure was post-restart
  (§2, §3). It is never forced when there is nothing safe to roll back to.
- **No separate config flag / env var in this slice.** It is a per-request field,
  not a daemon-global setting — keeps the agent stateless about policy and lets
  the caller (today: a human/CP per apply) decide each time. No
  `CULVERT_*` toggle is introduced.
- **Future CP/GUI controls (out of scope, documented for direction):** the CP may
  expose a per-environment default for `rollback_on_failure`, and the GUI may
  render the rollback outcome ("upgrade failed — service auto-restored to the
  previous release"). Per #363 these live in the CP/GUI; the agent contract stays
  the single boolean + the structured result.

---

## 2. Prior digest capture

- **When:** at apply's existing **`capture_before`** stage — the first stage,
  before anything is touched. No new capture point. It records the running
  proxy's `RepoDigests`.
- **What the impl must add:** `capture_before` currently stores only
  `acc.priorDigests` (bare `sha256`). Inline rollback needs a **full pinned ref**
  to pull/restart, so the accumulator gains `acc.priorRef string` =
  `ri.PriorRef()` (the first `repo@sha256:<digest>` RepoDigest).
- **Validation of the rollback target:** `acc.priorRef` must satisfy the **same
  strict gate as standalone rollback** — `rollbackDigestRefRE`
  (`<repo>@sha256:<64hex>`) **and** the operator `image_allowlist`. The prior
  image was running moments ago so it is inherently trusted, but it is
  re-validated for parity and defense-in-depth (an allowlist that was tightened
  mid-flight must still gate it).
- **No valid rollback target exists** (fresh deploy / stack was down at apply
  start → `capture_before` found no running proxy, OR the running image is a
  locally-built image with **no** `RepoDigest`, OR `priorRef` fails the regex /
  allowlist): there is **nothing safe to roll back to**. Inline rollback is
  **skipped**; on a post-restart failure the op ends `failed` with the upgrade's
  own reason and an explicit op-log + result marker
  (`rollback_attempted=false`, `rollback_skipped_reason="no_prior_digest"`).
- **Capture succeeds but verification data is incomplete** (e.g. multiple
  RepoDigests, or a digest present but the image-id capture was partial): treat as
  **no valid single target** and skip with `rollback_skipped_reason=
  "ambiguous_prior_digest"`. Inline rollback never *guesses* a target — if the
  prior pin is not exactly one strict digest, it does not run.

## 3. Operation state model — and the central decision

| Path | Op state | failure_reason | result highlights |
|---|---|---|---|
| Upgrade healthy | `succeeded` | — | `upgrade_succeeded=true, rollback_attempted=false` |
| Upgrade health/verify fails, **no** prior target | `failed` | `health_failed` | `rollback_attempted=false, rollback_skipped_reason=...` |
| Upgrade fails, rollback **succeeds** | **`failed`** | **`health_failed`** | `rollback_attempted=true, rollback_succeeded=true` |
| Upgrade fails, rollback **fails** | `failed` | **`rollback_failed`** | `rollback_attempted=true, rollback_succeeded=false` |
| Failure **before** restart (pull/pre-backup) | `failed` | original (`command_error`, …) | `rollback_attempted=false, rollback_skipped_reason="pre_restart_failure"` |

### Decision: rollback-after-failed-upgrade ends as `failed` (NOT a new state)

The op's terminal **state stays the binary `failed`**. The "rollback restored
service" nuance is carried by **`failure_reason` + the structured `result`**, not
by a new state enum value.

**Rejected alternatives and why:**

- **`succeeded_with_rollback`** — *rejected.* It would report success for an
  operation whose entire purpose (land the new image) **failed**. Generic tooling
  that keys off `state == succeeded` (dashboards, "last upgrade ok?", CP
  promotion gates) would be actively misled.
- **`failed_with_successful_rollback`** as a **state** — *rejected as a state,
  adopted as a `failure_reason`-level distinction instead.* Adding rollback-shaped
  members to the op-state enum bloats a type that is consumed by
  state-agnostic machinery (maintenance lock, idempotency dedupe,
  `/v1/operations` listing, restart reconciliation). Those layers only need
  "did the requested action terminate ok?" → `failed`. Encoding the rollback
  outcome in `failure_reason` keeps the state enum small and stable.
- **Binary `failed` + reason + result** — *chosen.* The state answers "did the
  upgrade succeed?" (no). `failure_reason` answers "is service OK?":
  `health_failed` ⇒ rollback restored service; `rollback_failed` ⇒ it did not
  (page). The `result` makes both facts machine-explicit. One source of truth per
  question, no enum bloat, no lying.

**Operator reading guarantee.** `state` answers "did the upgrade land?"; the
**`result` fields answer "is service up?"** — `failure_reason` is the failure
*class*, **not** a service-state proxy. Do **not** equate `failure_reason=
health_failed` with restored service: the skipped-rollback rows in §4
(no/unavailable/ambiguous prior target, `rollback_on_failure=false`) are *also*
`health_failed` yet leave the **unhealthy new image running** (service down).

Service state is derived **only** from the result:

| Service state at op end | Predicate | Page? |
|---|---|---|
| Up — new image | `upgrade_succeeded == true` | no |
| Up — prior image (rolled back) | `rollback_attempted && rollback_succeeded` | no |
| Up — old image (never restarted) | `rollback_skipped_reason == "pre_restart_failure"` | no |
| **Down / unknown** | `state == failed` and none of the above | **yes** |

So the one-line paging rule is **not** "page iff `rollback_failed`" — it is:

```
page  ⇔  state == failed
         AND NOT (rollback_succeeded == true
                  OR rollback_skipped_reason == "pre_restart_failure")
```

`rollback_failed` is the paging reason for an *attempted* rollback that did not
restore service; a **skipped** rollback after a post-restart failure
(`rollback_attempted=false`, reason `health_failed`) **also pages** by the rule
above. The decisive bit is always `rollback_succeeded`, never the reason alone.

## 4. Failure-reason contract

`rollback_failed` is an **additive** failure reason (proposed in
`D1.6c-rollback-plan.md` §6.3; first shipped here). Exact mapping:

| Situation | failure_reason | rollback_attempted | rollback_succeeded |
|---|---|---|---|
| Upgrade health gate failed, rollback restored service | `health_failed` | true | true |
| Upgrade verify failed (digest mismatch post-restart), rollback restored | `health_failed` | true | true |
| Rollback **pull** failed | `rollback_failed` | true | false |
| Rollback **restart** failed | `rollback_failed` | true | false |
| Rollback **health** failed | `rollback_failed` | true | false |
| Rollback **verify** failed (didn't land prior digest) | `rollback_failed` | true | false |
| Rollback **target unavailable** (no/invalid prior digest) | `health_failed` | **false** | false |
| Failure **before** restart (resolve/pull/pre-backup of the *upgrade*) | original reason | **false** | false |

Notes:
- **Why "target unavailable" keeps `health_failed`, not `rollback_failed`:** no
  rollback was *attempted* (nothing to attempt), so `rollback_failed` (which means
  "the rollback we ran did not restore service") would be misleading. The op
  failed because the upgrade was unhealthy → `health_failed`, with
  `rollback_attempted=false` + a `rollback_skipped_reason` saying why.
- **Why pre-restart upgrade failures never trigger rollback:** if pull or
  pre-backup fails, the proxy is **still on the old image** (never restarted) —
  service is intact, there is nothing to roll back. The op fails with the
  upgrade's original reason and `rollback_attempted=false`
  (`rollback_skipped_reason="pre_restart_failure"`).
- **Paging is decided by service state, not by `failure_reason` alone** (see the
  §3 predicate). `health_failed` with `rollback_succeeded=true` is a *handled*
  failure (service up, no page). But `health_failed` with a **skipped** rollback
  after a post-restart failure (`rollback_attempted=false`) leaves the unhealthy
  image running and **must page**. `rollback_failed` always pages. A monitor that
  keys on `failure_reason` alone would under-page the skipped-and-down case — it
  must read `rollback_succeeded` / `rollback_skipped_reason`.

## 5. Result structure

Inline auto-rollback ships the **structured `result` map** on the apply op
(apply's result was deferred in #361; this is the natural slice to add it). Exact
fields:

```json
{
  "upgrade_succeeded":      false,
  "rollback_attempted":     true,
  "rollback_succeeded":     true,
  "rollback_skipped_reason":"",                  // set only when rollback_attempted=false
  "upgrade_digest":         "sha256:<target>",   // pinned digest the upgrade tried to land
  "rollback_digest":        "sha256:<prior>",    // the prior digest rolled back to (== capture_before)
  "final_running_digest":   "sha256:<actual>"    // what is ACTUALLY running at op end
}
```

Field semantics (all digests are bare `sha256:<hex>`, never tags, never raw
inspect blobs):

- `upgrade_succeeded` — the upgrade landed healthy. When `true`, all rollback
  fields are zero/empty and `final_running_digest == upgrade_digest`.
- `rollback_attempted` — a rollback ran (target was valid **and** failure was
  post-restart).
- `rollback_succeeded` — rollback pulled+restarted+health+verify all passed;
  `final_running_digest == rollback_digest`.
- `rollback_skipped_reason` — `""` when attempted; otherwise one of
  `no_prior_digest`, `ambiguous_prior_digest`, `pre_restart_failure`,
  `disabled` (operator passed `rollback_on_failure=false`).
- `upgrade_digest` / `rollback_digest` / `final_running_digest` — let the operator
  confirm exactly what is live. On a **failed** rollback, `final_running_digest`
  is whatever the failed rollback left running (often the unhealthy upgrade image
  or an indeterminate state) — captured best-effort.

**Consistency rule:** exactly one of these holds — `upgrade_succeeded=true`
(no rollback); `rollback_attempted=true` (then `rollback_succeeded` is decisive);
or `rollback_attempted=false` with a non-empty `rollback_skipped_reason`.

The same struct is reused for **standalone** rollback (#369) where
`upgrade_*` fields are omitted/zero — keeping one result vocabulary.

## 6. Operation-log contract

Existing digest-only hygiene (#351/#357) continues — **no raw inspect output**,
only parsed `sha256:` digests and bounded command stdout/stderr.

**Ordering** (apply op log, failure-with-rollback path):
```
capture_before   prior_digests=<…> prior_ref=<repo@sha256:…>
resolve_target   requested=<…> pinned=<repo@sha256:…>
pre_backup       <…>                         (if requested)
pull             <compose pull output>
restart          <compose up output>
health_gate      ready=… health=… → FAIL
                 (verify is SKIPPED — upgrade already failed)
recovery:rollback_pull      <compose pull output>      (target=prior_ref)
recovery:rollback_restart   <compose up output>
recovery:rollback_health    ready=… health=…
recovery:rollback_verify    running_digests=<…> ⊇ prior?  
report           <summary line>
```

- Inline rollback stages are **`recovery:`-prefixed** (the orchestrator already
  marks post-failure `ContinueOnError` stages as recovery), so the log visibly
  separates "the upgrade" from "the recovery".
- **Summary line** (always emitted by `report`):
  `upgrade_apply requested=<…> pinned=<target> health=[…] | rollback attempted=<bool> succeeded=<bool> target=<prior> final_running=<…>`.
- **Successful rollback:** operator sees the upgrade health FAIL, then four
  `recovery:rollback_*` stages succeeding, then a summary with
  `rollback succeeded=true final_running=<prior>`.
- **Failed rollback:** the failing `recovery:rollback_*` stage carries the error;
  summary shows `rollback succeeded=false` and the last known
  `final_running` digest. Both prior and target digests appear so the operator can
  reconcile by hand.

## 7. Audit events

Auto-rollback is part of the **single** `upgrades.apply` op (one operator action =
one op), so it does **not** create a second `rollbacks.create` op. Audit coverage:

| action | outcome | object | when |
|---|---|---|---|
| `upgrades.apply` | `started` | `op_id` | on admission (after dedupe + lock) |
| `upgrades.apply` | `failed` | `op_id` | terminal; detail carries `failure_reason` + `rollback_attempted`/`rollback_succeeded` |
| `upgrades.apply` | `succeeded` | `op_id` | terminal, healthy upgrade (no rollback) |
| `upgrades.apply:rollback` | `started` | `op_id` | only when a rollback actually fires (post-restart failure + valid target) |
| `upgrades.apply:rollback` | `succeeded` | `op_id` | rollback restored service |
| `upgrades.apply:rollback` | `failed` | `op_id` | rollback did not restore service |

- **Actor:** the authenticated peer identity that called `POST /v1/upgrades/apply`.
  Inline rollback **inherits** it — it is the same operator action, not a new
  actor. No `system`/anonymous actor is introduced.
- **Object:** the apply `op_id` for every entry (the rollback has no op_id of its
  own). This lets an auditor correlate the upgrade and its recovery to one
  operation.
- The `:rollback` sub-action entries are emitted **only** when a rollback runs —
  a skipped rollback (no target / pre-restart / disabled) emits no `:rollback`
  audit, but the `upgrades.apply failed` entry's detail still records
  `rollback_attempted=false` + reason, so "did rollback run?" is always answerable
  from audit alone.

## 8. Reuse strategy — share the stages, don't fork them

**Decision: extract a shared internal stage builder; both paths call it.** This is
the explicit anti-drift mechanism.

- Refactor #369's `buildImageRollbackStages(targetRef)` so the **stage sequence**
  (capture → pull → restart → health → verify) lives in one helper, e.g.
  `imageRollbackStages(targetRef, acc *rollbackAccumulator) []ops.FlowStage`.
- **Standalone** rollback (`handleRollback`) wraps it as a full op with its own
  lock + `KindRollbackCreate` (unchanged behavior).
- **Inline** rollback **appends the same stages** (with `recovery:` names +
  `ContinueOnError=true`) to the apply flow, sourcing `targetRef` from
  `acc.priorRef` instead of the request body.
- **Why not have apply just call `POST /v1/rollbacks` internally?** *Rejected* —
  a nested HTTP call would re-acquire the maintenance lock (deadlock against the
  in-flight apply op) and spawn a second op. Sharing the **stage builder** gives
  identical pull/restart/health/verify behavior with **zero** lock/op duplication.
- **Drift guard (test, §11):** a parity test asserts the inline recovery stages
  and the standalone stages are produced by the same builder (same stage names,
  same order, same `CULVERT_PROXY_IMAGE` pinning), so manual and automatic
  rollback can never diverge silently.

---

## 9. Locking / idempotency

- **One lock, one op.** Inline rollback runs **inside** the apply op and **inside
  its existing maintenance-lock tenure**. It does **not** acquire the lock again
  and does **not** create a nested or second operation.
- **Not a nested op.** The rollback is a set of recovery stages on the apply
  op's flow — there is no child `op_id`, no separate `/v1/operations` entry.
- **Idempotency:** the apply request's `idempotency_key` covers the **entire**
  upgrade-then-maybe-rollback sequence. A replay of the same key returns the
  original apply `op_id` (and its result, including the rollback outcome) — it
  never re-runs and never triggers a fresh rollback. There is no separate rollback
  idempotency key.
- **Agent restart mid-rollback:** the apply op is marked `failed`
  `agent_restart_interrupted` at startup (existing behavior); the lock is
  released. No auto-resume of the rollback — the operator inspects `/v1/status`
  and re-acts. (Documented in §10 F6.)

## 10. Failure modes

| # | Condition | Behavior | Operator recovery |
|---|---|---|---|
| F1 | **No prior digest captured** (fresh deploy / stack down at start) | rollback skipped; op `failed` `health_failed`; `rollback_attempted=false, rollback_skipped_reason="no_prior_digest"` | manual `POST /v1/rollbacks` with a CP-supplied digest, or redeploy |
| F2 | **Rollback target missing/invalid** (no RepoDigest, regex/allowlist reject, ambiguous) | rollback skipped; same as F1 with `rollback_skipped_reason="ambiguous_prior_digest"` / `"no_prior_digest"` | manual rollback / fix allowlist |
| F3 | **Rollback pull fails** | recovery stage fails; op `failed` `rollback_failed`; `rollback_succeeded=false`; `final_running` = unhealthy upgrade image (best-effort) | **page**; retry rollback manually or data-rollback |
| F4 | **Rollback restart fails** | op `failed` `rollback_failed`; container state indeterminate; `final_running` best-effort | **page**; `/v1/status`; manual re-run |
| F5 | **Rollback health fails** (rolled back but still unhealthy) | op `failed` `rollback_failed`; worst case | **page**; deeper diagnosis / data rollback |
| F6 | **Rollback verify fails** (health ok but running digest ≠ prior) | op `failed` `rollback_failed` (we cannot trust an unexpected image) | **page**; reconcile via `/v1/status` digests |
| F7 | **Agent restart mid-rollback** | op `failed` `agent_restart_interrupted`; lock freed; no auto-resume | `/v1/status`; manual re-run |
| F8 | **Operation timeout during rollback** | in-flight stage cancelled; op `failed` `timeout` (timeout promotion wins over `rollback_failed`); `final_running` best-effort | `/v1/status`; manual re-run |
| F9 | **Rollback succeeds but upgrade already marked failed** | **expected, not an error.** Op state stays `failed`/`health_failed`; `rollback_succeeded=true`. The final-reason override (§below) does NOT fire (rollback didn't fail) | none — service is restored; informational |

### Required orchestration change — final-reason override (from #364)

The orchestrator keeps the **first** failure reason and `ContinueOnError` recovery
stages do not change it. So a recovery rollback that **fails** after `health_gate`
already failed would otherwise stay `health_failed`, and `rollback_failed` (the
paging signal) would never surface. The slice **must** add a **narrow
final-reason override**: a failed recovery-rollback stage promotes the op's
`failure_reason` to `rollback_failed`. Precedent: the orchestrator already promotes
the final reason to `ReasonTimeout` on deadline. Scope it to the recovery stages'
outcome only — **not** a general "last failure wins" (which would perturb
unrelated flows). F9 confirms the override must fire **only on rollback
failure**, never on rollback success (success must preserve `health_failed`).

## 11. Test matrix

Integration tests reuse the apply/rollback rig (faked exec + fake health).

| Test | Asserts |
|---|---|
| Upgrade success (healthy) | op `succeeded`; `upgrade_succeeded=true`; `rollback_attempted=false`; no `:rollback` audit; `final_running==upgrade_digest` |
| Upgrade health fail + rollback success | op `failed`/`health_failed`; `rollback_attempted=true, rollback_succeeded=true`; `final_running==prior`; pull+up pinned to prior; `recovery:rollback_*` stages in log; `:rollback started/succeeded` audit |
| Upgrade health fail + rollback **pull** fail | op `failed`/**`rollback_failed`**; `rollback_succeeded=false`; `:rollback started/failed` audit; restart-of-prior not reached |
| Upgrade health fail + rollback **restart** fail | op `failed`/`rollback_failed`; `rollback_succeeded=false` |
| Upgrade health fail + rollback **health** fail | op `failed`/`rollback_failed` (final-reason override fired, NOT `health_failed`) |
| Upgrade health fail + rollback **verify** fail | op `failed`/`rollback_failed` |
| Upgrade **verify** fail (post-restart digest mismatch) + rollback success | op `failed`/`health_failed`; `rollback_succeeded=true` |
| **Missing rollback target** (no prior digest) | op `failed`/`health_failed`; `rollback_attempted=false`, `rollback_skipped_reason="no_prior_digest"`; no `:rollback` audit; no pull/up issued for rollback |
| **Pre-restart** upgrade failure (pull fails) | op `failed`/`command_error`; `rollback_attempted=false`, `rollback_skipped_reason="pre_restart_failure"`; old image untouched |
| `rollback_on_failure=false` + health fail | op `failed`/`health_failed`; `rollback_attempted=false`, `rollback_skipped_reason="disabled"` |
| **Idempotent replay** | second apply with same `idempotency_key` → same `op_id`, same result (incl. rollback outcome), no second run, no second rollback |
| **Audit coverage** | `upgrades.apply started/failed` present for every run; `upgrades.apply:rollback started/(succeeded\|failed)` present iff a rollback fired; actor==apply caller, object==op_id (content-based assertion, never `len()` deltas — CLAUDE.md ring-saturation pitfall) |
| **Op-log coverage** | digest-only hygiene holds; `recovery:rollback_*` ordering; summary line carries `rollback attempted/succeeded/target/final_running` |
| **Stage-parity (drift guard)** | inline recovery stages == standalone stages from the shared builder (names, order, `CULVERT_PROXY_IMAGE` pin) |
| **Final-reason override invariance** | rollback **success** preserves `health_failed`; rollback **failure** promotes to `rollback_failed`; timeout still wins over both |
| **Service-state / paging predicate** (§3) | the §3 predicate holds across cases: paging fires for post-restart unhealthy with rollback failed **and** with rollback **skipped** (`health_failed`, `rollback_attempted=false`); does NOT fire for rollback-success, pre-restart failure, or upgrade-success. Proves `failure_reason` alone is insufficient |

## 12. Slice boundaries (what the impl PR does / does not do)

**Does:** add `rollback_on_failure` (default true) to the apply request; capture
`acc.priorRef` + validate; extract the shared `imageRollbackStages` helper; append
guarded `recovery:rollback_*` stages to apply; add the `rollback_failed` reason +
the narrow final-reason override; add the structured `result` map (apply +
standalone); add the `upgrades.apply:rollback` audit sub-action; the test matrix.

**Does not:** activate or change any endpoint surface (apply/rollbacks already
live), add a sudoers entry or runner template (reuses pull/up + capture), do
**data** rollback, add GUI/CP surfaces, or give the agent any release/channel
awareness. The `env_keep` privilege-boundary hardening (`D1.6c-rollback-plan.md`
§13.2) remains its own follow-up and is inherited unchanged.
