# D1.6d / P1.2 — B1: Docker `RepoDigests` contract verification (design note)

**Status:** RESEARCH / DESIGN NOTE ONLY. No runtime code changes. This closes the
**§1.1 implementation prerequisite** of
`roadmap/D1.6d-P1.2-release-catalog-runtime-plan.md` (the B1 reverse-map
blocker): empirically determine what `docker image inspect`'s `RepoDigests`
contains after a pull by (1) manifest-list digest, (2) per-arch digest, and
(3) tag, and decide whether the shipped `Current()` exact-match design holds or
needs a data-model change.

**TL;DR:** `Current()` exact-match **works as implemented** for the deployment
path. A catalog-deployed image's `RepoDigests` contains the **manifest-list
digest**, which is exactly the catalog `PinnedRef`. **No data-model change is
required — keep `Current()` as-is.** The one production caveat is **not** a
catalog-API change: air-gapped/mirrored deployments rewrite the **repo prefix**
(same digest, different registry host), so the **dispatch/reverse path** must
normalize the running ref's repo prefix to the catalog's canonical repo before
exact-matching (§4.1).

---

## 1. Method

Live verification was run in this session. **Docker Hub and `ghcr.io` are blocked
by the environment's egress allowlist** ("denied: Host not in allowlist"), so the
real `ghcr.io/kidcarmi/culvert` image could not be pulled. A reachable,
**multi-arch** public image was used instead — the digest mechanics are a
property of Docker's repo-digest recording + the OCI/Docker manifest-list
structure, so they are image-independent.

- **Daemon:** Docker `29.3.1`, classic image store (`--storage-driver=vfs`).
- **Image:** `mcr.microsoft.com/cbl-mariner/base/core:2.0`
  - mediaType `application/vnd.docker.distribution.manifest.list.v2+json` (a
    multi-arch manifest list / image index).
  - **manifest-LIST digest** (what the tag resolves to):
    `sha256:c833841d2dcfd3081d2ee807050d19368854f70d9b6faef027463e2c6f45ee41`
  - **amd64 per-arch (image-manifest) digest**:
    `sha256:fdf30afe733831d3af0db95aa8e6870fb1094b2c4f531caaaa06e37481b95253`
- Host platform: linux/amd64. A fresh image (`docker rmi`) preceded each pull.

## 2. Exact observed `RepoDigests` values

| # | Pull mode | command | observed `RepoDigests` |
|---|---|---|---|
| 3 | **by tag** | `docker pull …/core:2.0` | `["…/core@sha256:c833…ee41"]` → the **LIST** digest |
| 1 | **by manifest-list digest** | `docker pull …/core@sha256:c833…ee41` | `["…/core@sha256:c833…ee41"]` → the **LIST** digest |
| 2 | **by per-arch digest** | `docker pull …/core@sha256:fdf3…95253` | `["…/core@sha256:c833…ee41", "…/core@sha256:fdf3…95253"]` → **LIST + per-arch** |

Raw values:
- (3) tag → `["mcr.microsoft.com/cbl-mariner/base/core@sha256:c833841d2dcfd3081d2ee807050d19368854f70d9b6faef027463e2c6f45ee41"]`
- (1) list digest → `["mcr.microsoft.com/cbl-mariner/base/core@sha256:c833841d2dcfd3081d2ee807050d19368854f70d9b6faef027463e2c6f45ee41"]`
- (2) per-arch digest → `["mcr.microsoft.com/cbl-mariner/base/core@sha256:c833841d2dcfd3081d2ee807050d19368854f70d9b6faef027463e2c6f45ee41","mcr.microsoft.com/cbl-mariner/base/core@sha256:fdf30afe733831d3af0db95aa8e6870fb1094b2c4f531caaaa06e37481b95253"]`

### Key facts established
1. **Pull by manifest-LIST digest records the LIST digest** in `RepoDigests`
   (case 1). This is exact and unambiguous.
2. **Pull by tag records the LIST digest** too (case 2/“3”): for a multi-arch
   image the tag resolves to the index, and the *resolved* digest (the list
   digest) is what `RepoDigests` records — **not** the per-arch digest.
3. **Pull by per-arch digest records the per-arch digest** — and, here, the LIST
   digest as well (see the caveat below).

> **Caveat on case 2 (per-arch).** It was pulled *after* the tag/list pulls; the
> shared amd64 content was not fully evicted by `docker rmi`, so the prior LIST
> association persisted and re-attached. A fully-isolated per-arch-ONLY pull is
> *expected* to yield `["…@sha256:<per-arch>"]` alone — an isolated re-run could
> not be completed in this sandbox (the fresh-data-root daemon would not start).
> This caveat does **not** affect the conclusion: in every observed case the
> running `RepoDigests` either **is** or **contains** the list digest, except a
> truly-isolated per-arch-only pull (a non-deployment edge), which is safely
> Unknown.

> **`RepoDigests` is an ARRAY.** Case 2 directly demonstrates it can hold more
> than one `repo@sha256:…` entry. This matters for integration (§5).

## 3. Does `Current()` exact-match work as implemented?

**Yes.** The shipped `Current(runningRef)` returns `Known` iff `runningRef`
exactly equals a catalog `PinnedRef`, where `PinnedRef = repo@<list_digest>`.
Mapping the observed behavior onto the real deployment:

| Scenario | running `RepoDigests` | vs `PinnedRef` (= list digest) | `Current()` |
|---|---|---|---|
| **Catalog-deployed** (P1.4 agent `docker pull <repo>@<list_digest>` + retag to `culvert/proxy:pinned`) | `[repo@<list>]` | **equal** | **Known** ✓ |
| Manually tag-deployed multi-arch (a catalog release's tag) | `[repo@<list>]` | **equal** | **Known** ✓ (bonus) |
| Pulled by per-arch digest only | `[repo@<per-arch>]` (or `+<list>`) | per-arch ≠ list (list, if present, =) | Unknown, or Known if the list entry is present — **both acceptable** |
| Legacy / pre-catalog / foreign repo / not in catalog | not a catalog `PinnedRef` | unequal | **Unknown/Custom** ✓ |

The decisive line is the first one. The **P1.4 agent pulls by the list digest**
(the catalog hands it `PinnedRef = repo@list_digest`), and case 1 proves that
pull records **exactly the list digest** in `RepoDigests`. Retagging to the local
`culvert/proxy:pinned` adds **no** `RepoDigest` (local tags are not registry
digest associations). So `/v1/status.running_image.repo_digests` (P1.1) will
contain the list digest = `PinnedRef`, and `Current()` returns **Known**.

`Unknown/Custom` remains the correct, safe outcome for per-arch-only pulls and
anything not in the catalog — exactly the §3.1 contract.

## 4. Required data-model change

**None — for the digest contract itself.** The reverse index keyed on `PinnedRef`
(the repo-bound **list** digest) is the correct key:
- it is what a list-digest pull and a tag pull both record, and
- it is what the P1.4 deployment path produces.

Keying on the per-arch digest would have been **wrong** (a tag/list pull never
records it). The shipped `Current()`/`Lookup()` design is correct; the B1
**digest** assumption is **confirmed**.

### 4.1 Caveat — air-gapped / rewritten repo prefixes (a dispatch-layer concern)

`Current()`/`Lookup()` exact-match the **full repo-bound** ref
(`repo@sha256:<list>`), **not** the digest alone. Air-gapped and enterprise
deployments routinely **mirror the image into a local registry**, which
**rewrites the repo prefix while preserving the digest**. The running container
then reports:

```
local.registry.internal/culvert@sha256:c833…ee41     ← RepoDigests after a mirror pull
ghcr.io/kidcarmi/culvert@sha256:c833…ee41            ← the catalog PinnedRef
```

Same digest, **different repo prefix** → the strings are unequal → `Current()`
returns **Unknown** even though it is, in fact, a catalog-deployed release.

This is **not** a data-model change to *this* slice — the catalog correctly keys
on the repo-bound `PinnedRef` it was given, and repo equality / repo rewriting is
explicitly **the dispatch layer's responsibility** (plan §2.4). But closing B1 as
"no data-model change" **without** recording this would let the next slice ship a
reverse path that reports air-gapped, catalog-deployed images as Unknown. So the
requirement lands on the **dispatch/reverse path**, which MUST, before
exact-matching against catalog `PinnedRef`s, **normalize or rewrite the running
ref's repo prefix to the catalog's canonical repo** (e.g. strip/replace the
mirror prefix per a configured registry-rewrite map, then compare on
`canonical_repo@digest`). Equivalently, it may compare on the **digest component
alone once the repo has been confirmed equivalent**. Either way the decision is
the dispatch layer's; the catalog API is unchanged.

## 5. Integration note for the dispatch slice (not this slice)

`RepoDigests` is an array (§2). `Catalog.Current(runningRef string)` takes a
**single** ref by design. The CP→agent integration that wires P1.1's
`running_image.repo_digests` to the catalog must therefore:

> iterate every `repo_digests` entry and call `Lookup`/`Current` on each; treat
> the release as **Current** if **any** entry matches a catalog `PinnedRef`.

This is robust against multi-entry `RepoDigests` (case 2) and needs **no change**
to the catalog API. Document it where the dispatch slice consumes the running
digest.

---

## 6. Recommendation

**Keep `Current()` as-is. Do NOT defer reverse mapping.** The exact-match design
is verified correct for the deployment path and degrades safely (`Unknown`) for
per-arch-only / legacy / foreign images, matching the §3.1 contract. The reverse
index (`byPinnedRef`, keyed on the list digest) needs no rework.

One **dispatch-layer** follow-on (NOT a catalog change): the reverse path must
**normalize/rewrite the running ref's repo prefix** to the catalog's canonical
repo before exact-matching, or air-gapped/mirrored catalog deployments will
report `Unknown` despite matching digests (§4.1, plan §2.4).

### Residual confirmations (cheap, before the dispatch slice ships)
1. **Re-confirm on the production daemon + the real image.** This run used Docker
   `29.3.1` with the **classic** image store and a Microsoft mirror image (Hub /
   ghcr.io are egress-blocked here). The containerd-snapshotter image store
   (default on newer Docker) records `RepoDigests` the same way (name @
   resolved-digest), but a one-off `docker pull ghcr.io/kidcarmi/culvert@<list>`
   + `docker image inspect --format '{{json .RepoDigests}}'` on the real host
   should be checked once to be 100% certain for that exact image + daemon.
2. **Verify P1.1 surfaces the list digest.** Confirm that, for an
   agent-deployed (pull-by-list-digest) proxy container,
   `GET /v1/status.running_image.repo_digests` actually contains the list digest
   end-to-end — i.e. that `CaptureRunningProxyImage` reads it from the running
   container as expected.

Both are confirmations of an already-validated mechanism, not blockers to the
catalog's current design.

## Appendix — reproduction commands (run on a host with registry egress)

```sh
IMG=ghcr.io/kidcarmi/culvert:<tag>          # or any multi-arch image
REPO=ghcr.io/kidcarmi/culvert

# list digest + a per-arch digest
docker manifest inspect "$IMG"              # manifests[].digest = per-arch; the
                                            # tag's resolved digest = list digest

# (3) tag
docker rmi -f "$REPO" 2>/dev/null; docker pull "$IMG"
docker image inspect --format '{{json .RepoDigests}}' "$IMG"     # => [repo@<list>]

# (1) list digest
docker rmi -f "$REPO@<list>" 2>/dev/null; docker pull "$REPO@<list>"
docker image inspect --format '{{json .RepoDigests}}' "$REPO@<list>"  # => [repo@<list>]

# (2) per-arch digest (isolate: fresh --data-root for a clean store)
docker pull "$REPO@<per-arch>"
docker image inspect --format '{{json .RepoDigests}}' "$REPO@<per-arch>"  # => [repo@<per-arch>]
```
