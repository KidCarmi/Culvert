# D1.6 — Maintenance Agent / Host Operations — implementation plan

**Status:** design slice — no code, no compose changes, no CP/GUI integration.
**Audience:** maintainers, code reviewers, future implementers of D1.6a–D1.6d.
**Companion to:** [`roadmap/D1.6-maintenance-agent-design.md`](./D1.6-maintenance-agent-design.md) (architectural rationale, trust boundary, supported platforms, security non-negotiables, out-of-scope scope). The design doc captures **why**; this doc captures **how**, staged.

---

## 0. Why this exists

D1.5 pinned the operator contract: every backup / restore / cleanup / future-upgrade action is a sequence of `docker compose` invocations driven through the profile-gated `cli` service. That contract is human-driven today. D1.6 automates it from the GUI without putting `docker.sock` inside the GUI/CP container.

This file is the staged implementation plan: D1.6a (foundation) → D1.6b (backup/restore) → D1.6c (upgrade/rollback) → D1.6d (CP-side integration). Each stage is its own slice with its own design + implementation PRs.

---

## 1. Deployment model

Per the existing D1.6 design — refined and made concrete:

- **Host-side `systemd` service.** `culvert-maint.service` running a single static Go binary. No runtime deps beyond Docker Engine + Compose v2 on the host.
- **Containerized agent: rejected for D1.6a–D1.6c.** A containerized agent driving Docker Compose on its own host needs `docker.sock` plus access to the project directory plus the right cwd — that bind-mount surface is exactly what we're removing from the GUI/CP container. Reopening containerized deployment requires a new design slice (likely tied to K8s/Helm) and is **not** a configuration toggle in D1.6.
- **Linux only** for D1.6.
- **Supported distros**: Ubuntu Server LTS (24.04, 22.04), Debian stable (12), RHEL 9, Rocky 9, AlmaLinux 9.
- **Host requirements**: `systemd`, Docker Engine, Docker Compose v2, read access to the operator's compose project directory, read/write access to `/data` and `/backup` *via Compose* (the agent never touches volumes directly — it always shells out to `docker compose --profile cli run --rm cli …`).
- **Architectures**: `x86_64` first; `arm64` optional / later.
- **Service account**: `culvert-maint` system user. Group membership / sudo posture: see § 4.4.

The forcing function from D1.5 holds: every state-changing op the agent performs is an invocation of the `cli` service that the human operator could also run by hand. The agent is an allowlisted automation layer, not an arbitrary execution surface. It reduces Docker/host exposure from the CP container, but it is still privileged host automation and must be treated as sensitive — UDS permissions, audit, the command-runner contract (§ 4.1), and the fixed allowlist (§ 4.2) are non-negotiable.

### 1.1 Distribution

- **D1.6a** ships as a tarball (`culvert-maint-<version>-linux-amd64.tar.gz`) with the binary, the systemd unit, the sample `config.toml`, the sudoers allowlist file (initially only the minimal read-only `docker compose ps` entry needed by `/v1/status`; § 4.6), and a documented manual install (`install.sh` or copy-paste steps).
- **`.deb` / `.rpm` packaging** is **out of D1.6a** — deferred to a later follow-up once the agent's contract has stabilized through D1.6b/c. Premature packaging locks in artifact-naming conventions and dependency declarations the slices may still want to change.

### 1.2 Stable install / config layout

D1.6a fixes the on-disk layout. These paths are part of the contract from day one — no temporary `/tmp/...` paths, no per-deployment improvisation. Future slices and packaging follow these paths.

| Path | Purpose | Owner / Mode |
|---|---|---|
| `/usr/local/bin/culvert-maint` | Agent binary (single static Go executable) | `root:root` `0755` |
| `/etc/culvert-maint/config.toml` | Operator-controlled configuration (§ 1.3) | `root:culvert-maint` `0640` |
| `/etc/sudoers.d/culvert-maint` | Sudoers allowlist (§ 4.6); shipped from D1.6a, populated incrementally per slice | `root:root` `0440` |
| `/var/lib/culvert-maint/` | State directory (audit log, op logs, optional state.json) | `culvert-maint:culvert-maint` `0750` |
| `/var/lib/culvert-maint/operations/` | Per-operation stdout/stderr captures (`<op_id>.log`) | `culvert-maint:culvert-maint` `0750` |
| `/var/lib/culvert-maint/audit.jsonl` | Append-only audit log | `culvert-maint:culvert-maint` `0640` |
| `/var/lib/culvert-maint/state.json` | Optional last-known-status summary | `culvert-maint:culvert-maint` `0640` |
| `/run/culvert-maint.sock` | UDS API endpoint | `culvert-maint:culvert-maint` `0660` |
| `packaging/systemd/culvert-maint.service` | Systemd unit (in source tree; installed to `/etc/systemd/system/culvert-maint.service`) | `root:root` `0644` |

Deviating from these paths is not supported. Operator configuration controls behavior (§ 1.3), not layout.

### 1.3 Configuration contract

The agent reads `/etc/culvert-maint/config.toml` at startup. The keys below are the stable D1.6a contract; new slices may add keys but must not rename or remove existing ones without a major version bump.

| Key | Type | Default | Purpose |
|---|---|---|---|
| `compose_project_dir` | path | required | Directory containing the operator's `docker-compose.yml`. The agent's cwd for every `docker compose` invocation. |
| `compose_file` | string | `docker-compose.yml` | Filename within `compose_project_dir`. Multi-file overlay is a future slice; D1.6a is single-file. |
| `socket_path` | path | `/run/culvert-maint.sock` | UDS path. Mode is fixed at `0660` regardless of config. |
| `state_dir` | path | `/var/lib/culvert-maint` | State directory root (§ 1.2). |
| `privilege_mode` | enum | `"sudoers"` | `"sudoers"` (production default; § 4.5) or `"docker_group_lab"` (dev/lab opt-in; root-equivalent; § 4.5). No third value. |
| `health_base_url` | URL | `http://127.0.0.1:8080` | Host-published proxy endpoint for health checks. Change when ports are remapped or fronted by TLS terminator. |
| `health_path` | string | `/health` | Path on `health_base_url` for liveness probe. |
| `ready_path` | string | `/ready` | Path on `health_base_url` for readiness probe (must return `status:"ready"`). |
| `operation_timeout` | duration | `30m` | Hard ceiling on a single operation. Exceeding triggers cancel + `failed` with reason `timeout`. |
| `stage_timeout` | duration | `5m` | Default per-stage timeout. Per-stage overrides allowed in code. |
| `log_retention_days` | int | `30` | Retention for `operations/<op_id>.log` and `audit.jsonl`. |
| `allowed_backup_dir` | path (as seen by the cli container) | `/backup` | Backup-path policy. Every `--backup` / `--restore` argument the agent forwards to the `cli` service must be a string whose `filepath.Clean`-ed form has this prefix; otherwise the request is rejected. **This is the path inside the cli container, not on the host filesystem** — the agent never reads or writes that path directly. The `cli` container mounts the `culvert-backups` volume at `/backup` per D1.5 § 1.2, so the default matches the supplied compose. Operators who remap the cli's `/backup` mount must update this key to keep the prefix check meaningful. |
| `image_allowlist` | regex (TOML string) | see below | D1.6c upgrade target allowlist (§ 3.6.1). `image_ref` is rejected if it doesn't match. |

The default `image_allowlist` regex (logical form):

```
^ghcr\.io/kidcarmi/culvert(:[A-Za-z0-9._-]+|@sha256:[a-f0-9]{64})$
```

Stored in `config.toml` as a TOML basic string (which interprets `\` as an escape):

```toml
image_allowlist = "^ghcr\\.io/kidcarmi/culvert(:[A-Za-z0-9._-]+|@sha256:[a-f0-9]{64})$"
```

Or as a TOML literal string (no `\` escaping; preferred):

```toml
image_allowlist = '^ghcr\.io/kidcarmi/culvert(:[A-Za-z0-9._-]+|@sha256:[a-f0-9]{64})$'
```

The literal-string form (single quotes) is the recommended way to write the regex in `config.toml` — what you write is what the regex engine sees. The default config file shipped with the install uses the literal-string form.

A sample `config.toml` ships with the install tarball. Required keys without defaults (`compose_project_dir`) cause startup to fail closed with a clear error.

## 2. API surface — phased

Versioned, allowlisted, async-by-default. JSON over HTTP/1.1 over a Unix-domain socket at `/run/culvert-maint.sock` (mode `0660`, owner `culvert-maint:culvert-maint`).

The full eventual surface is documented here in one place; each slice adds only its rows. The agent ships the routes that are implemented; everything else returns `404`.

### 2.1 D1.6a — read-only foundation

| Verb | Path | Purpose | Sync? |
|---|---|---|---|
| `GET` | `/v1/health` | Agent self-health (cheap; "is the binary up, is the socket accepting"). | Yes |
| `GET` | `/v1/status` | Compose project status: which services are up (parsed from `docker compose ps`), agent version, last successful operation timestamp. | Yes |
| `GET` | `/v1/audit` | Recent audit events. Paginated. | Yes |
| `GET` | `/v1/operations/{id}` | Operation state machine + structured per-stage progress. | Yes |
| `GET` | `/v1/operations/{id}/logs` | Per-operation stdout/stderr capture (chunked stream). | Yes |

D1.6a has **no state-changing operations**. The op framework is exercised by the test suite and by the read endpoints (`/v1/operations/{id}` and `…/logs` work against synthetic ops the test driver creates). This is intentional — D1.6a's job is to land the foundation, not the ops.

### 2.2 D1.6b — backup / restore / cleanup

| Verb | Path | Purpose | Sync? |
|---|---|---|---|
| `POST` | `/v1/backups` | Create a backup (encrypted by default). | Async, returns op ID |
| `GET` | `/v1/backups` | List backup archives in `/backup`. | Yes |
| `POST` | `/v1/restores/dryrun` | Validate a backup against current `/data` (no writes). | Async, returns op ID |
| `POST` | `/v1/restores/commit` | Stop stack → restore commit → start stack → health-check. | Async, returns op ID |
| `POST` | `/v1/cleanups` | Cleanup `.bak.*` / `.staging.*` leftovers (runtime-OK per D1.3c). | Async, returns op ID |

### 2.3 D1.6c — upgrade / rollback

| Verb | Path | Purpose | Sync? |
|---|---|---|---|
| `POST` | `/v1/upgrades/check` | Check for newer image digest. | Async, returns op ID |
| `POST` | `/v1/upgrades/apply` | Pre-backup → pull → restart → health-check → optional auto-rollback. | Async, returns op ID |
| `POST` | `/v1/rollbacks` | Image rollback or `/data` rollback from `.bak.*`. | Async, returns op ID |

### 2.4 D1.6d — CP-side integration

D1.6d **does not add new agent endpoints.** It adds:

- A CP-side Go client for the agent's existing API (UDS / mTLS).
- Admin API endpoints inside the CP/proxy (with the existing `requireRole` and audit hooks) that proxy to the agent — operators authenticate to the CP, the CP connects to the agent.
- A **minimal admin surface** in the existing admin UI: operation list, current stack status, "create backup" / "restore" / "upgrade" / "rollback" buttons. **The full GUI UX for backup / restore / update / rollback (forms, wizards, diff views, scheduling, retention rules) is D2 territory and is not part of D1.6d.** D1.6d gets us "the agent is reachable from the GUI"; D2 makes that reach pleasant.
- Audit forwarding: agent audit events forwarded into the proxy's `audit.jsonl` for unified auditing.
- Operator documentation for migrating off the legacy `updater` sidecar.

### 2.5 Operation lifecycle (applies to all slices)

Async POSTs accept an optional `idempotency_key` field (opaque string, ≤ 128 chars). When provided, the agent computes a hash of `(actor, kind, idempotency_key)` and dedupes:

- If a matching op exists in `pending` / `running` state → return that op's `op_id` and current state (no new op started).
- If a matching op completed within the dedupe window (default 24h, configurable) → return the prior `op_id` and its terminal state.
- If no match → start a new op.

Without `idempotency_key`, every POST starts a fresh op. The CP/GUI is expected to use idempotency keys for operator-driven flows so an accidental double-click does not run restore or upgrade twice.

D1.6a defines and stores `idempotency_key` in the op record. D1.6b is the first slice with state-changing ops that actually need it. Behavior in D1.6a is "accept and store, no dedupe" — the field round-trips but does nothing. D1.6b adds dedupe semantics.

Async POSTs return immediately:

```json
{ "op_id": "01J0X3F…ULID", "state": "pending", "kind": "backup.create" }
```

Clients poll `GET /v1/operations/{id}`:

```json
{
  "op_id":            "01J0X3F…",
  "kind":             "backup.create",
  "state":            "running",
  "started_at":       "2026-05-02T12:14:00Z",
  "finished_at":      null,
  "actor":            "uid=1234,user=culvert-cp",
  "idempotency_key":  "cp-backup-20260502-pre-restore",
  "lock_held_by":     "01J0X3F…",
  "progress": [
    { "stage": "preflight",   "state": "succeeded", "started_at": "...", "ended_at": "..." },
    { "stage": "compose-run", "state": "running",   "started_at": "..." }
  ],
  "result": null
}
```

State machine: `pending → running → succeeded | failed | cancelled`. Terminal states populate `finished_at` and `result`. Stage timestamps are captured for every transition. The `lock_held_by` field references § 4.9.

## 3. Operation flows (forward-look only — implemented per slice)

Each flow is fully predetermined; the operator/CP cannot inject arbitrary steps. Flows are documented here for completeness; only the D1.6a flows (none — read-only) are implemented in the foundation slice.

### 3.1 Backup create — D1.6b

```
preflight  → resolve passphrase_ref to a value
           → validate filename matches ^culvert-.*\.tar\.gz\.enc$
           → check /backup is writable (smoke test via cli --list-restore-leftovers)
compose-run → docker compose --profile cli run --rm \
                 -e CULVERT_BACKUP_PASSPHRASE \
                 cli --encrypt --backup /backup/<filename>
verify     → re-list /backup, confirm new file present, size > 0
report     → record path, size, encryption metadata
```

### 3.2 Restore dry-run — D1.6b

Non-destructive; can run while proxy is up.

```
preflight   → confirm backup_path exists, mode valid, resolve passphrase_ref
compose-run → docker compose --profile cli run --rm \
                 -e CULVERT_BACKUP_PASSPHRASE \
                 cli --restore <backup_path> --mode <mode>
parse       → capture cli stdout (the D1.3b plan), surface in op logs
report      → guard outcomes (DP re-enrollment, TOTP rollback) parsed and surfaced
```

### 3.3 Restore commit — D1.6b (offline; the most operationally sensitive flow)

```
preflight   → confirm backup_path exists
            → confirm proxy is currently up (operator expectation)
            → confirm acknowledgments match guards
            → resolve passphrase_ref
            → emit pre-commit audit event
stack-stop  → docker compose down  (whole stack — see note below)
            → on failure: abort, do NOT run --confirm
compose-run → docker compose --profile cli run --rm \
                 -e CULVERT_BACKUP_PASSPHRASE \
                 cli --restore <backup_path> --confirm --mode <mode> [flags...]
            → on failure: stack stays down; surface error and recovery hint;
              the prior /data is preserved at /data.bak.<ts>-<pid> per D1.3b.2b.
              The agent does NOT auto-roll-back here — that's an explicit D1.6c feature.
stack-start → docker compose up -d
health-check → poll proxy /health and /ready up to health_check_timeout_sec
report      → final state, .bak path, op duration, health-check result
```

**Why `docker compose down` for the whole stack, not only `proxy`.**
Restore commit intentionally stops the whole stack — `proxy`, `clamav`, and
`updater` — for the duration of the `/data` swap, not just the `proxy`
service. The reason: while `/data` is being renamed under the
`proxy-data` volume, any sidecar still holding open file descriptors
into that volume can keep the old inode pinned, race against the
rename, or quietly write stale state through. The `updater` service
in particular mounts `proxy-data:/data:ro` and would silently observe
an inconsistent view mid-swap. A whole-stack stop avoids the
sidecar-interaction class of bug entirely; the few extra seconds of
downtime are a fair trade against the risk of partial-state confusion.
Narrower stop behavior (e.g. stop only `proxy` + `updater`, leave
`clamav` running because it doesn't share `proxy-data`) is a possible
optimization to revisit in a future slice if the downtime cost ever
matters; D1.6b ships the conservative whole-stack default.

### 3.4 Cleanup leftovers — D1.6b (runtime-OK)

```
preflight   → validate older_than (parsed time.Duration), keep_last (>= 0)
compose-run → docker compose --profile cli run --rm cli \
                 --cleanup-restore-leftovers --older-than <X> --keep-last <N> --confirm
report      → cli's structured output captured
```

### 3.5 Upgrade check — D1.6c (read-only)

```
local-inspect  → docker image inspect <current> → digest_local
remote-inspect → docker manifest inspect <target image_ref> → digest_remote
compare        → equal → "up-to-date"; else → "upgrade available", include both digests
```

#### 3.5.1 Harden follow-ups (deferred from the read-only check PR)

The first read-only-check PR (`POST /v1/upgrades/check`) ships with two known
limitations, deliberately deferred to the harden phase so the initial slice
stays small and reviewable. Both were raised in review and are tracked here:

- **Compare against the running image, not the target tag.** The shipped check
  inspects the *requested* `image_ref` locally, not the *currently-running*
  Compose image. If the target was already pulled but the stack still runs an
  older image (failed apply before restart, manual pull), the local/remote
  digests can intersect and the op log reports `up_to_date=true` even though
  the service was never restarted onto that digest. Resolving this requires a
  bounded way to inspect a status-derived image reference that is **not**
  constrained by `image_allowlist` — a new sudoers/validation surface. Land it
  with the upgrade-apply slice, which already needs the running-digest capture
  for pinning + rollback.
- **Propagate non-"not-found" local-inspect failures.** The shipped check
  swallows every `docker image inspect` error as `local_present=false`, which
  is only correct for the "image absent locally" case. A local inspect that
  fails because Docker is unavailable, sudoers is missing, or the stage times
  out is currently masked as a clean "absent" result, and the op still finishes
  `succeeded` with an inaccurate local view. Harden by distinguishing the
  "no such image" signature from environment/permission/timeout failures and
  surfacing the latter (op-log note + a degraded/uncertain marker; the op may
  still succeed since the remote answer remains valid).

### 3.6 Upgrade apply — D1.6c

```
preflight     → resolve image_ref against image_allowlist (§ 1.3)
                — by default ONLY ghcr.io/kidcarmi/culvert with a tag
                  or @sha256: digest
              → if image_ref is a tag (not a digest), resolve to a digest
                via `docker manifest inspect` and pin it for the rest of
                the operation (digest pinning is REQUIRED — § 3.6.1)
              → resolve passphrase_ref if pre_backup is true
pre-backup    → if pre_backup: invoke § 3.1 with filename pre-upgrade-<ts>.tar.gz.enc
              → on backup failure: abort upgrade, do NOT pull
pull          → docker compose pull proxy   (only the named service; uses pinned digest)
stack-restart → docker compose up -d        (recreate proxy with new image)
health-check  → poll /health and /ready up to health_check_timeout_sec
              → on failure AND rollback_on_failure: invoke § 3.7 with the
                prior image digest captured in preflight
report        → before/after image digests, pre-backup path, health result
```

Upgrade is opinionated: only the `proxy` service is pulled/restarted. `clamav`, `updater`, and `cli` are out of scope for the upgrade flow (separate release cadences).

#### 3.6.1 Production posture for upgrade

D1.6c ships with these defaults; weakening any of them is operator-explicit.

- **Pre-upgrade encrypted backup is the default and strongly recommended.** `pre_backup: true` is the API default. Operators who choose `pre_backup: false` accept the risk of no point-in-time fallback, and the audit event records "no pre-upgrade backup taken".
- **Image allowlist is required.** The agent **rejects** any `image_ref` that does not match `image_allowlist` (§ 1.3). The default accepts only `ghcr.io/kidcarmi/culvert:<tag>` or `ghcr.io/kidcarmi/culvert@sha256:<digest>`. Operators may broaden the allowlist in `config.toml` but cannot bypass it per-request.
- **Digest capture / pinning is required.** Tag-based `image_ref` is resolved to a digest in preflight, pinned for the rest of the op, and recorded in the op result. The same digest is the rollback target if the health gate fires. Tag-only upgrades that don't capture a digest are not supported.
- **Arbitrary registry/image refs are NOT accepted by default.** The default allowlist rejects e.g. `docker.io/library/alpine`. The audit event records the resolved digest, not just the supplied tag.
- **Signature verification is a future follow-up.** Cosign / Sigstore-style signature verification is queued for a later slice. Digest pinning gives bit-for-bit reproducibility once an allowed image is pulled the first time; signature verification adds the missing identity layer.

### 3.7 Rollback — D1.6c

Two modes, mutually exclusive per request:

```
mode=image:
  preflight     → captured prior digest from a recent upgrades.apply op
  pull          → docker pull <prior_digest>
  stack-restart → docker compose up -d (with prior digest pinned)
  health-check  → /health and /ready

mode=data:
  preflight     → identify target .bak.<ts>-<pid> (or operator-supplied)
  stack-stop    → docker compose down
  swap          → atomically rename /data → /data.failed.<ts>-<pid>
                  rename <selected .bak> → /data
  stack-start   → docker compose up -d
  health-check  → /health and /ready
```

Both modes audit-log the prior state path so operators can inspect or re-roll-back.

## 4. Security model

### 4.1 Command execution model (non-negotiable)

The agent's privilege boundary is enforced by an internal command runner, not by ad-hoc handlers. The runner contract is:

- **No shell.** No `sh -c`, no `bash -c`, no shell expansion, no globbing. The runner uses `exec.Cmd` with explicit `argv` only.
- **execve-style argv arrays only.** Every operation maps to a fixed `[]string` template; arguments are appended one at a time after validation. A mistyped argument cannot be split into a flag + value by the shell.
- **Fixed command templates.** Every endpoint resolves to one of a small number of templates (e.g. `["docker", "compose", "-f", <FILE>, "--profile", "cli", "run", "--rm", "-e", "CULVERT_BACKUP_PASSPHRASE", "cli", "--encrypt", "--backup", <FILENAME>]`). Templates live in code, not in config or in user input.
- **Validated bounded args.** Every variable position has a validator: filename regex (e.g. `^culvert-.*\.tar\.gz\.enc$`), enum membership (`mode ∈ {full, trust-root-only, state-only}`), path-prefix check (argument under `allowed_backup_dir` after `filepath.Clean`), duration parser, etc. Validation runs before the runner is invoked.
- **Fixed working directory.** Every `docker compose` invocation runs with `cwd = compose_project_dir` from `config.toml`. Cwd is set explicitly via `exec.Cmd.Dir`; relative-path tricks in operator-supplied args cannot escape it.
- **Environment allowlist.** The child process inherits a minimal env: `PATH`, `HOME`, `LANG`, `TZ`, plus an explicit allowlist of pass-through variables (`CULVERT_BACKUP_PASSPHRASE`, `CULVERT_CA_PASSPHRASE` if needed). The runner builds the env from scratch — `os.Environ()` is **not** inherited.
- **Bounded stdout/stderr capture.** Per-stage capture limit (default 1 MiB, configurable). Beyond the limit, capture truncates with a clear marker; full output already lives in `/var/lib/culvert-maint/operations/<op_id>.log` for on-disk inspection.
- **Per-command timeout.** Every `exec.Cmd` runs with a context-bound timeout from `stage_timeout` (or per-stage override). Timeout fires `SIGTERM` then `SIGKILL` 5s later; the operation transitions to `failed` with reason `timeout` and the partial output is preserved.
- **No operator-supplied compose paths.** The compose file is `<compose_project_dir>/<compose_file>`, both from config. Operators cannot pass `-f /tmp/whatever.yml` per-request.
- **No arbitrary docker args.** The runner only invokes `docker compose <SUBCOMMAND> [args]` with `<SUBCOMMAND>` from a closed set (`up`, `down`, `pull`, `ps`, `run`, `manifest inspect`, `image inspect`). Other subcommands are not reachable.

These rules apply uniformly across D1.6a–D1.6d and to any future operation. Adding a new command template or argument validator is a code review surface; "just pass the raw argv through" is not a permitted shortcut.

### 4.2 No arbitrary execution

External-facing restatement of what § 4.1 implies:

- **No** `/v1/exec`. **No** generic Docker API proxy. **No** endpoint that takes a shell command, a Dockerfile, or operator-supplied compose YAML.
- Every endpoint maps to a fixed operation backed by a § 4.1 template. Bounded args are validated before exec.
- Adding a new operation requires editing the agent source, updating the sudoers allowlist (§ 4.6), and shipping a new agent version. Operators cannot extend the surface at runtime.

### 4.3 Transport

- **Default**: Unix domain socket at `/run/culvert-maint.sock`, owner `culvert-maint:culvert-maint`, mode `0660`.
- **Optional (D1.6d)**: mTLS over loopback for containerized CP deployments where CP and agent share a network namespace but not a filesystem. Cert pinning with a CA the agent ships with the install; keys persisted under `/var/lib/culvert-maint/tls/` (mode `0700`).
- **Never**: agent listens on a non-loopback interface. `0.0.0.0` is not a configuration option.

### 4.4 Authentication

- **UDS path (default)**: `SO_PEERCRED` check on every connection. Allowlist is `culvert-cp` (CP service account). Anyone else gets `403`.
- **mTLS-on-loopback (optional, D1.6d)**: pinned client cert SAN must match `cp.culvert.local` or operator-configured equivalent. Cert rotation is operator-driven; no auto-rotation in D1.6.

### 4.5 Privilege model — sudoers + path-bound is the production default

The agent's `culvert-maint` user needs to invoke `docker compose`. D1.6a ships **two** modes selected by `privilege_mode` in `config.toml` (§ 1.3):

**`privilege_mode = "sudoers"` — production default.**
The `culvert-maint` user is **not** in the `docker` group. Instead, `/etc/sudoers.d/culvert-maint` allows `NOPASSWD` execution of a fixed list of `docker compose` invocations from `compose_project_dir` (§ 4.6). The agent's command runner (§ 4.1) prepends `sudo` to every templated invocation. `sudo`'s arg matching enforces that the agent cannot deviate from the allowlisted set, even with an in-process bug. Privilege is bounded to the exact set of compose commands the operations require.

**`privilege_mode = "docker_group_lab"` — dev / lab only, opt-in.**
The `culvert-maint` user is added to the `docker` group. **This is effectively root-equivalent** — anyone in the `docker` group can launch a container that bind-mounts `/` and edits arbitrary host files. This mode exists for fast iteration during development and lab demos; **it is not appropriate for any production deployment**. The agent emits a `WARN` log line on startup and a flag in `/v1/status` whenever `privilege_mode = "docker_group_lab"` is active. Documentation and packaging both surface this.

Plan:

- **D1.6a ships both modes.** Default is `"sudoers"`. The sudoers allowlist (§ 4.6) is initially populated with **only** the minimal read-only `docker compose ps` entry needed by `/v1/status`; it grows incrementally as D1.6b/c add operations.
- **D1.6b and D1.6c** add operations and matching sudoers entries together (§ 4.6 contract).
- **`.deb` / `.rpm` packaging** (when it ships) defaults `privilege_mode = "sudoers"`. Overriding to `"docker_group_lab"` is an explicit operator action.

The systemd unit applies kernel-level hardening regardless of mode: `User=culvert-maint`, `Group=culvert-maint`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `NoNewPrivileges=true`, `RestrictNamespaces=true`, `MemoryDenyWriteExecute=true` (where compatible). The agent **never** runs as `root`.

### 4.6 Sudoers allowlist contract

`/etc/sudoers.d/culvert-maint` is part of the install from D1.6a. Each operation's exact command line is added to the allowlist as the operation lands. The allowlist file is the **single source of truth** for which `docker compose` invocations the agent can run.

The contract for adding a new operation is:

1. **Typed API handler** in the agent (handler signature pinned, no `interface{}` payloads for argv).
2. **Command template** in the runner (§ 4.1), with explicit argv and argument validators.
3. **Sudoers allowlist entry** — exact-match line in `/etc/sudoers.d/culvert-maint`. Wildcards are minimized to validated argument positions.
4. **Tests** — unit tests for the validators, integration tests that exercise the full handler-to-runner path against a fixture compose project, and a static-analysis test that asserts every template in the runner has a matching sudoers entry (and vice versa).

Skipping any of the four is a review block. Operations cannot land partially.

**D1.6a sudoers scope is minimal — read-only `compose ps` only.**
The sudoers file shipped with D1.6a contains a **single** entry, sufficient for `/v1/status` to query the running stack:

```
culvert-maint ALL=(root) NOPASSWD: /usr/bin/docker compose -f /<compose_project_dir>/<compose_file> ps
```

(Path components are bound to the values in `config.toml` at install time; no wildcards on the project dir.)

There are **no** backup, restore, cleanup, upgrade, rollback, `up`, `down`, `pull`, or `manifest inspect` entries in the D1.6a sudoers file. Those entries land **with** their corresponding operations:

- **D1.6b** adds entries for `run --rm cli --backup`, `run --rm cli --restore`, `run --rm cli --restore --confirm`, `run --rm cli --cleanup-restore-leftovers`, and `up -d` / `down`.
- **D1.6c** adds `pull proxy` and `manifest inspect <allowed-image>`.

Each operation's sudoers entry lands in the same PR as the matching handler + template + tests (§ 4.6 contract). A D1.6a installation cannot perform any state-changing operation, even if the agent had a bug, because the sudoers file simply doesn't allow the underlying command line.

### 4.7 Passphrase handling

Passphrases never appear in API requests. The CP and the agent agree on a **reference**:

- `env:NAME` — the agent reads `os.Getenv(NAME)` from its own process env.
- `file:/path` — the agent reads from a file it has read access to.

The agent reads the value at the moment of exec (`-e CULVERT_BACKUP_PASSPHRASE` forwarding to the cli container) and **never serializes it**. Audit log entries record the *reference*, never the value. The command runner's environment allowlist (§ 4.1) enforces that the passphrase env var is the only secret-class variable forwarded; everything else is filtered out.

This mirrors the D1.4 / D1.5 contract: passphrases never appear in argv, in `docker compose logs`, or in any structured output.

### 4.8 Audit (stable schema from D1.6a)

The audit schema is **stable from D1.6a**. Future slices may add optional fields but cannot rename or remove existing ones.

| Field | Type | Required | Purpose |
|---|---|---|---|
| `ts` | RFC 3339 timestamp (UTC) | yes | Event time. |
| `actor` | string | yes | UID + username of the connecting peer (`uid=1234,user=culvert-cp`). For mTLS-on-loopback, the cert SAN. |
| `op_id` | ULID string | yes | Operation this event belongs to. |
| `kind` | enum string | yes | Operation kind (`backup.create`, `restore.commit`, `upgrade.apply`, etc.). Closed set. |
| `params` | object | yes | Operation parameters. **Secrets appear only as references** (`passphrase_ref: "env:CULVERT_BACKUP_PASSPHRASE"`); never as values. |
| `outcome` | enum string | yes | `started` (admission), `succeeded`, `failed`, `cancelled`. |
| `outcome_at` | RFC 3339 timestamp (UTC) | yes for terminal events | When the outcome was recorded. Null for `started`. |
| `failure_reason` | string | yes when `outcome = failed` | Stable, parseable reason: `timeout`, `validation`, `auth`, `health_failed`, `cli_error`, `command_error`, `concurrency_conflict`, `agent_restart_interrupted`. |
| `idempotency_key` | string | optional | If the request supplied one. |

Sample entries:

```json
{
  "ts":              "2026-05-02T12:14:00Z",
  "actor":           "uid=1234,user=culvert-cp",
  "op_id":           "01J0X3F…",
  "kind":            "backup.create",
  "params":          { "encrypt": true, "passphrase_ref": "env:CULVERT_BACKUP_PASSPHRASE", "filename": "culvert-…tar.gz.enc" },
  "outcome":         "started",
  "outcome_at":      null,
  "idempotency_key": "cp-prerestore-20260502T1214Z"
}
{
  "ts":             "2026-05-02T12:14:42Z",
  "actor":          "uid=1234,user=culvert-cp",
  "op_id":          "01J0X3F…",
  "kind":           "backup.create",
  "params":         { "encrypt": true, "passphrase_ref": "env:CULVERT_BACKUP_PASSPHRASE", "filename": "culvert-…tar.gz.enc" },
  "outcome":        "succeeded",
  "outcome_at":     "2026-05-02T12:14:42Z"
}
```

Storage: append-only `/var/lib/culvert-maint/audit.jsonl` (mode `0640`). Rotation is internal to the agent (rotated by file size; default 100 MiB → `audit.jsonl.1`, `…2`, etc.; pruned past `log_retention_days`). Never overwritten in place. **Secrets never appear in audit** — the schema does not have a value field for passphrases or certificates; the runner refuses to log argv that would include a secret.

### 4.9 Concurrency / global maintenance lock

The agent runs **at most one state-changing operation at a time**. State-changing means any op kind that mutates `/data`, `/backup`, the running compose stack, or the agent's persistent state.

| Op kind | State-changing? | Lock behavior |
|---|---|---|
| `backup.create` | yes | Acquires the lock for the duration. |
| `restore.dryrun` | no | Read-only; runs concurrently with other read-only ops. |
| `restore.commit` | yes (exclusive) | Acquires the lock; refuses to start if **any** other op holds it. |
| `cleanups.create` | yes | Acquires the lock. (Even though cleanup is "runtime-OK" for the proxy, the agent serializes its own ops.) |
| `upgrades.check` | no | Read-only. |
| `upgrades.apply` | yes (exclusive) | Acquires the lock. |
| `rollbacks.create` | yes (exclusive) | Acquires the lock. |
| `GET /v1/health`, `/v1/status`, `/v1/audit`, `/v1/operations/*` | no | Always concurrent. |

The lock is a single in-memory mutex protecting the active-op slot. On acquisition, the agent records `lock_held_by = <op_id>` in the operation record. On release (terminal state), the slot is freed.

When a state-changing POST arrives and the lock is held:

- The agent returns **HTTP 409 Conflict** with a body that includes the holding op's `op_id`, `kind`, `started_at`, and `actor`.
- The audit log records the rejection with `outcome = failed`, `failure_reason = concurrency_conflict`.
- Idempotency-key dedupe (§ 2.5) runs **before** the lock check, so a duplicate of an already-running op short-circuits to the existing `op_id` instead of returning 409.

`restore.commit` and `upgrades.apply` are explicitly mutually exclusive — neither can start while the other is running, even though the lock would already prevent it. This is documented for clarity.

## 5. Persistence / state model

### 5.1 D1.6a — simple files

```
/var/lib/culvert-maint/
├── operations/
│   └── <op_id>.log     # per-op stdout/stderr captures
├── audit.jsonl         # append-only audit log; rotated by file size
├── state.json          # optional: small JSON file with last-known status
│                       # (last-op-of-each-kind summary for /v1/status)
└── config.toml         # operator-controlled config (allowlists, retention)
```

D1.6a uses **simple persistence** — flat files plus active-operation tracking in memory. No database. Rationale:

- Active operations (`pending`, `running`) live in process memory. On agent restart, in-flight ops are marked `failed` with reason "agent restarted"; this is correct behavior because the underlying `docker compose` invocation was interrupted.
- Completed operations are looked up from `operations/<op_id>.log` plus an in-memory index rebuilt at startup by listing the directory. Bounded by retention policy (default 30 days).
- `state.json` is optional — can be regenerated from the audit log + on-disk op logs at startup.

### 5.2 SQLite — deferred option

SQLite is **not mandatory for D1.6a**. It can be revisited if D1.6b or D1.6d shows that:

- Indexed history queries dominate (e.g. "show me all upgrades in the last 30 days that failed at the health-check stage").
- Concurrent reads from the GUI's polling client compete with the op writer in a way flat files don't handle well.

If SQLite is added later, it is an additive option: the agent gains a config knob `state.backend = "files" | "sqlite"`, defaulting to `"files"`. No external service.

### 5.3 Retention

Default 30 days for `operations/<op_id>.log` and audit.jsonl. Configurable via `log_retention_days` in `config.toml` (§ 1.3). Rotation is internal to the agent; no external `logrotate` dependency.

### 5.4 Timeout and restart behavior

**Operation timeout.** The default `operation_timeout` from `config.toml` (default 30m) is the hard ceiling on a single op. When exceeded, the agent cancels in-flight stages, transitions the op to `failed` with `failure_reason = timeout`, and releases the maintenance lock.

**Stage timeout.** The default `stage_timeout` (default 5m) bounds an individual stage. A stage timing out fails the stage; the operation may continue, fail, or run a cleanup stage depending on the flow's contract. The runner sends `SIGTERM` to the child process, then `SIGKILL` after a 5-second grace, and preserves whatever stdout/stderr was captured before termination.

**Agent restart mid-operation.** If the agent crashes, is killed, or is restarted while an operation is `pending` or `running`:

- On startup, the agent scans its state directory for any operations still marked `pending` / `running`.
- Each is transitioned to `failed` with `failure_reason = agent_restart_interrupted` and `finished_at = startup time`.
- The maintenance lock is released (the new agent process owns a fresh lock).
- The op log file is preserved as-is; operators can read whatever stages had completed before interruption.
- The agent **never guesses** that an operation succeeded after restart. Even if `docker compose run --rm cli --backup` had completed and produced a backup file on disk, the operation record is still marked `failed` because the agent has no way to verify the post-completion stages (`verify`, `report`) actually ran.
- Operators inspecting recovery use `/v1/operations/{id}/logs` to see how far the op got; they may then re-run the operation explicitly.

**No automatic resume.** Operations are not resumable. If a restore commit was interrupted between rename A and rename B, the recovery is operator-driven (the cli's error message names the exact `mv` recovery command per the D1.3b.2b contract).

## 6. Observability

### 6.1 Operation IDs

ULID (lexicographically sortable, time-prefixed). Returned by every async POST. Used as the primary key in operation storage and as the operator-facing reference (`"operation 01J0X3F… failed at stage compose-run"`).

### 6.2 Progress

Each operation has a fixed list of stages (per § 3 flows). Stages transition `pending → running → succeeded | failed | skipped`. Stage timestamps are captured. A stage's `output` field can carry small structured data (parsed cli stdout, etc.) up to a bounded size; oversized output goes to the per-op log file.

### 6.3 Logs

Per-operation log file at `/var/lib/culvert-maint/operations/<op_id>.log` captures:

- Each stage's stdout/stderr from `docker compose` invocations.
- Each cli sub-process's full output (sanitized; passphrase never present).
- Health-check probe results.

`GET /v1/operations/{id}/logs` streams this file.

### 6.4 Last-operation summary

`GET /v1/status` returns the last completed op of each kind (last backup, last restore, last upgrade, etc.) so the GUI/CP can render dashboard tiles without paging through history.

### 6.5 Health-check primitives (D1.6b onward)

Reusable across `restores.commit`, `upgrades.apply`, `rollbacks`. Because the agent is a host-side systemd service, it does **not** rely on Docker-network container DNS. Health checks use the host-published endpoint from the compose config, defaulting to `http://127.0.0.1:<published-port>/health` and `/ready`. The endpoint is configurable in `/etc/culvert-maint/config.toml` (host, port, scheme — useful when the proxy port has been remapped or the operator fronts it with a TLS terminator).

- `GET http://127.0.0.1:<published-port>/health` — must be 200.
- `GET http://127.0.0.1:<published-port>/ready` — must be 200 with `status:"ready"`.
- Optional: a smoke probe (one outbound HTTP through the proxy) — D1.6c.

Per-probe and total timeouts are operator-configurable per request.

## 8. HA / cluster future posture (light touch)

D1.6 standalone-CP is the focus. Cluster posture is documented but **not** implemented in any D1.6 slice.

When the cluster slice arrives (D1.7-or-later):

- Each CP and DP node runs its own local Maintenance Agent. Agents do not coordinate among themselves.
- The CP orchestrates fleet operations by talking to the **local** agent on each target node — a CP-side fan-out from one operator command to N agent calls. There is no cross-host agent dial.
- DP upgrades are rolling, one node at a time, with health gating between nodes.
- HA CP upgrades follow the standby-first pattern: standby is upgraded → health-gated → promoted via failover → old active is upgraded → re-paired.
- Error budget: a configurable threshold of failed nodes halts a fleet rollout.

D1.6's API is shaped so cluster orchestration can be added without breaking existing endpoints — the CP-side client gains a "fleet" facade that fans out to per-node agent calls. The agent stays single-host.

## 10.1 Documented D1.6a limits (operator-visible behaviors deferred to later slices)

These are not bugs — they are deliberate D1.6a scope boundaries. Listing them here so operators reading the plan see the contract surface that's already pinned vs. the surface that grows in D1.6b/c/d.

- **`/v1/audit` reads the full audit.jsonl file.** D1.6a uses retention-day pruning + size-based rotation internally; the reader is a single-pass full-file scan. For typical operator deployments this is bounded (audit grows with operation count, not request count). If operators run thousands of ops per day for sustained periods, log_retention_days should be tightened or a tail-mode parser added in a follow-up slice. Tracked under `log_retention_days`.
- **`/v1/operations/{id}/logs` streams the entire op log file with no built-in size cap.** Per-op log files inherit the runner's bounded-capture cap (default 1 MiB stdout + 1 MiB stderr) so the worst case per op is small. A future `?tail=N` query parameter or HTTP Range support is a D1.6b/c improvement, not a D1.6a contract.
- **Audit on read-only API requests is intentionally not emitted.** D1.6a audits state-changing requests only (which D1.6a doesn't have any of yet). Read traffic on `/v1/health`, `/v1/status`, `/v1/audit`, `/v1/operations/*` is high-volume and low-signal; auditing it would generate noise without a corresponding security gain. The CP-side admin API in D1.6d will continue to audit *operator* actions (who clicked what) at its own layer, not the agent's per-request layer.
- **`NoNewPrivileges=true` is intentionally NOT set in the systemd unit.** `privilege_mode=sudoers` (the production default) requires `sudo -n docker compose ...`, and sudo's setuid escalation does not work under `PR_SET_NO_NEW_PRIVS`. The trade-off is bounded: the sudoers allowlist is the privilege boundary, and the rest of the systemd hardening (`ProtectSystem=strict`, `PrivateTmp`, `ProtectKernelTunables`, `MemoryDenyWriteExecute`, etc.) still applies. A future hardening pass may move to `RuntimeDirectory=culvert-maint` for a tighter `/run/culvert-maint/` socket path; tracked there.
- **`/run/culvert-maint.sock` lives directly under `/run`.** D1.6a's `ReadWritePaths=/var/lib/culvert-maint /run` is the broadest hardening compromise that lets `/run` socket creation work. A `RuntimeDirectory=culvert-maint` follow-up moves the socket to `/run/culvert-maint/culvert-maint.sock` with a managed parent directory.

## 11. Open questions for the implementation slices

Captured here so reviewers can flag concerns now; none gate this design.

Several earlier open questions are now resolved by the production-grade posture:

- **Privilege mode** — resolved. `privilege_mode = "sudoers"` is the D1.6a default; `"docker_group_lab"` is opt-in dev/lab only and warned-on at startup. See § 4.5.
- **Image allowlist** — resolved. Default `^ghcr\.io/kidcarmi/culvert(:[A-Za-z0-9._-]+|@sha256:[a-f0-9]{64})$`; operator-configurable in `config.toml`. See § 1.3 + § 3.6.1.
- **Audit schema stability** — resolved. Schema locked from D1.6a per § 4.8.
- **Idempotency** — resolved. Field added in D1.6a; dedupe semantics activate in D1.6b. See § 2.5.

Remaining open:

1. **State backend** — D1.6a is files-only. SQLite revisit when D1.6b/d reveals a query pattern that warrants it. **Defer.**
2. **Progress streaming** — SSE vs WebSocket vs poll-only. Polling is simpler for D1.6a–c; SSE only if D1.6d shows the GUI needs sub-second updates. **Defer.**
3. **Cancellation** — cancel an in-flight op? Restore commit is uncancelable mid-swap; backup is cancelable up to the point the cli container starts; upgrade is cancelable up to `docker compose pull` completing. **Detail per-op in D1.6b.**
4. **Multi-file compose overlays** — D1.6a is single-file. Operators using `-f a.yml -f b.yml` need a future slice that broadens `compose_file` to a list. **Confirm demand before D1.6b kickoff.**
