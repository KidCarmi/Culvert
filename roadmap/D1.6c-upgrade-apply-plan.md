# D1.6c — Upgrade Apply / Rollback: Focused Implementation Plan

**Status:** PLAN ONLY. No code, no sudoers changes, no endpoint activation, no
apply/rollback implementation lands with this document. `POST /v1/upgrades/apply`
and `POST /v1/rollbacks` remain `404` (server.go `notImpl` list) until their
implementation slices ship.

**Scope of this doc:** turn the §3.6/§3.7 sketches in
`D1.6-maintenance-agent-implementation-plan.md` into a build-ready spec for the
first *destructive* maintenance operation, with the failure modes and the
running-image-digest problem worked through before any code is written.

**Builds on what already shipped:**
- `upgrades.check` (read-only) — `handlers_upgrade.go`, op kind `upgrades.check`,
  templates `compose.image.inspect` + `compose.manifest.inspect`.
- D1.6b state-changing plumbing — `compose.up` (`up -d`), `compose.down`,
  backup/restore templates, the maintenance lock, `startAsyncOp`, the
  orchestrator (`internal/ops/orchestrator.go`), and the health probe
  (`internal/health`).

> **Non-negotiable carry-forward from PR #351.** The apply slice must compute
> the upgrade verdict from the **actually-running container's image digest**,
> captured at apply time. It must **not** trust `local_cache_up_to_date` from
> `upgrades.check` — that flag only compares the requested ref against the local
> image cache and reports `true` for a pulled-but-not-restarted stack. See
> [§1](#1-current-running-image-digest-capture) and
> [§11](#11-carry-forward-351--running-image-comparison).

## 0. Operation shape (recap)

```
POST /v1/upgrades/apply
{
  "image_ref":            "ghcr.io/kidcarmi/culvert:v1.2.4",   // tag or @sha256: digest
  "pre_backup":           true,                                 // default true
  "passphrase_ref":       "env:CULVERT_BACKUP_PASSPHRASE",      // required iff pre_backup
  "rollback_on_failure":  true,                                 // default true
  "idempotency_key":      "cp-upgrade-20260604T1200Z"           // optional
}
```

- Op kind: `upgrades.apply` (plural, matching `upgrades.check`).
- State-changing, **exclusive** (mutually exclusive with `restore.commit`).
- Opinionated: only the `proxy` service is pulled/restarted. `clamav`, `cli`,
  `updater` are out of scope.

`POST /v1/rollbacks` (kind `rollbacks.create`) is specified in
[§5](#5-rollback-preconditions); image-mode rollback is the auto-invoked path
when the apply health gate fires.

## 1. Current running image digest capture

This is the heart of the slice and the #351 carry-forward. The agent must learn
**which image digest the running `proxy` container is actually executing** — not
what a tag currently resolves to in the local cache.

### 1.1 Why `compose ps` alone is insufficient

`internal/status` already runs `docker compose ps --format json`, but the parsed
`composePSEntry` exposes only `Image` (a name/tag string, e.g.
`ghcr.io/kidcarmi/culvert:v1.2.3`). Resolving that tag with
`docker image inspect <tag>` returns the image the **tag currently points to in
the local cache**, which can differ from what the container started with if the
tag was re-pulled after the container launched. That is exactly the trust gap
PR #351 refused to paper over.

### 1.2 Authoritative capture (chosen mechanism)

Capture the running container's **immutable image content digest**, then resolve
its registry digest:

1. `docker compose ps --format json` → locate the `proxy` service entry. Extend
   the parsed struct to also read the container **`ID`** field (compose ps JSON
   includes it; today's `composePSEntry` ignores it). Validate exactly one
   running `proxy` container; zero or many is a capture failure (see
   [§9](#9-failure-modes-and-recovery)).
2. `docker inspect --format '{{json .Image}}' <container_id>` → the container's
   image **config digest** (`sha256:…`). This is bound to the running container
   and cannot drift under a moving tag.
3. `docker image inspect <that image id>` (existing `compose.image.inspect`
   template, reusing the #351 digest-extraction helper) → the image's
   `RepoDigests`. **Capture the full `repo@sha256:…` RepoDigest reference**, not
   the bare `sha256:…` digest: `docker compose pull` / `up` (and any `CULVERT_PROXY_IMAGE`
   override) require a `NAME[:TAG|@DIGEST]` reference — a bare digest is not a
   valid image ref and would point at no repository (Docker `docker image pull`
   ref format). This full ref is the comparison basis and the **rollback pin**.

> **Image-ref convention (applies throughout this doc).** Fields named
> `*_digest` (e.g. `prior_digest`, `resolved_digest`) carry the bare `sha256:…`
> form **for display/audit only**. Every value used as an *image reference* — a
> pin, a `CULVERT_PROXY_IMAGE` override, a `pull`/`up` target — MUST be the full
> `repo@sha256:…` ref (named `*_ref`: `prior_ref`, `target_ref`). The repo is
> always the allowlisted `image_ref`'s repository; the agent constructs
> `<repo>@<digest>` rather than ever pulling/overriding with a bare digest.

The captured `prior_ref` (full `repo@sha256:…`), `prior_digest` (bare, for
display), and `prior_image_id` (local config digest) are recorded in the op
result and audit; **`prior_ref`** is the rollback pin.

### 1.3 New surfaces this requires

- **Runner template** `compose.container.inspect` →
  `docker inspect --format {{json .Image}} <container_id>`. One bounded variable
  position (`<container_id>`), validated by a new `validateContainerIDShape`
  (`^[a-f0-9]{12,64}$` — docker container IDs are hex). Read-only,
  `StateChanging: false`.
- **`compose ps` parse extension** in `internal/status` (and/or a dedicated
  capture helper in the runner) to surface the container `ID`. Keep the status
  endpoint's behavior unchanged; only add the field.
- **Sudoers entries** — see [§8](#8-sudoerstemplate-additions).

> `docker inspect` is a *different binary surface* from `docker compose`. Its
> sudoers entry must be exact-match on the format string and a bounded container
> id, never a free `docker inspect *`.

### 1.4 Op-log hygiene (carried from #351)

The `capture_running` stages must write **parsed digests only** to the op log,
never the raw `docker inspect` / `docker image inspect` JSON (which carries
`Config.Env`, labels, build metadata). Reuse the #351 pattern: emit
`capture_running: running_digest=<…> running_image_id=<…>`, preserve stderr for
diagnosis.

## 2. Target image validation and digest pinning

### 2.1 Validation (two layers, same as check)

1. **Argv-safety shape** — `runner.ValidateImageRef` (`validateImageRefShape`,
   already shipped).
2. **Policy** — `image_allowlist` regex from `config.toml`. Default accepts only
   `ghcr.io/kidcarmi/culvert:<tag>` or `…@sha256:<digest>`. Rejection → `400`
   before any runner method / sudo. Same gate `upgrades.check` uses.

### 2.2 Pinning

- If `image_ref` is already `…@sha256:<digest>`, that digest is the pin.
- If `image_ref` is a tag, resolve it to a digest in preflight via the existing
  `compose.manifest.inspect` template and pin `image_ref@sha256:<digest>` for the
  remainder of the op. Tag-only upgrades that skip digest capture are **not
  supported** (§3.6.1 of the master plan).
- The pinned digest is recorded in the op result and audit (`resolved_digest`),
  and is the bit-for-bit identity that `pull` + `up` must land.

### 2.3 Making compose honor the pinned digest (packaging precondition)

`docker compose pull proxy` / `up -d` pull whatever the **compose file** names.
To pin a digest, the compose file's `proxy.image` must be overridable via an
environment variable the agent controls. **Shipped** (`docker-compose.yml`):

```yaml
proxy:
  image: ${CULVERT_PROXY_IMAGE:-ghcr.io/kidcarmi/culvert:latest}
# the profile-gated `cli` service shares the SAME override so the backup/
# restore CLI never version-skews from the running daemon (D1.5 invariant).
```

The agent forwards the pinned `CULVERT_PROXY_IMAGE=ghcr.io/kidcarmi/culvert@sha256:…`
through the **environment allowlist** (§4.1) for the `pull` and `up` stages.
`CULVERT_PROXY_IMAGE` is **already in the runner env allowlist**
(`runner.EnvCulvertProxyImage`, wired in `main.go`) so the future pull/up path
can forward it; nothing forwards it yet and no read-only path carries it
(proven by `env_proxy_image_test.go`).

**Precondition status — ✅ all shipped:** (1) compose parameterization; (2) runner
env allowlist entry (overlay-only); (3) sudo env-preservation (§2.3.1) — the
`Defaults:culvert-maint env_keep += "CULVERT_PROXY_IMAGE"` line shipped with the
apply slice (the `ComposePull` / `ComposeUpWithImage` overlay forwards the pin).
The same slice also added `env_keep` for `CULVERT_BACKUP_PASSPHRASE` — without it
encrypted backup (and pre-upgrade backup) under `privilege_mode=sudoers` never
received the passphrase.

#### 2.3.1 Env preservation across `sudo` (REQUIRED — and it IS a sudoers change)

Setting `CULVERT_PROXY_IMAGE` in the runner's child env is **not sufficient** in
`privilege_mode=sudoers`. The runner prepends `sudo -n` (`runner.go` `buildArgv`),
and `sudo`'s default `env_reset` strips the child environment before exec'ing
`docker compose` — so the variable set on the `sudo` process never reaches
`docker compose`, `pull`/`up` silently use the compose-file default tag, and the
op lands in the **healthy-but-old-image** failure path (F11). The installed
`/etc/sudoers.d/culvert-maint` currently has **no** `env_keep`/`SETENV` directive.

Therefore the override needs an **explicit env-preservation mechanism**, chosen at
implementation time:

- **Option A — sudoers `env_keep` (recommended).** Add to the rendered sudoers
  file:
  ```
  Defaults:culvert-maint env_keep += "CULVERT_PROXY_IMAGE"
  ```
  This IS a sudoers change and rides the apply slice under the §4.6 four-part
  contract (and the parity test must learn to allow/verify the `Defaults` line).
  Bounded: only this one variable, only for the `culvert-maint` user.
- **Option B — `sudo --preserve-env=CULVERT_PROXY_IMAGE`.** A runner change
  (extend `buildArgv` to emit `--preserve-env=<name>` for the pull/up templates).
  No `Defaults` line, but it widens the runner's sudo invocation surface and must
  be scoped to exactly the one variable. Its own security review.

> **Correction to an earlier draft:** forwarding `CULVERT_PROXY_IMAGE` is **not**
> "just an env-allowlist change." Env preservation through `sudo` is required and
> is a privilege-boundary change (sudoers `env_keep` or a scoped `--preserve-env`).
>
> **Verify the existing `CULVERT_BACKUP_PASSPHRASE` path while here.** The backup/
> restore templates rely on `docker compose run -e CULVERT_BACKUP_PASSPHRASE`,
> which reads the variable from `docker compose`'s own environment — the **same**
> sudo-`env_reset` exposure. The sudoers file has no `env_keep` for it either, so
> the apply-slice work must confirm whether encrypted backup actually receives the
> passphrase under strict sudoers mode (and, if not, fix it the same way). Tracked
> as a precondition, not assumed working.

> **Open packaging item (must land with — or before — the apply impl slice):**
> ship a compose file that parameterizes `proxy.image`, add `CULVERT_PROXY_IMAGE`
> to the runner env allowlist, **and** add the env-preservation mechanism above.
> Without all three, "pinning" is cosmetic — compose would re-pull the moving
> tag. Called out here so it is not discovered mid-implementation. Alternative
> considered and rejected: writing a generated digest-override compose fragment
> per-op (more moving parts, more failure surface than a single env var).

## 3. Maintenance lock behavior

Reuse the existing in-memory exclusive lock (§4.9 of the master plan):

- `upgrades.apply` and `rollbacks.create` are **state-changing, exclusive**.
- Idempotency-key dedupe runs **before** the lock check: a duplicate of a running
  apply short-circuits to the existing `op_id`, not a 409.
- If the lock is held, `POST` returns **409 Conflict** with the holder's
  `op_id`, `kind`, `started_at`, `actor`; audit records `outcome=failed`,
  `failure_reason=concurrency_conflict`.
- `upgrades.apply` ⟂ `restore.commit` mutual exclusion is automatic via the lock;
  documented explicitly.
- The lock is held across the **entire** apply flow including an auto-rollback —
  a rollback triggered by a failed health gate runs **inside** the apply op's
  lock tenure, not as a second lock acquisition.

## 4. Health-gated apply flow

Stages map onto the existing orchestrator (`FlowStage`, `ContinueOnError`,
per-stage `FailureReason`). Health gating reuses `internal/health.Probe`
(`/ready` polled to a budget, `/health` one-shot; `Result.Failed() == !ReadyOK`).

```
preflight        → validate image_ref (shape + allowlist)
                 → resolve+pin digest (manifest inspect if tag)
                 → resolve passphrase_ref if pre_backup
capture_running  → §1: capture prior running container digest (proxy)
                 → compute authoritative running-vs-target verdict (§11)
                 → if already on target digest: SHORT-CIRCUIT to "succeeded,
                   no-op" (no pull/restart); record already_current=true
pre_backup       → if pre_backup: invoke backup template, filename
                   pre-upgrade-<ts>.tar.gz.enc
                 → on backup failure: ABORT (do not pull/restart). FailureReason
                   cli_error/command_error. No state changed yet.
pull             → CULVERT_PROXY_IMAGE=<pinned> docker compose pull proxy
stack_restart    → CULVERT_PROXY_IMAGE=<pinned> docker compose up -d
health_gate      → health.Probe.Run; ReadyOK gates
                 → on success: capture post digest, verify == pinned target
                 → on failure AND rollback_on_failure: run rollback_inline (§5)
report           → assemble op result (§6)
```

- `capture_running`, `report` are `ContinueOnError` so a summary/result is always
  emitted. `pre_backup`, `pull`, `stack_restart`, `health_gate` are hard-gating
  (a failure short-circuits subsequent normal stages per the orchestrator's
  `firstErr` logic).
- **Post-restart digest verification:** after a healthy restart, re-run §1
  capture and assert the running digest now equals the pinned target. A healthy
  stack still running the *old* digest (e.g. compose didn't pick up the override)
  is a `health_failed`-class failure, not a success — this closes the #351 gap on
  the *output* side too.

## 5. Rollback preconditions

### 5.1 Inline (auto) rollback — image mode

Triggered only when: `rollback_on_failure == true` **and** the health gate
failed **and** `prior_digest` was successfully captured in `capture_running`.

Preconditions (all required; if any unmet, do NOT attempt rollback — fail the op
with the original `health_failed` reason and a clear op-log note that rollback
was skipped and why):
- `prior_ref` (full `repo@sha256:…`) is present and well-formed (a bare digest
  is insufficient — see the image-ref convention in §1.2).
- the prior image is locally present **or** re-pullable (it was running moments
  ago, so the image is in the local store unless pruned mid-op).

Flow (image mode, runs inside the apply lock):
```
pull (prior)     → CULVERT_PROXY_IMAGE=<prior_ref> docker compose pull proxy
stack_restart    → CULVERT_PROXY_IMAGE=<prior_ref> docker compose up -d
health_gate      → health.Probe.Run
```
- Rollback success → op terminal state `failed` with `failure_reason=health_failed`
  but `result.rollback.succeeded=true` (the **upgrade** failed; the **service**
  is back on the known-good image). The distinction lives in the result, not the
  state.
- Rollback failure → terminal `failed`, `failure_reason=rollback_failed`
  (**new** reason — see [§6.3](#63-failure-reason-additions)); op-log + audit
  carry the prior/target digests and the stack's last-known state. **No further
  auto-action**; this is an operator-paging condition.

### 5.2 Standalone rollback endpoint — `POST /v1/rollbacks`

Per §3.7 of the master plan, two mutually-exclusive modes:
- **`mode=image`** — operator supplies (or the agent recalls from a recent
  `upgrades.apply` op result) a prior digest; same pull→up→health flow as §5.1.
- **`mode=data`** — `down` → atomically rename `/data` → `/data.failed.<ts>-<pid>`
  and a selected `.bak` → `/data` → `up` → health. This has a **stack-down +
  filesystem-swap window** ([§9](#9-failure-modes-and-recovery)).

Standalone rollback is its own op kind (`rollbacks.create`), its own lock tenure,
its own audit/result. This plan specifies image-mode in service of apply; data-mode
detail rides with the rollback impl slice.

## 6. Audit events

Uses the **stable schema** (§4.8). No renamed/removed fields.

### 6.1 Events

| `kind` | `outcome` | When |
|---|---|---|
| `upgrades.apply` | `started` | On admission (after dedupe + lock acquired). |
| `upgrades.apply` | `succeeded` | Healthy on target digest (or already-current no-op). |
| `upgrades.apply` | `failed` | Any gating-stage failure; `failure_reason` set. |
| `upgrades.apply` | `failed` (`concurrency_conflict`) | Lock held by another op. |

### 6.2 `params` (secrets only as references)

```json
{
  "image_ref":           "ghcr.io/kidcarmi/culvert:v1.2.4",
  "resolved_digest":     "sha256:…",
  "prior_digest":        "sha256:…",
  "pre_backup":          true,
  "passphrase_ref":      "env:CULVERT_BACKUP_PASSPHRASE",
  "rollback_on_failure": true
}
```
`passphrase_ref` is a **reference**, never a value (§4.7). The runner refuses to
log argv that would include a secret.

### 6.3 Failure-reason additions

Existing reasons cover most paths (`timeout`, `validation`, `health_failed`,
`cli_error`, `command_error`, `concurrency_conflict`, `agent_restart_interrupted`).
**Propose one additive value:** `rollback_failed` — the upgrade health gate fired
and the subsequent rollback also failed its health gate (the worst case; distinct
from `health_failed` so dashboards/alerts can page on it specifically). Additive
to the stable set per §4.8 ("future slices may add optional fields/values but
cannot rename or remove existing ones").

## 7. Operation log / result contract

### 7.1 Structured `result` (on the op record / `GET /v1/operations/{id}`)

```json
{
  "image_ref":          "ghcr.io/kidcarmi/culvert:v1.2.4",
  "target_ref":         "ghcr.io/kidcarmi/culvert@sha256:bbbb…",
  "resolved_digest":    "sha256:bbbb…",
  "prior_ref":          "ghcr.io/kidcarmi/culvert@sha256:aaaa…",
  "prior_digest":       "sha256:aaaa…",
  "prior_image_id":     "sha256:cccc…",
  "already_current":    false,
  "pre_backup":         { "taken": true, "path": "pre-upgrade-20260604T1200Z.tar.gz.enc" },
  "pulled":             true,
  "restarted":          true,
  "running_digest_after": "sha256:bbbb…",
  "health":             { "ready_ok": false, "ready_detail": "ready_timeout after 60s", "health_ok": false },
  "rollback":           { "attempted": true, "mode": "image", "target_ref": "ghcr.io/kidcarmi/culvert@sha256:aaaa…", "succeeded": true }
}
```
- `*_ref` fields are the full `repo@sha256:…` references used for pulls/overrides;
  `*_digest` fields are the bare display/audit form (§1.2 convention).
- `running_digest_after` is the **authoritative** post-restart verdict (§4).
- `result` is populated by the `report` stage and on `Manager.Finish`.
- `timed_out` / `timed_out_at_stage` continue to be set by the orchestrator on
  operation timeout.

### 7.2 Per-op log (`GET /v1/operations/{id}/logs`)

- One START/END marker per stage (existing oplog behavior).
- **Inspect/capture stages emit parsed digests only**, never raw inspect JSON
  (#351 hygiene). stderr preserved for diagnosis.
- `pull` / `up` / `down` stages: capture docker compose stdout/stderr (bounded,
  1 MiB) — these are operational output, not image metadata, and are diagnostic.
- A rollback, when it runs, is logged as `recovery:`-prefixed stages (the
  orchestrator already marks post-failure `ContinueOnError` stages as recovery).

## 9. Failure modes and recovery

| # | Stage / event | Effect | Recovery |
|---|---|---|---|
| F1 | Preflight validation (shape/allowlist) | `400`, nothing executed | Operator fixes ref. No state. |
| F2 | Digest resolve (manifest inspect) fails | op `failed` `command_error`, no pull | Registry/network issue; nothing changed. Retry. |
| F3 | `capture_running` finds 0 or >1 proxy containers | op `failed` `command_error` before pull | Stack is in an unexpected state; `/v1/status` shows it. Operator reconciles before retry. **Do not pull blind.** |
| F4 | `pre_backup` fails | op `failed`, **abort before pull** | No state changed. Fix backup target/passphrase; retry. |
| F5 | `pull` fails | op `failed` `command_error`; old container still running | Registry/disk issue; service unaffected (not yet restarted). Retry. |
| F6 | `stack_restart` (`up -d`) fails | new container may be partially up | Health gate will fail → inline rollback (if enabled). Else operator runs rollback. |
| F7 | `health_gate` fails, `rollback_on_failure=true` | inline rollback to `prior_digest` | If rollback healthy → `failed`/`health_failed`, service restored (F7a). |
| F7b | Inline rollback **also** fails health | op `failed` `rollback_failed`; stack on neither known-good nor target | **Operator-paging.** op-log + audit carry both digests + last state. Manual intervention; `/v1/status` + data-mode rollback available. |
| F8 | `health_gate` fails, `rollback_on_failure=false` | op `failed` `health_failed`, stack on new image but unhealthy | Operator decides: standalone rollback (image or data mode). |
| F9 | Operation timeout (`operation_timeout`) | in-flight stages cancelled (SIGTERM→SIGKILL), op `failed` `timeout`, lock released | Stack state depends on stage reached; `/v1/status`. Possibly mid-restart → operator runs `up -d` or rollback. |
| F10 | **Agent restart mid-op** | in-flight op marked `failed` `agent_restart_interrupted` at startup; lock released | Docker compose invocation was interrupted. `/v1/status` reports actual running image; operator re-runs apply or rollback. No auto-resume (correct: we cannot know how far `up -d` got). |
| F11 | Post-restart digest ≠ pinned target (healthy but wrong image) | treated as `health_failed`-class failure (§4) | Compose override (`CULVERT_PROXY_IMAGE`) likely misconfigured; F8/F7 handling applies. |

Cross-cutting recovery guarantees:
- The maintenance lock is **always** released on terminal state (incl. timeout,
  crash-marked-failed at next startup).
- No stage deletes the prior image during apply — `prior_digest` stays pullable
  for rollback unless an external prune races (documented limitation).
- Data-mode rollback's `/data` rename window (down→swap→up) is the only
  filesystem-destructive path; it renames (never `rm`) to `/data.failed.<ts>-<pid>`
  so the prior state is always recoverable.

## 10. Test matrix

### 10.1 Unit
- `validateContainerIDShape` — accepts 12/64-hex, rejects whitespace, `-`-lead,
  over-length, metacharacters.
- Digest pinning: tag→digest resolution parse; `@sha256:` pass-through.
- Running-digest capture parse: `compose ps` JSON → proxy container id; 0/>1
  container → error.
- Verdict computation: running-vs-target equality (the #351-correct comparison).
- Op-result assembly (`report` stage) shape.

### 10.2 Integration (faked exec, `upgradeRig`-style)
| Test | Asserts |
|---|---|
| Already current (running digest == target) | short-circuit, `succeeded`, `already_current=true`, **no pull/up captured** |
| Happy upgrade, healthy | `pull` + `up` ran, `running_digest_after == target`, `succeeded` |
| Upgrade unhealthy + rollback succeeds | `health_failed`, `rollback.succeeded=true`, final running == prior |
| Upgrade unhealthy + rollback fails | `rollback_failed`, both digests in log/audit |
| Upgrade unhealthy, `rollback_on_failure=false` | `health_failed`, no rollback attempted |
| Healthy but wrong digest (F11) | `health_failed`-class, not `succeeded` |
| `pre_backup` failure aborts | no pull/up captured, `failed`, backup path absent |
| Capture finds 0/>1 proxy (F3) | `failed` before pull |
| Concurrency: apply while lock held | `409`, `concurrency_conflict` audit |
| Idempotency dedupe | second identical POST → same `op_id`, no second op |
| Ref not in allowlist / malformed | `400`, nothing reaches runner |
| Agent restart mid-op (F10) | op marked `agent_restart_interrupted`, lock free |
| Passphrase ref only as reference | audit/log never contain the value |

### 10.3 Parity & hygiene
- Template↔sudoers bidirectional parity for `compose.pull`,
  `compose.container.inspect` (extends existing parity test).

## 11. Carry-forward (#351) — running-image comparison

**Requirement:** the apply slice solves the running-vs-target comparison
authoritatively; it does **not** trust `local_cache_up_to_date`.

How this plan satisfies it:
1. **Input side** — the `capture_running` stage ([§1](#1-current-running-image-digest-capture))
   reads the **running container's** image config digest and resolves its registry
   digest, then compares *that* to the pinned target. The decision to skip
   (already-current) or proceed is made from the running container, never from the
   tag/local cache.
2. **Output side** — after restart, [§4](#4-health-gated-apply-flow) re-captures
   the running digest and verifies it equals the pinned target before reporting
   success (F11). A healthy-but-old stack is a failure, not a success.
3. **`upgrades.check` stays a hint** — its `local_cache_up_to_date` is explicitly
   *not* consulted by apply. The check remains a cheap pre-flight advisory; apply
   re-derives ground truth.

This retires the `TODO(apply-slice)` in `handlers_upgrade.go` and the deferred
item in `D1.6-maintenance-agent-implementation-plan.md` §3.5.1 — to be removed
when the apply impl slice lands.

## 13. Future direction (D1.6d / D2) — release UX and pin hardening

These are **not** part of the apply MVP; they shape how upgrade is exposed and
secured once the CP/GUI layer lands. The deployment model stays the same — Docker
Compose + the maintenance agent today, a future OVA wrapping that same Compose +
agent — and the **agent remains the low-level executor**.

### 13.1 Curated release UX (CP/GUI owns it; agent does not change)

- The **GUI must not expose `image_ref`** (raw registry/tag/digest) to operators.
- The GUI presents **curated releases**: a `release_id` / `version_id` plus a
  channel label (**Recommended / LTS / Critical**), not Docker image strings.
- The **CP** maps a `release_id` to a **signed, curated release manifest** and a
  **pinned digest**, then issues the agent a normal apply request carrying that
  already-pinned `repo@sha256:<digest>`.
- The agent stays low-level/internal: it validates (`image_allowlist` +
  `ValidateImageRef`), resolves/pins (a tag→digest convenience that becomes a
  no-op once CP sends digests), and executes. No release/version semantics leak
  into the agent.
- This also resolves the multi-arch tag→digest caveat (§2.2): CP sends the
  authoritative **manifest-list** digest, so the agent never has to pick a
  per-platform descriptor from `manifest inspect --verbose`.

### 13.2 Pin privilege-boundary hardening (tracked from PR #361 review)

The apply MVP preserves `CULVERT_PROXY_IMAGE` across `sudo` via a **global**
`Defaults:culvert-maint env_keep` line. Review (#361) correctly noted this is a
privilege-boundary erosion: the `env_keep` applies to **every** allowlisted
command, and both `docker compose up -d` (restore) and the `cli run` service
resolve `image: ${CULVERT_PROXY_IMAGE:-…}`. A **compromised agent** could set the
variable and invoke an allowlisted command directly, running an arbitrary image
as the root-managed proxy (with `/data` + `/backup` mounts), bypassing the
handler's `image_allowlist` / `ValidateImageRef`.

Harden in a dedicated follow-up (a sudoers/privilege-boundary change, kept out of
the apply MVP per scope). Candidate approaches, to be chosen then:
- **Argv-bounded pin** — deliver the digest as a sudoers-pattern-matched argument
  (e.g. `docker pull <repo>@sha256:[0-9a-f]{64}` + a bounded retag), so the
  privilege boundary itself validates the image; drop `env_keep` entirely. Fully
  closes the bypass.
- **Command-scoped `env_keep`** — `Defaults!<apply pull/up cmd>` scoping plus a
  distinct service-scoped apply `up` command, removing the variable from
  restore / `cli run` / `down`. Removes the worst vectors (arbitrary image with
  `/data`+`/backup` mounts) but the apply commands themselves remain a
  direct-invocation bypass — partial.

`CULVERT_BACKUP_PASSPHRASE` has the same global-`env_keep` shape; revisit it in
the same follow-up (it is currently required for encrypted backup under
`privilege_mode=sudoers`).
