# D1.6d — Release Management: Focused Design

**Status:** DESIGN ONLY. No code, no endpoint activation, no GUI code. This
expands the direction note `roadmap/D1.6d-release-ux-direction.md` (#363) into a
full design for the curated release system that the CP/GUI layer will build on
top of the already-live agent.

**What's live today (the substrate this sits on):**
- Docker Compose + maintenance agent. `upgrades.check` / `upgrades.apply`
  (#361), image rollback + inline auto-rollback (#369/#378), data rollback
  (#385) — all driven by **raw `image_ref` / `filename`** at the agent.
- The agent pins/pulls/restarts/verifies a digest and validates against
  `image_allowlist`; it knows nothing about "releases."

**Where this goes:** a future OVA wraps the *same* Compose + agent architecture;
the CP/GUI gains a curated release layer so **operators never see image
tags/digests**.

> ## The one invariant everything else serves
> **The agent stays a low-level executor and NEVER gains release/channel
> awareness.** It accepts a pinned `repo@sha256:<digest>` (and backup filenames)
> and validates+executes. All release/channel/version/signature logic lives in
> the **CP**. The **GUI/CP never expose digests or tags** to operators. Every
> design choice below preserves this split. (Restated from #363; it is the
> acceptance test for this whole plan.)

---

## 1. Identity model — `release_id` / `version_id`

Three distinct identifiers, deliberately separated:

| ID | Owner | Shape | Mutable? | Who sees it |
|---|---|---|---|---|
| `release_id` | CP catalog | opaque stable key, e.g. `rel_2026_04_v1` | **immutable** | CP/GUI (the canonical handle) |
| `version_id` | CP catalog | human semver, e.g. `1.4.2` | immutable | operators (display) |
| **pinned digest** | release manifest | `repo@sha256:<list-digest>` | immutable | **agent only** (never operators) |

- A **Release** is the immutable triple `(release_id, version_id, pinned
  digest)` plus metadata (channels, severity, changelog, `min_upgrade_from`,
  `created_at`, signature). `release_id` is the key the GUI/CP pass around;
  `version_id` is what humans read; the digest is the agent-facing artifact.
- **Channels are pointers, not identities.** `recommended`, `lts`, `critical`
  are named pointers that resolve to a `release_id` *at a point in time* (like a
  moving tag, but resolved+pinned by the CP, never by the agent). A release's
  channel membership can change (a build gets promoted to `recommended`); its
  `release_id`→digest binding never does.
- The agent never receives `release_id` / `version_id` / channel — only the
  resolved digest. The CP is the sole place that knows the mapping.

---

## 2. Channels (the curated views)

Each channel is a signed pointer in the release index (§7) to one `release_id`,
plus the **Current** and **Rollback** views which are *derived*, not stored.

- **Recommended** — the default "upgrade to this" target for most operators.
  The GUI's primary action.
- **Current** — *derived*: the release the stack is running **now**. The CP
  obtains the running digest from the agent (`upgrades.check` / capture) and
  **reverse-maps** it to a `release_id` for display. If no release matches →
  `current = unknown/custom` (see §10 F6). Informational; not selectable as an
  upgrade target.
- **LTS** — pointer to the newest release on the long-term-support line, for
  operators who upgrade conservatively.
- **Critical security** — pointer to a release flagged `severity: critical`.
  The GUI surfaces it prominently ("Security update available — apply now") and
  may pin it above Recommended.
- **Rollback candidates** — *derived* set (§6): prior releases the operator can
  safely return to (image-mode) plus curated pre-upgrade backups (data-mode).

> Channels are **CP-side metadata**. The agent has no channel concept; it only
> ever sees the one digest the CP resolved.

---

## 3. Recommended / Current / LTS / Critical — resolution

```
GUI shows channel  →  CP resolves channel → release_id → manifest → list digest
                                                                       │
                                                          agent image_ref (digest)
```

- **Recommended / LTS / Critical** resolve forward: channel pointer → `release_id`
  → signed manifest → pinned **list digest** → agent call.
- **Current** resolves *backward*: agent reports the running digest → CP looks it
  up in the catalog → `release_id` → human `version_id` + channel badges.
- The reverse-map (digest → release) is a CP index built from all known release
  manifests. It is the only way "Current" and "is an upgrade available" become
  human-readable without the operator ever seeing a digest.

---

## 4. Rollback candidates

Two kinds, both CP-curated, both resolving to artifacts the agent already
accepts:

- **Image rollback candidates** — prior releases whose pinned digest the CP
  recalls from release history (and which `min_upgrade_from`/policy permit
  returning to). The GUI lists them as "roll back to `<version_id>`"; selecting
  one → CP calls `POST /v1/rollbacks` `mode=image` with that prior digest. (The
  agent's standalone image rollback, #369, already takes a pinned digest.)
- **Data rollback candidates** — curated **pre-upgrade backups** (the
  `pre-upgrade-*` archives apply writes). The CP enumerates them via the agent's
  backup-list and presents them as "restore data from before `<version_id>`";
  selecting one → `POST /v1/rollbacks` `mode=data` with the filename + the
  restore safety acks. (Agent data rollback, #385.)
- The CP decides *which* candidates to offer (recency, known-good, policy); the
  agent just executes the chosen digest/filename. Auto-rollback stays
  image-only and agent-internal (#378) — the release layer never auto-restores
  data.

---

## 5. Digest pinning model

- The manifest carries the **authoritative multi-arch manifest-LIST digest**
  (`repo@sha256:<list>`), not a per-platform digest. The CP hands the agent that
  list digest as `image_ref`.
- This **retires the agent's multi-arch caveat** (D1.6c apply plan §2.2): today
  the agent resolving a *tag* picks one per-platform descriptor from
  `docker manifest inspect --verbose`; with the CP supplying the list digest,
  the agent pulls/pins/verifies the exact list digest and Docker selects the
  right platform at pull time.
- The agent's verify step (#361) checks the running image's `RepoDigest`
  includes the pinned digest — unchanged; it just receives a better (list)
  digest.
- The digest is the **single bit-for-bit identity** that flows: manifest → CP →
  agent `image_ref` → pull/up → verify. Nothing downstream re-resolves it.

---

## 6. Release manifest format

A signed JSON document, one per release. **Format only — no parser ships here.**

```json
{
  "schema_version": 1,
  "release_id": "rel_2026_04_v1",
  "version_id": "1.4.2",
  "severity": "normal",            // normal | critical
  "created_at": "2026-04-18T00:00:00Z",
  "image": {
    "repo": "ghcr.io/kidcarmi/culvert",
    "list_digest": "sha256:<multi-arch manifest list digest>",
    "platforms": ["linux/amd64", "linux/arm64"]   // informational
  },
  "min_upgrade_from": "1.2.0",      // refuse direct upgrades from older
  "changelog_url": "https://…",     // or an offline ref for air-gapped
  "notes": "…"
}
```

- The CP-facing **release index** (the catalog) is a separate signed document
  listing all releases + the channel pointers:

```json
{
  "schema_version": 1,
  "generated_at": "2026-04-18T00:00:00Z",
  "channels": { "recommended": "rel_2026_04_v1", "lts": "rel_2026_01_v3", "critical": "rel_2026_04_v1" },
  "releases": [ { "release_id": "…", "version_id": "…", "manifest_ref": "…", "manifest_sha256": "…" }, … ]
}
```

- `manifest_sha256` in the index binds each manifest, so the index signature
  transitively authenticates every manifest (a Merkle-ish chain: sign the index;
  the index pins manifest hashes).
- **No backup-format change, no agent-format change** — these are *new CP-side*
  documents; the agent never reads them.

---

## 7. Signature / authenticity model

- **Two signed artifacts:** (1) the **release index** (the catalog + channel
  pointers), (2) **each release manifest**. The index pins each manifest's
  `sha256`, so signing the index authenticates the set; manifests may *also*
  carry their own signature for defense-in-depth / independent distribution.
- **Mechanism (to be chosen at impl):** detached signatures over the canonical
  JSON (e.g. ed25519 with a CP-held release-signing key), and/or **cosign /
  Sigstore** over the OCI image so the digest itself is attested. The image
  digest in the manifest SHOULD also be cosign-verifiable against the registry.
- **Trust root distribution:** the release-signing public key (and any cosign
  trust root) is baked into the **CP build / OVA image** and rotated via signed
  index updates. The agent holds **no** signing trust — it only ever gets a
  digest the CP already authenticated.
- **CP verifies before acting:** index signature → manifest hash match →
  (optional) cosign image verification → only then resolve a digest and call the
  agent. A verification failure means the CP refuses to offer/apply the release
  (§10 F1).
- The agent's `image_allowlist` remains the **independent, defense-in-depth**
  gate at the privilege boundary — even a CP-supplied digest must match the
  allowlisted repo. (CP authenticity + agent allowlist are complementary, not
  redundant.)

---

## 8. Air-gapped behavior

- No internet → the catalog, manifests, signatures, **and images** ship as a
  signed **release bundle** (a tarball: signed index + manifests + `docker save`
  / OCI layout of the images, or a registry seed).
- **Import flow:** operator loads the bundle → CP **verifies the bundle
  signature** (same trust root) → loads images into the **local registry** the
  compose file references → the catalog becomes available offline. Verification
  is identical to online; only the *transport* differs.
- The compose `proxy.image` (via `CULVERT_PROXY_IMAGE`) points at the local
  registry digest; the agent pulls from there. **The agent is unchanged** — it
  still receives a `repo@sha256:<digest>` and pulls it; whether the registry is
  remote or the local air-gap mirror is invisible to it.
- `changelog_url` and other online refs must have offline equivalents in the
  bundle (the GUI degrades to bundled notes).
- Air-gap is therefore a **CP/bundle concern only** — no new agent surface.

---

## 9. Responsibilities split (the contract)

**CP (all the new logic):**
- Fetch/host + **signature-verify** the release index and manifests (online or
  air-gapped bundle).
- Resolve channel → `release_id` → list digest (forward); reverse-map running
  digest → `release_id` (Current).
- Compute rollback candidates (image + data).
- Drive the agent: `upgrades.check`, `upgrades.apply`, `POST /v1/rollbacks`
  (`mode=image|data`) — always with **resolved digests / filenames**.
- Keep the agent's `image_allowlist` in sync with the catalog repo.
- Audit release-level decisions (who chose which release via which channel) and
  correlate to the agent `op_id`.
- **Never** expose digests/tags to operators; own the air-gap bundle lifecycle.

**Agent (unchanged — the hard line):**
- Validate (`ValidateImageRef` + `image_allowlist`), pin/pull/restart/health/
  verify; image/data rollback; op-level audit + structured result.
- Receives only digests + filenames + safety acks. **No** release/channel/
  version/signature awareness. No new endpoint for this feature.

```
operator ──▶ GUI ──▶ CP (release catalog, verify, resolve) ──▶ agent (digest) ──▶ docker compose
            releases   release_id → signed manifest → digest    low-level executor
```

---

## 10. Upgrade-check flow (end to end)

```
1. GUI lists channels by version_id + badges (Recommended/Current/LTS/Critical).
2. Operator selects a release (release_id) — never a digest.
3. CP verifies the manifest signature → extracts list digest.
4. CP calls agent upgrades.check { image_ref: <list digest> } (read-only):
     agent compares running digest vs target → "available / already current".
5. GUI shows "Update available: 1.4.2 (Recommended)" — NO digest.
6. Operator confirms → CP calls upgrades.apply { image_ref: <list digest>,
     pre_backup, rollback_on_failure } → agent pins/pulls/restarts/health/verify
     (+ inline auto-rollback on failure, #378).
7. CP reverse-maps the post-apply running digest → release_id → updates "Current".
```

- `upgrades.check` stays the read-only verdict primitive; the CP just feeds it a
  curated digest instead of an operator-typed tag.
- The operator's entire interaction is in `version_id` + channel terms.

---

## 11. GUI dropdown behavior

- A **release selector** lists curated entries: `version_id` + a channel **badge**
  (Recommended / LTS / Critical / Current) + severity + a short changelog
  summary. **No tags, no digests, ever.**
- The **Current** release is marked (and not offered as an upgrade target).
- **Critical** security releases are surfaced prominently (banner / pinned to
  top), independent of the dropdown.
- A separate **"Roll back to…"** control lists rollback candidates (prior
  versions for image rollback; "restore data from before `<version>`" for data
  rollback, with the safety-ack confirmations surfaced as human prompts, not raw
  `accept_dp_reenrollment` flags).
- Selecting any entry triggers the CP resolve→check→apply (or rollback) flow;
  the GUI shows progress via the agent op status, still digest-free.

---

## 12. Audit implications

**Two correlated audit layers:**
- **CP audit** (new): the *release-level* decision — `actor`, `release_id`,
  `version_id`, channel, severity, signature-verification result, and the agent
  `op_id` it dispatched. This is the human-meaningful record ("alice upgraded to
  1.4.2 via Recommended").
- **Agent audit** (existing): the *op-level* execution — `upgrades.apply` /
  `rollbacks.create`, the pinned digest, outcome, failure_reason. Already
  records the digest (#361/#385).
- **Correlation:** the CP audit references the agent `op_id`; together they map
  release_id ⇄ digest ⇄ op outcome. The agent audit stays digest-based (it has
  no release_id); the CP is the only place the two are joined. No change to the
  agent audit schema.

## 13. Failure modes

| # | Condition | Behavior |
|---|---|---|
| F1 | **Signature/verification fails** (index, manifest, or cosign) | CP refuses to offer/apply the release; surfaces a clear error + alert; agent is never called. Fail-closed. |
| F2 | **Catalog/manifest unavailable** (network / missing bundle) | CP can't resolve channels → GUI shows "release info unavailable"; upgrades blocked (no digest to apply). Rollback to a *known* prior digest may still work if cached. |
| F3 | **`release_id` not found** | `404`-class at the CP; not dispatched to the agent. |
| F4 | **Manifest digest not in registry** (or air-gap bundle missing the image) | agent `pull` fails → `upgrades.apply` fails `command_error`; inline auto-rollback restores the prior image (#378). CP surfaces "image not available." |
| F5 | **`min_upgrade_from` violated** | CP refuses the jump (or requires an intermediate release); not dispatched. |
| F6 | **Running digest maps to no known release** | `Current = unknown/custom`; CP still offers upgrades (forward resolve works); rollback candidates may be limited. |
| F7 | **Agent `image_allowlist` rejects the CP digest** | agent `400`; indicates catalog/allowlist drift — CP must reconcile (§9). Defense-in-depth working as intended. |
| F8 | **Air-gap bundle tampered** | bundle signature fails → import refused (= F1). |
| F9 | **Channel pointer stale / mid-rotation** | CP resolves the index atomically (signed snapshot); a stale pointer just offers an older release, never an unsigned/unknown one. |

The agent's own failure modes (timeout, health, rollback) are unchanged and
already specified in the apply/rollback plans; the release layer only adds
CP-side pre-dispatch failures, all fail-closed.

---

## 14. Migration path from the raw `image_ref` APIs

**Additive and backward-compatible — the agent API never changes.**

1. **Today:** agent raw APIs (`image_ref` tag/digest, `filename`) are the
   contract; the GUI exposes raw `image_ref` input.
2. **Phase A — CP release layer (additive):** the CP gains the catalog, signing,
   resolve/reverse-map, and drives the *same* agent APIs with curated digests.
   No agent change. Raw `image_ref` input still works in parallel.
3. **Phase B — GUI cutover:** the GUI replaces raw `image_ref` input with the
   release selector (§11). Operators stop typing tags/digests. The raw field is
   removed from the GUI but the agent endpoint is untouched.
4. **Phase C — allowlist tightening (optional hardening):** narrow the agent
   `image_allowlist` so only catalog-repo digests are accepted, making
   off-catalog images unusable even via direct agent calls. Combine with the
   §13.2 env_keep / pin-value-binding follow-up for the strongest boundary.
- **Rollback safety during migration:** because the agent contract is unchanged,
  a CP/GUI release-layer bug can always be bypassed by the existing raw agent
  API for emergency recovery (until Phase C tightening, which would be gated on
  operational confidence).

---

## 15. Scope boundary

**This plan covers:** the CP/GUI release-management design — identity model,
channels, manifest + index format, signing/air-gap, the responsibilities split,
flows, audit, failure modes, and migration.

**Out of scope / explicitly NOT here:** any agent change (the agent stays the
low-level digest executor — no release awareness, no new endpoint); GUI/CP code;
exposing digests/tags to operators; the concrete signing implementation choice
(ed25519 vs cosign — decided at impl); and the §13.2 pull/up pin-value-binding
hardening (independent, tracked in the apply plan). All of D1.6d implementation
is a future CP/GUI workstream (D2).
