# D1.6c — Data Rollback (`mode=data`): Focused Design

**Status:** DESIGN ONLY. No code, no endpoint surface change, no sudoers/template,
no GUI, no CP changes, no release-manifest work, no backup-format change. This
drives a later impl slice; it must leave no ambiguity for it.

**Scope:** activate `mode=data` on the already-live `POST /v1/rollbacks`
(`rollbacks.create`, #369). It rolls `/data` back by restoring a backup — and it
does so by **wrapping the existing `restore.commit` primitive**, not by writing a
second restore implementation.

> **Prime directive (from the task): do not expose a more dangerous path than
> `restore.commit`.** `mode=data` rollback MUST funnel through the *identical*
> stage builder (`buildRestoreStages(commit=true, …)`), the *identical* runner
> method (`ComposeRestoreCommit`), the *identical* validation
> (`resolveBackupPath` / `ValidateBackupFilename` / `RestoreMode.IsValid` /
> `validatePassphraseRefShape`), and the *identical* CLI `WouldBlock` safety
> guards. It adds **no new capability, no new privilege, and no new bypass** over
> `restore.commit`. The only thing it adds is the *rollback framing* (op kind +
> a CP/GUI-facing "roll back to the pre-upgrade snapshot" entry point).

> **Hard safety boundary — data rollback is NEVER automatic.** Inline
> auto-rollback (#378) is **image-only** and must stay so. A failed upgrade must
> never auto-restore `/data` — that is destructive, offline, and cluster-affecting
> (see §5/§6). `mode=data` rollback is **always** operator/CP-initiated, standalone,
> with explicit safety acknowledgements. This asymmetry is the single most
> important invariant of this slice.

## 1. `POST /v1/rollbacks` — `mode=data` contract

```
POST /v1/rollbacks
{
  "mode":           "data",                       // required
  "filename":       "pre-upgrade-…tar.gz.enc",    // required (the backup to restore)
  "restore_mode":   "full" | "trust-root-only" | "state-only",  // default full
  "passphrase_ref": "env:CULVERT_BACKUP_PASSPHRASE",            // required if encrypted
  "accept_dp_reenrollment": false,                // safety ack (pass-through, §6)
  "allow_counter_rollback": false,                // safety ack (pass-through, §6)
  "idempotency_key": "cp-rollback-…"              // optional
}
```

- Dispatched by the existing `handleRollback`: `mode=image` → the #369 image path;
  `mode=data` → the restore-commit wrapper defined here. Unknown mode → `400`
  (today's "mode must be image" message broadens to "image|data").
- **Field mapping to `restore.commit`:** `restore_mode` maps to
  `runner.RestoreMode`; `passphrase_ref`, `accept_dp_reenrollment`,
  `allow_counter_rollback` map 1:1 to the restore-commit fields.
- **`filename` resolution differs from `restore.commit`'s `path` and needs a
  filename-specific resolver — do NOT reuse `resolveBackupPath` directly.**
  `restore.commit` takes a full `path` and `resolveBackupPath` runs it through
  `IsAllowedBackupPath` (a `/backup`-prefix containment check) before returning
  the basename — so a **bare** `filename` like `pre-upgrade-…tar.gz.enc` would be
  **rejected with `400`** by that helper. The rollback contract intentionally
  sends a bare basename, so `mode=data` resolves it with
  `ValidateBackupFilename(filename)` — basename shape, no separators (the same
  check `restore.commit` ultimately relies on for the `/backup/*` sudoers
  wildcard, and itself the containment guarantee: a separator-free name cannot
  escape the backup dir). It then passes the **bare `filename`** to
  `buildRestoreStages` / `ComposeRestoreCommit` (which prepend `/backup/` and
  re-validate the basename). It does **not** host-stat the backup — see §4 (the
  backup dir is the `cli`-CONTAINER path). This reuses the same shape check as
  `restore.commit`
  without forcing clients to send `/backup/…`.
- **No `dryrun` under `/v1/rollbacks`.** A rollback is the commit action;
  operators who want to preview use the existing `POST /v1/restores/dryrun`. This
  keeps the rollback surface minimal and avoids a second dry-run path.

## 2. Relationship to `restore.commit` — wrap, don't reimplement

```
POST /v1/rollbacks {mode:data}                 POST /v1/restores/commit
        │                                               │
        ▼                                               ▼
   handleRollback ──┐                            handleRestore(commit=true)
                    │  (same validation +               │
                    └──────────────┬────────────────────┘
                                   ▼
                buildRestoreStages(commit=true, filename, mode,
                                   acceptDP, allowCounter, passphrase)
                                   ▼
        stop_stack → run_cli_restore_commit (--confirm + flags)
                   → start_stack (best-effort) → health_check
```

- **Exactly one restore implementation.** `mode=data` is a thin entry point that
  builds the **same** `buildRestoreStages(commit=true, …)` list. The impl slice
  must call that existing builder, not copy it.
- **The only differences from `POST /v1/restores/commit`:**
  1. Op kind is `rollbacks.create` (not `restore.commit`) — so rollback
     operations group under one audit kind and one CP integration surface (#363).
  2. The CP/GUI frames it as "roll back to a pre-upgrade snapshot" and curates the
     candidate (§3).
  None of these is a capability or privilege difference.
- **Why a second entry point at all** (vs. telling the CP to call
  `/v1/restores/commit`): a single `/v1/rollbacks` surface for both image and data
  rollback gives the CP one "rollback candidate → execute" integration and one
  `rollbacks.create` audit/op kind to reason about. The alternative (CP calls
  restore.commit directly for data) is also valid; this plan chooses the unified
  surface for CP simplicity, accepting that it is a **thin wrapper**.

## 3. Backup selection rules

- **The agent does not curate; the CP does** (#363). The request names one
  `filename`; the agent validates + executes. The CP/GUI typically offers the
  `pre-upgrade-*` backups apply writes (`compose.cli.backup.list` →
  `GET /v1/backups`, filtered to the `pre-upgrade-` prefix) as "rollback
  candidates," but that filtering is a CP concern.
- **The agent applies NO new prefix restriction.** `mode=data` accepts any valid,
  existing backup filename — *exactly* the set `restore.commit` accepts.
  Restricting the agent to a `pre-upgrade-*` prefix was considered and **rejected**:
  it would (a) diverge from "wrap, don't reimplement," (b) add a rollback-only code
  path, and (c) provide no security benefit (`restore.commit` already permits any
  backup, so a prefix filter on the rollback entry point is trivially bypassed via
  restore.commit). Candidate curation stays in the CP where it belongs.
- Enumeration for the CP is the existing `GET /v1/backups`; no new discovery
  surface is added.

## 4. Backup validation rules

Order (all before any privileged exec — see §1 for the filename-resolution
rationale):
1. `mode == "data"` and `filename` present → else `400`.
2. `ValidateBackupFilename(filename)` — `^[a-zA-Z0-9._-]{1,255}$` (the same shape
   the `/backup/*` sudoers wildcard relies on); rejects separators/traversal —
   this separator-free basename IS the containment guarantee (the same one
   `resolveBackupPath` gives `restore.commit`), so no further host path check is
   needed or correct (next paragraph).
3. `RestoreMode.IsValid()` — `full|trust-root-only|state-only`.
4. `validatePassphraseRefShape` — `env:NAME` scheme, NAME in the runner's closed
   `EnvAllow`.
5. **Manifest / schema / sha256 / WouldBlock / EXISTENCE validation happens
   inside the CLI** at restore time (the `cli --restore … --confirm` step
   validates the backup's manifest, schema version, per-file digests, that the
   file exists, and computes the DP-reenroll / counter-rollback `WouldBlock`
   decisions before swapping `/data`). `mode=data` inherits this verbatim — it
   does not re-validate the backup contents itself.

> **No host-side existence check (corrected from the original §4 draft).** An
> earlier draft proposed a pre-stage `os.Stat(AllowedBackupDir/filename)` so a
> typo would fail `400` before `stop_stack`. That is **infeasible**:
> `allowed_backup_dir` is the path **as seen by the `cli` CONTAINER** (the
> `culvert-backups` volume is mounted only in `cli`, never on the agent host —
> see `Config.IsAllowedBackupPath` doc + `docker-compose.yml`). A host `os.Stat`
> would reject **every** valid rollback. Existence is therefore validated by the
> CLI inside the container at restore time, **exactly as `restore.commit` does**
> — a typoed filename fails as `cli_error` (the stack having been stopped first),
> identical to `restore.commit`. A container-backed pre-flight check (via the
> existing backup-list command) could restore the "no offline on typo" property
> as a future enhancement, but is not required for parity.

## 5. Certificate / key material handling

Governed entirely by `restore_mode`, inherited from `restore.commit`:
- **`full`** — restores all of `/data` including the cluster CA, leaf keys, and
  enrollment state from the backup. This is what reverts cert/key material to the
  pre-upgrade snapshot.
- **`trust-root-only`** — restores only the trust root / cluster CA material.
- **`state-only`** — restores state WITHOUT the CA/trust material (cert/key
  material is left as-is).

The encrypted backup is decrypted with the `passphrase_ref` value (read by the
handler, forwarded to the cli container via the command-scoped
`CULVERT_BACKUP_PASSPHRASE` overlay — the #380 hardening already scopes that var
to exactly these cli restore commands). Reverting CA/key material (`full` /
`trust-root-only`) is precisely what can force DP re-enrollment (§6).

## 6. DP re-enrollment, counter rollback, config versions

These are the genuinely dangerous effects of restoring `/data`. `mode=data`
surfaces and gates them **exactly** as `restore.commit` does — no weaker.

### 6.1 DP re-enrollment (`accept_dp_reenrollment`)
Restoring a pre-upgrade `/data` (esp. `full` / `trust-root-only`) can revert the
cluster CA / enrollment records so that **data-plane nodes no longer match and
must re-enroll** — they drop out of the cluster until re-enrolled. The restore CLI
computes this as a `WouldBlock` condition and **refuses** unless
`--accept-dp-reenrollment` is passed. `mode=data` forwards
`accept_dp_reenrollment` to that flag; without it, a rollback that would force
re-enrollment **fails closed** (no `/data` change). Operators must understand a
data rollback can disrupt the cluster.

### 6.2 Counter rollback (`allow_counter_rollback`)
Restoring old `/data` rolls **security counters backwards** — TOTP step counters,
anti-replay counters, session-revocation lists. Rolling these back enables replay
of old TOTP codes and un-revoking previously revoked sessions. The CLI guards this
as a `WouldBlock` condition; `allow_counter_rollback` forwards to
`--allow-counter-rollback`. Without it, a counter-rolling rollback **fails closed**.

### 6.3 Config versions
The config-version store (`/data/config_versions`, the monotonic version counter)
is part of `/data` and therefore **rolls back with it** — versions created after
the backup are lost and the version counter regresses to the snapshot. This is
expected for a `/data` restore and is covered by the §6.2 counter-rollback
acknowledgement class (a regressing monotonic counter). No separate flag; it is
inherent to restoring `/data` and is documented so operators are not surprised that
post-backup config history disappears.

## 7. Safety flags + additional acknowledgements

- **Exactly two pass-through acks**, identical to `restore.commit`:
  `accept_dp_reenrollment` and `allow_counter_rollback`. Each defaults `false`
  and gates the corresponding `WouldBlock` guard.
- **No additional ack is introduced.** Adding a rollback-only third
  acknowledgement was considered and **rejected**: it would make `mode=data`
  *diverge* from `restore.commit` for no security gain (the destructive surface is
  identical), and the contract value is parity, not novelty.
- **The real additional safety boundary is structural, not a flag:** `mode=data`
  is **standalone-only**. There is no inline/auto data rollback and the impl must
  not add one — the apply flow's `rollback_on_failure` path (#378) is image-only
  and must never dispatch a data restore. The offline, cluster-affecting nature of
  a `/data` restore makes "automatic on a failed upgrade" unacceptable.

## 8. Audit events

One op, one kind — `rollbacks.create` (NOT `restore.commit`):

| kind | outcome | when |
|---|---|---|
| `rollbacks.create` | `started` | on admission (after dedupe + lock) |
| `rollbacks.create` | `succeeded` | restore committed + stack healthy |
| `rollbacks.create` | `failed` | any gating-stage failure; `failure_reason` set |
| `rollbacks.create` | `failed` (`concurrency_conflict`) | lock held |

- `params` carry `mode=data`, `filename`, `restore_mode`,
  `accept_dp_reenrollment`, `allow_counter_rollback`, and `passphrase_ref`
  **as a reference, never the value** (same redaction as restore.commit).
- A `WouldBlock` refusal (missing ack) is a normal `failed` outcome with a
  reason that identifies the guard (§10 F4), so the audit trail records that the
  safety guard fired.
- No `restore.commit` audit entry is emitted for a data rollback — it is one
  operation under one kind. (Distinct from image inline rollback, which emits an
  `upgrades.apply:rollback` sub-action because it is nested inside an apply op;
  `mode=data` is a top-level op, so no sub-action is needed.)

## 9. Operation log / result contract

- **Op log** (`GET /v1/operations/{id}/logs`): the wrapped stages —
  `stop_stack`, `run_cli_restore_commit`, `start_stack`, `health_check` — with the
  `cli --restore` stdout/stderr captured (it includes the restore plan + the
  WouldBlock decision). **Secret hygiene:** the passphrase value never appears
  (forwarded by overlay/`-e`, never logged); only the `passphrase_ref` reference
  may appear. No image-digest hygiene applies (no images involved).
- **Structured `result`** (mirrors the #378 result discipline):
  ```json
  {
    "mode":                    "data",
    "filename":                "pre-upgrade-…tar.gz.enc",
    "restore_mode":            "full",
    "dp_reenrollment_accepted": false,
    "counter_rollback_allowed": false,
    "restore_committed":       true,
    "succeeded":               true,
    "health":                  "ready=… health=…"
  }
  ```
  `restore_committed` reflects whether the `/data` swap happened;
  `succeeded` additionally requires the post-restore stack to be healthy.
- **Summary line** (always emitted): `rollback mode=data filename=… restore_mode=… committed=… healthy=…`.

## 10. Failure modes

| # | Condition | Behavior | `/data` state |
|---|---|---|---|
| F1 | `mode`/`filename` missing or malformed; bad `restore_mode`; bad `passphrase_ref` shape | `400` before any exec | untouched |
| F2 | Backup not found (typo / absent) | NOT pre-checked on the host (backup dir is the `cli`-container path). Behaves exactly like `restore.commit`: `stop_stack` runs, then `run_cli_restore_commit` fails `cli_error` when the CLI can't find the file | atomic per F6 (CLI never swapped) |
| F2b | Malformed filename (separators/traversal) / bad `restore_mode` / bad `passphrase_ref` shape | `400` before any exec | untouched |
| F3 | Wrong passphrase / corrupt or schema-invalid backup | CLI validation fails BEFORE swap → op `failed` (`cli_error`) | untouched |
| F4 | **WouldBlock without the matching ack** (DP reenroll / counter rollback) | CLI **refuses** → op `failed` (`cli_error`, message names the guard) | untouched — the guard working as designed |
| F5 | `stop_stack` fails | abort before restore; op `failed` | untouched (stack may be down → operator) |
| F6 | `run_cli_restore_commit` fails mid-swap | the restore CLI's swap is atomic (rename A/B with the `.bak`/`.failed` contract) → `/data` is either old or fully restored, never half | atomic per restore contract |
| F7 | `start_stack` fails (best-effort recovery stage) | op `failed`; stack down after a (possibly successful) restore | `/data` may be restored; operator re-runs `up` / `/v1/status` |
| F8 | `health_check` fails after a successful restore | op `failed` (`health_failed`); `restore_committed=true`, `succeeded=false` | `/data` IS restored; service unhealthy → operator |
| F9 | Concurrency: lock held by apply/restore/another rollback | `409` `concurrency_conflict` | untouched |
| F10 | Agent restart mid-op | op `failed` `agent_restart_interrupted` at startup; lock released; no auto-resume | per F6 atomicity |
| F11 | Operation timeout | in-flight stage cancelled; op `failed` `timeout` | per F6 atomicity |

Cross-cutting: the maintenance lock is always released on terminal state; the
restore is **offline** (the proxy is down between `stop_stack` and `start_stack`)
— identical availability profile to `restore.commit`, NOT a new one.

---

## 11. Idempotency & locking

- **Idempotency:** `idempotency_key` via `BeginIdempotent` — a replay returns the
  original `op_id`, never a second destructive restore. Identical to
  restore.commit / image rollback.
- **Locking:** `rollbacks.create` is state-changing + **exclusive** (global
  maintenance lock). Mutually exclusive with `upgrades.apply`, `restore.commit`,
  and image-mode rollback (one lock). The offline window (proxy down during the
  restore) is the same as restore.commit.

## 12. Test matrix

Reuse the restore-commit rig (faked exec + fake health + a fake CLI that can
report a `WouldBlock` decision).

| Test | Asserts |
|---|---|
| Success, `restore_mode=full` | stop→commit→up→health; op `succeeded`; `result.restore_committed=true`; `rollbacks.create` audit started+succeeded |
| Success, `trust-root-only` / `state-only` | mode forwarded to `cli --restore --mode …`; op `succeeded` |
| **WouldBlock DP reenroll, no ack** | CLI refuses → op `failed` `cli_error` naming the guard; `/data` untouched; no `up` of restored data |
| WouldBlock DP reenroll, `accept_dp_reenrollment=true` | `--accept-dp-reenrollment` forwarded; proceeds |
| **WouldBlock counter rollback, no ack** | op `failed`; `/data` untouched |
| WouldBlock counter rollback, `allow_counter_rollback=true` | `--allow-counter-rollback` forwarded; proceeds |
| Missing/invalid `filename`; bad `restore_mode`; bad `passphrase_ref` | `400`, nothing reaches the runner |
| **Bare `filename` accepted (not `/backup/…`)** | a request with `filename="pre-upgrade-…"` resolves via the filename-specific resolver (§1) and does NOT `400` for "not under /backup"; the backup is NOT host-statted |
| **Malformed input rejected before runner** | missing filename / separator / bad `restore_mode` / bad `passphrase_ref` → `400`, no docker command issued |
| Wrong passphrase / invalid backup | op `failed` `cli_error`; `/data` untouched (validate-before-swap) |
| `start_stack` fail / `health_check` fail | op `failed`; result shows `restore_committed=true`, `succeeded=false` |
| Concurrency conflict | `409` `concurrency_conflict` |
| Idempotent replay | same `op_id`, no second restore |
| **Parity (no new surface)** | `mode=data` issues only the existing restore-commit sudoers commands; **no new sudoers line / runner template** is added; parity gate stays green |
| Secret hygiene | op log / audit never contain the passphrase value; only `passphrase_ref` |
| **Wrap, not fork** | a test/assertion pins that `mode=data` builds the SAME `buildRestoreStages(commit=true,…)` stage names/order as `restore.commit` (the anti-second-implementation guard) |
| **No auto data rollback** | the apply inline-rollback path never dispatches `mode=data` (image-only invariant, §7) |

## 13. Slice boundary (what the impl PR does / does not do)

**Does:** add the `mode=data` branch to `handleRollback`, funneling validated
input into the existing `buildRestoreStages(commit=true,…)` under the
`rollbacks.create` kind; add the structured `result`; add the test matrix.

**Does NOT:** add a new endpoint, a new runner template, or a new sudoers line
(reuses restore.commit's enumerated commands + the #380 command-scoped passphrase
`env_keep`); add a dry-run rollback; add any prefix restriction; add an inline/
auto data rollback; change the backup format; touch the CP/GUI. The full pull/up
image-value binding residual (§13.2 of the apply plan) is unrelated and stays out.
