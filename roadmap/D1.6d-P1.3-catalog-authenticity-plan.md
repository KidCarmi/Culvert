# D1.6d / P1.3 — Release Catalog Authenticity / Signatures (design)

**Status:** DESIGN ONLY. No code, no PR, no GUI, no agent changes, no dispatch,
no network refresh. This is the implementation contract for the **authenticity
layer** that sits on top of the P1.2 catalog runtime
(`roadmap/D1.6d-P1.2-release-catalog-runtime-plan.md`) and turns the parent
plan's §7 signature sketch (`roadmap/D1.6d-release-management-plan.md`) into a
concrete, smallest-viable trust boundary.

**The one thing this slice specifies:** a **detached ed25519 signature over the
raw `index.json` bytes**, verified by the Control Plane against a **baked-in
trust root (key ring)** **before** the index is parsed or any `manifest_sha256`
entry is trusted. Signing the index transitively authenticates every manifest
(the index already binds each manifest by `sha256` — P1.2 §4.9), so **one
signature over one document** is the entire authenticity kernel.

> ## The prime invariant it must not break (restated from #389 / P1.2)
> **The agent stays release-agnostic.** Signature verification is **100%
> Control-Plane-side**. The agent holds **no** signing trust, sees **no** key,
> and verifies **no** catalog — it still only ever receives a repo-bound
> `repo@sha256:…` digest from a later dispatch slice. This slice adds a CP-side
> gate; it does not give the agent any release/version/signature awareness.

> ## Integrity → authenticity (what changes vs P1.2)
> P1.2 hash-binds each **manifest** to its index entry (catches corruption/drift)
> but leaves the **index itself unprotected**: a tampering attacker can rewrite a
> channel pointer to a *different existing* `release_id`, or swap an entire
> `(manifest, manifest_sha256)` pair, and P1.2 loads it happily. P1.3 closes that
> by signing the index. After P1.3, a catalog that loads in **enforce** mode is
> **authenticated end-to-end**: index signature → `manifest_sha256` chain →
> manifest bytes.

## 1. Scope & non-goals

**In scope (design only):**
- The signed artifact and its byte contract.
- The signature scheme + trust-root distribution + rotation model.
- The verification order and where it slots into P1.2 `LoadCatalog`.
- Enforcement modes + the migration path from unsigned P1.2 catalogs.
- Air-gap bundle authenticity *contract* (so the bundle slice lands additively).
- Failure modes, audit/log implications, test matrix.

**Explicit non-goals (deferred, by constraint):**
- **No code, no GUI, no admin API.** (A later slice surfaces verify status.)
- **No agent changes, no upgrade dispatch, no rollback computation.**
- **No network / refresh / Rekor / transparency-log lookups** — verification is
  **offline** (works air-gapped). Online transparency is a possible *additive*
  future layer, never a requirement of P1.3.
- **No image-signature verification in this slice.** The published *image* is
  already cosign-keyless-signed in CI (`.github/workflows/ci.yml`); binding the
  catalog's `list_digest` to a cosign attestation is a **separate, optional,
  deferred** defense-in-depth layer (§9). P1.3 authenticates the **catalog
  document**, not the image — the two trust paths are complementary (CP catalog
  authenticity + agent repo/allowlist pin, P1.4).
- **No CP→DP propagation.** The catalog and its trust root are CP-only.

## 2. What is signed — decision

Three candidates were on the table (from the task framing):

| Option | What it signs | Verdict |
|---|---|---|
| **A. `index.json` only** | A detached signature over the raw index bytes. The index already carries `manifest_sha256` for every release, so the signature transitively covers the manifests. | **RECOMMENDED.** Smallest layer; one signature, one verify; reuses the P1.2 Merkle-ish chain (sign the root, the leaves are hash-bound). |
| B. Index + per-manifest signatures | Each manifest *also* carries its own detached signature. | **Rejected for P1.3.** Redundant: the index signature already authenticates every hash-bound manifest. Per-manifest signatures only matter if manifests are distributed *independently* of the index (not a P1.x use case). Additive later if ever needed. |
| C. Bundle-level envelope only | One signature over the whole air-gap tarball (index + manifests + images). | **Deferred (air-gap slice), and insufficient alone.** A bundle envelope protects the *transport container* but, if it were the only signature, an online (non-bundle) catalog dir would have nothing to verify. P1.3 signs the **index**, which then works for BOTH the online dir source AND inside an air-gap bundle (§7). The bundle adds an *outer* signature over the images; the *catalog* authenticity is still the index signature. |

**Decision: sign `index.json` only.** The authenticity chain becomes:

```
ed25519 sig  ──signs──▶  raw index.json bytes
                              │  (each entry binds a manifest by sha256, P1.2 §4.9)
                              ▼
                         manifest_sha256[i]  ──binds──▶  raw manifest[i] bytes
```

Tampering with any manifest breaks its `manifest_sha256` (P1.2 already rejects);
tampering with the index (including any `manifest_sha256` value, channel pointer,
or `generated_at`) breaks the signature (P1.3 rejects). The two together are
end-to-end.

## 3. Signature scheme — decision

**RECOMMENDED: ed25519 detached signature over the raw `index.json` bytes, using
stdlib `crypto/ed25519`.**

| Criterion | ed25519 detached (recommended) | cosign / Sigstore keyless |
|---|---|---|
| **Dependency** | **stdlib only** (`crypto/ed25519`); zero new modules, no Dependency-Obituary risk. | Heavy: cosign libs + Fulcio/Rekor clients. |
| **Air-gap** | **Verifies fully offline** — exactly what an OVA / disconnected site needs. | Keyless verify needs Fulcio cert + Rekor transparency log → **online**, or a complex offline-bundle dance. Wrong default for catalog verification. |
| **Raw-byte fit** | Signs the exact bytes P1.2 already treats as canonical (no re-marshal). | cosign blob signing also works on bytes, but drags the online trust model with it. |
| **Trust model** | Simple **key ring** baked into CP/OVA (§4); operator-overridable. | Identity-based (OIDC issuer + subject); great for CI image signing, awkward for a self-hosted CP's own catalog. |
| **Already in repo** | New, but trivial + stdlib. | Already used for **images/binaries** in CI — keep it there. |

**Why not reuse cosign for the catalog.** Cosign keyless is the right tool for the
**image** (and the repo already does it). But it authenticates *the image at the
registry*, verified *online* against Sigstore. The **catalog document** is a
small CP-local JSON file that must verify **offline** in an air-gapped OVA. Using
cosign for it would (a) add a network dependency to a path that must work
disconnected, and (b) pull a large dependency surface. **Keep the two trust paths
separate:** ed25519 authenticates the catalog; cosign (existing, CI-side)
authenticates the image; the `list_digest` in the now-authenticated manifest is
the join between them. The optional image-attestation cross-check is §9.

**Why ed25519 over ECDSA-P256** (the repo's existing CA curve): ed25519 has
smaller keys/signatures, deterministic signing (no RNG-at-sign footgun), constant
shape, and a dead-simple stdlib `Verify(pub, msg, sig) bool`. ECDSA would also
work and is already vendored conceptually; ed25519 is chosen purely for the
simplest possible verify path. *(Either is acceptable; the doc commits to ed25519
to remove the choice.)*

### 3.1 Signature envelope (detached sidecar)

The signature is a **detached sidecar**, NOT embedded in `index.json` (embedding
would create a chicken-and-egg: you'd have to parse the index to find the
signature before you could verify the index). Sidecar file `index.json.sig`:

```jsonc
{
  "schema_version": 1,        // envelope major; gated like the index (P1.2 §4.0)
  "alg": "ed25519",           // only "ed25519" accepted in P1.3
  "key_id": "rel-2026-a",     // selects the trusted public key (§4); bounded, opaque
  "sig": "<base64 raw 64-byte ed25519 signature over the raw index.json bytes>"
}
```

- The envelope is **untrusted input**: it is parsed only to (a) choose which
  trusted key to use and (b) obtain the signature bytes. Tampering with `key_id`
  or `sig` simply makes verification **fail** against the real trusted key — the
  envelope needs no signature of its own.
- The **signed message is the raw `index.json` bytes**, nothing else. The
  envelope is never part of the signed payload.
- `alg` is pinned to `ed25519`; any other value is a fail-closed rejection
  (prevents downgrade/confusion). `key_id` is bounded like a P1.2 identifier
  (printable ASCII, ≤128 bytes) since it flows into logs/audit/SIEM.

## 4. Trust-root distribution & rotation

### 4.1 Trust store = a key ring (not a single key)

The CP holds a **`TrustStore`: an immutable map `key_id → ed25519 public key`**
plus the active **enforcement mode** (§6). A *set* (not one key) is mandatory so a
new key can be **introduced before** the old one is retired — overlap is what
makes rotation non-breaking.

### 4.2 Distribution — layered, most-trusted first

1. **Baked into the CP build / OVA image (primary).** The release-signing public
   key(s) are compiled into the CP binary (a small `var releaseTrustKeys = …` set
   of `{key_id, base64 pubkey}` literals) and/or shipped in the OVA's read-only
   config. This is the default trust root and needs no operator action. It is
   what the parent plan §7 specifies ("baked into the CP build / OVA image").
2. **Operator-supplied key file (override / self-hosters).** An optional config
   path (e.g. `release.trust_keys_file`) pointing at a small JSON key-ring file
   lets an operator who **re-signs their own catalog** (private fork, internal
   release process) supply their own key(s). When set, it **replaces** the baked
   set (explicit operator intent) — it does not silently union, to avoid a
   confusing "which key signed this" situation. (Union is a possible future knob;
   replace is the safe default.)
3. The agent gets **none** of this. Trust lives only where verification happens.

> **GUI parity note (CLAUDE.md):** the eventual config knobs (`trust_keys_file`,
> enforcement mode) must get an admin API + UI panel **when they ship as code** —
> but that is the integration slice, not P1.3. This design only names them.

### 4.3 Rotation model

- **Add-then-retire.** To rotate: build/ship a CP (or key file) whose ring
  contains **both** the old and the new key. Start signing new indexes with the
  new `key_id`. Once all sites run a CP that trusts the new key, ship the next CP
  with the old key **removed** from the ring. No catalog is ever unverifiable
  during the overlap because both keys are trusted.
- **`key_id` is the selector.** The index envelope names exactly one `key_id`; the
  verifier looks it up. Unknown `key_id` ⇒ fail-closed (§5). This means a catalog
  signed by a not-yet-trusted future key fails *closed* on an old CP — correct: an
  old binary must not accept a key it was never told to trust.
- **Compromise / emergency revocation.** If a signing key is compromised, ship a
  CP build (or key file) that **drops** the key from the ring. Because the ring is
  an allowlist (not a denylist + CRL), removal *is* revocation — no separate
  revocation list, no OCSP, no network. The blast radius is "indexes signed by the
  dropped key stop verifying," which is the desired effect. (A CRL/denylist is
  explicitly **not** in P1.3 — the allowlist ring is simpler and strictly safer.)
- **No key material at rest on the CP beyond public keys.** The CP never holds a
  **private** signing key; signing is an out-of-band release-engineering step
  (the same place CI already cosign-signs images). This keeps the CP a *verifier*,
  never a *signer*.

## 5. Verification order (the gate)

Verification is a **strict, fail-closed prefix** of the existing P1.2 load. It
runs on **raw bytes, before any `json.Unmarshal` of the index**, so no structural
trust is extended to unverified content.

```
1. read raw index.json bytes            (P1.2 src.ReadIndex — unchanged)
2. read raw index.json.sig bytes        (NEW: src.ReadSignature)
3. parse the SIG ENVELOPE only          (untrusted; just to get alg/key_id/sig)
4. alg == "ed25519"                      else → reject (downgrade guard)
5. key := TrustStore.lookup(key_id)      unknown key_id → reject
6. ed25519.Verify(key, rawIndexBytes, sig)   false → reject   ◀── THE TRUST BOUNDARY
   ───────────────────────────────────────────────────────────────────────────
7. json.Unmarshal(rawIndexBytes)         (P1.2 path resumes — now on TRUSTED bytes)
8. trust manifest_sha256[i] entries      (authenticated by step 6)
9. read + hash each manifest             (P1.2 §4.9 raw-byte hash-bind — unchanged)
10. build Catalog                        (P1.2 — unchanged)
```

Steps 7–10 are **exactly today's P1.2 `LoadCatalog`**. P1.3 only prepends steps
1–6. Nothing downstream of step 6 changes — the manifest hash chain, fail-closed
validation, semver ordering, and the reverse index are all reused verbatim.

> **Order is non-negotiable.** The signature MUST be checked **before** the index
> JSON is unmarshaled and **before** any `manifest_sha256` is read as truth. A
> verify-after-parse design would let a malformed/hostile index influence parsing
> (resource use, field coercion) before the trust check — forbidden.

### 5.1 Raw-byte contract (carried over from P1.2 §4.9)

- The signed message is the **exact `index.json` bytes as read** — the verifier
  MUST NOT re-marshal, re-indent, canonicalize, or trim before `ed25519.Verify`.
- The **producer MUST ship byte-stable `index.json`** and sign those same bytes.
  (Same discipline P1.2 already demands for `manifest_sha256`.)
- Consequence: re-indenting or re-serializing the index — even to semantically
  identical JSON — **breaks the signature** (and is caught by a test, §10). This
  is intentional: it keeps the trust anchor pinned to one byte representation and
  removes any canonicalization-algorithm attack surface.

### 5.2 Where it plugs into the P1.2 API (additive)

The P1.2 `CatalogSource` interface is extended **additively** with one method, and
a new verifying entry point wraps the existing loader:

```go
type CatalogSource interface {
    ReadIndex() ([]byte, error)
    ReadManifest(ref string) ([]byte, error)
    ReadSignature() ([]byte, error)   // NEW (P1.3): raw index.json.sig bytes
}

// NEW (P1.3): the verifying entry point. Reads raw index + sig, runs steps 1–6,
// then delegates to the EXISTING P1.2 parse/validate/build path on the now-trusted
// bytes. TrustStore carries the key ring + enforcement mode.
func LoadVerifiedCatalog(src CatalogSource, trust TrustStore) (*Catalog, error)
```

- **`LoadCatalog` (P1.2) is NOT widened** to verify by itself — keeping it lets the
  existing P1.2 tests/fixtures stay valid and makes the trust boundary an explicit,
  greppable call site (`LoadVerifiedCatalog`). The CP-integration slice calls the
  **verified** entry point; nothing calls the bare loader in production.
- The dir source's `ReadSignature()` reads `index.json.sig` with the **same
  symlink-refusing, size-bounded** discipline as every other read (P1.2
  `catalogReadBounded`).
- A future bundle/registry source implements `ReadSignature()` the same way — the
  trust boundary is source-independent (like the manifest-ref check in P1.2 §4.5).

## 6. Enforcement modes & migration from unsigned P1.2

This is the crux of shipping authenticity onto an already-deployed unsigned
catalog without a flag-day break. The model **mirrors the C2 metadata-enforcement
kill switch** already in the codebase (`CULVERT_C2_ENFORCE`, fail-closed default,
read-once at startup) so operators and reviewers see a familiar shape.

| Mode | Signed + valid | Signed + invalid | **Unsigned** (no `.sig`) | Use |
|---|---|---|---|---|
| **`enforce`** (target default) | load | **reject** | **reject** | Production. End-to-end authenticated. |
| **`permissive`** (migration only) | load | **reject** | **load + loud warn + counter** | Transition window only. A *bad* signature still fails closed; only a *missing* one degrades. |
| `disabled` (escape hatch) | load (no verify) | load (no verify) | load | Break-glass / local dev. Off by default; logged at startup. |

Key rule: **`permissive` never accepts a *bad* signature** — it only tolerates a
*completely absent* one (an un-upgraded catalog). A present-but-invalid signature
is always a hard reject, in every mode except `disabled`. This prevents
"permissive" from becoming a tamper bypass.

### 6.1 Migration path (ordered)

1. **Ship P1.3 code defaulting to `permissive`.** Existing unsigned P1.2 catalogs
   keep loading; every load emits a `release catalog: UNSIGNED catalog loaded …`
   warning + increments an `unsigned_catalog_total` counter so operators can see
   remaining unsigned sources.
2. **Sign catalogs.** Release engineering signs `index.json` with the release key
   (out of band, same locus as CI image signing) and ships `index.json.sig`
   alongside. (A tiny offline signing helper can live in release tooling — it is
   **not** part of the CP and not part of this slice.)
3. **Flip the default to `enforce`** in a subsequent release once signed catalogs
   are the norm — exactly the C2 shadow→enforce trajectory. The env/config knob
   lets a site flip early or hold back.
4. **`disabled`** remains only as a documented break-glass, off by default, noisy
   at startup.

> **No agent migration.** The agent never saw the catalog and never will; this
> whole migration is CP-internal. Air-gap bundles built before P1.3 (if any)
> import as "unsigned" under the same `permissive` rule until re-bundled signed.

## 7. Air-gap bundle behavior (contract only — bundle slice owns the code)

The air-gap bundle is a later slice (parent plan §8); P1.3 only fixes its
**authenticity contract** so it lands additively:

- The bundle is a tarball containing `index.json`, `index.json.sig`,
  `manifests/…`, and the `docker save` image blobs.
- **Catalog authenticity inside the bundle is the SAME index signature.** The
  bundle's `index.json` bytes are the signed bytes; the importer runs the **same
  steps 1–6** against the **same baked-in trust root**. There is **no separate
  catalog-signing scheme** for air-gap — the detached sig travels in the tarball.
- The bundle MAY add an **outer** signature over the whole tarball (covering the
  image blobs, which the index signature does not). That outer signature is the
  **bundle slice's** concern; its trust root is the **same** ed25519 ring (one
  trust root, two scopes: index-doc vs whole-bundle). Image *content* trust is
  ultimately the registry/cosign path (§9) — the bundle's `list_digest` still
  binds the image identity.
- Offline is the whole point: ed25519 verify needs **no network**, so a
  disconnected OVA verifies the catalog with only its baked-in public key. This is
  precisely why §3 rejects cosign-keyless for the catalog document.

## 8. Failure modes

All failures below are **fail-closed** (nil catalog, non-nil error) in `enforce`
and `permissive` modes, **except** the one explicitly-degrading case (FA9 unsigned
under `permissive`). Each gets a **distinct error kind** so audit/alerting and the
later GUI can distinguish "unverified" from P1.2's "malformed".

| # | Condition | Behavior |
|---|---|---|
| FA1 | `index.json.sig` missing/unreadable, mode = `enforce` | reject — unsigned catalog refused. |
| FA2 | Signature envelope not JSON / wrong shape | reject — malformed signature envelope. |
| FA3 | `alg` ≠ `"ed25519"` | reject — **downgrade/unknown-alg guard** (distinct kind). |
| FA4 | `key_id` not in the TrustStore ring | reject — **untrusted key** (covers rotation-not-yet-trusted + attacker key). |
| FA5 | `sig` not valid base64 / not 64 bytes | reject — malformed signature. |
| FA6 | `ed25519.Verify` returns false (tampered index OR wrong key) | reject — **signature verification failed** (the core trust failure; loudest alert). |
| FA7 | TrustStore ring is **empty** (no baked key, no key file) in `enforce` | reject — **misconfiguration**, fail-closed (an empty allowlist trusts nothing). |
| FA8 | Key file configured but unreadable / malformed | reject at startup config load — fail-closed (don't silently fall back to baked keys; explicit operator intent was a file). |
| FA9 | `index.json.sig` missing, mode = `permissive` | **load + warn + `unsigned_catalog_total`++** — the ONLY degrading case (§6). A *present-but-invalid* sig (FA2–FA6) still rejects in `permissive`. |
| FA10 | mode = `disabled` | load without verifying; **startup logs the disabled state**; per-load debug log. Break-glass only. |
| FA11 | Index verifies (step 6) but a manifest hash mismatches (P1.2 §4.9) | reject — P1.2 F4, unchanged. Defense-in-depth: the signed index's `manifest_sha256` is authentic, so this now means genuine manifest corruption. |
| FA12 | Index re-indented/re-serialized after signing | reject via FA6 — the raw-byte contract (§5.1); caught by a dedicated test. |

Distinct kinds matter: FA6 (verification failed) is a probable **attack/tamper**
signal and should alert at higher severity than FA1/FA9 (merely unsigned, a
**rollout** signal).

---

## 9. (Deferred, optional) image-attestation cross-check

Not P1.3 — recorded so the boundary is clear. After the catalog is authenticated,
the manifest's `list_digest` is a trusted pointer to an image. The image is
**already** cosign-keyless-signed in CI. A future *optional* layer could
`cosign verify` that digest against the expected CI identity before dispatch. That
is **online**, image-side, and **dispatch-slice** territory — deliberately
separate from P1.3's offline catalog-document authenticity. P1.3 must not couple
to it.

## 10. Audit / log implications

- **Every verified load emits one structured event** (CP-side, via `logger.Printf`
  per CLAUDE.md — never `log`/`fmt`): outcome (`verified` / `unsigned` /
  `verify_failed` / `untrusted_key` / `disabled`), the `key_id` used, the index
  `generated_at`, the SHA-256 of the index bytes, and the mode. All
  externally-influenced strings (`key_id`, error text) are wrapped with
  `sanitizeLog` + `%q` (CWE-117).
- **Counters** (Prometheus `culvert_*`, per metrics.go convention): a verify
  outcome counter labeled by result, plus `unsigned_catalog_total` for migration
  visibility. (Exposed when the slice wires metrics — named here.)
- **Alerting** (reuse `alerts.go`, HMAC-signed webhook): FA6 (verification
  failed) and FA4 (untrusted key) fire a security alert — these are tamper
  signals. FA1/FA9 (unsigned) are informational, not alerts, during migration.
- **Audit-ring vs governance log.** A *verify failure that blocks a catalog load*
  is an operational/security event for the structured logger + alert path, not an
  admin-action audit-ring entry (the ring is for admin mutations). If/when a
  catalog load is triggered *through an admin action* (e.g. operator imports a
  bundle), **that** action is audited via `auditEvent` in the handler — the verify
  result is included as a field. (Mirrors the C4/governance split in CLAUDE.md:
  governance observability ≠ admin-action audit.)
- **Test pitfall (CLAUDE.md):** any audit-ring assertions use content-matching on
  a unique discriminator, never `len(auditGet())` deltas (ring saturates at 500).

## 11. Test matrix

| Area | Test | Asserts |
|---|---|---|
| verify | **happy path** — valid sig, trusted key, `enforce` | catalog loads; outcome=`verified`; `key_id` recorded. |
| verify | **tampered index** (flip one byte) | FA6 reject; distinct verify-failed error kind. |
| verify | **wrong key** (sig by a key not in ring) | FA4/FA6 reject (untrusted/!verify). |
| verify | **unknown `key_id`** in envelope | FA4 reject. |
| verify | **`alg` ≠ ed25519** (e.g. `"rsa"`, `""`) | FA3 reject (downgrade guard). |
| verify | **malformed envelope** (not JSON / missing fields) | FA2 reject. |
| verify | **bad `sig` encoding / wrong length** | FA5 reject. |
| order | **verify-before-parse** — index that is *signed but structurally invalid* vs *unsigned but structurally valid* | signed-invalid: passes step 6, then P1.2 rejects on validation; unsigned-valid (enforce): rejected at step 6 BEFORE parse (prove parse never ran, e.g. via a poisoned field that would error only if parsed). |
| raw-byte | **re-indent the signed index** (same JSON, different bytes) | FA12/FA6 reject — proves no canonicalization (§5.1). |
| rotation | **two keys in ring**, index signed by either | both accepted; selected by `key_id`. |
| rotation | **add-then-retire** — index signed by old key after old key dropped from ring | FA4 reject (retired key no longer trusted). |
| modes | **enforce + unsigned** | FA1 reject. |
| modes | **permissive + unsigned** | loads + warn + `unsigned_catalog_total`++ (FA9). |
| modes | **permissive + present-but-invalid sig** | **reject** (FA6) — permissive is NOT a tamper bypass. |
| modes | **disabled + tampered index** | loads (no verify); startup/per-load logs the disabled state (FA10). |
| trust | **empty ring + enforce** | FA7 reject (empty allowlist trusts nothing). |
| trust | **key file unreadable/malformed** | FA8 reject at config load. |
| chain | **valid index sig + tampered manifest** | FA11 reject (P1.2 §4.9 still fires; defense-in-depth). |
| invariant | **agent-agnostic** | the verify path imports/needs no agent client; agent sees only digests (carried from P1.2). |
| invariant | **P1.2 unchanged** | existing `LoadCatalog` tests still pass untouched; `LoadVerifiedCatalog` is the only new trust boundary. |
| determinism | repeated verify of the same bytes/key | identical outcome; no map-order leakage into logs/results. |

Fixtures: a signed `testdata/release/signed/` (valid `index.json` +
`index.json.sig` + a throwaway test key pair generated in-test), plus tampered /
wrong-key / unknown-key_id / wrong-alg / re-indented variants. Test key pairs are
generated in-test (never a real release key in the repo).

## 12. Implementation checklist (for the eventual PR — NOT this slice)

Recorded so the design is actionable; **no code lands with this document.**

1. Envelope type + parse (untrusted) — `alg`/`key_id`/`sig`, bounded `key_id`.
2. `TrustStore` — `key_id → ed25519.PublicKey` ring + mode; baked-key set
   (compiled-in literals) + optional key-file loader (fail-closed, FA8); read-once
   at startup like `CULVERT_C2_ENFORCE`.
3. `ReadSignature()` on `CatalogSource`; dir-source impl reads `index.json.sig`
   via `catalogReadBounded` (symlink-refusing, size-bounded).
4. `LoadVerifiedCatalog(src, trust)` — steps 1–6, then delegate to the **existing**
   `LoadCatalog` parse/validate/build path on the verified bytes. Do **not** widen
   `LoadCatalog`.
5. Enforcement-mode plumbing (`enforce`/`permissive`/`disabled`), default
   `permissive` at introduction → `enforce` in a later release; env + config knob.
6. Structured logging + counters + alert wiring (§10), `sanitizeLog`/`%q`.
7. Full §11 test matrix incl. the verify-before-parse ordering proof and the
   raw-byte re-indent proof.
8. **No changes** to the agent, dispatch, `ConfigSnapshot`, GUI, or network paths.
   GUI/admin-API exposure of verify status + the `trust_keys_file`/mode knobs is a
   **later** integration slice (GUI-parity tracked there, not here).

**Constraints honored:** design only; no code; no GUI; no agent changes; no
dispatch; no network refresh; agent stays release-agnostic; authenticity is
CP-only and offline.

## 13. Summary of decisions

| Question | Decision |
|---|---|
| **What is signed** | `index.json` only (raw bytes); transitively covers manifests via the P1.2 `manifest_sha256` chain. |
| **Scheme** | ed25519 detached signature, stdlib `crypto/ed25519`, sidecar `index.json.sig` envelope (`alg`/`key_id`/`sig`). Offline. |
| **Why not cosign for the catalog** | cosign-keyless needs online Sigstore; catalog must verify air-gapped. Keep cosign for the *image* (existing CI), ed25519 for the *catalog doc*. |
| **Trust root** | Key **ring** baked into CP/OVA; optional operator key-file override (replace, not union). |
| **Rotation** | Add-then-retire overlap by `key_id`; ring is an allowlist, so removal = revocation. No CRL/OCSP/network. |
| **Verification order** | read raw index + sig → parse envelope → check alg → look up key → **ed25519.Verify on raw bytes** → *then* parse/trust manifests (P1.2 path). Verify strictly before parse. |
| **Raw-byte contract** | Sign/verify exact `index.json` bytes; no canonicalization; producer ships byte-stable file. |
| **Air-gap** | Same index signature travels in the bundle; verifies offline against the baked key. Optional outer bundle signature is the bundle slice's job. |
| **Migration** | `permissive` (unsigned loads + warns, bad sig still rejects) → sign catalogs → flip default to `enforce`. Mirrors `CULVERT_C2_ENFORCE`. |
| **Agent impact** | **None.** CP-only; agent stays release/signature-agnostic. |
