# D1.6 — Maintenance Agent / Host Operations

**Status:** design slice — no implementation in this iteration.
**Supersedes:** [`docker-system-update.md`](./docker-system-update.md) (now deprecated; preserved for historical context, not deleted).

> **Important:** D1.6 does **not** delete the update capability. The goal is to redesign it safely.

---

## Why this exists

The original `docker-system-update.md` design assumed the GUI/CP container could drive Docker directly via a mounted `/var/run/docker.sock`. That posture is too broad:

- The GUI/CP container is internet-adjacent (admin UI, OIDC callbacks, webhook ingress).
- A compromise of the GUI process with a mounted Docker socket is effectively a host takeover.
- "Update" is only one of several host operations we need (backup, restore commit, health checks, log preservation, rollback). They share the same trust boundary.

D1.6 redraws that boundary: the GUI/CP **never** speaks to Docker directly. A separate, scoped **Maintenance Agent** runs on each CP/DP node and exposes a tightly defined API to the local CP. The CP orchestrates; the agent executes.

---

## Target architecture

```
┌──────────────────────────┐   tightly scoped, audited
│  CP GUI / CP API         │ ─────────────────────────────▶ ┌──────────────────────────────┐
│  (no docker.sock)        │   localhost / unix-socket      │  Maintenance Agent           │
└──────────────────────────┘   or mTLS-on-loopback          │  (host-side, systemd unit)   │
                                                            │                              │
                                                            │  ─ allowlisted ops only      │
                                                            │  ─ Docker Compose lifecycle  │
                                                            │  ─ pull / pin images         │
                                                            │  ─ pre-upgrade backup        │
                                                            │  ─ restore commit driver     │
                                                            │  ─ health checks             │
                                                            │  ─ rollback                  │
                                                            │  ─ progress reports          │
                                                            └──────────────┬───────────────┘
                                                                           │ unix socket
                                                                           ▼
                                                            ┌──────────────────────────────┐
                                                            │  Docker Engine + Compose v2  │
                                                            │  Filesystem (/data, logs)    │
                                                            └──────────────────────────────┘
```

For HA / cluster deployments, every CP and DP node runs its own Maintenance Agent. The CP orchestrates a fleet operation by talking to the **local** agent on each target node — there is no cross-host agent dial, only local node-→node-agent calls coordinated by the CP control plane.

---

## Required capabilities (post-design)

The design must accommodate, but D1.6 does **not** implement, all of:

| Capability | Notes |
|---|---|
| Standalone CP upgrade | Single-node deployment path |
| DP node upgrade | One-at-a-time rolling, drain-aware |
| HA CP rolling upgrade | Standby first → failover → upgrade old active |
| Rollback | Triggered by failed health checks or operator command |
| Pre-upgrade backup | Reuses D1.3a `--backup` artifact |
| Post-upgrade health checks | Liveness + readiness + smoke probes; results gate rollback |
| Update reports | Per-node and aggregate; persisted; exposed in admin UI |
| GUI-driven orchestration | Operator launches from CP UI; agent executes; CP narrates |

---

## Agent responsibilities

The agent is a **narrow, allowlisted** process. It does not accept arbitrary commands.

- Run **only** allowlisted host operations defined by the agent's own protocol (no shell escape, no eval, no user-provided commands).
- Manage **local** Docker Compose lifecycle for the Culvert stack on this host.
- Pull and update container images (with digest pinning).
- Drive pre-upgrade backup via D1.3a (offline) or via the appropriate online path when added.
- Drive restore commit (D1.3b.2b) and maintenance-mode toggling.
- Run post-operation health checks against the local stack.
- Stream progress / status back to the CP for the operator's report.
- Preserve logs and update reports across upgrade cycles (separate volume from `/data`).

---

## Cluster orchestration

- **CP orchestrates** updates; agents do not coordinate among themselves.
- DP updates are **rolling**, one node at a time, with health gating between nodes.
- HA CP updates use **standby-first**: standby is upgraded → health-gated → promoted via failover → old active is upgraded → re-paired.
- Each fleet operation enforces an **error budget** (configurable threshold for failed nodes before halting the rollout).
- A failed health check triggers **automatic rollback** for that node, with the CP recording the failure and pausing the rollout for operator review.

## Security posture (non-negotiable)

1. **No arbitrary shell endpoint.** The agent's API surface is finite, allowlisted, and reviewed.
2. **No user-provided command execution.** No "run this script" verb, ever.
3. **No Docker socket in the GUI/CP container.** Period.
4. **If a Docker socket is used, it lives only inside the agent's process namespace** — never bind-mounted into Culvert itself.
5. **Prefer a systemd host service** running as a privileged service account, exposing either:
    - a unix-domain socket on the host (preferred; permissioned to the local CP user), or
    - a localhost-bound HTTP/gRPC port with **mTLS** (for cases where the agent runs in a separate container with shared network namespace).
6. **Strong auth.** mTLS on any TCP/loopback transport; unix-socket permissions on UDS.
7. **Audit every maintenance action.** Operator identity, action, target, parameters, outcome — to the same audit pipeline as policy changes.
8. **Read-once, scoped credentials.** No long-lived shared secret in the GUI; the CP authenticates per-operation.

## Supported platform matrix (first design)

This is intentionally narrow. We will widen later only after the first cohort is rock-solid.

**Linux only** for D1.6.

| Distribution | Status |
|---|---|
| Ubuntu Server LTS | Officially supported |
| Debian stable | Officially supported |
| RHEL | Officially supported |
| Rocky Linux | Officially supported |
| AlmaLinux | Officially supported |

**Host requirements:**

- `systemd` (the agent ships as a systemd unit).
- Docker Engine.
- Docker Compose v2 plugin (CLI plugin form, not legacy `docker-compose`).
- Persistent `/data` path (or operator-configured `dataDir`).
- Agent runs as `root` or as a tightly scoped privileged service account with the minimum capabilities to drive Docker Compose and write to `/data`.

**Architectures:**

- `x86_64` required.
- `arm64` optional / later.

**Explicitly unsupported in D1.6:**

- Windows.
- macOS.
- Non-systemd Linux (Alpine init, runit, OpenRC).
- Arbitrary NAS / appliance OSes (Synology, QNAP, Unraid, TrueNAS).
- Kubernetes nodes — K8s is handled later via a Helm chart and/or operator path, **not** by this agent.

## Out of scope for D1.6 design

D1.6 is a **design** slice. The following are explicitly out of scope here and will land in their own future slices:

- Implementation (agent code, CP integration, packaging).
- GUI implementation for orchestration / progress / reports.
- Kubernetes operator.
- OVA / appliance packaging.
- Cluster rolling upgrade code.
- HA upgrade code.
- Self-updating agent (agent-upgrades-itself bootstrap).

## Migration / deprecation

- `roadmap/docker-system-update.md` is **superseded** by this document. It is retained in the repository for historical context and to preserve the design rationale of the earlier socket-centric approach. New work targets D1.6.
- The existing in-binary self-update flag set (`--updater-url`, `--updater-url-allowlist`, etc.) is **not** removed by D1.6. Any deprecation of those flags will be handled by a follow-up slice once the agent path can fully replace the in-binary updater. Until then, both paths coexist.

## Open questions for the implementation slice

(Not blocking the design; called out so reviewers can flag concerns now.)

1. **Transport.** UDS-only by default? Optional mTLS-on-loopback for containerized agent deployments?
2. **Agent identity.** How does the CP know it's talking to its own host's agent? (Likely: file-system-pinned shared secret + UDS perms; no network identity.)
3. **State storage.** Where does the agent persist update reports / rollback metadata? Separate volume from `/data` to survive `restore commit`.
4. **Bootstrap.** First-time install of the agent — packaged as a `.deb` / `.rpm` per distribution, or as a curl-installer with checksum pinning, or as a sidecar container with `--privileged` (last option strongly disliked).
5. **Upgrade of the agent itself.** Out of D1.6 scope, but the design must not paint us into a corner.
