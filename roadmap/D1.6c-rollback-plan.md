# D1.6c — Rollback: Focused Implementation Plan

**Status:** PLAN ONLY. No code, no endpoint activation, no sudoers changes, no
destructive behavior lands with this document. `POST /v1/rollbacks` stays `404`
(server.go `notImpl`) until the impl slice ships.

**Scope:** turn the §3.7 sketch in `D1.6-maintenance-agent-implementation-plan.md`
and the deferred items in `D1.6c-upgrade-apply-plan.md` (§5, §13.2) into a
build-ready spec for rollback — both the **inline auto-rollback** after a failed
upgrade and the **standalone `POST /v1/rollbacks`** endpoint.

**Builds on what already shipped:**
- `upgrades.apply` (#361) — capture → resolve+pin → pre_backup → pull → restart →
  health gate → verify. The apply MVP fails the op on health failure with **no
  rollback**; this slice adds the rollback.
- Capture primitives (#357): `CaptureRunningProxyImage` → `{ContainerID,
  RunningImageID, RepoDigests}`, `PriorRef()`.
- Image pin path: `compose.pull` + `ComposeUpWithImage`, both forwarding the
  pinned `repo@sha256:<digest>` via the `CULVERT_PROXY_IMAGE` overlay.
- Restore path: `restore.commit` (down → `cli --restore --confirm` → up →
  health) + `compose.cli.backup.list`.

> **Design principle — rollback composes existing primitives.** Image-mode
> rollback is "apply, to a prior digest"; data-mode rollback is "restore.commit,
> from a curated backup." **No new runner templates and no new sudoers entries
> are required** — only the `rollbacks.create` op kind, the handler, an additive
> `rollback_failed` failure reason, and (for inline) a health-gate hook in apply.

> **Alignment with #363 (release UX).** The agent stays a **low-level executor**:
> it validates and runs a *pinned* rollback target. The CP/GUI surfaces a
> **"Rollback candidate"** curated release (and curated backups) to operators and
> maps the choice to a pinned digest / backup filename before calling the agent.
> The agent never exposes or curates digests/filenames.

## 1. Standalone `POST /v1/rollbacks` contract

```
POST /v1/rollbacks
{
  "mode":           "image" | "data",      // required, mutually exclusive
  "image_ref":      "ghcr.io/kidcarmi/culvert@sha256:…",  // mode=image (pinned)
  "filename":       "pre-upgrade-…tar.gz.enc",            // mode=data
  "passphrase_ref": "env:CULVERT_BACKUP_PASSPHRASE",      // mode=data (if encrypted)
  "restore_mode":   "full" | "trust-root-only" | "state-only", // mode=data, default full
  "accept_dp_reenrollment": false,          // mode=data — restore safety flag (pass-through)
  "allow_counter_rollback": false,          // mode=data — restore safety flag (pass-through)
  "idempotency_key":"cp-rollback-…"          // optional
}
```

- Op kind: `rollbacks.create`. State-changing, **exclusive** (mutually exclusive
  with `upgrades.apply` and `restore.commit`).
- **`mode=image`** — roll the proxy back to a prior **pinned** image. The
  `image_ref` is the digest the CP recalls (it issued the upgrade, so it knows
  the prior). Validated exactly like apply's target: `runner.ValidateImageRef`
  (argv-safety) + `image_allowlist` (policy). Then: pull → restart → health gate
  → verify, pinned to that digest (reuses the apply primitives). **No backup is
  taken** (a rollback is the recovery action; an extra backup adds risk/time).
- **`mode=data`** — roll `/data` back by restoring a backup. The `filename` is a
  pre-upgrade backup (or operator-chosen). This **is** `restore.commit` with a
  curated candidate: down → `cli --restore <filename> --mode <restore_mode>
  [--accept-dp-reenrollment] [--allow-counter-rollback] --confirm` → up → health.
  Validated via `runner.ValidateBackupFilename` + passphrase-ref shape (same as
  restore). **The full `restore.commit` safety surface MUST pass through** —
  `accept_dp_reenrollment` and `allow_counter_rollback` (both default `false`)
  map to the same flags the `restore.commit` API and the enumerated
  runner/sudoers combinations already expose. Without them, a curated backup that
  `POST /v1/restores/commit` *can* restore (one the CLI guards behind a
  re-enrollment or counter-rollback confirmation) would be **unrecoverable**
  through `/v1/rollbacks` — so rollback must not be a strictly weaker restore.

Image-mode is the lighter, more common path (a bad image, data intact);
data-mode is heavier and only needed when `/data` was migrated/corrupted by the
upgrade. See [§4](#4-data-rollback) for the data-mode scope decision.

## 2. Inline auto-rollback after a failed upgrade health gate

This **modifies the apply flow** (#361) — the only code change to apply.

- The apply request gains `rollback_on_failure: bool` (default **true**).
- Apply's `health_gate` stage failure currently fails the op. With this slice,
  when `rollback_on_failure == true` **and** a prior digest was captured in
  `capture_before`, apply runs an **inline image-mode rollback** to
  `acc.priorRef` **inside the same op and the same maintenance-lock tenure** (not
  a second lock acquisition, not a second op).
- The prior digest is the in-memory `acc.priorDigests` / `acc.priorRef` captured
  before the pull — **no discovery needed** (this is why inline is trivial and
  standalone is where discovery matters).
- Inline rollback stages run as `recovery:`-prefixed stages (the orchestrator
  already marks post-failure `ContinueOnError` stages as recovery), so the op log
  clearly shows the upgrade failed and the recovery ran.

> **Orchestration change REQUIRED — final-reason override.** The orchestrator
> today keeps the **first** failure reason (`firstReason`) and `ContinueOnError`
> recovery stages do **not** change it. So if `health_gate` fails first
> (`health_failed`) and the recovery rollback *also* fails, the op would still
> finish `health_failed` — `rollback_failed` would never surface, defeating the
> worst-case paging signal. The slice MUST add a **final-reason override** so a
> failed recovery rollback promotes the reason to `rollback_failed`. There is
> direct precedent: the orchestrator already promotes the final reason to
> `ReasonTimeout` when the operation deadline fires (overriding whichever stage
> reason came first). Model the rollback-failure promotion the same way — a
> narrow, explicit override keyed on the recovery stages' outcome, not a general
> "last failure wins" change (which would alter unrelated flows). Without this
> override, this plan's `rollback_failed` outcomes below are unreachable.

Inline rollback outcomes:
- **rollback healthy** → op terminal state `failed`, `failure_reason=health_failed`
  (the **upgrade** failed), but `result.rollback.succeeded=true` (the **service**
  is back on the known-good image). The distinction lives in the result/log, not
  the op state.
- **rollback unhealthy / errored** → op `failed`, `failure_reason=rollback_failed`
  (the worst case — operator paging; see [§9](#9-failure-modes)). Requires the
  final-reason override above; a standalone rollback op has no such issue (its
  health failure *is* the op's first and only failure reason).
- **no prior digest captured / `rollback_on_failure=false`** → no rollback;
  op `failed` `health_failed` with an explicit op-log note that rollback was
  skipped and why.

## 3. Image rollback using the prior pinned digest

Flow (image mode — standalone, and the inline body), pinned to the target digest:

```
[capture_before] → (standalone only) record the current running digest, for the
                   result/log. Inline already has it from the apply op.
pull (prior)     → CULVERT_PROXY_IMAGE=<prior_ref> docker compose pull proxy
restart          → CULVERT_PROXY_IMAGE=<prior_ref> docker compose up -d
health_gate      → internal/health probe
verify           → re-capture; HARD-verify running RepoDigest ⊇ prior digest
report           → summary (always emitted)
```

- Identical machinery to apply's pull/restart/verify, pinned to the **prior**
  digest instead of the **target** digest. `<prior_ref>` is always a concrete
  `repo@sha256:<digest>` (a rollback target is never a moving tag — the CP sends
  a digest; an operator-supplied digest is required).
- **Pin hardening dependency:** this path forwards `CULVERT_PROXY_IMAGE` exactly
  like apply, so it inherits the `env_keep` privilege-boundary concern tracked in
  `D1.6c-upgrade-apply-plan.md` §13.2. The rollback slice does **not** re-open
  that decision; it is resolved once, for both apply and rollback, in the
  dedicated hardening follow-up.

## 4. Data rollback (mode=data) — scope decision

Data-mode rollback **is** `restore.commit` driven by a curated backup, so it
reuses the shipped restore template, sudoers entries, and the down→restore→up→
health stage sequence verbatim. The only additions are the `rollbacks.create`
kind wrapping it and candidate discovery ([§5](#5-candidate-discovery)).

**Recommended split:** land **image-mode + inline first** (the common, lighter
path), then data-mode as a fast follow within the slice. Data-mode carries the
restore flow's heavier risk profile (a stack-down + `/data` swap window, offline
`--confirm`), and most upgrade failures are image regressions with intact data,
for which image rollback is sufficient and safer. If the slice must stay minimal,
data-mode can ship in a second PR; this plan specs both.

The legacy `/data → /data.failed.<ts>` rename sketch in master-plan §3.7 is **not**
used: the agent has no rename template, and the proxy `cli --restore` already owns
the atomic swap inside its container. Data-mode rollback = restore from a
pre-upgrade backup, full stop.

## 5. Candidate discovery and validation

The agent does not *curate* candidates (that is the CP/GUI per #363); it
**validates** a supplied candidate and can **enumerate** what exists.

- **Inline image rollback:** target = the in-memory prior digest from the apply
  op. No discovery, no extra validation (it was the running image moments ago).
- **Standalone image rollback:** target = `image_ref` from the request.
  Validation: `runner.ValidateImageRef` + `image_allowlist`. Must be a digest
  ref (`@sha256:`); a bare tag is rejected for rollback (a rollback target must
  be exact). The CP recalls the prior digest (it issued the upgrade); the agent
  does not mine op history.
- **Standalone data rollback:** candidate = `filename` from the request, plus the
  `restore_mode` + `accept_dp_reenrollment` + `allow_counter_rollback` safety
  flags (§1). Validation: `runner.ValidateBackupFilename` + existence under
  `/backup` + mode enum; the safety flags map to the already-enumerated
  `restore.commit` runner/sudoers combinations, so no new privilege surface.
  **Enumeration:** the existing `GET /v1/backups` (`compose.cli.backup.list`)
  already lists backups; the CP filters for `pre-upgrade-*` (the names apply
  writes) and presents them as "Rollback candidate" data points. No new
  discovery surface in the agent.
- **Why no op-history mining:** apply persists no structured `result` yet
  (D1.6c §7 deferred), so a prior digest is only in the op *log* text. Parsing
  that is brittle. Persisting `prior_digest` in the apply op result is the clean
  enabler and is tracked as the D1.6c structured-result follow-up; until then,
  the CP supplies the digest (it has it).

## 6. Maintenance lock / idempotency

- `rollbacks.create` is **state-changing, exclusive** — add it to
  `ops.stateChangingKinds`. It acquires the global maintenance lock; a 409 with
  the holder's `op_id`/`kind`/`actor` is returned if held (the standard path).
- **Mutually exclusive** with `upgrades.apply` and `restore.commit` (automatic
  via the single lock; documented for clarity).
- **Inline rollback acquires no lock** — it runs inside the apply op's existing
  tenure.
- **Idempotency:** `idempotency_key` is honored via `BeginIdempotent` (dedupe
  runs *before* the lock check), so a retried rollback returns the original
  `op_id` rather than a 409 or a second destructive run.

## 7. Audit events

Stable schema (master-plan §4.8). No renamed/removed fields.

| `kind` | `outcome` | When |
|---|---|---|
| `rollbacks.create` | `started` | On admission (after dedupe + lock). |
| `rollbacks.create` | `succeeded` | Rolled back and healthy. |
| `rollbacks.create` | `failed` | Any gating-stage failure; `failure_reason` set. |
| `rollbacks.create` | `failed` (`concurrency_conflict`) | Lock held. |

- `params` (secrets only as references): `mode`, `image_ref` (mode=image),
  `filename` + `passphrase_ref` + `restore_mode` (mode=data). `passphrase_ref`
  is a reference, never a value.
- **Inline rollback emits no separate audit kind** — it is part of the
  `upgrades.apply` op; the apply audit `failed` event plus the op result/log
  record that a recovery ran. (This keeps "one operator action = one op" intact.)
- **Additive failure reason:** `rollback_failed` (already proposed in
  D1.6c §6.3) — the rollback itself failed (pull/restart/health). Distinct from
  `health_failed` so dashboards/alerts can page on the worst case specifically.
  For **inline** rollback this reason only surfaces via the final-reason override
  (§2); for a **standalone** rollback it is simply the op's failure reason.

## 8. Operation log / result contract

- **Op log** (`GET /v1/operations/{id}/logs`): per-stage START/END; inline
  rollback stages are `recovery:`-prefixed. Inspect/capture stages emit **parsed
  digests only** (#351/#357 hygiene); pull/up/restore stdout/stderr are captured
  (operational, bounded 1 MiB).
- **Summary line** (always emitted by `report`):
  `rollback mode=<image|data> target=<ref|filename> already_<...> running_after=<digests> health=[…]`.
- **Structured `result`** (the apply slice's deferred map, finally worth adding
  here): `{ mode, target_ref|filename, prior_running, running_after, health,
  succeeded }`. For inline rollback the apply op's result gains a
  `rollback: { attempted, mode, target_ref, succeeded }` sub-object. Recommend
  landing the structured result with this slice (it is the natural place — both
  inline and standalone need to report "did the recovery work").

## 9. Failure modes

| # | Condition | Effect | Recovery |
|---|---|---|---|
| F1 | **Rollback target missing** (inline: no prior digest captured; standalone: `image_ref`/`filename` absent or invalid) | inline: no rollback, op `failed` `health_failed` + skip note. standalone: `400` (validation) before any exec | Operator supplies a valid target; nothing executed in the standalone case. |
| F2 | **Pull prior digest fails** (registry/disk) | rollback stage `failed`, op `rollback_failed`; image not swapped | The (broken, inline) or unchanged (standalone) stack stays; retry or data rollback. |
| F3 | **Rollback restart fails** (`up -d`) | new/old container partially up; op `rollback_failed` | `/v1/status` shows actual state; operator re-runs rollback or `up -d`. |
| F4 | **Rollback health fails** (rolled back but still unhealthy) | op `rollback_failed` — worst case | **Operator paging.** Log/audit carry prior+target digests + last state; consider data rollback. |
| F5 | **Partial rollback state** (interrupted between pull and restart, or mid data-swap) | op marked `failed`; for data-mode the `cli --restore` swap is atomic per its own contract, so `/data` is either old or restored, never half | `/v1/status` is the source of truth; data-mode leaves the failed copy aside per the restore contract; operator reconciles. |
| F6 | **Agent restart mid-rollback** | op marked `failed` `agent_restart_interrupted` at startup; lock released | No auto-resume; operator re-runs. |
| F7 | **Operation timeout** | in-flight stages cancelled (SIGTERM→SIGKILL), op `failed` `timeout`, lock released | `/v1/status`; possibly mid-restart → operator re-runs rollback. |

Cross-cutting: the maintenance lock is **always** released on terminal state; no
rollback stage deletes the target image; data-mode never `rm`s `/data` (the
restore contract renames the failed copy aside).

## 11. Test matrix

### Unit
- Request validation: mode required + mutually exclusive; image-mode requires a
  digest `image_ref` (tag rejected); data-mode requires `filename` (+ passphrase
  shape). Allowlist gate.
- Inline trigger logic: rollback runs iff `rollback_on_failure` && prior captured.

### Integration (faked exec + fake health, `applyRig`/`upgradeRig`-style)
| Test | Asserts |
|---|---|
| Inline rollback, recovers healthy | upgrade health fails → rollback pull/up to prior runs → healthy; op `failed`/`health_failed`, `result.rollback.succeeded=true`, running == prior |
| Inline rollback, also fails health | op `failed` `rollback_failed` (NOT `health_failed`) — exercises the final-reason override (§2); prior+target in log/audit |
| Inline, `rollback_on_failure=false` | no rollback attempted; op `failed` `health_failed` |
| Inline, no prior captured | no rollback (skip note); op `failed` `health_failed` |
| Standalone image rollback, success | pull+up to the supplied digest, health ok, verify ⊇ digest; op `succeeded` |
| Standalone image rollback, tag rejected | `400` (rollback target must be a digest) |
| Standalone data rollback, success | down→`cli --restore`→up→health; op `succeeded` |
| Data rollback forwards safety flags | `accept_dp_reenrollment`/`allow_counter_rollback` reach the `cli --restore` argv (parity with `restore.commit`); a backup needing them is recoverable |
| Standalone, missing/invalid target | `400`, nothing reaches the runner |
| Concurrency: rollback while apply holds the lock | `409`, `concurrency_conflict` audit |
| Idempotency dedupe | second identical POST → same `op_id`, no second run |
| Agent restart mid-op | op `agent_restart_interrupted`, lock free |
| Passphrase ref only as reference | audit/log never contain the value (data-mode) |

### Parity & hygiene
- No new templates → existing parity stays green (assert no `rollbacks`-specific
  sudoers line was added).
- Op-log hygiene: capture/verify stages contain only `sha256:` digests, no raw
  inspect JSON.
- Audit content assertions follow the ring-saturation-safe pattern (unique
  discriminator, never `len()` deltas — see CLAUDE.md test pitfalls).

## 12. Slice ordering (impl PRs that follow this plan)

1. **Standalone image-mode rollback (MVP)** ✅ *shipped* — `rollbacks.create` kind,
   the standalone image handler (reusing `ComposePull` / `ComposeUpWithImage` /
   `CaptureRunningProxyImage`; strict `repo@sha256:` target; no new template or
   sudoers entry), capture → pull → restart → health gate → verify, audit + op-log
   summary, lock + idempotency, and tests (success, invalid/missing target, pull
   failure, health failure). Activates `POST /v1/rollbacks` for `mode=image`.
   **Deferred from this MVP** (no inline auto-rollback yet, so unneeded here): the
   apply `rollback_on_failure` hook, the **orchestrator final-reason override**
   (§2), the `rollback_failed` reason, and the structured `result` map — they land
   with the inline-auto-rollback slice (**build-ready spec:**
   `roadmap/D1.6c-inline-auto-rollback-plan.md`).
2. **Data-mode standalone** — wrap `restore.commit` as `mode=data`, forwarding the
   **full safety-flag surface** (`restore_mode` + `accept_dp_reenrollment` +
   `allow_counter_rollback`, §1), candidate enumeration via the existing
   backup-list, and tests. Completes `POST /v1/rollbacks`.

Neither PR adds a sudoers entry or a runner template; both carry their handler +
tests and keep the parity gate green. The `env_keep` hardening (§13.2) and the
CP/GUI "Rollback candidate" surface (#363) proceed independently.
