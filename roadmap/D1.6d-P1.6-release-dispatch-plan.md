# D1.6d / P1.6 — Release Dispatch (CP → agent upgrade) — design

**Status:** DESIGN ONLY. No code, no GUI, no agent changes, no new agent
endpoints. This is the design for **how the Control Plane dispatches a verified
catalog release to the already-shipped agent upgrade API** — the slice the
parent plan (`roadmap/D1.6d-release-management-plan.md` §9–§10) and P1.5
(`roadmap/D1.6d-P1.5-catalog-distribution-plan.md` §15) queued after the
catalog runtime (P1.2), authenticity (P1.3), pin binding (P1.4), and
distribution (P1.5a–d) landed.

> ## The prime invariant (restated, unchanged)
> **The agent stays a low-level, release-agnostic executor.** Dispatch is
> entirely CP-side: the CP resolves a channel to a release to a **repo-bound
> pinned digest** and calls the agent's **existing** `upgrades.apply` /
> `rollbacks` with that digest. The agent gains no release/channel/version/
> signature awareness and **no new endpoints**. Its own validation
> (`validate` + `image_allowlist` + `proxy_repo` binding, P1.4) remains the
> independent last line — dispatch never asks it to be weakened.

> ## The one thing this slice designs
> A CP-side **dispatch orchestrator**: `Resolve(channel) → preflight →
> upgrades.apply(PinnedRef) → poll op → verify-by-running-digest → audit`,
> with Current/already-current derived **only** from the authoritative running
> `RepoDigests` (P1.1), repo-equality/rewrite owned here (P1.2 §2.4), and the
> legacy tag-based Docker updater retired behind it.

## 1. Inputs this design builds on (all shipped)

| Piece | Surface used (unchanged) |
|---|---|
| Catalog runtime (P1.2) | `Resolve(ch) → ResolvedRelease{ReleaseID, VersionID, Severity, PinnedRef}`; `Lookup(pinnedRef)`; `Current(runningRef)`; `List()`; `MinUpgradeFrom` parsed (not yet enforced). |
| Authenticity (P1.3) | Only verified catalogs are ever published — dispatch never sees an unverified one. |
| Distribution (P1.5) | `Refresher.GetCatalog()` (nil ⇒ no-catalog), `Meta()`, `Staleness()`. The published `*Catalog` is **immutable**. |
| Agent — apply | `POST /v1/upgrades/apply` `{image_ref, pre_backup, passphrase_ref?, rollback_on_failure?, idempotency_key?}` → async op (`op_id`), staged pin/pull/restart/health/verify, **inline auto-rollback on failure** (#378). |
| Agent — rollback | `POST /v1/rollbacks` `{mode: image\|data, image_ref, filename, …, idempotency_key?}`. |
| Agent — running image (P1.1) | `GET /v1/status` → `running_image: {image_id, repo_digests[]}` — the **only** authoritative "what is running" source. |
| Agent — pin binding (P1.4) | Agent accepts only `<proxy_repo>@sha256:<64hex>` per its `image_allowlist`; pulls the digest and retags the fixed local `culvert/proxy:pinned`. |

## 2. Forward path: channel → release → digest

### 2.1 Selection (Recommended / LTS / Critical)

- The GUI (later slice) lists releases via `List()` — digest-free
  `{ReleaseID, VersionID, Severity, Channels[]}` — and the channel pointers
  `recommended` / `lts` / `critical` resolved via `Resolve(ch)`.
- **The operator selects a `release_id` (optionally via a channel shortcut) —
  never a digest** (parent plan §10). Channels are *pointers, not identities*:
  selecting "Recommended" at dispatch time snapshots the release it points to
  **at that moment**; the dispatch op records the resolved `release_id`, not the
  channel, so a mid-flight channel re-point cannot change an in-flight op.
- `critical` is a channel like any other; `Severity` is display/alert
  prominence (a `critical`-severity release may warrant an operator alert when
  it appears), **not** an auto-update trigger. No auto-dispatch in this slice.

### 2.2 Resolve → PinnedRef

`Resolve(ch)` (or `byReleaseID[release_id]` for a direct selection) yields the
**repo-bound** `PinnedRef = repo@sha256:<list_digest>` — already the agent's
native currency (P1.2 §2.2). Dispatch performs **no string reconstruction**; the
only permitted transformation is the §4 repo rewrite.

## 3. Current detection (reverse path)

Derived **exclusively** from P1.1 `running_image.repo_digests` — **never** from
`upgrades.check`'s local-cache hint (#351 caveat, restated in the parent plan
§10).

```
current := Unknown
for each ref in running_image.repo_digests:        // it is an ARRAY (B1 §5)
    norm := rewriteRepoPrefixToCatalog(ref)         // §4 — air-gap normalization
    if rel, ok := catalog.Lookup(norm); ok:
        current = Known(rel); break
```

- **Iterate every `repo_digests` entry** and treat the node as Current on
  *any* match (the B1 verification proved the array can hold list + per-arch
  entries; the deployment path always records the list digest —
  `roadmap/D1.6d-P1.2-B1-repodigests-verification.md` §5).
- **Repo-prefix normalization before `Lookup`** (B1 §4.1): in air-gapped /
  mirrored deployments the running ref is `local.registry/...@<digest>` while
  the catalog's `PinnedRef` is `ghcr.io/...@<digest>`. The dispatch layer maps
  the configured deployment repo (and only it) back to the catalog repo before
  the exact match — see §4. Without this, catalog-deployed air-gap nodes would
  report Unknown forever.
- `running_image` absent (old agent, Docker down) ⇒ Current = Unknown, with the
  reason surfaced. Never guessed.

### 3.1 Unknown / custom current release

`{Known:false}` is a **normal state** (legacy install, foreign image, per-arch
edge): dispatch is **still allowed** — the target is absolute (a digest), not
relative to the current version. Consequences when current is Unknown:

- GUI shows "Custom / unrecognized release" (never an error).
- `min_upgrade_from` (when a later slice enforces it) **cannot be evaluated** —
  policy: surface a "current release unknown — minimum-version check skipped"
  warning and require the operator's normal confirm; never hard-block on
  Unknown alone. (In this slice `min_upgrade_from` remains parsed-not-enforced,
  P1.2; the policy is recorded so enforcement lands consistently.)
- The pre-dispatch running digest is still captured (whatever it is) as the
  rollback anchor (§6) — rollback needs a digest, not a release identity.

## 4. Repo equality & repo rewrite (owned HERE, per P1.2 §2.4)

The catalog's `PinnedRef` carries the **catalog's** repo
(`ghcr.io/kidcarmi/culvert`); the agent accepts only refs matching the
**deployment's** `proxy_repo` (P1.4). Dispatch owns reconciling the two:

- **Connected deployment (default):** require `catalog.repo ==
  agent.proxy_repo` *exactly*. On mismatch ⇒ **refuse to dispatch** with a
  configuration error (never "fix" the ref by guessing). The agent would reject
  it anyway (allowlist) — dispatch failing first gives a clear CP-side error
  instead of an opaque agent denial.
- **Air-gap / mirrored deployment:** a single explicit CP config mapping (e.g.
  `release.repo_rewrite: {from: ghcr.io/kidcarmi/culvert, to:
  registry.local/culvert}`) rewrites the `PinnedRef`'s repo prefix **keeping
  the digest** before dispatch — digests are registry-agnostic, so the rewrite
  preserves identity. The SAME mapping is applied in reverse for Current
  detection (§3). The rewritten repo must equal the agent's `proxy_repo`.
- **The digest is NEVER rewritten.** Only the repo prefix, only via the one
  configured mapping, validated at config load (both sides must be bare repos,
  P1.2 §4.13 shape).
- The agent's own allowlist remains the independent backstop: a dispatch bug
  that produces a foreign repo is still refused at the agent (CP authenticity +
  agent allowlist are complementary — parent plan §7).

## 5. Already-current behavior

Two layers, deliberately redundant (#351-correct):

1. **CP preflight:** before dispatch, re-read `running_image.repo_digests` and
   compare (normalized, §4) against the target `PinnedRef`. Equal ⇒ **no-op
   success**: no agent call, audit `release.dispatch outcome=already_current`,
   GUI shows "Already on <version>". This is a *courtesy short-circuit* on
   possibly-stale data.
2. **Agent recompute (authoritative):** `upgrades.apply`'s own
   `capture_before`/verify recompute already-current from the RUNNING digest at
   execution time, so a stale CP read can never cause a wrong restart (parent
   plan §10.6). Dispatch treats the agent's already-current result as a normal
   success, not an error.

## 6. The apply request contract (CP → agent, existing endpoint)

```jsonc
POST /v1/upgrades/apply
{
  "image_ref":           "<PinnedRef after §4 rewrite>",  // repo@sha256:<64hex> — the ONLY release-derived field
  "pre_backup":          true,                            // default TRUE iff a passphrase_ref is available (see policy)
  "passphrase_ref":      "<ref>",                         // REQUIRED iff pre_backup=true; MUST be absent when pre_backup=false
  "rollback_on_failure": true,                            // ALWAYS set EXPLICITLY by the CP (see policy below)
  "idempotency_key":     "rel-<release_id>-<dispatch_op_ulid>"
}
```

- **`rollback_on_failure` policy: default `true`, set explicitly on every
  dispatch** — never rely on the agent-side default, so the audit record states
  the policy that actually applied. The mechanism is the agent's existing
  inline auto-rollback (#378): on pull/restart/health/verify failure the agent
  restores the prior image within the same op. An operator may opt out
  per-dispatch (surfaced as an explicit, non-default toggle) — recorded in the
  audit event.
- **`pre_backup` ⇔ `passphrase_ref` is a HARD agent invariant — match it exactly.**
  The shipped handler (`handlers_upgrade_apply.go`) takes the **encrypted** backup
  path for every `pre_backup=true` and therefore **rejects with 400**: (a)
  `pre_backup=true` **without** `passphrase_ref`, and (b) `pre_backup=false` **with**
  a `passphrase_ref`. So `passphrase_ref` is required **iff** `pre_backup`. The CP
  MUST construct the request to satisfy this before any dispatch:
  - **`pre_backup` defaults to `true` ONLY when the CP can supply a valid
    `passphrase_ref`** (an env-allowlisted ref per the agent's
    `validatePassphraseRefShape`). The CP resolves the ref during preflight.
  - **If no passphrase_ref is available, the CP dispatches `pre_backup=false`
    (and sends NO passphrase_ref)** rather than send an invalid pair that the
    agent 400s before the op starts. This is surfaced to the operator as
    "config backup will be skipped (no backup passphrase configured)" and
    recorded in the audit event — never silently.
  - The ref indirection keeps the secret out of the request body (the agent
    resolves it from its env allowlist), per the existing contract.
- **`idempotency_key` is CP-generated per dispatch op** (release-scoped + a
  fresh ULID — the repo already uses `oklog/ulid` for stable op IDs). A network
  retry of the same dispatch op reuses the SAME key, so the agent
  deduplicates; a NEW operator-initiated dispatch gets a new key.
- **No other release data crosses the wire.** Version, severity, changelog,
  release_id stay CP-side; the agent sees a digest and flags it already
  understands.

## 7. Operation lifecycle (CP-side state machine)

```
IDLE
 └─ dispatch(release_id | channel, opts)
     ├─ [resolve]    catalog snapshot := Refresher.GetCatalog()      (§10)
     │               target := Resolve(...)                           (§2)
     ├─ [preflight]  repo equality / rewrite (§4)
     │               running := GET /v1/status.running_image          (anchor + already-current §5)
     │               staleness check (§11: warn, not block)
     │               single-flight: one dispatch op per agent at a time
     ├─ [apply]      POST upgrades.apply → 202 {op_id}                (§6)
     ├─ [watch]      poll the agent op (existing op surface) to terminal state
     ├─ [verify]     re-read running_image.repo_digests
     │               normalized ref == target PinnedRef ?             (§3)
     └─ terminal:
         SUCCEEDED            (verified on target)
         ALREADY_CURRENT      (no-op, §5)
         FAILED_ROLLED_BACK   (agent op failed; inline auto-rollback restored prior image; CP verifies prior digest is back)
         FAILED_NEEDS_ATTN    (op failed AND auto-rollback failed/disabled, or post-apply verify mismatch — manual intervention; the §6 rollbacks endpoint with the recorded anchor digest is the operator's tool)
```

- **The catalog snapshot is pinned at op start** (§10): the immutable
  `*Catalog` pointer taken from the holder is used for the whole op; a refresh
  mid-op cannot change an in-flight dispatch.
- **The pre-dispatch running digest is recorded as the rollback anchor** before
  apply. It backs `FAILED_NEEDS_ATTN` recovery (manual
  `POST /v1/rollbacks {mode:image, image_ref:<anchor>}`) and the
  `FAILED_ROLLED_BACK` verification.
- **Verify-by-digest is the only success criterion.** A "successful" agent op
  whose post-apply running digest does not reverse-map to the target release is
  `FAILED_NEEDS_ATTN` (verify mismatch) — never reported as success.
- **Single-flight per agent**, mirroring the agent's own op serialization; a
  second dispatch while one is in flight is rejected CP-side with a clear
  "dispatch in progress (op …)" error.
- Poll timeouts use the agent op surface's existing semantics; a CP-side watch
  timeout marks the op `FAILED_NEEDS_ATTN` (state unknown) and tells the
  operator to inspect the agent op directly — the CP never guesses a terminal
  state it did not observe.

## 8. Audit events (CP-side, release-level — parent plan §12)

Release decisions are **admin actions** → the audit ring (`auditEvent`), with
the structured logger carrying operational detail. Two events per dispatch:

1. **`release.dispatch`** (at apply): actor (admin identity), `release_id`,
   `version_id`, channel used (or "direct"), `severity`, target `PinnedRef`
   (post-rewrite), `pre_backup`, `rollback_on_failure`, catalog `generated_at`
   + verify mode (it was verified — P1.3), staleness at dispatch, and the
   **agent `op_id`** once returned — the correlation key between CP audit and
   the agent's own op-level audit.
2. **`release.dispatch.outcome`** (at terminal state): the §7 terminal state,
   the post-op running digest + reverse-mapped release, duration, and error
   detail on failure.

`ALREADY_CURRENT` and refused preflights (repo mismatch, no catalog,
single-flight rejection) also emit `release.dispatch` events with the refusal
outcome — refusals are decisions too. All identifiers are bounded/validated
upstream (P1.2 §4.7); log lines use `sanitizeLog` + `%q` per CLAUDE.md.

## 9. Error handling

| # | Failure | Behavior |
|---|---|---|
| E1 | No catalog published (§10) | Refuse dispatch: "release catalog unavailable". Never dispatch from memory of a prior catalog. |
| E2 | Unknown channel / release_id | Refuse: resolve error (P1.2 `Resolve` semantics). |
| E3 | Repo mismatch, no rewrite configured (§4) | Refuse with a configuration error naming both repos. No agent call. |
| E4 | Agent unreachable / status read fails | Refuse preflight (can't anchor or check already-current). Retryable. |
| E5 | `upgrades.apply` rejected (agent allowlist / validation) | Surface the agent error verbatim; audit refusal. Indicates CP config drift (P1.4 backstop fired) — flagged as a config alert, not a transient. |
| E6 | Agent op fails, inline auto-rollback succeeds | `FAILED_ROLLED_BACK`; CP verifies the anchor digest is running again; audit outcome with the agent failure stage. |
| E7 | Agent op fails, rollback fails or was disabled | `FAILED_NEEDS_ATTN` + alert (`alerts.go`); operator recovery = manual `rollbacks` with the anchor digest. |
| E8 | Post-apply verify mismatch (running ≠ target) | `FAILED_NEEDS_ATTN` + alert — success is only verified-by-digest (§7). |
| E9 | CP watch timeout / CP restart mid-op | Op state unknown ⇒ `FAILED_NEEDS_ATTN` (inspect the agent op; the agent op itself is unaffected — it runs to completion agent-side). The idempotency key allows a safe re-poll/retry, never a duplicate restart. |
| E10 | Concurrent dispatch attempt | Rejected by CP single-flight (§7). |

## 10. Interaction with the P1.5 Holder / Refresher

- **Read at op start, pin for the op.** `Refresher.GetCatalog()` is read once
  per dispatch op; nil ⇒ E1. Because the published `*Catalog` is immutable, the
  pinned pointer stays internally consistent for the whole op even if the
  refresher swaps in a new catalog mid-flight; the NEXT dispatch sees the new
  one.
- **Dispatch never triggers I/O on the catalog path** (reads are lock-free
  pointer loads — P1.5 anti-dependency: query surface never drives refresh).
  An operator-facing "refresh now" stays a separate Refresher action.
- `Meta()`/`Staleness()` feed the §11 staleness surface and the §8 audit
  fields.

## 11. No-catalog & stale-catalog behavior

- **No catalog (holder nil):** release features are *unavailable* — `List`,
  Current, and dispatch all refuse with "catalog unavailable" (P1.5 §7
  fail-closed-unavailable). Nothing is offered, nothing dispatched.
- **Stale catalog:** staleness **warns, never blocks** (consistent with P1.5
  §12 — air-gapped sites legitimately run old catalogs). The dispatch confirm
  surface shows catalog age (`GeneratedAt`) and time-since-refresh; past the
  configured `max_staleness` the warning escalates (and is recorded in the §8
  audit event) but dispatch proceeds on the operator's explicit confirm. A
  hard-block knob is a possible later option, default off — an absolute,
  signed, digest-pinned target is safe to apply even from an old catalog; the
  risk of blocking (no security updates at all) is worse.

## 12. Deprecating the legacy Docker updater

Two legacy artifacts are superseded by catalog dispatch for the **proxy
image** path:

1. **`update.go`'s Docker update mode** — tag-based (`triggerUpdaterSelfUpdate(tag)`,
   `apiUpdateApply`): polls for a newer *tag*, no signature chain, no pinned
   digest, no catalog identity.
2. **The compose `updater` sidecar** — already documented as superseded by the
   D1.6 maintenance agent (D1.5 note) but not yet removed.

Phased retirement (each phase is its own later slice; recorded here so the
end-state is agreed):

- **Phase A — freeze (now, by convention):** no new features on the tag-based
  Docker path; release dispatch is the strategic proxy-image update path.
- **Phase B — default off:** once dispatch + its GUI ship, the update-checker's
  Docker mode defaults off; `apiUpdateApply` for the proxy image returns a
  "superseded by Release Management" error unless a legacy opt-in flag is set.
  The GUI update panel points at the release panel. (GUI-parity per CLAUDE.md:
  the new toggles get API + UI in that slice.)
- **Phase C — removal:** the `updater` sidecar leaves `docker-compose.yml`
  (its volumes/profiles with it) and the Docker branch of `update.go` is
  deleted. **The binary (non-Docker) self-update path of `update.go` is out of
  scope** — it serves bare-metal installs that have no agent; it stays until a
  separate decision retires it.
- The deprecation is **one-way by design:** dispatch is digest-pinned,
  signature-chained (catalog → P1.3) and allowlist-bound (P1.4); the tag path
  is none of those. No fallback from dispatch to the tag path is ever added.

## 13. Non-goals (deferred)

- **No GUI** (the release panel consumes this design in a later slice; GUI
  parity obligations land there).
- **No agent changes, no new agent endpoints** — `upgrades.apply`,
  `rollbacks`, `/v1/status` are used exactly as shipped.
- **No auto-update / scheduled dispatch** (operator-confirmed only).
- **No rollback-candidate computation** (parent plan §4 — later slice; this
  slice only records the anchor digest and uses the existing `rollbacks`
  endpoint for manual recovery).
- **No `min_upgrade_from` enforcement** (policy recorded in §3.1; enforcement
  is a later slice).
- **No multi-node / cluster rolling dispatch** — this slice dispatches to the
  CP's own agent; cluster-wide orchestration composes later with
  `update_cluster.go`'s patterns.
- **No CP→DP catalog propagation** (catalog stays CP-only).

## 14. Summary of decisions

| Question | Decision |
|---|---|
| Forward path | Operator picks `release_id` (channel = shortcut, snapshotted at dispatch); `Resolve` yields the repo-bound `PinnedRef`; no reconstruction. |
| Current detection | Iterate ALL `running_image.repo_digests`, normalize the repo prefix (§4), exact `Lookup` — never `upgrades.check`. Absent/unmatched ⇒ Unknown (normal state). |
| Already-current | CP preflight short-circuit (no-op success) + the agent's own authoritative recompute; both are normal successes. |
| Repo equality / rewrite | Dispatch-owned: exact-match required; one explicit configured rewrite mapping for air-gap (digest never rewritten); applied forward (dispatch) and reverse (Current). Agent allowlist stays the backstop. |
| Apply contract | Existing `upgrades.apply`; `image_ref` = post-rewrite PinnedRef; `passphrase_ref` REQUIRED iff `pre_backup` (hard agent 400 either way — match it); `pre_backup` defaults true only when a passphrase_ref is available, else `pre_backup=false` (no ref) with an audited skip notice; `rollback_on_failure` default true, ALWAYS explicit; CP-generated idempotency key per dispatch op. |
| Lifecycle | resolve → preflight (anchor digest, single-flight) → apply (op_id) → watch → **verify-by-digest** → terminal {SUCCEEDED, ALREADY_CURRENT, FAILED_ROLLED_BACK, FAILED_NEEDS_ATTN}. Catalog snapshot pinned per op. |
| Audit | `release.dispatch` + `release.dispatch.outcome` in the audit ring, correlated to the agent `op_id`; refusals audited too. |
| No catalog | Dispatch refused (fail-closed-unavailable). |
| Stale catalog | Warn + confirm, never block (consistent with P1.5 §12). |
| Unknown current | Dispatch allowed (target is absolute); min-version checks warn-skip, never hard-block on Unknown. |
| Legacy updater | Tag-based Docker path frozen → default-off → removed (sidecar + `update.go` Docker branch); binary self-update out of scope; no fallback path. |
| Agent impact | **None** — existing endpoints, release-agnostic, allowlist backstop intact. |
