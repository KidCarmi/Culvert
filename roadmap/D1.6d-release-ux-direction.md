# D1.6d / D2 — Release UX Direction (design note)

**Status:** DIRECTION ONLY — docs, no code. This note records the product
direction for how upgrades are *exposed* to operators, so future upgrade work
builds toward it. It changes no endpoint and no #361 behavior; the maintenance
agent's contract is unchanged.

It complements `roadmap/D1.6c-upgrade-apply-plan.md` (§13), which tracks the same
direction alongside the apply implementation and the `env_keep` hardening
follow-up.

## Deployment model (unchanged)

- **Today:** Docker Compose + the maintenance agent (`cmd/culvert-maint`). The
  agent executes pinned, validated operations over a local UDS; the Control
  Plane (CP) / GUI drives it.
- **Future:** an OVA (virtual appliance) wraps the **same** Compose + agent
  model. The appliance form factor changes packaging, not the agent contract —
  the agent stays the low-level executor inside it.

## Layering decision

```
operator ──▶ CP / GUI ──▶ maintenance agent ──▶ docker compose
            (release UX)   (low-level executor)
```

- **The agent is a low-level, internal executor.** It accepts a **pinned**
  `image_ref` (a `repo@sha256:<digest>`, or a tag it resolves to a digest as a
  convenience), validates it (`image_allowlist` + `ValidateImageRef`), and runs
  the pull / restart / health-gate / verify flow. It has **no notion of
  "releases," channels, or versions.** It is not operator-facing.
- **The CP / GUI owns the release UX.** It is the only layer operators interact
  with for upgrades, and the only layer that understands product releases.

## What the GUI exposes — and what it must not

**Must NOT expose to operators:**
- Raw Docker **image references, tags, or digests**.
- Registry hostnames / repository paths.
- Any free-text image input that reaches the agent unmediated.

**MUST expose instead — curated releases**, selected by a stable
`release_id` / `version_id` and a channel label:

| Channel | Meaning |
|---|---|
| **Current** | The release the stack is running now (informational). |
| **Recommended** | The default "upgrade to this" target for most operators. |
| **LTS** | Long-term-support line for operators who upgrade conservatively. |
| **Critical** | A security/critical fix the operator should apply promptly. |
| **Rollback candidate** | A known-good prior release to roll back to (feeds the future rollback slice). |

The operator chooses a **release**, never an image. The channel labels are
product metadata, not Docker concepts.

## CP resolution pipeline

```
release_id / version_id
   │   (CP looks up)
   ▼
signed / curated release manifest         ← CP-trusted; signature-verified
   │   (CP extracts)
   ▼
pinned digest  repo@sha256:<digest>        ← authoritative, list-digest correct
   │   (CP issues)
   ▼
agent apply request { image_ref: <pinned digest>, ... }
```

- The CP maps a `release_id` to a **signed / curated release manifest** and
  verifies it before acting (the trust boundary for "what is a real release"
  lives in the CP, not the agent).
- The CP extracts the **pinned digest** from that manifest and hands the agent
  an already-pinned request. The agent never sees the tag or the operator's
  channel choice.
- This also retires the multi-arch caveat in the agent (D1.6c §2.2): the CP
  supplies the authoritative **manifest-list** digest, so the agent never has to
  pick a per-platform descriptor from `docker manifest inspect --verbose`.

## Why this shape

- **Smaller untrusted-input surface at the agent.** Image refs arrive pre-pinned
  from a trusted CP, not as free-text from operators. This is also why the agent
  can stay simple and low-level.
- **Operators reason about product, not plumbing.** "Upgrade to the Recommended
  release" / "apply the Critical fix" / "roll back to the last known-good" — no
  digests, no registries.
- **Supply-chain integrity is a CP responsibility.** Signature/curation
  verification happens once, in the CP, against the release manifest — the
  natural place for it.
- **OVA-ready.** The same CP→agent contract works whether the agent runs under a
  hand-rolled Compose deployment or inside the OVA.

## Out of scope here (tracked elsewhere)

- The **`env_keep` privilege-boundary hardening** for the pin (D1.6c §13.2) — a
  compromised agent can currently run an arbitrary image via direct `sudo`;
  fixed in a dedicated follow-up. (The pre-pinned-from-CP model shrinks but does
  not eliminate this, since it concerns a *compromised agent*, not the input
  source.)
- **Standalone rollback** (`/v1/rollbacks`) and **inline auto-rollback** — the
  "Rollback candidate" channel feeds these (D1.6c slice 4).
- The concrete release-manifest schema, signing scheme, and CP/GUI surfaces —
  these belong to the CP/GUI workstream (D2), not the agent.
